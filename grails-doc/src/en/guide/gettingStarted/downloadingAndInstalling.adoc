There are many ways to create a Grails application.
The best way is to use either https://start.grails.org[start.grails.org] or use the Grails CLI via https://sdkman.io[SDKMAN].
SDKMAN greatly simplifies installing and managing multiple Grails versions.

=== The `grails` Command

Grails has one command line, `grails`. It creates projects from application types and features, creates the classes of a project (controllers, domain classes, services and so on), adds features to a project, and runs the build of a project through Gradle (`run-app`, `test-app`, `assemble` and the other commands of that kind). `grails help` lists the commands there are in the current directory, and xref:commandLine[The Command Line] describes them.

The same generator is behind https://start.grails.org[start.grails.org], which creates a project without anything being installed.

Many commands of `grails` are a Gradle build of the project, and those can be run with Gradle as well:

[options="header,autowidth"]
|===
| `grails` | Gradle

| `grails run-app` | `./gradlew bootRun`
| `grails run-app -Dgrails.env=test` | `./gradlew bootRun -Dgrails.env=test`
| `grails test-app` | `./gradlew test integrationTest`
| `grails assemble` | `./gradlew assemble -Dgrails.env=production`
| `grails run-command dbm-update` | `./gradlew runCommand -Pargs="dbm-update"`, or `./gradlew dbmUpdate`
|===

NOTE: Before Grails 9 an installation had three commands: `grails-shell-cli`, the Grails shell with its profiles, `grails-forge-cli`, and `grails`, which started one of the two according to its `-t` option or the `GRAILS_PREFERRED_SHELL` environment variable. Grails 9 has the `grails` command only, without that option, and no profiles: see link:applicationTypes.html#profilesReplaced[What Became of Profiles] and link:upgrading.html#upgrading90x[Upgrading from Grails 8 to Grails 9].

=== Install with SDKMAN

To install the latest version of Grails using SDKMAN, run this on your terminal:

[source,console]
$ sdk install grails

You can also specify a version

[source,console,subs=attributes+]
$ sdk install grails {version}

You can find more information about SDKMAN usage on the https://sdkman.io/usage/[SDKMAN Docs].
After installing, the `grails` command will be available.

=== Manual installation

For manual installation follow these steps:

* https://github.com/apache/grails-core/releases[Download] a binary distribution of Grails and extract the resulting zip file to a location of your choice.
Then add the bin directory to your system path.

==== Unix/Linux

** This can be done by adding `export PATH="$PATH:/path/to/grails/bin"` to the startup file of your shell, such as `~/.bashrc` or `~/.zshrc`

==== Windows
** Copy the path to the bin directory inside the grails folder you have downloaded, for example,

----
C:\path_to_grails\bin
----

** Go to Environment Variables, you can typically search or run the command below, the type env and then Enter

----
Start + R
----

** Edit the Path variable on User Variables / System Variables depending on your choice.
** Paste the copied path in the Path Variable.

If Grails is working correctly you should now be able to type `grails --version` in the terminal window and see output similar to this:

[source,console,subs=attributes+]
----
Grails Version: {version}
----

=== Grails Wrapper

A generated project includes a wrapper, `grailsw` (with `grailsw.bat` and `grails-wrapper.jar`), that can be checked into source control.
The wrapper downloads the command line of the version of Grails the project is on, the `grailsVersion` of its `gradle.properties`, to `~/.grails/wrapper` and starts it, so `./grailsw` takes the commands `grails` takes.
The environment variable `GRAILS_WRAPPER_HOME` names another directory than `~/.grails` for the downloads. Unless it is told to, the wrapper keeps nothing in the project. If you name the `.grails` directory of a project, which also holds the record of how the project was generated, the downloads are in `.grails/wrapper`: add that directory to `.gitignore` to keep them out of version control.
It is meant to be a lightweight option if SDKMAN is not available, and it gives everyone who works on the project the command line of the same version.

The command line is looked for in the repositories that the `GRAILS_REPO_URL` environment variable (or the `grails.repo.url` system property) names, then in Maven Central and then in the ASF repository. A download is installed only when it is whole:

* it is compared with the strongest checksum file the repository has beside the jar (`.sha512`, `.sha256`, `.sha1`, `.md5`). Where the repository has none, as a local Maven repository does not, every entry of the jar is read and compared with the CRC the jar records for it;
* it opens as a jar and has the class the command line starts with.

The checksum file comes from the repository the jar comes from. The comparison finds a download that was cut off or damaged on the way; it does not tell whether the repository is to be trusted. Name only repositories you trust.

A repository that does not have the command line, whose `maven-metadata.xml` cannot be read, or whose download fails or is not whole is passed over, and the next one is tried. For a repository you named, and for every failure that is more than the command line not being there, one line says which repository and why. When no repository gave the command line, the wrapper ends with exit code 1 and lists each repository with its reason. A user name and password in the address of a repository are not printed. An address that cannot be read with certainty, because the password has an `@`, a `/`, a `#`, a `?`, a bracket or a space in it that is not percent-encoded, or because the scheme is missing, is shown with everything from the start of the address (after `https://` where it has one) to its last `@` replaced by `***`, and an address without an `@` whose host is not a plain host name and port has the host replaced: `https://***@repo.example.com/maven`. That can hide a little more than the user and the password, such as an `@` in the path, and never shows a part of them. A remote address in which no host can be found where it belongs, as a `/`, `#` or `?` in a password leaves it, is refused before anything is downloaded, and the wrapper ends with that message: what Java would say of such an address is a part of the password. Percent-encode those characters in a password (`%2F`, `%23`, `%3F`, `%40` for `@`).

The download is written to a file beside the place of the jar and moved there in one step, so a wrapper that is interrupted, or that runs at the same time as another one with the same home, as jobs of a build server do, leaves no part of a jar where the next run would start it. A jar in the home that cannot be started, which an interrupted download of an earlier wrapper can have left, is said in one line and downloaded again, once. The versions that were downloaded are all kept, so that projects of different versions do not download again; delete a directory under `~/.grails/wrapper` to remove one.

When the home cannot be written to, the wrapper says which directory and ends with exit code 1 without asking a repository: make the directory writable or name another one with `GRAILS_WRAPPER_HOME`.

The three files of the wrapper are replaced by those of another version of Grails with `./grailsw update-wrapper`, after `grailsVersion` in `gradle.properties` is changed to that version. The wrapper downloads the command line of that version, which writes its `grailsw`, `grailsw.bat` and `grails-wrapper.jar` over the ones of the project where they differ and names the files to commit. The wrapper of a project of Grails 7 or 8 is replaced in the same way when the project is upgraded to Grails 9. On Windows two of the files are in use while the wrapper runs: the command writes the new ones beside them and names the step that is left. See `update-wrapper` in the reference of the command line.
