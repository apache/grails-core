== Commands

The plugin has three commands that create domain classes and add their settings to the configuration of the project. They are commands of the plugin that only write files of the project, so they are run without the application being started: the Gradle task `runCommand` compiles the project and calls the command, and an application that has no security settings yet, or cannot start for another reason, has the commands all the same.

A command is run in one of three ways, here for `s2-quickstart`:

[source,bash]
----
grails run-command s2-quickstart com.yourapp User Role
./gradlew runCommand -Pargs="s2-quickstart com.yourapp User Role"
grails s2-quickstart com.yourapp User Role
----

The first two work as soon as the plugin is a dependency of the project. `grails` has the commands under their own names, as in the third line, once the build of the project has listed the commands of the application and its plugins, which `grails gradle grailsCommandCatalog` does.

The settings are appended to `grails-app/conf/application.groovy` when the project has that file. A project without it that has `grails-app/conf/application.yml` gets them there, as one more YAML document at the end of the file, and a project with neither file gets `application.groovy`. A domain class that already exists is kept as it is. `s2-create-persistent-token` and `s2-create-role-hierarchy-entry` append their settings again when they are run again; `s2-quickstart` writes nothing when the configuration already has a setting that it writes, unless it is given `--force` (see <<core-s2-quickstart>>).

NOTE: Before Grails 9 the three were also script commands of the plugin, which the Grails shell ran by their names, as in `./grailsw s2-quickstart com.yourapp User Role`; earlier builds of Grails 9 ran them with `./gradlew runScriptCommand`. The scripts are removed; the commands have the same names and arguments. link:upgrading.html#upgrading90x[Upgrading from Grails 8 to Grails 9] says what the commands do differently from the scripts.
