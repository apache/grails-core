=== Per Environment Configuration


Grails supports the concept of per environment configuration. The `application.yml` and `application.groovy` files in the `grails-app/conf` directory can use per-environment configuration using either YAML or the syntax provided by {groovydocumentation}#_configslurper[ConfigSlurper]. As an example consider the following default `application.yml` definition provided by Grails:

[source,yaml]
----
environments:
    development:
        dataSource:
            dbCreate: create-drop
            url: jdbc:h2:mem:devDb;LOCK_TIMEOUT=10000;DB_CLOSE_ON_EXIT=FALSE
    test:
        dataSource:
            dbCreate: update
            url: jdbc:h2:mem:testDb;LOCK_TIMEOUT=10000;DB_CLOSE_ON_EXIT=FALSE
    production:
        dataSource:
            dbCreate: update
            url: jdbc:h2:prodDb;LOCK_TIMEOUT=10000;DB_CLOSE_ON_EXIT=FALSE
            properties:
               jmxEnabled: true
               initialSize: 5
        ...
----

The above can be expressed in Groovy syntax in `application.groovy` as follows:

[source,groovy]
----
dataSource {
    pooled = false
    driverClassName = "org.h2.Driver"
    username = "sa"
    password = ""
}
environments {
    development {
        dataSource {
            dbCreate = "create-drop"
            url = "jdbc:h2:mem:devDb"
        }
    }
    test {
        dataSource {
            dbCreate = "update"
            url = "jdbc:h2:mem:testDb"
        }
    }
    production {
        dataSource {
            dbCreate = "update"
            url = "jdbc:h2:prodDb"
            properties {
               jmxEnabled = true
               initialSize = 5
            }
        }
    }
}
----

Or the equivalent in `application.yml`:

[source,yaml]
----
dataSource:
    pooled: false
    driverClassName: "org.h2.Driver"
    username: "sa"
    password: ""
environments:
    development:
        dataSource:
            dbCreate: "create-drop"
            url: "jdbc:h2:mem:devDb"
    test:
        dataSource:
            dbCreate: "update"
            url: "jdbc:h2:mem:testDb"
    production:
        dataSource:
            dbCreate: "update"
            url: "jdbc:h2:prodDb"
            properties:
               jmxEnabled: true
               initialSize: 5
----

Notice how the common configuration is provided at the top level and then an `environments` block specifies per environment settings for the `dbCreate` and `url` properties of the `DataSource`.


=== Packaging and Running for Different Environments


Grails' link:commandLine.html[command line] has built in capabilities to execute any command within the context of a specific environment. The format is:

[source,bash]
----
grails <<environment>> <<command name>>
----

In addition, there are 3 preset environments known to Grails: `dev`, `prod`, and `test` for `development`, `production` and `test`. For example to create a WAR for the `test` environment you would run:

[source,bash]
----
grails test war
----

To target other environments you can pass a `grails.env` variable to any command:

[source,bash]
----
grails -Dgrails.env=UAT run-app
----

[source,bash]
----
./gradlew bootRun -Dgrails.env=UAT
----

Views are compiled ahead of time by the build: GSP pages by the `compileGroovyPages` and `compileWebappGroovyPages` tasks, JSON views by `compileGsonViews` and markup views by `compileGmlViews`. The page compiler reads `application.yml` and `application.groovy`, and the view compilers `application.yml`, for one environment, so the settings a compiled view carries, such as the GSP codecs under `grails.views.gsp.codecs`, are those of that environment. The build compiles its views for the environment it is run with, given as `-Dgrails.env` to Gradle or as the `GRAILS_ENV` environment variable, and for `development` where neither is given:

[source,bash]
----
./gradlew bootJar -Dgrails.env=UAT
----

A `-Dgrails.env` a build gives the compiler itself, among the fork options of a compile task, is kept, and outranks both.

The build compiles each view once, for one environment, and the JSON and markup views it compiles serve the tests as well as the archive. A setting such a view carries therefore cannot differ between the tests and the archive: it belongs at the top level of the configuration rather than under `environments.test`, or the tests are run with the environment stated as above. Each compile task empties its output directory before it compiles, so the directory is the task's own: within the build directory, and not one the views are compiled against.

A build can state the environment on the compile tasks instead, each of which has a `grailsEnvironment` property; the JSON and markup tasks, `compileGsonViews` and `compileGmlViews`, take it the same way where their plugins are applied:

[source,groovy]
----
tasks.named('compileGroovyPages') {
    grailsEnvironment = 'uat'
}
tasks.named('compileWebappGroovyPages') {
    grailsEnvironment = 'uat'
}
----

The environment is part of what the compiled views are, so the build cache keeps views compiled for different environments apart.


=== Programmatic Environment Detection


Within your code, such as in a Gant script or a bootstrap class you can detect the environment using the link:{api}grails/util/Environment.html[Environment] class:

[source,groovy]
----
import grails.util.Environment

...

switch (Environment.current) {
    case Environment.DEVELOPMENT:
        configureForDevelopment()
        break
    case Environment.PRODUCTION:
        configureForProduction()
        break
}
----


=== Per Environment Bootstrapping


It's often desirable to run code when your application starts up on a per-environment basis. To do so you can use the `grails-app/init/BootStrap.groovy` file's support for per-environment execution:

[source,groovy]
----
ServletContext servletContext

def init = {
    environments {
        production {
            servletContext.setAttribute("env", "prod")
        }
        development {
            servletContext.setAttribute("env", "dev")
        }
    }
    servletContext.setAttribute("foo", "bar")
}
----


=== Generic Per Environment Execution


The previous `BootStrap` example uses the `grails.util.Environment` class internally to execute. You can also use this class yourself to execute your own environment specific logic:

[source,groovy]
----
Environment.executeForCurrentEnvironment {
    production {
        // do something in production
    }
    development {
        // do something only in development
    }
}
----
