Grails controllers support a simple mechanism for declarative exception handling.  If a controller declares a method that accepts a single argument and the argument type is `java.lang.Exception` or some subclass of `java.lang.Exception`, that method will be invoked any time an action in that controller throws an exception of that type.  See the following example.

[source,groovy]
.grails-app/controllers/demo/DemoController.groovy
----
package demo

class DemoController {

    def someAction() {
        // do some work
    }

    def handleSQLException(SQLException e) {
        render 'A SQLException Was Handled'
    }

    def handleBatchUpdateException(BatchUpdateException e) {
        redirect controller: 'logging', action: 'batchProblem'
    }

    def handleNumberFormatException(NumberFormatException nfe) {
        [problemDescription: 'A Number Was Invalid']
    }
}
----


That controller will behave as if it were written something like this...


[source,groovy]
.grails-app/controllers/demo/DemoController.groovy
----
package demo

class DemoController {

    def someAction() {
        try {
            // do some work
        } catch (BatchUpdateException e) {
            return handleBatchUpdateException(e)
        } catch (SQLException e) {
            return handleSQLException(e)
        } catch (NumberFormatException e) {
            return handleNumberFormatException(e)
        }
    }

    def handleSQLException(SQLException e) {
        render 'A SQLException Was Handled'
    }

    def handleBatchUpdateException(BatchUpdateException e) {
        redirect controller: 'logging', action: 'batchProblem'
    }

    def handleNumberFormatException(NumberFormatException nfe) {
        [problemDescription: 'A Number Was Invalid']
    }
}
----

The exception handler method names can be any valid method name.  The name is not what makes the method an exception handler, the `Exception` argument type is the important part.

The exception handler methods can do anything that a controller action can do including invoking `render`, `redirect`, returning a model, etc.

One way to share exception handler methods across multiple controllers is to use inheritance.  Exception handler methods are inherited into subclasses so an application could define the exception handlers in an abstract class that multiple controllers extend from.  Another way to share exception handler methods across multiple controllers is to use a trait, as shown below...

[source,groovy]
.src/main/groovy/com/demo/DatabaseExceptionHandler.groovy
----
package com.demo

trait DatabaseExceptionHandler {
    def handleSQLException(SQLException e) {
        // handle SQLException
    }

    def handleBatchUpdateException(BatchUpdateException e) {
        // handle BatchUpdateException
    }
}
----

[source,groovy]
.grails-app/controllers/com/demo/DemoController.groovy
----
package com.demo

class DemoController implements DatabaseExceptionHandler {

    // all of the exception handler methods defined
    // in DatabaseExceptionHandler will be added to
    // this class at compile time
}
----

Exception handler methods must be present at compile time.  Specifically, exception handler methods which are runtime metaprogrammed onto a controller class are not supported.

With `grails.exceptionresolver.springHandlers: true`, which Grails 10 makes the default, an exception an action throws
and does not handle itself is resolved first as Spring MVC resolves one a handler method throws: by the
`@ExceptionHandler` methods of the controller's class, and by those of the `@ControllerAdvice` beans that apply to the
controller, scoped by its type or package as for a Spring MVC controller, Spring Boot's handler of
`spring.mvc.problemdetails.enabled` among them, which answers the exceptions of Spring MVC with RFC 9457 problems. What
such a method returns, such as a `ProblemDetail` or a `ResponseEntity`, is written as Spring MVC writes it. An exception
none of them handles is resolved as without the setting, by Spring MVC's other resolvers and the Grails exception
resolver, which renders the application's error page.

[source,groovy]
.src/main/groovy/com/demo/BookExceptionAdvice.groovy
----
package com.demo

import org.springframework.http.HttpStatus
import org.springframework.http.ProblemDetail
import org.springframework.web.bind.annotation.ControllerAdvice
import org.springframework.web.bind.annotation.ExceptionHandler

@ControllerAdvice(assignableTypes = BookController)
class BookExceptionAdvice {

    @ExceptionHandler(BookNotFoundException)
    ProblemDetail notFound(BookNotFoundException e) {
        ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.message)
    }
}
----

Declare the advice as a bean, in `grails-app/conf/spring/resources.groovy` or as a `@Bean` of a configuration class.

With `grails.exceptionresolver.problemDetails: true`, an exception an action throws that no exception handler method handles is written as an https://www.rfc-editor.org/rfc/rfc9457.html[RFC 9457] problem to a client that does not prefer HTML, using the translation Spring Framework 7.1 adds, and the application's error page stays for browsers. A problem is the last resort after those methods, so the setting turns on `grails.exceptionresolver.springHandlers` unless the application sets that to `false`:

[source,yaml]
.grails-app/conf/application.yml
----
grails:
    exceptionresolver:
        problemDetails: true
----

----
HTTP/1.1 500
Content-Type: application/problem+json

{"status":500,"title":"Internal Server Error"}
----

* An `ErrorResponse`, a `ResponseStatusException` or an exception annotated `@ResponseStatus`, or one caused by such an exception, keeps its status and detail. Any other exception is a `500` without a detail, so its message is never exposed.
* The type, title and detail can be customized in the message bundles, with the codes `ErrorResponse` defines.
* The `ResponseBodyAdvice` beans that apply to the controller and the `ErrorResponse.Interceptor` beans apply to it, as to a problem a handler method returns.
* An unexpected exception is logged at `ERROR`, by Spring's `org.springframework.web.method.annotation.ProblemDetailExceptionHandler` logger with its stack trace, and by Grails with the method and URI of the request.

The Grails exception resolver and the application's error page still resolve an exception for:

* A client that prefers HTML: a request whose format, from its URL or its `Accept` header, is `html`, or, where Grails resolves any format, as for a browser under `grails.mime.disable.accept.header.userAgents`, whose first concrete `Accept` type is HTML. A client that accepts any type, such as `curl`, gets the problem.
* An exception that a URL mapping names, or whose root cause it names, such as `"500"(controller: 'errors', action: 'denied', exception: AccessDeniedException)`. A `"500"` mapping without an `exception` is the error page of the clients that prefer HTML, and does not apply to the others.

An exception a view throws while it renders is not one an action throws, and goes to the error page for every client.

WARNING: Do not use Spring Framework's `ProblemDetailsConfigurer.renderUnhandledExceptions(true)` in a `WebMvcConfigurer` for this. It makes Spring MVC's resolver, which runs ahead of the Grails exception resolver, answer every exception of every action with a problem, a browser's included, and `"500"` URL mappings no longer apply.
