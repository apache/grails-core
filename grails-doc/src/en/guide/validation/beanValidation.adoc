==== Bean Validation Annotations

Domain classes can also be constrained with https://jakarta.ee/specifications/bean-validation/[Jakarta Bean Validation] annotations, either instead of or alongside the `constraints` block:

[source,groovy]
----
import jakarta.validation.constraints.Email
import jakarta.validation.constraints.Max
import jakarta.validation.constraints.Min
import jakarta.validation.constraints.NotBlank
import jakarta.validation.constraints.NotNull
import jakarta.validation.constraints.Size

class Member {
    @NotBlank @Size(max = 30) String name
    @NotNull @Email String email
    @NotNull @Min(1L) @Max(5L) Integer level
    String referenceCode

    static constraints = {
        referenceCode nullable: false, matches: /[A-Z]{2}-\d{4}/
    }
}
----

GORM detects the annotations at compile time and validates such a domain class with the Bean Validation provider (Hibernate Validator) in addition to its own constraints. Calling `validate()` or `save()` checks both, and each violation is reported once in the `errors` of the instance: the annotations with Spring's Bean Validation message codes (for example `NotBlank.com.example.Member.name`, `NotBlank.name` and `NotBlank`, falling back to the message of the annotation), and the `constraints` block with the usual link:validation.html#constraints[constraint] codes.

The nullability of a property is decided by its annotations of the default group when it has any: `@NotNull`, `@NotBlank` and `@NotEmpty` make it required and `@Null` keeps it empty, regardless of the `grails.gorm.default.nullable` setting or a `nullable` constraint in the block. `validate()` and `save()` validate the default group only, so an annotation restricted to another group (such as `@NotNull(groups = OnPublish)`) leaves the `nullable` constraint of the block in force. When a domain class redefines its default group with `@GroupSequence`, every group the sequence validates belongs to the default group, including the groups those groups extend and the groups of a nested sequence. As Hibernate Validator applies it, the sequence of a superclass covers the annotations declared by that superclass and the classes above it, whereas a subclass that does not redefine the default group itself validates its own annotations in the `Default` group only. Declare every other rule once, either as an annotation or in the block, as a rule declared in both places is checked twice.

GORM cascades validation to the associations of an annotated domain class exactly as it does for any other domain class, validating the annotations of an annotated associated class together with its `constraints` block, so `@Valid` is not needed on an association between domain classes. An associated instance is validated in the default group, as it is on its own, except through an association marked `@Valid`: as Bean Validation cascades, the instance is then validated in the groups of the instance owning it, converted as the `@ConvertGroup` annotations of the association declare. With `@Valid @ConvertGroup(from = Default, to = OnPublish)` on `lines`, `invoice.validate()` checks the `OnPublish` annotations of each line instead of its default ones, together with the `constraints` block of the line, whose `nullable` constraint then gives way to the `OnPublish` annotations declaring the nullability of a property. The errors of an associated instance are reported under the path of the association, as `lines[0].label` for example, and a class level constraint of the associated class on the path of the association itself, as `lines[0]`. As with Spring's nested validation, the message codes of an annotation error found through the association name the validated class and the path, such as `NotBlank.com.example.Invoice.lines[0].label` and `NotBlank.com.example.Invoice.lines.label`, while the codes of the `constraints` block keep the class of the associated instance. A message keyed `NotBlank.com.example.InvoiceLine.label` therefore applies to a line validated on its own but not through its invoice, whereas `NotBlank.lines.label`, `NotBlank.label` and `NotBlank` apply both ways. The conversions of an association apply to the groups Bean Validation validates when a group of the owning instance is validated: a group and the groups it extends, and, for a group sequence such as the `to` group of a conversion further up, its groups in their order, so a `@ConvertGroup(from = OnPublish, to = OnArchive)` on an association of the line applies when the invoice converted the default group to a sequence of `OnPublish`. A sequence none of whose groups an association converts keeps stopping at the first of its groups with a violation. An instance reached through two associations is validated once in each distinct list of groups, so an attachment that is both the `cover` and the `appendix` of a dossier is checked in the groups each association converts to.

The validator of an annotated domain class is a Spring `SmartValidator`: the validation hints that are classes are the groups to validate in, so `ValidationUtils.invokeValidator(validator, instance, errors, OnPublish)` and `DataBinder.validate(OnPublish)` check the `OnPublish` annotations of the instance instead of its default ones, together with its `constraints` block, and cascade with these groups as the associations marked `@Valid` convert them. `validate()` and `save()` take no groups and validate the default group.

The constrained properties of the domain class (its `constrainedProperties`), used by scaffolding, the OpenAPI descriptions and plugins such as the fields plugin, describe the annotations of the default group as well: `@NotNull` as `nullable: false`, `@Size` as `minSize` and `maxSize`, `@Min`, `@Max`, `@DecimalMin` and `@DecimalMax` as `min` and `max` (on an integer property, the nearest whole number the bound admits), `@Email` as `email`, `@Pattern` as `matches`, `@AssertTrue` and `@AssertFalse` as `inList`, and Hibernate Validator's `@Length`, `@Range`, `@URL` and `@CreditCardNumber` as their GORM counterparts. A custom constraint composed of these annotations is described through them, with the attributes it overrides applied; annotations without an equivalent, such as `@Past` or a custom constraint with its own validator, and a constraint on a getter without a backing field, such as a cross field `@AssertTrue`, are only validated.

Unit tests mocking a domain class with link:testing.html#unitTestingDomainClasses[DataTest] or `DomainUnitTest` validate the annotations and the `constraints` block the same way.
