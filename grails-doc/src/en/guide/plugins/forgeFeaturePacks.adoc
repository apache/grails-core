A plugin can describe what an application needs in order to use it: the dependency on the plugin, settings, files. That description is a _feature pack_. With it, the plugin is a feature that can be selected when an application is created, like the features Grails itself offers.

NOTE: Feature packs are new in Grails 9 and the first form of them is described here: a pack is given to the `create-` commands as a directory, or is that of a published plugin that is given by its coordinates, or by the name of its feature when you name a feature catalog that has the plugin for that name. The list of published plugins does not record feature packs yet and is not such a catalog.


==== The Layout of a Pack


A plugin keeps its pack in `src/main/forge`:

[source]
----
src/main/forge/
    feature.yml          <1>
    templates/           <2>
        AuditConfig.groovy.gsp
        audit.properties
----
<1> The descriptor: what the feature is called and what it adds.
<2> The files the descriptor names. Nothing else in `src/main/forge` is part of the pack.

When the directory exists, the `org.apache.grails.gradle.grails-plugin` Gradle plugin puts `feature.yml` and `templates` into `META-INF/grails-forge` of the plugin's jar and records the name of the pack in the jar's manifest as `Grails-Forge-Pack`. A pack is published with the plugin; there is nothing else to configure. The build fails when the pack could not be read from the jar: when `src/main/forge` has templates and no `feature.yml`, when a file under `templates` is a symbolic link, and when a file is one Gradle leaves out of every archive, such as `.gitignore` or `.DS_Store`. Give such a file another name in the pack and its real name in `to`; this is for a file in a directory of its own, since the `.gitignore` at the root of the application is written by Grails and a pack cannot write it too.

The pack is read only from a jar in the form the `jar` task writes by default; a jar that is built with `zip64 = true`, or that is given a comment or a launch script afterwards, is <<forgeFeaturePackJar,refused>> by the command that would use the pack.


==== The Descriptor


[source,yaml]
.src/main/forge/feature.yml
----
format: 1
kind: feature
templateApi: 1
name: acme-audit
compatibility:
  grails: '[9.0.0,10.0.0)'
  forge: '[9.0.0,10.0.0)'
title: Acme Audit Trail
description: Records who changed which domain instance
applicationTypes: [web, rest-api]
requires: [database-migration]
dependencies:
  - scope: implementation
    coordinates: com.acme:acme-audit-grails
    version: '2.3.0'
configuration:
  acme.audit.enabled: true
  environments:
    test:
      acme.audit.enabled: false
files:
  - from: AuditConfig.groovy.gsp
    to: 'src/main/groovy/{packagePath}/AuditConfig.groovy'
  - from: audit.properties
    to: grails-app/conf/audit.properties
readme: The audit trail is configured in `AuditConfig`.
----

[cols="1,3"]
|===
|Key |Meaning

|`format`, `kind`, `templateApi`
|Required. `1`, `feature` and `1`. A descriptor whose `kind` is `preset` is that of a preset, which an application is made from: see xref:applicationTypes#presets[Making Applications from a Preset].

|`name`
|Required. The name the feature is selected by: lowercase letters, digits and single hyphens, starting with a letter. It cannot be the name of a feature Grails offers.

|`compatibility`
|Required. The versions of Grails (`grails`) and of the generator (`forge`) the pack is for. `[9.0.0,10.0.0)` is 9.0.0 and later and before 10.0.0, `[9.1,)` is 9.1.0 and later, `9.0.0` is that release only, and several intervals are separated by commas. A snapshot, milestone or release candidate counts as the release it leads to. A pack that is not for the Grails that generates the application is refused.

|`title`, `description`, `category`, `documentation`
|`description` is what `--list-features` shows for the feature, under its `category`. `title` and `documentation`, a link, are for tools that present features.

|`thirdPartyDocumentation`
|A link to the documentation of what the plugin integrates, for the `README.md` of the application.

|`applicationTypes`
|The kinds of application the feature can be selected for: `web`, `rest-api`, `plugin`, `web-plugin`, `rest-api-plugin`. All of them when left out.

|`requires`
|Features that are selected with this one. They can be features of Grails or of other packs given to the same command. Two packs can require each other: both are selected, whichever of them is named. A required feature cannot be left out with `--exclude-features`.

|`conflicts`
|Features this one cannot be used with. The application is refused, before anything of it is written, when it would have one of them, whether that feature was selected, is there by default or was brought in by another feature.

|`oneOf`
|An exclusive group the feature belongs to, such as `acme-audit-store`: only one feature of a group can be selected. The group is one of packs; a pack cannot join a group of Grails, such as `database-driver`.

|`dependencies`
|Dependencies of the application. `scope` is a Gradle configuration (`implementation`, `compileOnly`, `runtimeOnly`, `developmentOnly`, `testImplementation`, `testCompileOnly`, `testRuntimeOnly`), `coordinates` is `group:artifact`, `version` is optional and left out when the Grails BOM or a platform manages it, and `excludes` lists `group:artifact` or `group` to exclude.

|`platforms`
|BOMs to import, with `coordinates` and `version`.

|`buildPlugins`
|Gradle plugins to apply, by `id` and optional `version`.

|`build.properties`
|Entries for `gradle.properties`.

|`build.extensions`
|Code for `build.gradle`, by the name of the block it goes into, for example `assets: minifyJs = false`.

|`configuration`
|Settings for `application.yml`. Settings under `environments.<name>` apply to that environment.

|`files`
|Files to write. `from` is a path under `templates`; `to` is the path in the application and can use `{name}`, `{packageName}`, `{packagePath}`, `{className}`, `{naturalName}` and `{propertyName}`.

|`readme`
|A paragraph for the application's `README.md`.
|===

A pack only adds. It cannot change what another selected feature gives the application: a setting, a build property or the version of a dependency that is already there with another value is an error, and so is a file another feature writes, such as the `.gitignore` and the `.gitattributes` at the root of an application. A descriptor with an unknown key, or a destination outside the application, is refused with a message that names the key.


==== Templates


A file whose name ends with `.gsp` is a template. It is rendered when the application is generated; every other file is written as it is. A template is GSP, and this is all the generator reads in it:

[cols="1,3"]
|===
|In the template |Is

|`${...}`
|An expression: its value is written, unescaped.

|`<% ... %>`, `<%= ... %>`
|A scriptlet, and a scriptlet whose value is written.

|`%{ ... }%`
|A scriptlet, in its other form.

|`<%-- ... --%>`, `%{-- ... --}%`
|A comment, which is left out.

|`<%@ page import="..." %>`
|A directive of the page.

|`<g:if>`, `<g:elseif>`, `<g:else>`, `<g:unless>`, `<g:each>`, `<g:while>`, `<g:collect>`, `<g:findAll>`, `<g:grep>`, `<g:def>`
|The ten <<forgeFeaturePackTags,instruction tags>>.

|A backslash directly in front of one of the above, or of any tag
|An <<forgeFeaturePackEscapes,escape>>.
|===

Everything else is text and is written as it is, character for character: every other tag, and also what a GSP of a web application would read and a template has no use for, `@{ ... }` and `!{ ... }!`. A line that holds nothing but scriptlets, directives and comments writes nothing, not even its line break.

// example::template[]
[source,gsp]
.src/main/forge/templates/AuditConfig.groovy.gsp
----
package ${project.packageName}

class AuditConfig {
<% if (features.contains('grails-spring-security')) { %>
    boolean recordUser = true
<% } %>
    String application = '${project.name}'
}
----

For an application `com.example.shop` without Spring Security, this writes:

// example::template-written[]
[source,groovy]
----
package com.example

class AuditConfig {
    String application = 'shop'
}
----


A template can refer to these names. Any other name is an error, so a misspelled name fails the generation and does not write an incomplete file.

[cols="1,3"]
|===
|Name |Value

|`project.name`
|The name of the application, `shop`

|`project.packageName`, `project.packagePath`
|Its package, `com.example`, and the package as a path, `com/example`

|`project.className`, `project.propertyName`, `project.naturalName`
|The name as that of a class (`Shop`), of a property (`shop`), and as words (`Shop`)

|`features`
|The names of all features of the application, sorted

|`applicationType`
|`web`, `rest-api`, `web-plugin`, `plugin` or `rest-api-plugin`

|`options.jdk`
|The version of Java the application is for, as a number

|`options.data`, `options.servlet`, `options.reloading`
|What the application has of what the `--data`, `--servlet` and `--reloading` options choose, written as the values of those options, such as `hibernate7`, `tomcat` and `devtools`. Where the application has none, the value is `none`: a plugin has no servlet container unless one is asked for

|`grailsVersion`
|The version of Grails the application is generated for

|`pack.name`
|The name of the feature of the pack
|===

These names are template API 1, the one `templateApi: 1` in the descriptor asks for. A template API does not change once it is released: when a later version of Grails gives templates more, that is template API 2, and a pack that declares 1 is still given exactly the names above. A pack that declares a template API the generator does not have is refused, with the ones it has in the message.

A template has to be text in UTF-8, and a file of a pack can have at most 1 MiB, before and after it is rendered.

A template that cannot be compiled, or that fails while it is rendered, stops the generation before any file is written. The message names the template and the line of it the error is on, for example `The template AuditConfig.groovy.gsp of the feature acme-audit cannot be rendered: line 4: ...`. For an error in a scriptlet or an expression of several lines, the line is the one it starts on; a block or an instruction tag that is never closed is reported on the last line of the template.

A template is compiled into one method of a class, and a method has a size it cannot be over. A template with too much in it is refused with `it has more expressions, scriptlets and instructions than the page of one template can hold: divide it into several files`, long before its text is 1 MiB: a template holds about 1,500 expressions, or 2,000 instruction tags, or 3,800 tags that are text, a start tag and an end tag counting as one each, and fewer when it has several of these kinds. A view of an application is far below that.


[[forgeFeaturePackTags]]
==== Tags in a Template


The ten instruction tags are run when the application is generated, and are not written to the file. They take the attributes they take in a view, with these differences:

* The `test` of `<g:if>`, `<g:elseif>`, `<g:unless>` and `<g:while>` has to be one expression, `test="${...}"`. In a view `test="false"` and `test="1 == 2"` are text, and text is always true; in a template they are refused.
* `env` is refused. It would ask for the environment the generator runs in; the environment of the application is not known when it is generated.
* A `>` ends a tag, also inside the quotes of an attribute, unless it is inside an expression: write `expr="${it > 1}"`, not `expr="it > 1"`.

// example::instructions[]
[source,gsp]
.src/main/forge/templates/audit.properties.gsp
----
audit.store=<g:if test="${options.data == 'mongodb'}">collection</g:if><g:else>table</g:else>
audit.types=<g:each in="${['create', 'update']}" var="type">${type};</g:each>
----

writes, for an application that does not use MongoDB:

// example::instructions-written[]
[source,properties]
----
audit.store=table
audit.types=create;update;
----

A line that holds only a tag still writes its line break; only a line of scriptlets, directives and comments writes nothing. So an instruction tag suits a choice within a line, and a scriptlet a choice of whole lines.

*Every other tag is text.* The generator has no tag libraries. `<g:link>`, `<g:message>`, `<g:render>`, `<g:form>`, `<sec:ifLoggedIn>`, `<asset:javascript>`, `<tmpl:row>` and any other `<prefix:name>` are written to the file exactly as the template has them, with their attributes, their body and their end tag. An attribute such as `params="[id: 1]"` or `model="[book: book]"` is written as it is. This is what a pack wants when the file it writes is a view of the application. A tag named like an instruction in another namespace, such as `<my:if>`, is text as well.

WARNING: `<g:set>` is a tag of a tag library, so in a template it is written out and sets nothing. For a value the template itself needs, use `<g:def var="x" value="${...}"/>` or a scriptlet. The same holds for `<g:message>`, `<g:render>`, `<g:include>` and `<g:formatDate>`: they are for the application, and the generator does not run them.

`${...}` is evaluated wherever it stands, also in the attributes and the body of a tag that is text, and an instruction tag in the body of such a tag is run:

// example::text-tags[]
[source,gsp]
----
<g:form controller="${project.propertyName}Audit" params="[max: 10]">
<g:if test="${options.servlet != 'none'}">    <g:submitButton name="search"/>
</g:if></g:form>
----

writes, for an application named `shop`:

// example::text-tags-written[]
[source,gsp]
----
<g:form controller="shopAudit" params="[max: 10]">
    <g:submitButton name="search"/>
</g:form>
----


===== Writing a View


A view has GSP of its own, which has to reach the application and must not be evaluated when it is generated.

A view with nothing to fill in is not a template. Give it a name in the pack that does not end with `.gsp`, and its real name in `to`. It is then written byte for byte:

[source,yaml]
----
files:
  - from: book/show.gsp.txt
    to: grails-app/views/book/show.gsp
----

In a template, the tags of the view need nothing, since they are text; neither does `@{ model="..." }`, the first line of a view that scaffolding generates. What the generator would read is written with a backslash in front of it, and the backslash is not written.

[[forgeFeaturePackEscapes]]
[cols="1,3"]
|===
|In the template |Writes

|`\${`
|`${`, an expression of the view

|`\<%`
|`<%`, which starts a scriptlet, a `<%@ page %>` directive or a `<%-- --%>` comment of the view

|`\%{`
|`%{`, which starts a scriptlet or a `%{-- --}%` comment of the view, or is text such as the `%{http_code}` of a `curl` command

|`\<%{`
|`<%{`: the backslash in front of `<%` also takes the `%{` that begins with the same `%`, which starts nothing. For a `<` of the view directly in front of a `%{ }%` scriptlet of the template, write the `<` as an expression: `${'<'}%{ ... }%`.

|`\<g:if`, `\</g:if` and the other nine
|The instruction tag, for the view to run

|`\<g:link`, `\</g:link`, `\<sec:ifLoggedIn` and any other tag
|The tag, as without the backslash. So it is safe to put a backslash in front of every tag of a view, without knowing which ones are instructions.

|`\\${...}`, `\\<% ... %>`, `\\<g:if ...>`
|One backslash, and then the expression, scriptlet or instruction is run. Backslashes directly in front of one of these count in twos: each two write one, and one left over is the escape. `C:\Users\\${project.name}` writes `C:\Users\shop`.

|`\\\${`
|`\${`: one backslash, and the expression is written and not evaluated

|`\` anywhere else: `\n`, `\$5`, `c:\dir`, `\<p>`, `\@{`
|Itself. Only backslashes directly in front of `${`, `<%`, `%{` or a tag are an escape.
|===

Nothing is needed where these end: `}`, `%>`, `--%>` and `--}%` are text.

// example::escapes[]
[source,gsp]
----
\${book.title} costs $5; \\${project.name} and \\\${book.id}
\<g:each in="\${books}">\<g:link action="show">x\</g:link>\</g:each>
C:\Users\\${project.name}\file @{ model="Book book" } !{ x }! \n
token: \${{ secrets.TOKEN }}; curl -w "\%{http_code}"
----

writes, for an application named `shop`:

// example::escapes-written[]
[source,gsp]
----
${book.title} costs $5; \shop and \${book.id}
<g:each in="${books}"><g:link action="show">x</g:link></g:each>
C:\Users\shop\file @{ model="Book book" } !{ x }! \n
token: ${{ secrets.TOKEN }}; curl -w "%{http_code}"
----

To turn a view into a template:

. Where the view already has backslashes directly in front of a `${`, a `<%`, a `%{` or a tag, double them.
. Put a backslash in front of every `${`, `<%` and `%{`, and in front of the start and end tags of the ten instructions, or of every tag. Where a `<%` is directly followed by a `{`, the two share the `%` and the one backslash in front of the `<%` is for both: `\<%{` writes `<%{`.
. Remove the backslash where the generator is to fill something in.

// example::view[]
[source,gsp]
.src/main/forge/templates/book/show.gsp.gsp
----
\%{-- Shows a book of \${grailsApplication.config.info.app.name}. --}%
\<%@ page import="${project.packageName}.Book" %>
<h1>\${book.title} in ${project.naturalName}</h1>
\<g:if test="\${book.authors}">
    \<g:each in="\${book.authors}" var="author">
        <g:link action="show" id="\${author.id}" params="[from: 'book']">\${author.name}</g:link>
    \</g:each>
\</g:if>
\<% if (book.isbn) { %><p>\${book.isbn}</p>\<% } %>
<g:render template="row" model="[book: book]"/>
----

writes, for an application `com.example.shop`:

// example::view-written[]
[source,gsp]
----
%{-- Shows a book of ${grailsApplication.config.info.app.name}. --}%
<%@ page import="com.example.Book" %>
<h1>${book.title} in Shop</h1>
<g:if test="${book.authors}">
    <g:each in="${book.authors}" var="author">
        <g:link action="show" id="${author.id}" params="[from: 'book']">${author.name}</g:link>
    </g:each>
</g:if>
<% if (book.isbn) { %><p>${book.isbn}</p><% } %>
<g:render template="row" model="[book: book]"/>
----

What is inside an expression, a scriptlet or a comment of the template is theirs: nothing in it is escaped or made text.


==== Checking a Pack


A plugin with a pack has it checked when the plugin is checked:

[source,console]
----
$ ./gradlew check
----

`check` runs the task `checkForgePack`, which can also be run by itself. It reads the pack with the generator, the way the pack is read when an application is created, and fails the build with the problems it finds, one on a line, up to 50 of them. A problem of a key of the descriptor starts with that key, such as `files[0].to:`; one of the pack as a whole, such as a missing `feature.yml`, has none. It checks:

* the whole descriptor: unknown keys, missing or malformed values, destinations outside the application;
* every file the descriptor names: that it is there under `templates`, is a file and not a link, and is not too large;
* `compatibility`: that the pack is for the version of Grails, and for the version of the generator, it is checked with;
* every template: that it compiles, and that it renders without an error. A name the template API does not have, such as a misspelled `project.pakageName`, is an error. The problem names the line of the template, as the message does when an application is created. A tag that is not one of the ten <<forgeFeaturePackTags,instruction tags>> is no problem: it is output, and is not looked up in a tag library.

The templates are found through the descriptor, so while the descriptor has a problem only its problems are reported: the templates are checked once it can be read.

No application is generated. A template is compiled once and rendered for a few applications that are made up, and a problem names the one it was found for. All of them are named `com.example.shop` and have the feature of the pack, the features it `requires` and no other feature. With all five `applicationTypes` they are:

[cols="1,1,1,1,1"]
|===
|`applicationType` |`options.jdk` |`options.data` |`options.servlet` |`options.reloading`

|`web`
|`21`
|`hibernate5`
|`tomcat`
|`devtools`

|`rest-api`
|`25`
|`hibernate7`
|`jetty`
|`jrebel`

|`web-plugin`
|`26`
|`mongodb`
|`undertow`
|`none`

|`plugin`
|`21`
|`neo4j`
|`none`
|`devtools`

|`rest-api-plugin`
|`25`
|`hibernate5`
|`tomcat`
|`jrebel`
|===

A descriptor with fewer `applicationTypes` has those in the first column, in this order and starting over when they run out. So every value of an option is rendered once, and a typing error in what a template does for one value is found. What a template does only for an application that is not in the table is not rendered, and an error there is found only when such an application is created:

* for a feature the pack does not require, for example inside `if (features.contains('grails-spring-security'))`;
* for a combination that is not a row of the table, such as `hibernate7` with `undertow`;
* for another name or package than `com.example.shop`.

Try the pack out for those, as described below. Rendering a template runs its code, as creating an application does. Neither is checked what depends on the other features of an application: that no other feature sets a setting, a build property or the version of a dependency of the pack differently, or writes one of its files.

A plugin without `src/main/forge` skips the task. The task is up to date when neither the pack nor the generator changed. Building the jar does not run it: `jar`, `assemble` and `publishToMavenLocal` package a pack that was not checked. `check` and `build` fail for a pack that cannot be used, and so does publishing the plugin to a repository with the `maven-publish` plugin (`publish` and the `publish...Repository` tasks), which checks the pack first.

NOTE: Every task that publishes a plugin with a pack to a Maven repository checks the pack, a repository that is a directory (`file:`) included. So such a plugin cannot be published, even to a directory, unless the generator for its `grailsVersion` can be resolved from the repositories of the build, or another one is declared as shown below. `publishToMavenLocal` is the exception: it installs the plugin with a pack nobody checked.

The task takes a check for passed only when the generator says, in one line and nothing else, that it checked the pack. That keeps an accident from passing: a template that ends the JVM, or writes to the standard output itself, fails the task. It is no protection against a template written to imitate that line, and is not meant as one: the templates of a pack are code of its author.

The generator runs in a JVM of its own, with the Java of the toolchain of the project, and is not a dependency of the plugin. It is resolved from the repositories of the build as `org.apache.grails.forge:grails-forge-core`, in the version of Grails the plugin is built with (`grailsVersion`), with the versions of its own dependencies it was published with: `groovy.version` and the overrides of BOM properties of the project do not apply to it. When no repository of the build has it the task fails and says so. To check the pack with another version, declare it:

[source,groovy]
.build.gradle
----
dependencies {
    grailsForgePackTooling 'org.apache.grails.forge:grails-forge-core:9.0.1'
}
----


==== Testing a Pack with Applications


The check renders the templates of a pack for applications that are made up. The task `forgePackTest` goes the whole way: the generator creates real applications with the feature of the pack selected, as a `create-` command does, and each of them is then built with its own Gradle wrapper. It finds what the check cannot: a dependency that does not resolve, a build file block that does not work, a source file that does not compile, a setting or a file another feature of the application also has.

[source,console]
----
$ ./gradlew forgePackTest
----

The task runs only when it is asked for. `check`, `build` and the tasks that publish the plugin do not run it, because of what it costs: every application is a Grails build of its own, which downloads its Gradle distribution and its dependencies the first time and takes minutes rather than seconds. The builds use the Gradle user home of the build of the plugin, so what one of them downloads is there for the next, and the Java of the toolchain of the plugin. A plugin without `src/main/forge` skips the task, and the task is up to date when the pack, the generator, the publications of the plugin and what is configured below are as they were when it last passed.

The applications are built with the plugin as this build has just built it. When the plugin applies `maven-publish`, `forgePackTest` builds every Maven publication of the project first (its artifacts, its POM and its Gradle module metadata) and puts them into `build/forge-pack-repository`, a Maven repository of the task that the applications resolve from before any other. Where the descriptor declares the plugin in `dependencies` with the version the build has, an application gets the plugin from there, whatever the local Maven repository or another repository has of the same version, and without `publishToMavenLocal`; a descriptor that declares another version gets that one from the other repositories. The publications are inputs of the task: a plugin whose code changed is tested again although its version did not change. A plugin without a Maven publication gives the applications no repository of its own, and they resolve it from the repositories below, as any other dependency.

Each application is a _fixture_. Without configuration there is one for each of the `applicationTypes` of the descriptor, named after its type (`web`, `rest-api`, `web-plugin`, `plugin`, `rest-api-plugin`), with the options every application has by default and no feature but that of the pack and the ones every application of the type has. All of them are named `com.example.shop`. In each the task runs `assemble`, which compiles the application and packages it and runs none of its tests.

Fixtures, and how they are built, are configured in the `grails` block of the plugin. Once a fixture is named, the named ones are the only ones, and they are generated and built in the order of their names:

[source,groovy]
.build.gradle
----
grails {
    forgePackTest {
        fixture('web')                               // <1>
        fixture('mongo') {
            applicationType = 'rest-api'             // <2>
            options = [data: 'mongodb', jdk: '25']   // <3>
            features = ['views-markup']             // <4>
        }
        tasks = ['assemble', 'test']                 // <5>
        arguments = ['--stacktrace']                 // <6>
        repositories = ['https://repo.example.org/maven'] // <7>
        mavenLocal = true                            // <8>
        offline = false                              // <9>
        fixtureTimeout = java.time.Duration.ofMinutes(45) // <10>
    }
}
----
<1> A fixture has a name of lower case letters, digits and single hyphens, which names its directory and its log. Its type of application is `web` unless it says otherwise.
<2> One of `web`, `rest-api`, `web-plugin`, `plugin` and `rest-api-plugin`.
<3> Any of `data`, `servlet`, `reloading` and `jdk`, with the values the `create-` commands take. An option that is left out has its default.
<4> Features to select besides that of the pack.
<5> The tasks to run in each application. The default is `assemble`.
<6> Further arguments for the Gradle of each application.
<7> The repositories the applications resolve from before the ones every generated application has: addresses, which have to be `https`, paths of directories, `mavenLocal()` or `mavenCentral()`. See below for the default and for addresses with a password.
<8> Puts the local Maven repository before the others, after the repository of the publications of the plugin, for a Grails or another plugin that was installed with `publishToMavenLocal`. Not by default. The plugin itself needs it only when it has no Maven publication.
<9> Builds the applications with `--offline`, which works once everything they need is in the Gradle user home. `./gradlew forgePackTest --offline-fixtures` does the same for one run, and so does running the build of the plugin itself with `--offline`.
<10> How long the build of one application can take. The default is 30 minutes. A build that takes longer is stopped, with every process it started, and its fixture is one that could not be built; the other fixtures are still built.

The repositories are written into the build files of the applications the way `GRAILS_REPO_URL` writes them for a `create-` command. The value that variable has in the environment of the build is not used.

Without `repositories`, the applications get the Maven repositories the build script of the plugin declares in its `repositories` block, by their addresses alone: without their credentials and without their content filters. Maven Central and the local Maven repository are recognized by what they are, not by the name a repository has. Two kinds of repository are left out, and the task says so in a warning each time it runs:

* a repository whose address has a user or a password in it (`https://user:password@host/...`). The warning names its host only;
* a repository whose address is not `https` and not a directory, such as an `http` repository with `allowInsecureProtocol` or an `s3:` one, which a generated application cannot be given.

Repositories that are declared in `settings.gradle` are not seen at all. Name any of these in `repositories` if the applications need it.

WARNING: An address you list in `repositories` is written into `build.gradle` of every generated application, and into the copy the application keeps under `.grails`, exactly as you list it, a user and a password included. The log of an application can show it too. The task itself keeps it out of what it prints, of `report.txt` and of what Gradle records of the task's inputs. Do not list an address with a password in a build script that is shared; pass it in from a Gradle property or an environment variable, and treat `build/forge-pack-fixtures` and `build/forge-pack-test` as holding it.

The applications are generated in `build/forge-pack-fixtures/<fixture>`, where they stay to be looked at until the task runs again, and everything the build of one writes goes to `build/forge-pack-test/<fixture>/build.log`. `build/forge-pack-test/report.txt` says of each fixture whether it was built. When an application cannot be built, the others are still built, and the task then fails with, for each that failed, the tasks that failed, where the application and the whole log are, and what Gradle says went wrong, or the last lines of the log when it does not say.

Only `build/forge-pack-test` is an output of the task. The applications are not, and neither is `build/forge-pack-repository`: when `build/forge-pack-fixtures` is deleted, or an application in it is changed, a task that is up to date stays up to date and does not generate them again. Run `./gradlew forgePackTest --rerun` for that, or delete `build/forge-pack-test`.

An application is generated the way a `create-` command generates it, with one addition: an application without a `settings.gradle`, which is every application unless a feature adds one, gets one that only names it. Without it Gradle would find the settings of the plugin above the application and refuse to build it.

A fixture the generator refuses fails the task before anything is built, with what the generator says, as a `create-` command would say it: a fixture of a type the pack is not for, a feature there is not, an option the pack conflicts with, a template that fails for that application. So does a pack with a problem in its descriptor.

The generator is the one `checkForgePack` runs, resolved from `grailsForgePackTooling` as described above.


==== Trying a Pack Out


The `create-` commands take a pack from a directory with `--feature-pack-dir`, and its feature is then selected like any other:

[source,console]
----
$ grails create-app com.example.shop \
    --features=acme-audit \
    --feature-pack-dir=/path/to/acme-audit/src/main/forge
----

The command names every pack the application is made with and says what it adds before it writes anything: the templates and build file blocks, which are code, first, then every file it writes outside the sources, the source files, plugins, properties and dependencies. `--list-features` with the same option lists the feature of the pack among the others. The option can be given more than once.

WARNING: A pack is code. Its templates run when the application is generated, with everything the command can do, and what it adds to `build.gradle` runs when the application is built. Use a pack only when you trust where it comes from.


==== Using the Pack of a Published Plugin


Once the plugin is published, its feature is selected by giving the coordinates of the plugin, with its version, to `--features`, alone or among the names of other features:

[source,console]
----
$ grails create-app com.example.shop \
    --features=h2,com.acme:acme-audit-grails:2.3.0
----

The command takes the jar of that one version from a Maven repository, reads the pack in it and selects the feature of the pack, under the name the pack gives it. Nothing else of the plugin is fetched, none of its dependencies are resolved and nothing of the jar is run. The version is always given, and is one version: a range, a version with a `+` and `latest.release` are refused. A snapshot version can be given; the latest build of it is used and the file name of that build is recorded.

A pack does not add its plugin to the application by itself: the descriptor declares the plugin in `dependencies`, as in the example above. The command warns when the pack of a plugin does not declare that plugin, since the application is then generated without it. It also warns when the pack declares the plugin in another version than the one the pack was taken from, and says which version the application gets; a dependency without a version, which a BOM of the build manages, gets no warning.

The jar is looked for in the repositories of the `GRAILS_REPO_URL` environment variable, in their order, and then in Maven Central. That variable is written for the build of the application, so an entry of it that a pack cannot be taken from is left out with a warning and is not an error: an entry that is not `https` or a directory, a directory that is not given by its absolute path, and an entry with a user name and password in it. Credentials are not sent, and no message repeats an address with them. To look somewhere else, name the repositories with `--feature-pack-repository`, which can be given more than once. Only those repositories are asked then, so the coordinates of a private plugin are sent nowhere else:

[source,console]
----
$ grails create-app com.example.shop \
    --features=com.acme:acme-audit-grails:2.3.0 \
    --feature-pack-repository=https://repo.acme.example/maven
----

The address of a repository is `https`, or `file:` for a directory laid out as a Maven repository, such as `file:///home/me/.m2/repository`. An `http` address is refused, and an address cannot carry a user name, a password or a query: a repository that asks for credentials cannot be used yet. A host is a name, or an address written as four numbers with dots or in brackets; other ways of writing an address, such as one number, are refused. A redirect is followed only to another `https` address, and a repository on the internet is not followed to an address of your own computer or of a private network, when the redirect names such an address itself. A jar can have at most 64 MiB; it is read into memory and written to no file. A repository that does not answer a request, or stops in the middle of an answer, is waited for for 60 seconds, and one file for 5 minutes.

A repository that does not have the jar is passed over and the next one is asked. Any other failure ends the command, and the next repository is not asked: a repository that cannot be reached, one that answers with an error, a time-out, or a jar that fails a check below. The error is one line that names the coordinates and every repository that was asked with the reason. A repository that answers that access to the jar is refused (HTTP 401 or 403) ends the search too, and the message says so: the jar may be there, and asking the next repository would send the coordinates of a private plugin to it. A jar that was fetched and holds no pack that can be used is reported with the coordinates, the repository and every problem of its descriptor, each on a line; so is a pack whose feature has the name of a feature of Grails. In all of these cases nothing is created and the exit code is 1. A pack that requires a feature the application does not have is refused like any selection that cannot be had, with exit code 2, and the message names the coordinates the pack was taken by: name the missing feature, or the plugin that has it, in `--features`. Coordinates or an option that cannot be read are a mistake in the command line, with exit code 2 and the usage of the command.

Before anything is written, the command says where each pack came from and the SHA-256 of the jar that was read:

[source]
----
| Feature pack acme-audit from com.acme:acme-audit-grails:2.3.0 (https://repo.acme.example/maven/), sha256 5f2c...
    the jar matches the sha256 checksum the repository publishes for it
    dependencies: implementation com.acme:acme-audit-grails:2.3.0
----

`--list-features` with coordinates takes the jar too, and prints the first two of these lines before the list.

When the repository publishes a `.sha256` or `.sha1` file for the jar, the jar is checked against it and refused when it differs; when it gives neither, the command says that the jar was not checked. A checksum of the repository shows that the download is complete. It does not show who published the jar. To use only a jar you have looked at, give its SHA-256 with `--feature-pack-sha256`; a jar with another one is refused before it is opened:

[source,console]
----
$ grails create-app com.example.shop \
    --features=com.acme:acme-audit-grails:2.3.0 \
    --feature-pack-sha256=com.acme:acme-audit-grails:2.3.0=5f2c...
----

[[forgeFeaturePackJar]]
The jar has to be a plain jar, as Gradle, Maven and the `jar` tool of the JDK write one, and all of it is checked before the pack in it is read. A file can be made that one program reads as one jar and another program as a different jar, so that the jar you looked at is not the one that is used. Such a file is refused, and the error says what is wrong with it:

* a jar with a comment at its end, or with anything in front of it (such as the launch script of an executable jar), after it or between its entries;
* a jar in the ZIP64 format, which a jar with more than 65,534 entries or of 4 GiB needs, and which Gradle writes for any jar built with `zip64 = true`;
* an entry that is encrypted, or compressed with anything but deflate;
* two entries of one name, or an entry that is a file where another entry has a directory;
* an entry whose name is not a relative path in UTF-8, or has a backslash or a control character in it;
* an entry with an extra field other than those tools write for the times and the owner of a file: one kind of extra field is a second name for the entry, which some programs read as its name;
* an entry whose content does not have the length and the CRC-32 the jar gives for it, or for which the jar gives them twice and differently. This is checked for every entry of the jar, not only for those of the pack.

A jar can have 64 MiB, the names of its entries 4 MiB together, and its entries 256 MiB together when they are not compressed. A signed jar is read as any other, with the entries of its signature.

The signature of a signed jar is not verified. The coordinates, the version and the SHA-256 of each such pack are written to `.grails/forge.lock.yml` of the application, with the feature of the pack in the list of its features, and with them the repository when it is an `https` address. The name of the file is not written; for a snapshot the SHA-256 is what tells one build from another. A directory is not written, since its path names your computer.

===== Selecting the Feature of a Plugin by Its Name

A feature of a published plugin can also be selected by the name of the feature, when a _feature catalog_ is named that has a plugin for the name:

[source,console]
----
$ grails create-app com.example.shop --features=h2,acme-audit \
    --feature-catalog=https://catalog.acme.example/index.json
----

A catalog is named with `--feature-catalog`, which can be given more than once, or with the `GRAILS_FORGE_CATALOG` environment variable, which holds addresses separated by semicolons. There is no catalog unless you name one: without one, a name that is not a feature of Grails is refused as a feature that does not exist, at once, and nothing is asked of the network or written to your computer. A catalog has the format of the list of published plugins of Grails, `grails-plugins-index.json` of https://github.com/apache/grails-plugins-metadata, with a `pack` entry in the versions that have a feature pack. That list does not publish packs yet, so today a catalog is a file of your own in its format, and the list itself, when it is named, is read and has no feature. The address of a catalog is `https`, or `file:` for a file, under the rules for the address of a repository above; `none`, for the option or the variable, means no catalog.

WARNING: Naming a catalog trusts it as much as the plugins themselves. A catalog decides which plugin and version a name means, it can name the repository the jar is fetched from, and it supplies the SHA-256 the jar is checked against. A pack is code that writes into your application and its build. Whoever can change the catalog can therefore have a name run a pack of their choosing, and the SHA-256 does not stand in the way, because it comes from the same catalog: it shows that the jar is the one the catalog means, not that anybody else has looked at it. Name only a catalog whose maintainer you would also let choose your plugins, and prefer coordinates with `--feature-pack-sha256` when you want to decide yourself.

A name given to `--features` is looked up in the catalogs when it is not a feature of Grails, for any type of application, and not the feature of a pack that was given as a directory or by coordinates. The command then chooses a version and says, before it asks any repository for the plugin, what the catalog made of the name and where the jar is looked for. After that everything is as if the coordinates had been given: the jar is checked in the same way and the same lines are printed, with two more:

[source]
----
| The feature acme-audit is taken as com.acme:acme-audit-grails:2.3.0, which the feature catalog https://catalog.acme.example/index.json (sha256 91ab...) names for it, with the SHA-256 5f2c.... Asking https://repo.maven.apache.org/maven2/, and then https://repo.acme.example/maven/, the repository the catalog names
| Feature pack acme-audit from com.acme:acme-audit-grails:2.3.0 (https://repo.acme.example/maven/), sha256 5f2c...
    the coordinates are those the feature catalog https://catalog.acme.example/index.json (sha256 91ab...) has for the feature acme-audit
    the SHA-256 is the one that same catalog gives for the jar: the jar is the one the catalog means, which nobody else has checked
    the jar matches the sha256 checksum the repository publishes for it
----

The jar is the main jar of the version the catalog lists the pack under. The list of published plugins has versions that were published under other coordinates, or to another repository, than the plugin has now (`org.grails.plugins:grails-mail` was `org.grails.plugins:mail` up to 4.0.2), and gives such a version coordinates and a repository of its own; the jar is then taken by those. This is never done silently: the line that is printed before anything is asked names the plugin, the coordinates that are fetched and the repository the catalog names, and the coordinates that were fetched are what the state of the project records.

[source]
----
| The feature mail is taken as org.grails.plugins:mail:4.0.2, the coordinates the catalog gives for version 4.0.2 of the plugin org.grails.plugins:grails-mail, which the feature catalog ...
----

A pack cannot name an artifact of its own. A jar with another SHA-256 than the catalog gives is refused before it is opened, and the pack in the jar has to have the name that was asked for.

*Which version.* The version that is chosen is the latest release of the plugin whose pack is for the type of application that is created, for this version of Grails and for this version of the command. A release is a version made of numbers and dots only; which is the latest is found by comparing the versions, whatever their order in the catalog. A snapshot, a milestone or a release candidate is never chosen for a name, neither is a version the catalog says has no artifact, and neither is any version of a plugin the catalog marks as deprecated: the command says so, with the reason the catalog gives, and names the coordinates, by which such a version can still be used. A pack is for a version of Grails when both say so: the range the pack declares, and the range of the descriptor of the plugin, which the catalog has as `grailsVersion` (`7.0.0 > *`). Neither is taken over the other; a version whose `grailsVersion` cannot be read is left out, and the others of the plugin are still found.

*The BOM of the application.* An application is generated with a BOM of Grails, which manages the versions of Grails' own plugins: `org.apache.grails:grails-bom`, or `org.apache.grails:grails-hibernate7-bom` with `--data hibernate7`. The BOM has the version of the command, and the command knows what it manages (about 270 artifacts, among them all of `org.apache.grails`; not what Spring Boot's BOM manages). When the BOM of the application manages the artifact that would be fetched, the version it manages it at is the one that is taken, and no other: the build would have the plugin in that version whatever pack was read. When the catalog has no pack for that version, the name is refused, and the message names the BOM, the version and the coordinates by which another version can be insisted on. An artifact the BOM does not manage is taken in its latest release. With the Micronaut feature the application gets `grails-micronaut-bom` or `grails-hibernate7-micronaut-bom`, whose versions the command does not have: a name is then not looked up at all, and the plugin is given by its coordinates. The BOM is decided from the options and the features of Grails on the command line before a catalog is read; should the features of the application, once all are known, give it another BOM, the command says so and creates nothing.

*Which plugin.* A name of Grails is always the feature of Grails, whatever type of application it is for, and is never looked up: when a catalog that was read for another name has a plugin with a feature of such a name, the command says that the feature of Grails is the one that is used. When more than one plugin of the catalogs has a feature of the name that was asked for, the command refuses the name and lists the plugins; one of them is then selected by its full name, `group:artifact#name`:

[source,console]
----
$ grails create-app com.example.shop \
    --features='com.acme:acme-audit-grails#acme-audit'
----

With several catalogs, the first one named that lists a plugin at all, by its `group:artifact`, is the one that speaks for that plugin, also when it has no pack for it or not the name that is asked for; what a later catalog says of the same plugin is not looked at. The feature of one pack is selected once however it is asked for: by its name, its full name and the coordinates of its plugin together are one selection and one download.

*Where the jar is looked for.* In the repositories you have, in this order: those of `GRAILS_REPO_URL` and Maven Central. Only when none of them has the jar is the repository asked that the catalog names for the version or for the plugin, if it names one; it has to be an `https` address that is not of your computer or of a private network. When `--feature-pack-repository` is given, only the repositories it names are asked, and the one of the catalog is not.

*When a catalog is read.* Only when a name has to be looked up. A command that selects only features of Grails, packs of directories and coordinates makes no request for a catalog. `--list-features` reads one only when a name given with `--features` has to be looked up, as creating the application would. To see what the catalogs offer, use `--list-catalog-features`, which lists each feature that can be selected by its name with the plugin and the version that would be taken.

*The copy on your computer.* A catalog that was read from an `https` address is kept as a file in `.grails/forge/catalogs` of your home directory. The file holds the catalog as it was read and nothing else, under a name made from the address. For 24 hours the copy is used and the catalog is not asked for again; `--refresh` asks for it again at once. When a catalog cannot be read and there is an older copy, the copy is used and the command says so, with the time the copy was read and how old it is (not with `--refresh`). A catalog that is a file is read every time and is not copied. A copy is trusted no more and no less than the catalog: it is read with the same checks. The three directories `.grails`, `forge` and `catalogs` are created readable and writable by you alone; when one of them is a link, is not owned by the user who runs the command, or can be written to by its group or by everybody, no copy is read or written, and the command says so once, with which directory it is and what is wrong with it. A `.grails` that was there before can be such a directory: with a umask of `002`, which is common on Linux, it was created writable by your group, and `chmod go-w ~/.grails` makes it yours alone. With `--offline` the command then says that no copy is read, and why, rather than that there is none. The directory can be deleted at any time.

*Without a network.* `--offline` makes no request to the network: a catalog is read from its copy, however old, of which the command says the age, or from a file, and the jar of a plugin is taken only from a repository that is a directory, such as the local Maven repository. What is not there is reported and nothing is created.

*When something is wrong.* A catalog that cannot be read, is too large or is not a catalog ends the command with exit code 1 and one line that names the catalog and the reason; nothing is created. This is so only for a command that needed the catalog. A plugin of a catalog whose entry cannot be used is left out, and the others are still found; `--list-catalog-features` lists what was left out and why. A name that no catalog has does not exist, as before, with exit code 2, and the message says in which catalogs it was looked for. So do a name that more than one plugin has and a name whose plugin has no version that can be chosen.

A catalog is a JSON document in the format of `grails-plugins-index.json`: an array of plugins, of at most 4 MiB, with at most 5,000 plugins, 1,000 versions of a plugin and 200,000 values. What is read of it:

[source,json]
----
[
  {
    "coords": "org.grails.plugins:grails-mail",
    "name": "Mail",
    "desc": "Provides a convenient DSL for sending email",
    "maven-repo": "https://repo1.maven.org/maven2",
    "versions": [
      {
        "version": "5.0.3",
        "grailsVersion": "9.0.0 > *",
        "pack": {
          "format": 1,
          "kind": "feature",
          "name": "mail",
          "templateApi": 1,
          "applicationTypes": ["web", "rest-api"],
          "compatibility": { "grails": "[9.0.0,10.0.0)", "forge": "[9.0.0,10.0.0)" },
          "sha256": "5f2c..."
        }
      },
      {
        "version": "4.0.2",
        "grailsVersion": "6.0.0 > *",
        "coords": "org.grails.plugins:mail",
        "maven-repo": "https://repo.grails.org/plugins"
      }
    ]
  }
]
----

Of a plugin, `coords` (at most 120 characters) and `versions` are required; of a version, `version` (at most 60 characters). A version can have `coords` and `maven-repo` of its own, `grailsVersion`, and `artifactAvailable`, which is `false` for a version that is not offered. `deprecated` with a text that says why marks a plugin as deprecated (`true` does too; `false`, an empty text, and the text `false` do not). A `pack` is what the list's indexer copies from the descriptor of the feature pack in the jar, and the SHA-256 of the jar: everything shown is required except `applicationTypes`, which is left out for a pack that is for every type of application. It is not written by hand. Other properties are not read.

[[forgeFeaturePackSameEveryTime]]
==== What Is the Same Every Time


Reproducibility requires the same generator, pack contents, options and repository inputs. The rules below keep generated bytes independent of the directory, default language, time zone and character set. They do not make arbitrary template code deterministic. Rebuilding a published jar also requires the same resolved dependencies and build toolchain; the Grails release verification uses the exact JDK distribution and version of the release and its recorded `SOURCE_DATE_EPOCH`. It does not promise identical bytecode across different JDKs or untested operating systems.

*The jar.* The files of a pack go into the jar as the bytes they are in `src/main/forge`: nothing in them is replaced and no line ending is changed. Each archive input tree is traversed in reproducible order: in each directory, files before subdirectories, each group sorted by name. The declared order of archive inputs is retained. Entries have one fixed time, files have the permissions `rw-r--r--` and directories `rwxr-xr-x`, whatever the source files have on the computer that builds. These are the Gradle version used by Grails's archive defaults, so leave `preserveFileTimestamps`, `reproducibleFileOrder` and the permissions of the `jar` task as they are. The pack-specific manifest attribute contains its name only. What two computers can still differ in is the source bytes: Git can check a text file out with the line endings of the platform, and a template is rendered with the line endings it has. Keep pack checkout line endings fixed:

[source]
..gitattributes
----
src/main/forge/** eol=lf
----

*The order of the features.* The features of an application are a set. Reordering the names in `--features`, `--exclude-features` or one `feature add`, or the `--feature-pack-dir` options for distinct packs, does not change the generated application or its record. Compatible additive features can be added together or successively to an otherwise unchanged generated application with the same result. Existing user edits are merged and preserved; a selection that changes earlier choices can be refused. The features are applied in one order: by the phase of the feature, which for an external pack is the default phase, and within a phase by the name of the feature, character by character as the names are written, so `acme-audit` comes before `acme-audit-store` and that before `acme-b`. No language's rules for sorting are used.

*The order within a file.* What follows from that order, and what does not:

[cols="1,3"]
|===
|In the application |Order

|The dependencies in `build.gradle`
|By the dependency's order value, then the configuration's order, then group and artifact. External pack dependencies have the default order value. Two dependencies that are the same to that sort, such as the same artifact for `developmentOnly` and `testAndDevelopmentOnly`, retain feature order and then declaration order.

|The plugins in `build.gradle`
|By the plugin's order value, then in the order of the features, and those of one feature as its `buildPlugins` lists them. Plugins of external packs have the default order value. A plugin that another feature has already applied is not applied again and stays where it is.

|The lines of a `build.extensions` block, the entries of `gradle.properties`, the paragraphs of `README.md`
|In the order of the features, and those of one feature as its descriptor lists them.

|The settings in `application.yml`
|Sorted by key, after the sections every application starts with. The order of the features and of the descriptor does not matter.

|Imports contributed by compiled build plugins
|Sorted by the complete import line and deduplicated, with LF line endings. The current external pack format does not expose this contribution channel.

|Files
|A file is written by one feature; a second feature that writes it is refused.
|===

So where two packs add to the same place, the one whose feature has the earlier name comes first. `requires` selects another feature; it does not put that feature before this one. Keep tightly ordered contributions in one pack, in declaration order.

*Templates.* A template gives the same text for the same application when it uses the model and nothing else. `features` is sorted. Do not write the time, a random value, an environment variable, a system property, a path of the computer or the name of its user into a file, and do not go through a `HashMap` or `HashSet` to write lines. Text is turned to upper or lower case with `Locale.ROOT` (`name.toLowerCase(Locale.ROOT)`), and numbers and dates are formatted with it (`String.format(Locale.ROOT, ...)`): without it the text depends on the language of whoever generates the application, and `TITLE` in lower case is not `title` in Turkish. `feature add` renders the recorded selection again and checks it against the baseline; when that replay differs, it refuses the addition.

*The record.* In `.grails`, the features that were asked for and those that were left out are sorted by name, each once; the features of the lock are in the order they were applied in; the files of the baseline index are sorted by path. Paths are written with `/`, the files end their lines with a line feed and are UTF-8. A pack that was given as a directory is recorded by the name of its feature only, never by where it was; a pack that was taken from a repository by its coordinates, its version and the SHA-256 of its jar.

*Resolution inputs.* Catalog and repository order is meaningful: the first catalog that lists a plugin owns that plugin's entry, and repositories are tried in the configured order. For an artifact managed by the application's Grails BOM, catalog selection requires that exact version; otherwise it selects the latest compatible numeric release. Numerically equal versions such as `2.3` and `2.3.0` are distinct coordinates; the lexicographically greatest spelling wins the tie, independently of their order in the catalog. Ranges, `+` and `latest.*` selectors are refused for explicit pack coordinates. Changing a catalog, repository order or `GRAILS_REPO_URL` changes the inputs, so it need not give the same output.

*What deliberately varies.* A snapshot can resolve to different bytes later, and a cached catalog is normally used for 24 hours. The record keeps the chosen version and SHA-256; `project show` includes a digest pin for resolved artifacts. File modification times normally reflect generation time; a valid `SOURCE_DATE_EPOCH` fixes them. Neither time is written into the committed generation record. Transaction journals, cache freshness, temporary files and run state are machine-local: journals identify the absolute project path so an interrupted change can be recovered, and are not part of the committed baseline. The SBOM of a framework jar uses the release epoch in a release build and a fixed epoch in a developer build, so compare jars within the same mode, not between these two modes.

The hosted application generator at https://start.grails.org offers the features of Grails only: it takes neither a pack nor the coordinates of a plugin, and reads no catalog.
