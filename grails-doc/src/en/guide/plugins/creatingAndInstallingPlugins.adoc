=== Creating Plugins

Creating a Grails plugin is a simple matter of running one of the supported plugin generators:

Grails Shell CLI
[source,groovy]
----
grails create-plugin <<PLUGIN NAME>>
----

Grails Forge CLI
[source,groovy]
----
grails -t forge create-plugin <<PLUGIN NAME>>
----

This will create a plugin project for the name you specify. For example running `grails create-plugin example` would create a new plugin project called `example`.

You should consider whether the plugin you create requires a web environment or whether the plugin can be used with other profiles. If your plugin requires a web environment then use the "web-plugin" profile instead of the default "plugin" profile:

Grails Shell CLI
[source,groovy]
----
grails create-web-plugin <<PLUGIN NAME>>
----

Grails Forge CLI
[source,groovy]
----
grails -t forge create-web-plugin <<PLUGIN NAME>>
----

Make sure the plugin name does not contain more than one capital letter in a row, or it won't work. Camel case is fine, though.

Being a regular Grails project has a number of benefits in that you can immediately test your plugin by running (if the plugin targets the "web" profile):

[source,groovy]
----
grails run-app
----

NOTE: Plugin projects don't provide an index.gsp by default since most plugins don't need it. So, if you try to view the plugin running in a browser right after creating it, you will receive a page not found error. You can easily create a `grails-app/views/index.gsp` for your plugin if you'd like.

The structure of a Grails plugin is very nearly the same as a Grails application project's, except that a plugin
declares itself with a plugin class.

==== The Plugin Class

A plugin is a concrete subclass of `grails.plugins.Plugin` annotated with `grails.plugins.metadata.GrailsPluginDescriptor`,
written in Groovy or Java. Nothing else is a plugin: a class that does not extend `Plugin`, or that carries no
annotation, is never discovered, whatever its name.

[source,groovy]
----
package example

import org.springframework.beans.factory.BeanRegistrar
import org.springframework.beans.factory.BeanRegistry
import org.springframework.core.env.Environment

import grails.plugins.Plugin
import grails.plugins.metadata.GrailsPluginDescriptor

@GrailsPluginDescriptor(
        after = ['controllers', 'services'],
        dependsOn = ['core'],
        observe = ['controllers'],
        watchedResources = ['file:./grails-app/jobs/**/*Job.groovy'],
        pluginExcludes = ['example/demo/**'])
class ExampleGrailsPlugin extends Plugin {

    BeanRegistrar beanRegistrar() {
        return { BeanRegistry registry, Environment environment ->
            registry.registerBean('exampleService', ExampleService)
        } as BeanRegistrar
    }
}
----

The annotation declares everything known before the plugin runs, as constants:

[cols="1,3"]
|===
|Attribute |Meaning

|`name`
|The logical name. By default it is the class name without a `GrailsPlugin` suffix, in property form:
`ExampleGrailsPlugin` is `example`, `SpringSecurityCoreGrailsPlugin` is `springSecurityCore`.

|`grailsVersion`
|The range of Grails versions the plugin supports, such as `'9.0.0 > *'`. By default it is the version of Grails the
plugin is compiled against and any later version.

|`dependsOn`
|Plugins that must be present, as `'name'` or `'name:range'`. `${plugin.version}` stands for the plugin's own version,
so `'core:${plugin.version}'` requires the version of `core` the plugin is released with. A dependency that is not met
stops the application from starting: see <<unmetPluginDependencies,Unmet Dependencies>>. The plugin also comes after the
plugins it depends on, and a dependency of its project must provide each of them, which the Grails Gradle plugin checks
when the plugin is built.

|`after`, `before`
|Plugins this one comes after or before, when they are present. Grails puts all the plugins in one order, and where two
plugins provide the same thing, the later one wins: see <<understandingPluginLoadOrder,Understanding Plugin Load
Order>>.

|`observe`
|Plugins whose change events this plugin receives in its `onChange` method, or `'*'` for all plugins.

|`evict`
|Plugins this one replaces: they are not loaded when it is.

|`environmentsIncludes`, `environmentsExcludes`
|The environments the plugin is loaded in. A plugin that depends on it is left out of the other environments too.

|`watchedResources`
|Ant patterns of the files whose changes are passed to `onChange` while the application runs in development.

|`providedArtefacts`
|Artefact classes the plugin contributes beyond those compiled with it, such as a tag library from a library it uses.

|`pluginExcludes`
|Ant patterns of the artefact classes left out of the plugin's descriptor, written as class names with `/` between the
parts: `'com/example/demo/**'`. A pattern of source files, such as `'grails-app/views/**'`, is an error.
|===

A plugin has no switch that turns it off: an application leaves a plugin out by not depending on it, or by naming it in
`grails.plugin.excludes`.

The plugin's version is not declared: it is the version of the project that builds it. The description, license,
developers and source locations of a plugin are the publication's, declared in the `grailsPublish` block of
`build.gradle` and written to its POM.

The plugin's behaviour is the `Plugin` methods it overrides: `beanRegistrar()`, which with a `beans` block is how a
plugin registers beans, `doWithApplicationContext()`, `onChange(Map)`, `onConfigChange(Map)`, `onStartup(Map)` and
`onShutdown(Map)`, described in <<hookingIntoRuntimeConfiguration>> and <<participatingInAutoReloadEvents>>.

[[unmetPluginDependencies]]
==== Unmet Dependencies

Every `dependsOn` of every plugin the application loads must be met. When one is not, the application does not start:
plugin discovery throws a `grails.plugins.exceptions.PluginException` that names every plugin that cannot be loaded and,
for each, every dependency it lacks and why:

* the dependency is not on the class path;
* its version is outside the required range;
* it cannot be loaded itself;
* the application leaves it out with `grails.plugin.excludes`, or does not name it in `grails.plugin.includes`. Excluding
  a plugin does not exclude the plugins that depend on it: name them in `grails.plugin.excludes` too. Including a plugin
  includes the plugins it depends on;
* its `environmentsIncludes` or `environmentsExcludes` leave it out of the current environment. Leave the plugin that
  depends on it out of that environment as well.

A plugin that depends on a plugin another plugin evicts still loads: the evicting plugin stands in for the evicted one.

[[verifyingPlugins]]
==== Checking the Plugins When the Application Is Built

The Grails Gradle plugin adds `verifyGrailsPlugins` to `check`, in the build of every application and plugin. It runs the
same discovery the application runs when it starts, with the project's runtime and compile class paths, in a JVM of the
project's Java toolchain, so the build fails on what would stop the application from starting: a plugin built for an
earlier Grails, a descriptor that cannot be read, an unmet `dependsOn` and a plugin order that is circular. A plugin's
build is checked with the dependencies it declares, so a `dependsOn` that none of them provides fails it, not the
application that uses it later.

Each of the `development`, `test` and `production` environments is checked as the application starts in it: with the
plugins that support the environment, and with the `grails.plugin.includes` or `grails.plugin.excludes` of
`application.yml` and `application.groovy`, including their `environments` blocks. A failure names the environments
it happens in and gives the reason the application would give:

[source]
----
The Grails plugins of this project would stop its application from starting:
In the development, test, production environments: Grails plug-ins cannot be loaded because their dependencies are not met:
- Grails plug-in [audit] cannot be loaded: dependency [reports] with required version [*] is missing: add a dependency that provides it, or, if [audit] only has to come after [reports] when it is present, name it in after instead of dependsOn
----

The task writes the plugin order of each environment to `build/grails/plugin-order.txt`. A build that uses other
environments sets them:

[source,groovy]
----
tasks.named('verifyGrailsPlugins') {
    environments = ['development', 'test', 'staging', 'production']
}
----

Configuration the application gets elsewhere, such as from an environment variable, a system property or a Spring
profile, is not known when it is built, so the application still checks its plugins again when it starts. A project
that compiles Grails plugins without the Grails Gradle plugin applies `org.apache.grails.gradle.grails-plugin-verification`
to get the task.

==== The Plugin Descriptor

The compiler writes the plugin's descriptor beside its classes, so a plugin is described the same way however it is
built: by the Grails Gradle plugin, by an IDE, or by `groovyc`, in a plugin project, inside an application, or in a test
source set.

* `META-INF/grails/plugins.imports` lists the names of the plugins in the jar.
* `META-INF/grails/plugins/<name>/plugin.properties` holds the annotation's metadata, the plugin's version and the
  artefacts compiled with it, by type.
* `META-INF/grails/plugins/<name>/plugin.yml` (or `plugin.groovy`) is the plugin's configuration, copied from
  `grails-app/conf`.

Grails discovers plugins by reading those files, so it filters and orders them without loading or creating them. A
descriptor that cannot be read, that names a class missing from the class path, or a class that is not a `Plugin`
stops the application from starting: the jar it came from is broken.

The Grails Gradle plugin gives the compiler the project version and the location of `grails-app/conf`. A plugin compiled
without them, such as one in a test source set, has no version and no configuration file. A `dependsOn` range on a
plugin without a version cannot be checked, so the application does not start; depend on such a plugin by name alone.

A plugin class compiled into a test source set is a plugin of the tests: its descriptor is written beside the test
classes, so every test that starts an application discovers it. A plugin class a test registers itself, and that other
tests must not see, is compiled by the test at run time, with a `GroovyClassLoader`, rather than in the source set. A plugin written in Java has its descriptor written by the Grails annotation processor, which
it runs by adding `grails-core` to its `annotationProcessor` configuration.

==== Plugin Configuration

A Grails plugin can be configured in one of the following files:

- `grails-app/conf/plugin.yml`
- `grails-app/conf/plugin.groovy`

These files will be included in the plugin package while the `application.*` files are only used internally when developing the plugin. See <<excludedArtefacts>>.

==== Reading configuration properties

Instead of directly accessing Grails configuration as `grailsApplication.config.mail.hostName`, use a Spring Boot configuration bean (or a POJO) annotated with {springbootapi}org/springframework/boot/context/properties/ConfigurationProperties.html[ConfigurationProperties] annotation. Here is an example plugin configuration:

./src/main/groovy/example/MailPluginConfiguration.groovy
[source,groovy]
----
package example

import org.springframework.boot.context.properties.ConfigurationProperties

@ConfigurationProperties(prefix = "mail")
class MailPluginConfiguration {

    String hostName
    int port
    String from
}
----

You can inject the `MailPluginConfiguration` bean into your bean like any other bean.

./grails-app/services/example/MailService.groovy
[source,groovy]
----
package example

class MailService {

    MailPluginConfiguration mailPluginConfiguration

    void sendMail() {

    }

}
----

Please read the {springBootReference}features/external-config.html[Spring Boot Externalized Configuration] section for more information.

==== Installing Local Plugins

In order to install the Grails plugin to your local Maven, you could use Gradle https://docs.gradle.org/current/userguide/publishing_maven.html[Maven Publish] plugin. You may also need to configure the publishing extension as:

[source,groovy]
----
publishing {
    publications {
        maven(MavenPublication) {
            versionMapping {
                usage('java-api') {
                    fromResolutionOf('runtimeClasspath')
                }
                usage('java-runtime') {
                    fromResolutionResult()
                }
            }
            from components.java
        }
    }
}
----

NOTE: Please refer to the Gradle Maven Publish plugin documentation for up-to-date information.

To make your plugin available for use in a Grails application run the `./gradlew publishToMavenLocal` command:

[source,bash]
----
./gradlew publishToMavenLocal
----

This will install the plugin into your local Maven cache. Then to use the plugin within an application declare a dependency on the plugin in your `build.gradle` file and include `mavenLocal()` in your repositories hash:

[source,groovy]
----
...
repositories {
    ...
    mavenLocal()
}
...
implementation "org.apache.grails:grails-quartz:0.1"
----

NOTE: In Grails 2.x plugins were packaged as ZIP files, however from Grails 3.x+ plugins are simple JAR files that can be added to the classpath of the IDE.

==== Plugins and Multi-Project Builds


If you wish to setup a plugin as part of a multi project build then follow these steps.

*Step 1: Create the application and the plugin*

Using the `grails` command create an application and a plugin:

[source,groovy]
----
$ grails create-app myapp
$ grails create-plugin myplugin
----

*Step 2: Create a settings.gradle file*

In the same directory create a `settings.gradle` file with the following contents:

[source,groovy]
----
include "myapp", "myplugin"
----

The directory structure should be as follows:

[source,groovy]
----
PROJECT_DIR
  - settings.gradle
  - myapp
    - build.gradle
  - myplugin
    - build.gradle
----

*Step 3: Declare a project dependency on the plugin*

Within the `build.gradle` of the application declare a dependency on the plugin within the `plugins` block:

[source,groovy]
----
grails {
    plugins {
        implementation project(':myplugin')
    }
}
----

NOTE: You can also declare the dependency within the `dependencies` block, however reloading will not work correctly if defined this way.

*Step 4: (Optional) Configure the plugin for reloading

Within the `build.gradle` of the plugin, apply the gradle plugin `org.apache.grails.gradle.grails-exploded` to allow for proper reloading of the plugin:

[source,groovy]
----
apply plugin: 'org.apache.grails.gradle.grails-exploded'
----

NOTE: During development, `bootRun` uses the plugin's main source set output directories. These include the compiled Java and Groovy classes, with the plugin descriptor and its namespaced configuration beside them, and the processed resources.

*Step 5: Run the application*

Now run the application using the `grails run-app` command from the root of the application directory, you can use the `verbose` flag to see the Gradle output:

[source,groovy]
----
$ cd myapp
$ grails run-app -verbose
----

You will notice from the Gradle output that plugins sources are built and placed on the classpath of your application:

[source,groovy]
----
:myplugin:compileAstJava UP-TO-DATE
:myplugin:compileAstGroovy UP-TO-DATE
:myplugin:processAstResources UP-TO-DATE
:myplugin:astClasses UP-TO-DATE
:myplugin:compileJava UP-TO-DATE
:myplugin:configScript UP-TO-DATE
:myplugin:compileGroovy
:myplugin:copyAssets UP-TO-DATE
:myplugin:copyCommands UP-TO-DATE
:myplugin:copyTemplates UP-TO-DATE
:myplugin:processResources
:myapp:compileJava UP-TO-DATE
:myapp:compileGroovy
:myapp:processResources UP-TO-DATE
:myapp:classes
:myapp:findMainClass
:myapp:bootRun
Grails application running at http://localhost:8080 in environment: development
----


[[excludedArtefacts]]
==== Notes on excluded Artefacts


Although the link:{commandLineRef}create-plugin.html[create-plugin] command creates certain files for you so that the plugin can be run as a Grails application, not all of these files are included when packaging a plugin. The following is a list of artefacts created, but not included by link:{commandLineRef}package-plugin.html[package-plugin]:

* `grails-app/build.gradle` (although it is used to generate `dependencies.groovy`)
* `grails-app/conf/logback.xml`
* `grails-app/conf/logback-spring.xml`
* `grails-app/conf/application.yml`
* `grails-app/conf/application.groovy`
* `grails-app/conf/spring/resources.groovy`
* Everything within `/src/test/\*\*`
* SCM management files within `\*\*/.svn/\*\*` and `\*\*/CVS/\*\*`

==== Customizing the plugin contents


When developing a plugin you may create test classes and sources that are used during the development and testing of the plugin but should not be exported to the application.

To exclude test sources you need to set the `pluginExcludes` of the plugin's `@GrailsPluginDescriptor` AND exclude the compiled classes inside your `build.gradle` file. For example say you have some classes under the `com.demo` package that are in your plugin source tree but should not be packaged in the application. In your plugin descriptor you should exclude these:

[source,groovy]
----
@GrailsPluginDescriptor(pluginExcludes = ['**/com/demo/**'])
class ExampleGrailsPlugin extends Plugin {
}
----

And in your `build.gradle` you should exclude the compiled classes from the JAR file:

[source,groovy]
----
jar {
  exclude "com/demo/**/**"
}
----

==== Inline Plugins in Grails


In Grails 2.x it was possible to specify inline plugins in `BuildConfig`, from Grails 3.x+ this functionality has been replaced by Gradle's multi-project build feature.

To set up a multi project build create an application and a plugin in a parent directory:

[source,groovy]
----
$ grails create-app myapp
$ grails create-plugin myplugin
----

Then create a `settings.gradle` file in the parent directory specifying the location of your application and plugin:

[source,groovy]
----
include 'myapp', 'myplugin'
----

Finally add a dependency in your application's `build.gradle` on the plugin:

[source,groovy]
----
grails {
    plugins {
        implementation project(':myplugin')
    }
}
----

NOTE: You can also declare the dependency within the `dependencies` block, however your subproject will not reload correctly.

Using this technique you have achieved the equivalent of inline plugins from Grails 2.x.

==== Grails Forge Creating Plugins


Creating a Grails plugin is a simple matter of running the command:

[source,groovy]
----
grails create-plugin <<PLUGIN NAME>>
----

This will create a web-plugin project for the name you specify. For example running `grails create-plugin example` would create a new web-plugin project called `example`.

In Grails you should consider whether the plugin you create requires a web environment or whether the plugin can be used with other profiles. If your plugin does not require a web environment then use the "plugin" profile instead of the default "web-plugin" profile:

[source,groovy]
----
grails create-plugin <<PLUGIN NAME>> --profile=plugin
----

Make sure the plugin name does not contain more than one capital letter in a row, or it won't work. Camel case is fine, though.

Being a regular Grails project has a number of benefits in that you can immediately test your plugin by running (if the plugin targets the "web" profile):

[source,shell]
----
./gradlew bootRun
----

NOTE: Plugin projects don't provide an index.gsp by default since most plugins don't need it. So, if you try to view the plugin running in a browser right after creating it, you will receive a page not found error. You can easily create a `grails-app/views/index.gsp` for your plugin if you'd like.

The structure of a Grails plugin is very nearly the same as a Grails application project's, except that a plugin
declares itself with a plugin class: a `Plugin` subclass annotated with `@GrailsPluginDescriptor`. See
<<creatingAndInstallingPlugins>> above for the plugin class, its metadata and the descriptor the compiler writes for it.

=== Plugin Configuration

Instead of directly accessing Grails configuration as `grailsApplication.config.getProperty('mail.hostName', String)`, use a Spring Boot configuration bean (or a POJO) annotated with {springbootapi}org/springframework/boot/context/properties/ConfigurationProperties.html[ConfigurationProperties] annotation. Here is an example plugin configuration:

./src/main/groovy/example/MailPluginConfiguration.groovy
[source,groovy]
----
package example

import org.springframework.boot.context.properties.ConfigurationProperties

@ConfigurationProperties(prefix = "mail")
class MailPluginConfiguration {

    String hostName
    int port
    String from
}
----

You can inject the `MailPluginConfiguration` bean into your bean like any other bean.

./grails-app/services/example/MailService.groovy
[source,groovy]
----
package example

class MailService {

    MailPluginConfiguration mailPluginConfiguration

    void sendMail() {

    }

}
----

Please read the {springBootReference}features/external-config.html[Spring Boot Externalized Configuration] section for more information.
