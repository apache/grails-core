==== Add Tools to the Command Line

A plugin adds _tools_ to the `grails` command of every application that depends on it: classes that the application runs by their names, as `grails dbm-update` and `grails generate-all Book`. They are written as in an application, in two folders whose difference is what a tool can use and how it is run:

* `src/cli/groovy` for a tool that uses the classes of the application, and by default the running application: its beans, GORM and its configuration. The build of the application runs it, with the Gradle task `runTool`. Write one with `grails create-tool NAME`.
* `src/standalone/groovy` for a tool that only reads and writes files of the project, such as one that renders a template of the plugin into the application. The `grails` command runs it as a Java process of its own, without Gradle and without the application, also while the application does not compile. It has the tool API and its own libraries, and nothing of the plugin. Write one with `grails create-tool --standalone NAME`.

[source,groovy]
.src/cli/groovy/com/example/myplugin/cli/AuditReportTool.groovy
----
package com.example.myplugin.cli

import org.apache.grails.core.cli.ApplicationTool
import org.apache.grails.core.cli.ToolSupport

class AuditReportTool implements ApplicationTool, ToolSupport {

    String description = 'Prints an audit report'

    AuditService auditService

    boolean handle() {
        auditService.report().each { println it }
        return true
    }
}
----

A tool of `src/cli` has the application context in `applicationContext`, and is autowired like any other Spring bean. One that declares `boolean skipBootstrap = true` is run without the `BootStrap` classes of the application, and one that declares `boolean startsApplication = false` without the application at all, with the classes of the application on its class path.

[[pluginCliArtifact]]
===== The companion artifacts

Tools are only ever run from the command line, so they are not in the jar of the plugin. Every Grails plugin publishes them beside the plugin, in a companion artifact for each folder that has a tool: `<artifact>-cli` for `src/cli` and `<artifact>-cli-standalone` for `src/standalone`. `-cli` depends on the plugin; `-cli-standalone` never does. No line of the build of the plugin is needed for it: the Grails plugin Gradle plugin applies `org.apache.grails.gradle.grails-plugin-cli`, which builds the companions, with each tool registered as it is compiled, names the companions in the manifest of the plugin's jar, and, with the Grails publish plugin, publishes them with the plugin.

An application that depends on the plugin gets both companions in the scopes `grailsCli` and `grailsCliStandalone`, and with them the tools and the Gradle task of each, such as `./gradlew auditReport`:

[source,groovy]
.build.gradle
----
dependencies {
    implementation 'com.example:my-plugin:1.0.0'   // my-plugin-cli and my-plugin-cli-standalone follow automatically
}
----

The scripts of `src/main/scripts` of a plugin, which are deprecated (see xref:commandLine#creatingCustomScripts[Creating Custom Scripts]), are packaged into the `-cli` companion as `META-INF/commands`, and not into the jar of the plugin.

The tools of a plugin of Grails 8 are in `grails-app/commands`. That folder is compiled with `src/cli` and published in the `-cli` companion, where Grails 8 put it into the jar of the plugin, so the plugin publishes the companion with its next release. The folder is deprecated: move its classes to `src/cli/groovy`, as they are. A plugin released for Grails 7, whose commands implement `grails.dev.commands.ApplicationCommand`, needs a release for Grails 9: Grails 9 does not run those commands.

xref:commandLine#creatingTools[Creating Tools] has the details: what each folder can use, how a tool is named, how its libraries are declared (`cliImplementation`, `standaloneImplementation`), the `cliArtifact` block that names the companions, how an application takes the standalone tools of a plugin without the plugin, and how a plugin gives `grails run-app` an option of its own, as `--query-tail` of Grails Data does.

The main difference between a tool of `src/cli` and one of `src/standalone` is that the first can use the state of the application, its database and GORM, and the second can run before the application compiles. In Grails 2.x Gant scripts could be used to perform both these tasks; from Grails 3.x on, code generation and interacting with runtime application state are separated.


==== Adding a new grails-app artifact (Controller, Tag Library, Service, etc.)


A plugin can add new artifacts by creating the relevant file within the `grails-app` tree.

[source,groovy]
----
+ grails-app
      + controllers  <-- additional controllers here
      + services <-- additional services here
      + etc.  <-- additional XXX here
----


==== Providing Views, Templates and View resolution


When a plugin provides a controller it may also provide default views to be rendered. This is an excellent way to modularize your application through plugins. Grails' view resolution mechanism will first look for the view in the application it is installed into and if that fails will attempt to look for the view within the plugin. This means that you can override views provided by a plugin by creating corresponding GSPs in the application's `grails-app/views` directory.

For example, consider a controller called `BookController` that's provided by an 'amazon' plugin. If the action being executed is `list`, Grails will first look for a view called `grails-app/views/book/list.gsp` then if that fails it will look for the same view relative to the plugin.

However if the view uses templates that are also provided by the plugin then the following syntax may be necessary:

[source,groovy]
----
<g:render template="fooTemplate" plugin="amazon"/>
----

Note the usage of the `plugin` attribute, which contains the name of the plugin where the template resides. If this is not specified then Grails will look for the template relative to the application.


==== Excluded Artefacts

By default Grails excludes the following files during the packaging process:

* `grails-app/conf/logback.xml`
* `grails-app/conf/logback-spring.xml`
* `grails-app/conf/application.yml`
* `grails-app/conf/application.groovy`
* `grails-app/conf/spring/resources.groovy`
* Everything within `/src/test/\*\*`
* SCM management files within `\*\*/.svn/\*\*` and `\*\*/CVS/\*\*`


The default `UrlMappings.groovy` file is not excluded, so remove any mappings that are not required for the plugin to work.  You are also free to add a UrlMappings definition under a different name which *will* be included. For example a file called `grails-app/controllers/BlogUrlMappings.groovy` is fine.

The list of excludes is extensible with the `pluginExcludes` property:

[source,groovy]
----
// resources that are excluded from plugin packaging
def pluginExcludes = [
    "grails-app/views/error.gsp"
]
----

This is useful for example to include demo or test resources in the plugin repository, but not include them in the final distribution.
