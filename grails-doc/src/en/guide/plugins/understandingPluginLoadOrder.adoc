==== Controlling Plugin Dependencies


Plugins often depend on the presence of other plugins and can adapt depending on the presence of others. A plugin
declares both in its `@GrailsPluginDescriptor`. The first is `dependsOn`. For example, take a look at this snippet
from the Hibernate plugin:

[source,groovy]
----
@GrailsPluginDescriptor(dependsOn = ['dataSource', 'domainClass', 'i18n', 'core'])
class HibernateGrailsPlugin extends Plugin {
}
----

The Hibernate plugin is dependent on the presence of four plugins: the `dataSource`, `domainClass`, `i18n` and `core`
plugins.

The dependencies will be loaded before the Hibernate plugin and if all dependencies do not load, then the plugin will
not load.

A dependency can name a range of versions after a colon, in a mini expression language:

[source,groovy]
----
@GrailsPluginDescriptor(dependsOn = ['foo:* > 1.0'])
@GrailsPluginDescriptor(dependsOn = ['foo:1.0 > 1.1'])
@GrailsPluginDescriptor(dependsOn = ['foo:1.0 > *'])
----

When the wildcard * character is used it denotes "any" version. The expression syntax also excludes any suffixes such
as -BETA, -ALPHA etc. so for example the expression "1.0 > 1.1" would match any of the following versions:

* 1.1
* 1.0
* 1.0.1
* 1.0.3-SNAPSHOT
* 1.1-BETA2

`${plugin.version}` stands for the plugin's own version, which is the version of the project that builds it. Plugins
released together, as the Grails framework's are, require one another at that version:
`dependsOn = ['core:${plugin.version}']`. A plugin compiled outside a build that sets the version, such as one in a
test source set, has no version, and an unknown version satisfies every range.


==== Controlling Load Order


Using `dependsOn` establishes a "hard" dependency in that if the dependency is not resolved, the plugin will give up
and won't load. It is possible though to have a weaker dependency using `loadAfter` and `loadBefore`:

[source,groovy]
----
@GrailsPluginDescriptor(loadAfter = ['controllers'])
----

Here the plugin will be loaded after the `controllers` plugin if it exists, otherwise it will just be loaded. The
plugin can then adapt to the presence of the other plugin, for example the Hibernate plugin has this code in its
`doWithSpring` closure:

[source,groovy]
----
if (manager?.hasGrailsPlugin("controllers")) {
    openSessionInViewInterceptor(OpenSessionInViewInterceptor) {
        flushMode = HibernateAccessor.FLUSH_MANUAL
        sessionFactory = sessionFactory
    }
    grailsUrlHandlerMapping.interceptors << openSessionInViewInterceptor
}
----

Here the Hibernate plugin will only register an `OpenSessionInViewInterceptor` if the `controllers` plugin has been
loaded. The `manager` variable is an instance of the link:{api}grails/plugins/GrailsPluginManager.html[GrailsPluginManager]
interface and it provides methods to interact with other plugins.

You can also use `loadBefore` to specify one or more plugins that your plugin should load before:

[source,groovy]
----
@GrailsPluginDescriptor(loadBefore = ['rabbitmq'])
----


==== Environments


It's not only plugin load order that you can control. You can also specify which environments your plugin should be
loaded in:

[source,groovy]
----
@GrailsPluginDescriptor(environmentsIncludes = ['development', 'test', 'myCustomEnv'])
----

In this example, the plugin will only load in the 'development', 'test' and 'myCustomEnv' environments.
`environmentsExcludes` names the environments the plugin is not loaded in instead:

[source,groovy]
----
@GrailsPluginDescriptor(environmentsExcludes = ['production'])
----

==== Reading a published plugin definition

Tools can read the UTF-8 `META-INF/grails/plugins/<name>/plugin.properties` file with
`grails.plugins.metadata.PluginDefinition.read(name, reader)`. This returns an immutable definition with symbolic class
names: the plugin's class, version, Grails compatibility, dependency version constraints, ordering, environments,
watched resources and contributed artefacts. Reading the definition requires no classes from the plugin, and it is
everything Grails knows about a plugin before it creates it.

For a Java plugin built directly with `javac`, put Grails and its dependencies on the processor path, so that the
`org.grails.compiler.injection.JavaPluginDescriptorProcessor` it registers runs, compile to a class directory with
`-d`, and supply the version with `-Agrails.plugin.version=1.0`. Package the complete output directory. With Gradle, add
`grails-core` to the `annotationProcessor` configuration; the Grails Gradle plugin passes the version.
