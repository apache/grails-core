Grails 3.0's command line system differs greatly from previous versions of Grails and features APIs for invoking Gradle for build related tasks, as well as performing code generation.

When you type:

[source,groovy]
----
grails <<command name>>
----

Grails searches the https://central.sonatype.com/[profile repository] based on the profile of the current application. If the profile is for a web application then commands are read from the web profile and the base profile which it inherits from.

Since command behavior is profile specific the web profile may provide different behavior for the `run-app` command then say a profile for running batch applications.

When you type the following command:

[source,groovy]
----
grails run-app
----

It will first search the application, and then the profile for commands:

* `PROJECT_HOME/src/main/scripts/run-app.groovy`
* `&lt;profile&gt;/commands/run-app.groovy`
* `&lt;profile&gt;/commands/run-app.yml`

To get a list of all commands and some help about the available commands type:

[source,bash]
----
grails help
----

which outputs usage instructions and the list of commands Grails is aware of:

[source,bash]
----
grails <<environment>>* <<target>> <<arguments>>*'

| Examples:
$ grails dev run-app
$ grails create-app books

| Available Commands (type grails help 'command-name' for more info):
| Command Name                          Command Description
----------------------------------------------------------------------------------------------------
clean                                   Cleans a Grails application's compiled sources
compile                                 Compiles a Grails application
...
----

NOTE: Refer to the Command Line reference in the Quick Reference menu of the reference guide for more information about individual commands

=== Arguments

The `grails` command is a front to a `gradle` invocation, because of this there can be unexpected side-effects.
For example, when executing `grails -Dapp.foo=bar run-app` the `app.foo` system property won't be available to your application. This is because `bootRun` in your `build.gradle` configures the system properties.
To make this work you can simply append all `System.properties` to `bootRun` in `build.gradle` like:

[source,groovy]
----
bootRun{
    systemProperties System.properties // Please note not to use '=', because this will override all configured systemProperties. This will append them.
}
----

Or if you only want to pass through a limited set, you can prefix your system properties using an arbitrary prefix and configure `bootRun` like:

[source,groovy]
----
bootRun{
    bootRun {
        systemProperties System.properties.inject([:]){acc,item-> item.key.startsWith('boot.')?acc << [(item.key.substring('boot.'.length())):item.value]:acc }
    }
}
----

In this example only system properties starting with `boot.` are passed through.

Application and JVM arguments should be specified in `bootRun` as well.

[source,groovy]
----
bootRun{
    bootRun {
        jvmArgs('-Dspring.output.ansi.enabled=always')
        args('--app.foo=bar','--app.bar=foo') // Override the `app.foo` and `app.bar` config options (`grailsApplication.config`)
    }
}
----


=== Non-interactive mode


When you run a script manually, and it prompts you for information, you can answer the questions and continue running the script. But when you run a script as part of an automated process, for example a continuous integration build server, there's no way to "answer" the questions. So you can pass the `--non-interactive` switch to the script command to tell Grails to accept the default answer for any questions, for example whether to install a missing plugin.

For example:

[source,groovy]
----
grails war --non-interactive
----



The Grails Forge New Command-Line Interface (CLI) has undergone significant changes compared to its previous versions, primarily focusing on code generation. One notable alteration is the removal of APIs for invoking Gradle for tasks related to building using Gradle Tooling APIs. This shift in responsibility aligns with the framework's evolution and its integration with the Gradle build system.

=== Accessing the Grails CLI

The Grails CLI (Command Line Interface) can be swiftly and effortlessly accessed by simply typing the following command into your terminal or command prompt:

[source,shell]
----
grails
----

This command allows developers to quickly initiate the Grails CLI and begin working with the framework, making it an easy entry point for those looking to start their Grails projects.

The New Grails CLI! is the preferred method for initiating new Grails projects. This command-line interface offers various options for creating projects, enabling you to select your preferred build tools, test frameworks, GORM implementation, and more. Additionally, the CLI provides commands for generating essential components like controllers and domain classes.

=== The Grails Forge Website

You can also begin your Grails application without the need to install the Grails CLI by visiting https://start.grails.org/[the Grails Forge website]. This web-based platform allows you to initiate Grails projects conveniently, bypassing the installation of the CLI.

=== Understanding the New Grails Command-line Interface (CLI)

Once the Grails CLI has been successfully installed, you can activate it using the "grails" command. For example:

[source,shell]
----
grails create-app myapp
----

A Grails framework CLI project is recognizable by the presence of the "grails-forge-cli.yml" file, which is automatically generated at the project's root if it was created using the CLI. This file contains information about the project's profile, default package, and other variables.

The file was previously "grails-cli.yml", and that filename is backwards compatible for Grails Forge CLI.

A project generated by Grails 9 also has a `.grails` directory that records how it was generated (see xref:commandLine#creatingProject[Creating a Grails Project]). The code generation commands read the application type, the default package and the features from there, and read "grails-forge-cli.yml" only for a project that has no such directory or whose `.grails` directory cannot be used. In a project with a `.grails` directory, a change made to "grails-forge-cli.yml" by hand is not followed, and the commands warn when the two do not agree.

Here is an example of a "grails-forge-cli.yml" configuration for a default Grails web application:

[source,yaml]
----
applicationType: web
defaultPackage: com.example
reloading: devtools
sourceLanguage: groovy
buildTool: gradle
gormImpl: gorm-hibernate5
servletImpl: spring-boot-starter-tomcat
features:
  - app-name
  - asset-pipeline-grails
  - base
  - geb
  - gorm-hibernate5
  - gradle
  - grails-application
  - grails-console
  - grails-dependencies
  - grails-gorm-testing-support
  - grails-gradle-plugin
  - grails-gsp
  - grails-url-mappings
  - grails-web
  - grails-web-testing-support
  - h2
  - logback
  - readme
  - scaffolding
  - spock
  - spring-boot-autoconfigure
  - spring-boot-starter
  - spring-boot-starter-tomcat
  - yaml
----

This "grails-forge-cli.yml" configuration records the application type, default package, source language, build tool, GORM implementation, servlet implementation, and the list of enabled features the application was generated with. In a project that was generated by an earlier version, which has no `.grails` directory, it is what sets these values for the code generation commands.

=== Commands of a project, in every directory of it

The commands that work on a project (the `create-*` code generation commands, `add-property`, `feature add` and `gradle`) can be given in any directory of the project, not only in the one at its top. The project is the nearest directory, from the current one upwards, that has a `grails-app` directory, a `.grails/project.yml`, a `grails-forge-cli.yml` or a `grails-cli.yml`. Its record is read there and the files are written there, so `create-controller Book` given in `grails-app/views` creates the same `grails-app/controllers/.../BookController.groovy` as when it is given at the top of the project, and the paths the commands report are relative to the project. The templates of the project are the ones under `src/main/templates` at its top too, which is also where `install-templates` copies them, wherever in the project the command is given. The search does not go above the root of the Git repository the directory is in, and stops at the first project it finds: in a project that lies inside another one, the commands are those of the inner project, and when the inner project has no record there are no code generation commands, rather than those of the project around it.

=== Short forms of commands

With the Grails Forge CLI the name of a command can be shortened to the first letters of its words, with the first letter of every word after the first in upper case:

[source,console]
----
$ grails -t forge cA com.example.myapp    <1>
$ grails -t forge cDC Book                <2>
$ grails -t forge f a grails-quartz       <3>
----
<1> `create-app`
<2> `create-domain-class`
<3> `feature add`: the command of a command has a short form too

This is the rule the Grails shell goes by. There have to be as many parts as the name has words, and each part is the start of its word: `cA`, `creA`, `creat-app` and `CA` are all `create-app`; `ca` and `c` are not, because they are one part for a name of two words. Parts are told apart by upper case letters and hyphens only, so a short form has nothing but letters and hyphens in it.

* The name of a command always is that command, also when it happens to be the short form of another one.
* When a short form fits more than one command of the directory, none of them is run. The command line names the commands it fits and ends with exit code 2; type more of the name. Where the Grails shell runs the first command that fits, the Grails Forge CLI asks. In a project this happens with two short forms that come to mind first: `cC` fits `create-controller` and `create-command`, and `cS` fits `create-service` and `create-script`. `cCont` and `cSe` are the controller and the service, `cCom` and `cSc` the command and the script.
* Only the name of a command is ever looked at, never what follows it: in `create-app cA` the application is called `cA`, and everything after `gradle` reaches Gradle as it was typed.
* What stands where a command is expected and is neither a command nor the short form of one is refused with exit code 2, together with the commands that are most like it. After `--help` or `--version` (`-h`, `-V`) it is not looked at: `grails -t forge --help anything` shows the help.

=== Help

Every command of the Grails Forge CLI says how it is used when it is given `--help`. The `help` command shows the same for the command that is named after it, which can be shortened too, and lists the commands there are in the current directory when no command is named:

[source,console]
----
$ grails -t forge help
$ grails -t forge help create-app
$ grails -t forge help feature add
$ grails -t forge help gradle
----

`help gradle` is how to see the help of the `gradle` command itself, since `gradle --help` is given to Gradle. In a project, `help` lists the commands of the project as well, in every directory of it. A command there is not ends `help` with exit code 2.

The usage of every command is laid out for a width of 100 columns, and the list of commands shows the first sentence of the description of each.

`help --json` writes the commands of the current directory as one JSON document on one line of the standard output, and nothing else, for an editor or another tool to read:

[source,json]
----
{
  "format": 1,
  "complete": true,
  "diagnostics": [],
  "projectDirectory": "/home/me/myapp",
  "commands": [
    {
      "name": "create-controller",
      "aliases": [],
      "description": "Creates a Grails Controller",
      "project": true,
      "origin": "built-in",
      "options": [
        { "names": ["-f", "--force"], "arity": "0", "label": null, "required": false, "description": "Whether to overwrite existing files" }
      ],
      "parameters": [
        { "label": "CONTROLLER-NAME", "arity": "1", "description": "The name of the controller to create" }
      ],
      "commands": []
    }
  ]
}
----

[cols="1,3"]
|===
| Member | Meaning

| `format`
| The version of the document, `1`. It changes only when a reader of the earlier version would misread the document; members can be added without it changing, so a reader ignores the members it does not know.

| `complete`, `diagnostics`
| `complete` is `false` when not every command of the directory could be found, and `diagnostics` then says why, one line each: that the record of the project cannot be used, or that the project above the current directory is not your own and is not used (see the section on running Gradle with the Grails Forge CLI), in which cases the code generation commands are missing. `diagnostics` can also have a line when `complete` is `true`: a warning about a record that is used, for example that `grails-forge-cli.yml` was changed and no longer says what `.grails` says. In a project, `complete` is also `false` while the build has not listed the commands of the application and its plugins, or may list them differently now (see the section on the commands of the application and its plugins below); a command of the application that is not there because the Grails Forge CLI has a command by its name is a line of `diagnostics` and leaves `complete` as it is.

| `projectDirectory`
| The directory of the project the current directory is in, or `null` outside a project.

| `commands`
| The commands, in the order `help` lists them. `name` is what is typed, `aliases` are other names of the command, `description` is one line of plain text, `project` says whether the command works on a project and cannot be used outside one, `origin` says where the command comes from (`built-in` for the commands of the Grails Forge CLI itself), and `commands` holds the commands of the command, described in the same way. The commands of the application and its plugins come after those of the Grails Forge CLI. Their `origin` is `application`, the coordinates `group:artifact:version` of the artifact the command comes from, or `file:` and the name of a jar; they also have `target`, which is `application` because the command runs in the application, and `registration`, as the build of the project says it (see xref:commandLine#creatingCustomCommands[Creating Custom Commands]).

| `options`
| The options of the command: all the `names` of an option, the `label` of its value (`null` for an option that takes none), whether it is `required`, and its `arity`. A command of the application or of a plugin has neither `options` nor `parameters`: the build does not know them.

| `parameters`
| What the command takes besides options, in the order it is given, each with its `label` and `arity`.

| `arity`
| How many values are taken, as text: one number (`"0"`, `"1"`), or a least and a most number with `..` between them (`"0..1"`), where `*` stands for any number (`"1..*"`).
|===

=== Commands of the Application and its Plugins

An application and its plugins can have commands of their own (see xref:commandLine#creatingCustomCommands[Creating Custom Commands]). In a project, the Grails Forge CLI has each of them as a command, by the name the command has:

[source,console]
----
$ grails -t forge gradle grailsCommandCatalog
$ grails -t forge help
...
Commands of the application and its plugins:
  audit-report  Writes the audit report (com.example:my-plugin-cli:1.0.0)
  greet         Greets someone (application)
$ grails -t forge greet "Alice Smith" --loud
$ grails -t forge help greet
----

The commands are the ones the Gradle task `grailsCommandCatalog` of the project has written to `build/grails/command-catalog.json`. The Grails Forge CLI reads that file and runs nothing to have it, so that asking for help or mistyping a command never starts a build: run the task once, and again when the commands of the project have changed.

* `help` lists the commands after those of the Grails Forge CLI, each with where it comes from, `help NAME` shows one of them, and `help --json` describes them. They have short forms like every other command; a short form that fits a command of the Grails Forge CLI and a command of the application is refused with both named.
* Everything after the name of the command is given to the command as it is, each argument as the one argument it is: spaces, quotes, a leading dash and line breaks are kept, and no option of the Grails Forge CLI is read from it, so `--help`, `-x` and `--stacktrace` after the name are the command's. Not given are the character U+0000, more than 4095 arguments, or more than 1 MiB of them; the command line refuses those with exit code 2.
* The command runs in the application, started by the Gradle task `runCommand` of the project, with the Gradle wrapper of the project and everything that holds for the `gradle` command. The arguments are handed to Gradle in a file in a temporary directory that only you can read, and that is deleted when the command ends, fails or is cancelled. The exit code is 0 when the command succeeded and 1, after one line, when it failed or Gradle did.
* While there is no `build/grails/command-catalog.json`, the project has no such commands. `help` and `help --json` say so and name the task, and what is typed for a command and is none is refused with the same line added, since it may be a command of the application.
* A file that is older than `build.gradle`, `build.gradle.kts`, `settings.gradle`, `settings.gradle.kts`, `gradle.properties`, the directory `grails-app/commands` or the directory `build/classes/groovy/main/META-INF/grails-commands` is still used, and `help` and `help --json` say that the commands may have changed. `gradle grailsCommandCatalog --rerun` writes the file again also when Gradle finds the task up to date. A change that none of these files shows, such as a new version of a plugin from a version catalog or a changed description, is not noticed.
* The file is read as something that anything in the build may have written. A file that is a link, is behind a link, is not a plain file, has more than 4 MiB, or is not exactly the document the task writes (names of commands in lower case with single hyphens, descriptions of one line, origins that are coordinates) is not used at all: the project then has no such commands, and one line says what is wrong with the file without repeating anything of it.

==== When a command has the name of a command of the Grails Forge CLI

A command of the Grails Forge CLI keeps its name, the other names it has and the short forms of its name. A command of the application or of a plugin that is called `install-templates`, `war` (another name of `assemble`) or `stat` (short for `stats`) is therefore not a command of the Grails Forge CLI. This is never silent: `help` and `help --json` name the command, where it comes from and what has the name, and typing the name runs the command of the Grails Forge CLI after one warning line on the standard error. The command of the application is still run through Gradle:

[source,console]
----
$ grails -t forge install-templates
| Warning install-templates is a command of the CLI itself (built-in), so the command install-templates of org.apache.grails:grails-scaffolding:9.0.0 is not a command here. That one is run with: grails-forge-cli gradle runCommand --arg=install-templates
$ grails -t forge gradle runCommand --arg=install-templates
----

=== Grails Default Package Configuration

The project's default package is determined based on the project's name. For instance, running the following command:

[source, shell]
----
grails create-app myapp
----

Will set the default package to `myapp`.

If you wish to specify your own default package when creating the application, you can do so by prefixing the application name with the package like this:

[source, shell]
----
grails create-app com.example.myapp
----

In this case, "com.example" becomes the default package for your project.

Each part of the package becomes a directory of the sources, and the name of the application a directory and part of the names of files. A part that is one of the names Windows keeps for devices, such as `aux` in `com.aux.myapp`, is therefore refused, as is such a name for the application itself: the project could not be checked out on Windows. Those names are `con`, `prn`, `aux`, `nul`, `conin$`, `conout$`, `clock$`, and `com` or `lpt` followed by one digit, which can also be a superscript `¹`, `²` or `³`, in any case of letters. A name with a control character, a slash or a backslash, and a name for the application that not every file system takes for a directory (one with `:`, `*`, `?`, `"`, `<`, `>` or `|` in it, or with a space or a dot at its end), are refused as well, as mistakes in the command line.

=== Creating Classes with the Grails Forge CLI

In the directory of a project the Grails Forge CLI has commands that write a class of the application, most of them with a test beside it. Which commands there are depends on the type of the application and on its features, as recorded in the project:

[cols="2,4,2"]
|===
|Command |Writes |In

|`create-controller <name>`
|`grails-app/controllers/<package>/<Name>Controller.groovy` and `src/test/groovy/<package>/<Name>ControllerSpec.groovy`
|every project

|`create-service <name>`
|`grails-app/services/<package>/<Name>Service.groovy` and `src/test/groovy/<package>/<Name>ServiceSpec.groovy`
|every project

|`create-domain-class <name>`
|`grails-app/domain/<package>/<Name>.groovy` and `src/test/groovy/<package>/<Name>Spec.groovy`
|every project

|`create-taglib <name>`
|`grails-app/taglib/<package>/<Name>TagLib.groovy` and `src/test/groovy/<package>/<Name>TagLibSpec.groovy`
|every project

|`create-interceptor <name>`
|`grails-app/controllers/<package>/<Name>Interceptor.groovy` and `src/test/groovy/<package>/<Name>InterceptorSpec.groovy`
|every project

|`create-job <name>`
|`grails-app/jobs/<package>/<Name>Job.groovy`
|a project with the `grails-quartz` feature

|`create-unit-test <name>`
|`src/test/groovy/<package>/<Name>Spec.groovy`
|every project

|`create-integration-test <name>`
|`src/integration-test/groovy/<package>/<Name>Spec.groovy`
|web applications, REST API applications and web plugins

|`create-functional-test <name>`
|`src/integration-test/groovy/<package>/<Name>Spec.groovy`, a test that calls the running application over HTTP
|REST API applications

|`create-restful-controller <domain class>`
|`grails-app/controllers/<package>/<Name>Controller.groovy`, a controller that extends `RestfulController` for the domain class
|REST API applications

|`create-domain-resource <name>`
|`grails-app/domain/<package>/<Name>.groovy`, a domain class with `@Resource`, and `src/test/groovy/<package>/<Name>Spec.groovy`
|REST API applications

|`create-command <name>`
|`grails-app/commands/<package>/<Name>Command.groovy`
|every project

|`create-script <name>`
|`src/main/scripts/<name>.groovy`
|every project
|===

[source,shell]
----
$ grails -t forge create-unit-test BookFormatter
$ grails -t forge create-domain-resource org.bookstore.Book
$ grails -t forge create-command data-import
----

The name is the name of a class, with or without its package; without one, the class goes into the default package of the project. Its first letter is made upper case, and a name with hyphens such as `data-import` becomes `DataImport`. Every one of these commands holds the name to what the name of a new class can be, and refuses anything else as a mistake in the command line (exit code 2) before they write a file: the name and each part of the package have to be identifiers of Java, a package is given with dots and never as a path (a name with `/`, `\` or `:` is refused), and a control character, a name of more than 200 characters and a name Windows keeps for a device (see above) are refused too. The letters of a name are written in the composed form of Unicode (NFC), in which an accented letter is one character. Before Grails 9 `create-controller`, `create-service`, `create-domain-class`, `create-taglib`, `create-interceptor` and `create-job` took any text for a name and made directories and a file of it; a name they accepted and now refuse is a path, a name with a space or another character no identifier has, a package with a hyphen, a name that starts or ends with a hyphen, the name of a file such as `a.B.groovy`, and a device name of Windows such as `con`. `create-unit-test`, `create-integration-test`, `create-functional-test`, `create-restful-controller`, `create-domain-resource` and `create-command` also take a name that already ends with what they add to it: `create-unit-test BookSpec` writes `BookSpec.groovy`, `create-command ImportCommand` writes `ImportCommand.groovy`, and `create-restful-controller BookController` writes the controller of `Book`. A name that ends with `.groovy` or `.java`, as `Book.groovy`, is refused: the name of the class is given, not the name of its file. The first letter has to be one that has a capital, and a hyphen stands between two words. A script has no package and is named with the letters a to z and digits, in words that capitals or hyphens set apart: `create-script DataImport` and `create-script data-import` both write `src/main/scripts/data-import.groovy`.

A command writes all of its files or none. A file that is there already is not replaced: the command then writes nothing, not the other file either, says which file is in the way and ends with exit code 1. With `-f` or `--force` it replaces what is there. Before Grails 9 `create-controller`, `create-service`, `create-domain-class`, `create-taglib`, `create-interceptor` and `create-job` of the Grails Forge CLI kept such a file with a warning, wrote the other file and ended with exit code 0.

The files are written into the project and nowhere else. A project can come from a repository someone else made, and such a repository can have a link where a directory of the sources is expected. So a command, `install-templates` included, writes a file only when every directory from the project down to the file is a directory: when one of them is a link, also one that leads to another directory of the same project, or a file, or is there under a name written differently (`Example` where `example` is asked for, on a file system that takes one for the other), the command writes nothing, says which step of the path is in the way and ends with exit code 1. A link in the place of the file itself is replaced by the file when the command is forced, and never written through; a directory in the place of the file is left alone. A file that is replaced is moved aside under another name first and has its name again, with its content, its mode and its other names, when the command cannot write all of its files; when something cannot be taken back, the command says which file is now what. Every message names a file by its path in the project.

|===

The locations are those the templates had before Grails 9, in a profile and in the Quartz plugin, and so are the two ways of writing a name, so a template that only names what it wants can be put under `src/main/templates` as it is. No template is run: a template is text in which names are replaced. The shell ran `Job.groovy` and `artifacts/Script.groovy` as Groovy templates; a template that relied on that, with code or with an expression that is more than a name, has to be written without.

In a template with tokens these are replaced, and everything else, a `$`, `${...}` and `<% %>` included, is written as it is:

[cols="1,3"]
|===
|Token |Replaced by

|`@artifact.package@`
|The package declaration, `package org.bookstore` and the end of its line. Put it on a line of its own. For a class without a package, the token and the end of its line are left out.

|`@artifact.package.name@`
|The package, `org.bookstore`

|`@artifact.package.path@`
|The package as a path, `org/bookstore`

|`@artifact.name@`
|The name of the class without what the command adds to it: `Book` for `BookController`

|`@artifact.propertyName@`
|That name as a property: `book`
|===

A token that starts with `@artifact.` and is none of these is a mistake in the template, and the command fails.

[source,groovy]
.src/main/templates/artifacts/Controller.groovy
----
@artifact.package@
import groovy.transform.CompileStatic

@CompileStatic
class @artifact.name@Controller {

    def index() { }
}
----

`Job.groovy` names what it wants in braces, as the template of the Quartz plugin does: `${className}`, `${simpleName}`, `${propertyName}`, `${modelName}`, `${packageName}`, `${packagePath}`, `${fullName}` and `${lowerCaseName}` are replaced. A `$` that is to be written is written `\$`, and a backslash `\\`. A line that is only `package ${packageName}` is left out for a class without a package.

[source,groovy]
.src/main/templates/Job.groovy
----
package ${packageName}

class ${className}Job {

    static triggers = {
        cron name: '${propertyName}', cronExpression: '0 0 3 * * ?'
    }

    def execute() {
    }
}
----

Everything a Groovy template would evaluate is a mistake in this template, and the command fails with the line it is on: code between `<%` and `%>` or `<%=` and `%>`, an expression in braces that is more than one of the names (`${className.toLowerCase()}`), a name without braces (`$className`) and any other use of a backslash. Templates with logic are not supported.

A template is read only from inside the project, and only under the very names of its location: one that is a link, or is below a link, that leads out of the project is refused, and so are a template of more than 256 KiB, one that is not text in UTF-8 or has a NUL character, and one that is no file. A byte order mark at the start of a template is not written. A template that cannot be rendered fails the command with one line that names the template and the line: `The template src/main/templates/Job.groovy cannot be rendered: line 3: ...`. In each of these cases the command writes nothing, ends with exit code 1 and does not fall back to the template of the Grails Forge CLI.

`install-templates` copies the templates the Grails Forge CLI has for the commands of the project into `src/main/templates`, as a starting point for your own:

[source,shell]
----
$ grails -t forge install-templates
| Copied template to src/main/templates/artifacts/Command.groovy
| Copied template to src/main/templates/artifacts/Controller.groovy
...
----

It lists each file it writes. A template the project already has is kept and named; with `-f` or `--force` it is replaced. The templates of the scaffolding plugin under `src/main/templates/scaffolding` are a different set, which this command does not write: `./gradlew runCommand -Pargs="install-templates"` copies those.

=== Gradle Build Tool

Grails now utilizes the Gradle Build System for project management. The project's build configuration is specified in the `build.gradle` file, where you define critical aspects of your project such as its version, required dependencies, and the repositories from which these dependencies should be sourced. Here's an example of how this is done:

[source, groovy]
----
plugins {
    id 'org.apache.grails.gradle.grails-web' version "{version}" // Grails Application Gradle Plugin
}

repositories {
    mavenCentral()
}

dependencies {
    implementation platform("org.apache.grails:grails-bom:{version}")
    implementation 'org.springframework.boot:spring-boot-starter'
    implementation 'org.apache.grails:grails-core'
    // Add more dependencies as needed...
}
----

=== Utilizing Gradle Build Tool

To interact with your Grails project and perform various tasks related to building and running it, you should employ Gradle commands. Here are a few examples:

- Building the Grails application:

[source, bash]
----
gradle build
----

- Running the Grails application:

[source, bash]
----
gradle bootRun
----

- Listing available Gradle tasks:

[source, bash]
----
gradle tasks
----

By invoking these Gradle commands, you can effectively manage your Grails application's lifecycle.

It is important to remember that Grails leverages the power of Gradle for streamlined project management, including build automation and dependency resolution. This approach allows for greater flexibility and control over your Grails projects.
