=== Upgrade Instructions for Grails and Related Dependencies

To ensure compatibility with Grails {version}, please review the following upgrade instructions carefully.
This guide outlines the necessary steps and warnings to upgrade your Grails project from Grails 8.x to Grails 9.

==== 1. GPars Integration Deprecated in Favour of Groovy Concurrency

Grails 9 builds on Groovy 6, which brings a unified concurrency and parallel-processing toolkit into core under https://groovy-lang.org/releasenotes/groovy-6.0.html#concurrency-toolkit[GEP-18: Integrated Concurrency and Parallel Processing]. The `groovy.concurrent` package provides `Awaitable`, `DataflowVariable`, `Actor`, `Agent`, `Pool`, `ParallelScope` and the parallel collection methods such as `eachParallel` and `collectParallel`. The Groovy release notes describe the toolkit as modernising the patterns from GPars around virtual threads, structured concurrency and Groovy 6's `async`/`await`, and state that previous users of GPars will find much of its functionality there.

With those patterns part of the language, Grails no longer needs the separate GPars library, which was last released in 2014 and depends on Groovy 2.x and the Multiverse STM engine. The `grails-async-gpars` and `grails-events-gpars` modules remain available in Grails 9 but are deprecated for removal: their classes carry `@Deprecated(since = '9.0', forRemoval = true)` and log a warning when selected. They will be removed in a future release.

Their replacements are `grails-async-groovy-concurrent`, providing `org.grails.async.factory.groovy.AwaitablePromiseFactory`, and `grails-events-groovy-concurrent`, providing `org.grails.events.groovy.ActorEventBus`. Both are selected the same way the GPars modules are, by adding the dependency in place of the GPars one:

[source,groovy]
.build.gradle
----
runtimeOnly 'org.apache.grails.async:grails-async-groovy-concurrent'
runtimeOnly 'org.apache.grails.events:grails-events-groovy-concurrent'
----

Do not keep both the GPars and the Groovy module on the classpath: only the first service-loaded `PromiseFactory` is used, and the event bus builder refuses to start when more than one `EventBus` implementation is found.

The Groovy promise factory follows the failure contract of the default `CompletableFuture` factory rather than the GPars one: direct and chained `get()` calls throw `ExecutionException` with the original failure as the cause, a single-promise `onError` recovers with its callback result, and the aggregate `onError` observes the failure and leaves the returned promise failed. `onComplete` and `then` return a new promise instead of the receiver. Promises created by this factory are also Groovy `Awaitable` instances and can be passed to `await` directly.

The Groovy actor event bus delivers each event to its subscribers in publication order on a single Groovy actor. A subscriber that throws without a reply handler is logged and does not stop delivery to the remaining subscribers or later events.

Applications that use GPars directly, for example `GParsPool.withPool { list.eachParallel { } }`, should move to the Groovy equivalents: the parallel collection methods are available on every `Collection` without a pool, and `groovy.concurrent.ParallelScope.withPool(n) { scope -> list.eachParallel { } }` runs them on a pool of a chosen size. Once the deprecated modules are removed, Grails will no longer bring GPars onto the classpath, so an application that still needs it must declare `org.codehaus.gpars:gpars` itself.

NOTE: Groovy 6 marks the concurrency toolkit as incubating. The Grails modules that build on it expose only the Grails `Promise` and `EventBus` contracts, so changes to the Groovy API in later Groovy releases are absorbed by Grails rather than by application code.

==== 2. Groovy Code Is Compiled with invokedynamic

Grails 8 compiles every Groovy source set of an application without invokedynamic (`grails { indy = false }` was the default). Grails 9 leaves the setting unset, so the Groovy compiler's own default applies, and on Groovy 6 that is invokedynamic. An application that set `grails { indy = true }` can remove the line. Build logic that read the property, for example `grails.indy.get()`, must allow for it having no value now: use `grails.indy.getOrElse(true)` or check `grails.indy.present`.

An application that has to keep classic call sites, for example while it measures the difference, sets the property explicitly. An application that applies GraalVM's native image plugin cannot: the build fails with the reason, because an image needs invokedynamic.

To keep classic call sites:

[source,groovy]
.build.gradle
----
grails {
    indy = false
}
----

Classic call sites on Groovy 6 need `org.apache.groovy:groovy-callsite` on the classpath. Grails does not carry it, so an application that sets `indy` to `false` declares `implementation 'org.apache.groovy:groovy-callsite'` itself, at the version the Grails BOM manages, and again for every source set that does not see its implementation dependencies, such as the test fixtures of Gradle's `java-test-fixtures` plugin. Without it the Groovy compiler stops with a message naming the module.

A library compiled with classic call sites needs the module too, whatever the application's own setting, because Groovy 6 loads such a class only with it; the failure is a `NoClassDefFoundError` naming `org.codehaus.groovy.runtime.callsite.CallSiteArray`. Spock 2.5, Geb 8 and the Asset Pipeline 5.2 are compiled with invokedynamic, but `org.testcontainers:testcontainers-spock` is not, so an application that uses it declares `testRuntimeOnly 'org.apache.groovy:groovy-callsite'` next to it.

==== 3. XML Web Support Moves to a Separate Module

XML conversion, request-body binding, and REST renderers now live in the optional
`grails-xml` module. In Grails 9 the web starter still brings it, and so does `grails-web-boot`, which the
applications forge and the profiles generate list instead of the starter, preserving existing XML endpoints.
JSON-only applications can exclude `org.apache.grails:grails-xml` now:

[source,groovy]
.build.gradle
----
configurations.configureEach {
    exclude group: 'org.apache.grails', module: 'grails-xml'
}
----

In Grails 10 neither will bring it, and `@Resource` will default to JSON only.
Legacy XML conversion is scheduled for removal in Grails 11: `grails.converters.XML`, the `XmlRenderer`,
`XmlCollectionRenderer`, HAL XML, Atom and Vnd.Error XML renderers, and the XML validation errors
marshaller are deprecated for removal. The converter, and the HAL XML, Atom and Vnd.Error XML renderers, each log one
warning when they are used; the other XML renderers and the errors marshaller warn through the converter they render
with.
MIME type negotiation still recognizes `application/xml`, `text/xml`, Atom, and other XML media
types; recognizing a media type does not install an XML serializer.

New REST controllers, RESTful controllers, resources, and scaffolded controllers generated by the
`rest-api` profile advertise JSON only. After adding `grails-xml`, add `xml` to the artefact's
`responseFormats` or `formats` declaration when that endpoint should negotiate XML.

Applications that expose XML endpoints or use `grails.converters.XML`, XML object marshallers, XML data
binding, or the XML and Atom renderers need this module. It is supplied transitively by the Grails 9
web starter and `grails-web-boot`; applications without either, and applications upgrading to Grails 10, add it
explicitly:

[source,groovy]
.build.gradle
----
dependencies {
    implementation 'org.apache.grails:grails-xml'
}
----

The module preserves the established Grails XML APIs and compatibility marshalling for domain-shaped
payloads, collections, maps, validation errors, named converter configurations, and include/exclude
projections. Its XML renderers, and an application's `XmlRenderer` beans, find the view locator and the renderer
registry in the application context when they write a response, so their `groovyPageLocator` and `rendererRegistry`
properties are no longer autowired; they are set only where an application sets them.

Without the module, a request for an XML format that nothing else renders is answered like a request for
any unsupported format: `respond` sends a `406 Not Acceptable` error, or a `404` one for validation errors,
which have no renderer, so that the application's error pages apply, and writes a `ProblemDetail` as
`application/problem+json` (see section 10); an XML request body binds nothing and raises no error; and `request.XML`
fails with a `MissingPropertyException`. `encodeAsXML` and the `xml` codec still escape text, but an object
other than text is escaped as its string rather than rendered as XML. An application that sees these after
an upgrade needs the dependency above.

Set `grails.web.rendering.xml.spring: true` to write ordinary bean responses with Spring Framework's `JacksonXmlHttpMessageConverter`,
backed by the Spring Boot-managed Jackson XML mapper. As in a plain Spring Boot application, that
converter is registered only when Jackson's XML dataformat is on the classpath, so applications that
want it add the dependency themselves:

[source,groovy]
.build.gradle
----
dependencies {
    runtimeOnly 'tools.jackson.dataformat:jackson-dataformat-xml'
}
----

Grails 9 defaults this setting to `false`: adding the Jackson XML dependency alone does not bypass
registered XML marshallers. Enabling it explicitly selects Spring for ordinary beans, even when a
legacy marshaller is registered. Domain objects, collections, maps, validation errors and projections
continue to use the Grails XML converter; migrate these to DTOs or explicit application renderers
before legacy XML conversion is removed in Grails 11.

Without the Jackson XML dependency, `grails-xml` still renders XML through the Grails converter. Applications may also register
their own Spring XML message converter or OXM/JAXB infrastructure through public Spring configuration
APIs.

This change does not affect Grails plugin descriptors. Plugin metadata continues to be generated and
published in its existing descriptor format; `grails-xml` concerns application HTTP payloads only.

==== 4. Opt Into Spring JSON Conversion

Each JSON and XML path keeps its Grails 8 behaviour by default in Grails 9, and has a setting that opts into the
Jackson-based one. A `ProblemDetail` is the exception: `respond` writes it as Spring MVC writes it, whatever the
settings, with the exceptions section 10 lists.

[cols="2,3,1,2", options="header"]
|===
| Setting
| What it governs
| Grails 9 default
| Later default

| `grails.web.rendering.json.spring`
| JSON written by `respond`, including validation errors as problems
| `false`
| `true` in Grails 10

| `grails.converters.json.legacy`
| `grails.converters.JSON`: `render ... as JSON`, `JSON.parse` and `request.JSON`
| `true`
| `false` in a later release

| `grails.databinding.json.jackson`
| JSON request bodies bound to command objects and domain classes
| `false`
| `true` in Grails 10

| `grails.converters.json.domain.jackson.enabled`
| Domain classes written by Spring Boot's own `JsonMapper`
| `false`
| unchanged

| `grails.web.rendering.xml.spring`
| XML written by `respond` for ordinary beans
| `false`
| unchanged until legacy XML conversion is removed in Grails 11
|===

`request.JSON` and data binding parse a request body under different settings, so set
`grails.converters.json.legacy: false` and `grails.databinding.json.jackson: true` together for both to accept the
same JSON.

Grails 9 preserves the legacy `grails.converters.JSON` converter for `respond()` by default and logs one
deprecation warning when that path renders. Opt into Spring MVC's message converters, backed by Boot's
configured Jackson `JsonMapper`, with `grails.web.rendering.json.spring: true`. Grails 10 will enable it
by default; the legacy `respond()` path is scheduled for removal in Grails 11. Jackson can render date
formats, bean properties, circular references, and validation errors differently, so review the JSON
returned by `respond()` endpoints when you upgrade. Explicit `render value as JSON` calls still use the
legacy converter.

The setting alone determines the default response path: registering a marshaller does not implicitly
change it. `false` retains the legacy converter (with the warning); `true` uses Spring's converters
even while legacy marshallers are registered. Migrate those representations to Jackson serializers
before enabling it. Two legacy converter settings do not configure Jackson:
`grails.converters.json.pretty.print` gives way to `spring.jackson.serialization.indent-output`,
and `grails.converters.json.date` to Boot's `spring.jackson.*` date settings. Renderer beans an application declares, such as a `JsonRenderer` or an
`XmlRenderer` for one of its types, follow the same settings, apply their own `includes` and
`excludes`, and reach the same named configurations and message converters.

[source,yaml]
.application.yml
----
grails:
    web:
        rendering:
            json:
                spring: true
----

Grails selects the first configured MVC `HttpMessageConverter` that can write the
response type and negotiated JSON media type and advertises a JSON media type for that class
(`application/json`, `text/json`, or a `+json` subtype). Generic `*/*` string and byte-array converters
are skipped, so strings remain JSON strings and byte arrays use Jackson's base64 JSON representation.
The same media-family rule applies to XML conversion; a generic text converter cannot strip the XML
string element.

The standard Jackson converter uses an isolated mapper derived from Boot's configured `JsonMapper`.
It renders domain classes with the same Jackson serializer as the `JsonMapper` itself does when
`grails.converters.json.domain.jackson.enabled` is set, and as `render ... as JSON` does with
`grails.converters.json.legacy` set to `false` (see the section on domain classes below): the
persistent properties and the id, associated instances as references of their id, or in full with
`grails.converters.json.default.deep`, the version and class name with the `grails.converters.json.domain.*`
settings, and what Jackson applies to a bean, such as `@JsonIgnore`, `@JsonInclude` and the naming strategy. Per-response
`includes` and `excludes` apply to them. Ordinary non-domain beans retain Jackson's property rules. Application-provided converter
subclasses and per-type mapper registrations keep their configured behavior and precedence.

A domain object that leads back to itself while it is being written, such as an embedded value that points at its owner,
is written as `{"_ref": "..", "class": "..."}` by default, or as `grails.converters.json.circular.reference.behaviour`
selects, by the mapper as well as by a response and the converter. With `IGNORE`, the property is written as `null` where the
legacy converter left its name without a value. A plain bean that leads back to itself is written the same way by a response
and by the converter, and fails on the mapper, as it does in a plain Spring MVC controller.

Boot's shared mapper is not given the Grails domain serializer unless `grails.converters.json.domain.jackson.enabled`
is set, so plain Spring `@RestController` responses retain Jackson's normal domain property model. Both mappers serialize Groovy `GString`
values as strings. Only the Grails mapper serializes Spring `Errors` as an `errors` array containing
object, field, message, and codes, without rejected values; Grails `respond errors` adapts that array into an
RFC 9457 problem response.

Grails retains the legacy converter path when a renderer sets a legacy named converter
configuration, when a per-response `includes`/`excludes` projection is requested and the selected
converter is not Spring's standard Jackson converter, or when no configured MVC converter can write
the selected type and media type. Explicit application and plugin `Renderer` beans continue to take
precedence over the default renderer.

Jackson conversion uses UTF-8 for intermediate bytes; the response writer applies
`grails.converters.encoding`, so non-UTF response encodings do not corrupt the intermediate JSON.

Controller unit tests use Boot's Jackson configuration and the same setting. Supply a mapper or
`JsonMapperBuilderCustomizer` from a nested Spring `@Configuration` class, so Boot can see it before
evaluating its conditional beans. A mapper registered by the deprecated `doWithSpring` callback is too
late to make Boot back off. Named JSON
configurations work through `render` and `respond` in `ControllerUnitTest`. Section 13 covers the
other changes to web unit tests.

==== 5. JSON Converter Customization Moves to Jackson

The `grails.converters.JSON.registerObjectMarshaller(...)` API remains supported for
`render ... as JSON` and converter-based rendering. Registering a marshaller does not change the
`respond()` rendering setting. Marshaller registrations apply to its legacy converter path, not to
Spring's message converters. To customize the Spring path, configure Spring Boot's `JsonMapper` so
the same serializer is used by opted-in `respond`, Spring MVC message conversion, and other
Jackson-based integrations:

[source,groovy]
----
import org.springframework.boot.jackson.autoconfigure.JsonMapperBuilderCustomizer
import tools.jackson.databind.module.SimpleModule

@Bean
JsonMapperBuilderCustomizer bookJsonCustomizer() {
    { builder ->
        builder.addModule(new SimpleModule()
                .addSerializer(Book, new BookValueSerializer()))
    } as JsonMapperBuilderCustomizer
}
----

`BookValueSerializer` is an application-provided Jackson `ValueSerializer<Book>`. Use a module when several
serializers belong together, or register an individual serializer directly through the builder customizer.

For different JSON shapes selected by name, replace `JSON.createNamedConfig(...)` with the injectable
`NamedJsonConfigurationRegistry`. Each registration derives an isolated mapper from Spring Boot's configured
`JsonMapper`, so it retains application-wide Jackson settings without changing the shared mapper:

[source,groovy]
----
import grails.converters.json.NamedJsonConfigurationRegistry

class BootStrap {
    NamedJsonConfigurationRegistry namedJsonConfigurationRegistry

    def init = { servletContext ->
        namedJsonConfigurationRegistry.register('catalog') {
            it.serializer(Type, new TypeValueSerializer())
            it.serializer(Category, new CategoryValueSerializer())
        }
    }
}
----

Select the configuration per response with `respond`, or with the `json` render argument:

[source,groovy]
----
respond book, jsonConfiguration: 'catalog'
render json: book, jsonConfiguration: 'catalog'
// Without a name, use the default Jackson configuration:
render json: [ok: true]
----

Both accept `includes` and `excludes`. A projection applies to the properties of the type written,
or of each element's type when a collection or array is written, unlike the legacy converter, which
projected only a single root object. It applies to domain objects and other beans alike; objects of
other types inside them are written in full. Properties are named by their bean property names, and a JSON name given by a Jackson
annotation or naming strategy matches as well. A value with no properties to project, such as a map
or a string, throws `IllegalArgumentException` before anything is written. A type that a Jackson
serializer of its own writes is not filtered, and a warning names it, as does an `Iterable` that is not
a `Collection`, whose elements are not walked before writing in case it can be iterated only once. With
`grails.web.rendering.json.spring: true`, `respond x, includes: [...]` without a configuration name
applies projections the same way; otherwise it uses the legacy converter.
Registered configurations are immutable: configure them inside the registration callback, and
register the name again to replace a configuration rather than mutating a retained reference.

For direct serialization, inject the same registry and use
`namedJsonConfigurationRegistry.writeValueAsString('catalog', book)` or
`namedJsonConfigurationRegistry.writeValue('catalog', writer, book)`. These explicit operations replace the
thread-local scope established by `JSON.use(...)`. Every registry has a `deep` configuration, which writes the
associations of domain class instances in full, as `JSON.use('deep')` did, so `JSON.use('deep') { render book as JSON }`
becomes `render json: book, jsonConfiguration: 'deep'`. A configuration of the application's own does the same with
`it.deep()`. The legacy `JSON.createNamedConfig(...)` and `JSON.use(...)`
APIs, along with `JSON.getNamedConfig(...)` and `JSON.withDefaultConfiguration(...)`, are deprecated
and scheduled for removal in Grails 11 in favor of the request-safe Jackson registry. So are the `namedConfiguration`
property of `JsonRenderer` and `JsonCollectionRenderer` beans, which selects one of those legacy configurations, and
the `renderJson(JSON, RenderContext)` method their subclasses override to render with the legacy converter. This
timetable does not deprecate `JSON.registerObjectMarshaller(...)`.

==== 6. `grails.converters.JSON` Can Write JSON With Spring Boot's JsonMapper

In Grails 9, `render ... as JSON`, `respond` for a JSON request and every other use of `grails.converters.JSON` still
render JSON as Grails 8 did, by default (see <<renderingJsonAsGrails8,Rendering JSON As Grails 8 Did>>). Setting
`grails.converters.json.legacy` to `false` makes the JSON converter write JSON through the application's Jackson
`JsonMapper`, the one Spring Boot auto-configures, so that it renders values as a Spring Boot application does. A later
release makes that the default, so check your application's JSON with the setting before you upgrade to it:

[source,yaml]
----
grails:
    converters:
        json:
            legacy: false
----

While `grails.converters.json.legacy` is not set, Grails logs a warning once at startup that the default will change.
Setting it to either value turns the warning off.

With the setting `false`, the mapper writes the JSON text (numbers and pretty printing), and writes every single value
that it has a dedicated serializer for: dates and times, `Month`, `UUID`, `Locale`, `byte[]`, types with a `@JsonValue`,
and the types of any Jackson module registered with the application. Those values render as Spring Boot renders them,
and `spring.jackson.*` properties apply to them. For example, `spring.jackson.time-zone` writes `Date` and `Calendar`
values in that time zone, and converts `OffsetDateTime` and `ZonedDateTime` values to it. When the application context
has no `JsonMapper`, or has several and none is primary, as in a unit test, a default `JsonMapper` is used.

With the setting `false`, `JSON.parse` and `request.JSON` parse with the application's Jackson mapper. What they accept
is what the mapper's parser features allow, so strict JSON by default, where Grails' own parser also accepts single quotes,
comments, unquoted names and values, uppercase literals, trailing commas and `new Date(...)`. To accept some of that again,
enable the matching Jackson read features, for example `spring.jackson.json.read.allow-java-comments`,
`spring.jackson.json.read.allow-single-quotes`, `spring.jackson.json.read.allow-unquoted-property-names` or
`spring.jackson.json.read.allow-trailing-comma`; `new Date(...)` and the other forms Jackson has no feature for are no longer
accepted. Text after the value, such as a second JSON document, is rejected as well, unless
`spring.jackson.deserialization.fail-on-trailing-tokens` is set to `false`. What comes back does not change: the same `JSONObject` and `JSONArray` containers, which implement `Map` and `List`,
with the same number types (`Integer`, `Long`, `BigInteger`, `Double` or `BigDecimal`, depending on the number). With the
setting `true`, the default in Grails 9, both parse with Grails' own parser as before, except that a number beyond the
range of a `double`, such as `1e400`, is a `BigDecimal`, where Grails 8 threw a `NumberFormatException`.
`new JSONObject(String)` and `new JSONArray(String)` always parse with Grails' own parser, whatever the setting.

With the setting `false`, the mapper writes every value, as Spring Boot writes it: collections, maps, arrays, records,
`Optional` values, enums and beans, besides the single values above. The converter renders each value in them, so the
values they contain are rendered as any other value is. A marshaller that an application registers, with
`JSON.registerObjectMarshaller(...)` or an `ObjectMarshallerRegisterer`, still takes precedence over the mapper for the types
it supports, and a serializer of a Jackson module registered with the application's mapper takes precedence over those
Grails adds, such as the one for validation errors, as it does in `respond`. A collection, a map or a bean that contains itself is written as before, as an empty collection or map where it
repeats, or as the `grails.converters.json.circular.reference.behaviour` selects.

What Jackson applies to a bean applies to a bean the converter renders, where Grails 8 ignored it: `@JsonProperty`,
`@JsonIgnore`, `@JsonInclude`, `@JsonView`, `@JsonFormat`, `@JsonPropertyOrder`, mix-ins and the mapper's naming strategy and
inclusion. Properties come in the order Jackson gives them, where Grails 8 wrote the bean properties alphabetically and then
the public fields, and a bean with no properties is written as an empty object. The converter's includes and excludes for a
class, `setIncludes` and `setExcludes`, still decide which properties of a bean are written, and a method annotated
`@PersistenceMethod` or `@ControllerMethod` is still not a property. Subclasses of `GroovyBeanMarshaller` and
`GenericJavaBeanMarshaller` that you register still render the types they are registered for as they did.

With the setting `false`, two things deliberately differ from Spring Boot, as they do in Grails 8:

* Enums, including one with a `@JsonValue`, render by `name()`, where Jackson 3 writes `toString()` or the `@JsonValue`,
so that the JSON binds back to the enum.
* Strings are escaped for an HTML `<script>` element: `</` is written as `<\u002f` (as `<\/` in a `GString` or a
`StreamCharBuffer`, as in Grails 8), and U+2028 and U+2029 as `\u2028` and `\u2029`. The parsed values are the same as
Spring Boot's.

With the setting `false`, the following values render differently than in Grails 8. With the setting left `true`, Grails 9
renders them as Grails 8 did, apart from what Grails 8 failed to render or rendered as invalid JSON, such as a single
value or `NaN`, which renders as it does with the setting `false`:

[cols="2,2,3", options="header"]
|===
| Value
| Grails 8
| `legacy: false`

| `OffsetTime`
| `"03:00:00-03:00"`, `"03:00:00.5+05:30"`
| `"03:00-03:00"`, `"03:00:00.500+05:30"`, from `OffsetTime#toString()`

| `Month`
| `"SEPTEMBER"`
| `9`, a JSON number. A `Month` binds back from its number.

| `java.util.Locale`
| `"zh_TW_#Hant"`, from `Locale#toString()`
| `"zh-Hant-TW"`, its language tag

| `char`, `Character`
| `{}`
| `"c"`

| `byte[]`
| `[1,2,3]`
| `"AQID"`, Base64

| `UUID`, `URI`, a type with a `@JsonValue` other than an enum
| an object of its bean properties
| its value, such as `"123e4567-e89b-12d3-a456-426614174000"`

| `java.util.regex.Pattern`, `java.nio.charset.Charset`, `java.net.InetAddress`
| an object of its bean properties
| its string, such as `"a+b"`, `"UTF-8"` or the host name

| `java.io.File`, `java.nio.file.Path`, `java.nio.ByteBuffer`
| a failure to render it
| `"/tmp/a.txt"`, `"file:///tmp/a.txt"`, and `"AQID"`, Base64

| `char[]`

| an object of its bean properties

| `Optional`

| its value, or `null` when it is empty

| A map with a `null` key
| the entry is left out

| Validation errors, as in `render errors as JSON`
| `{"errors":[{"object":…,"field":…,"rejected-value":…,"message":…}]}`
| `{"errors":[{"object":…,"field":…,"codes":[…],"message":…}]}`, the entries `respond` writes, without the rejected value, which can be a password or a token; XML validation errors keep their Grails 8 shape, including the rejected value, until legacy XML conversion is removed

| A `Map.Entry`
| `{"key":"k","value":1}`
| `{"k":1}`, as the mapper writes it

| A `NaN` or infinite `double`
| `NaN`, which is not valid JSON
| `"NaN"`

| Pretty printed JSON (`grails.converters.json.pretty.print`, `JSON#toString(true)`)
| `"a": 1`, with every array element on its own line, or, from `toString(true)`, indented by three spaces
| `"a" : 1`, the layout of the mapper's default pretty printer

| A single value, such as `render Role.HEAD as JSON`
| a `ConverterException`
| the JSON value, `"HEAD"`
|===

The other default date and time formats are the same as Grails 8.0.0's, which already renders `Date`, `Calendar`,
`java.sql.Date` and `java.sql.Timestamp` with millisecond precision and supports the additional date and time types.
With the setting `false`, map keys use the mapper's key serializers, instead of Grails' fixed date formats or the key's
`toString()`: a `Date` or `Calendar` key is written in the mapper's configured date format and time zone, a
`ZonedDateTime` or `OffsetDateTime` key keeps its own offset, as before, a `Class` key is its name
(`"java.lang.String"`, where Grails 8 wrote `"class java.lang.String"`), and the key of a type with a `@JsonValue` is
that value.

With the setting `false`, `JSON#toString(false)` does not indent the JSON when `grails.converters.json.pretty.print` is
`true`; Grails 8 ignored the argument. JSON that is not pretty printed is not indented either when the application's
`JsonMapper` indents its output (`spring.jackson.serialization.indent-output`).

With the setting `false`, the JSON marshallers that rendered these values are not registered. They are deprecated:
`DateMarshaller`, `CalendarMarshaller`, `ToStringBeanMarshaller`, `ByteArrayMarshaller`,
`InstantMarshaller`, `LocalDateMarshaller`, `LocalDateTimeMarshaller`, `OffsetDateTimeMarshaller` and
`ZonedDateTimeMarshaller`, in the `org.grails.web.converters.marshaller.json` package. To render one of these types
differently, register a marshaller for it, or configure the `JsonMapper`. The XML marshallers of the same names are not
changed. The default JSON marshallers have implicit priorities that follow their order (-1, -2, and so on), and with
the setting `false` that order differs, so a marshaller registered with an explicit negative priority may come before or
after different defaults.

Whatever the setting, `org.grails.web.json.JSONWriter`, which the converter and its marshallers write to, now writes
through a Jackson `JsonGenerator`, and `new JSONWriter(writer)` writes with a default `JsonMapper`:

* It keeps its public methods, rejects the same misplaced calls, and writes the same JSON text. It also accepts a single
value outside any object or array, where it threw a `JSONException`.
* The generator buffers the text. It reaches the `Writer` as the buffer fills, once the JSON text is complete, and when
`flush()` is called, rather than as each value is written. The `Writer` itself is not flushed or closed.
* `array()`, `object()`, `key()` and the `value` methods no longer go through the protected `append` and `comma`
methods. A subclass that overrides those to change the output, or writes to the `writer` field directly, must use the
public methods instead.
* `PrettyPrintJSONWriter` still indents as Grails 8 did, and is deprecated. Use
`new JSONWriter(writer, new JsonMapperSupport(jsonMapper), true)`, which indents with the mapper's default pretty printer.

The JavaCC JSON parser in `org.grails.web.json.parser` (`JSONParser`), which Grails does not use, is deprecated. Use
`JSON.parse` or `new JSONObject(String)`.

Whatever the setting, with the `PATH` circular reference behaviour (`grails.converters.json.circular.reference.behaviour`),
an object with a `null` property, or a single value, now renders instead of failing, and a reference that follows a
number now has the right path: `"root.x.other"` where Grails 8 wrote `"root.x.n"`, after a property `n` that is a
number.

JSON views, the XML converter and the HAL renderer are not changed.

[[renderingJsonAsGrails8]]
===== Rendering JSON As Grails 8 Did

`grails.converters.json.legacy` is `true` by default in Grails 9. The JSON converter then renders values, including
domain classes, with the marshallers of Grails 8, formats map keys and indents pretty printed JSON as Grails 8 did, and
writes with a default `JsonMapper`, so that the application's `spring.jackson.*` settings and Jackson modules do not
change the text: `render ... as JSON` and `JSON#toString` return the same text as in Grails 8. What Grails 8 failed to
render, or rendered as invalid JSON, such as a single value, `NaN`, or a to-many association whose value is a `Map` with
other than one entry, renders as it does with the setting `false`. A reference that the `PATH` circular reference
behaviour writes after a number also has the right path, as described above, where Grails 8 wrote a wrong one. A later
release makes `false` the default; setting `grails.converters.json.legacy` to `true` explicitly keeps the Grails 8
rendering, and turns off the warning that Grails logs while it is not set. With
`grails.converters.json.domain.jackson.enabled` set to `true` as well, the JSON converter still renders as Grails 8 did,
and the application's `JsonMapper` renders domain classes with the module, as described below.

With the setting `false`, to keep the Grails 8 rendering of some types only, register a marshaller for each, for
example in `BootStrap.init`:

[source,groovy]
----
JSON.registerObjectMarshaller(Month) { Month month -> month.name() }
JSON.registerObjectMarshaller(Locale) { Locale locale -> locale.toString() }
JSON.registerObjectMarshaller(byte[]) { byte[] bytes -> bytes as List }
----

==== 7. Domain Classes Render as Jackson Beans of Their Persistent Properties

With `grails.converters.json.legacy` set to `false`, the JSON converter renders a domain class instance with Jackson's own
bean serializer, which Grails shapes to the domain class, as `DomainClassMarshaller` rendered it in Grails 8, with these
differences:

* What Jackson applies to a bean applies to the instance, where the converter ignored it in Grails 8: a property annotated
with `@JsonIgnore`, or with `@JsonProperty(access = WRITE_ONLY)`, is not rendered, nor is one that a class-level
`@JsonIgnoreProperties` names; property names follow `@JsonProperty`, `@JsonNaming` and the mapper's naming strategy
(`spring.jackson.property-naming-strategy`); `@JsonInclude` and `spring.jackson.default-property-inclusion` decide whether a
null or empty property is written; `@JsonView`, `@JsonFormat`, a `@JsonSerialize` serializer on a property, mix-ins, filters
and `@JsonPropertyOrder` apply; a domain class with `@JsonTypeInfo` is written with its type id, and an instance in a
`@JsonUnwrapped` property is written into the enclosing object. As with Jackson's own unwrapping, an instance with a type
id fails there, unless `SerializationFeature.FAIL_ON_UNWRAPPED_TYPE_IDENTIFIERS` is disabled.
* Only the persistent properties are rendered, as in Grails 8: a transient property, or a getter with nothing persisted
behind it, is not. They follow the class name, the id and the version, which are rendered ahead of them when they apply,
in the order the domain class declares them, unless `@JsonPropertyOrder` says otherwise.
* GORM names some properties in a `@JsonIgnoreProperties` it adds to every domain class, so Jackson leaves them out:
the tenant identifier of a multi-tenant domain class (`tenantId`) and the `dbo` of a MongoDB domain class, which
Grails 8 rendered. The version is written when it is included, as before.
* A to-many association whose value is a `Map` renders as an object of references, such as `{"a":{"id":1}}`, where it
failed before.
* A domain class with its own `@JsonSerialize` serializer, with a `@JsonValue`, or that implements `JacksonSerializable`
is written by Jackson, and so is a subclass of a domain class that is neither a domain class nor a proxy of one.
* `DomainClassMarshaller` and `DeepDomainClassMarshaller` render through the serializer. Their constructors and
protected methods (`includesProperty`, `excludesProperty`, `extractValue`, `asShortObject` and
`isRenderDomainClassRelations`) are unchanged, and a subclass that overrides them still renders as it did. They are
consulted before the mapper's value serializers, as `ProxyUnwrappingMarshaller` is.

The application's `JsonMapper` is not changed: writing a domain class instance with it, such as returning one from a
Spring MVC controller, renders it as a Jackson bean, as in Grails 8. To have the mapper render domain classes as
`render ... as JSON` does, set `grails.converters.json.domain.jackson.enabled` to `true`:

[source,yaml]
----
grails:
    converters:
        json:
            domain:
                jackson:
                    enabled: true
----

Grails then registers the module with the mapper, as the `domainClassJacksonModule` bean, which you can also add to a
`JsonMapper` you build yourself. The mapper renders associated instances as references of their id, such as `{"id":3}`,
rather than in full, and proxies as the instances they proxy, and names the id of a reference as the referenced class
names it.

==== 8. Rendering Single Values as JSON

In Grails 8, rendering a single enum value with `render(Role.HEAD as JSON)` threw a `ConverterException`.
It now produces the JSON string `"HEAD"`. The default enum marshaller uses the enum name, including when the
value is nested in an object or array.

The legacy JSON converter now accepts scalar root values: strings (including GStrings), numbers,
booleans, `null`, and enum names. Use `new JSON(value)` for scalar values, with or without
`grails.converters.json.pretty.print=true`. Groovy's built-in casts for strings and numbers do not
support `value as JSON`; construct the converter explicitly for those values.
Non-null scalar `respond` responses use the same rendering behavior. Rendering a scalar converter
no longer throws a `ConverterException` merely because the root is a scalar.
`JSONWriter` accepts a single value outside any object or array whatever the `grails.converters.json.legacy`
setting, as the section on writing JSON with Spring Boot's `JsonMapper` describes.

==== 9. Opt Into Jackson JSON Request Binding

Grails 9 retains `JsonSlurper` request binding by default and logs a startup deprecation notice. As
in Grails 8, an application `JsonSlurper` bean, for example one using `JsonParserType.LAX`, replaces
the default parser on that path; once Jackson parsing is enabled, configure it through
`JsonMapperBuilderCustomizer` instead.
Set `grails.databinding.json.jackson: true` to parse binding bodies with Boot's configured Jackson
`JsonMapper`. Jackson becomes the default in Grails 10 and legacy parsing is removed in Grails 11.
Mapper features installed through `JsonMapperBuilderCustomizer` then apply consistently
to request parsing as well as response rendering. This includes registered Jackson modules and parser
features such as support for an application-specific input format.

Both parsers report malformed bodies as binding errors, but Jackson rejects additional inputs that
the legacy parser accepted: trailing content after a document, trailing commas, leading-zero numbers,
unescaped tabs inside strings, trailing comments, nesting beyond its configured depth limit, and
integers beyond its configured number-length limit. Review clients before enabling the new parser;
configure intentional exceptions through `JsonMapperBuilderCustomizer`.

With Jackson enabled, ordinary untyped JSON numbers keep the types the previous parser produced. Values with a fractional part are read
as `BigDecimal` rather than `Double`, so binding a request value such as `1.15` to a `BigDecimal` property
retains exactly the digits the request sent. Whole numbers bind as `Integer`, `Long`, or `BigInteger`
when too large for a `Long`, as with the legacy parser.

==== 10. REST Validation Errors Use RFC 9457 Problems

With `grails.web.rendering.json.spring: true`, `respond()` renders Spring `Errors` as
`application/problem+json` instead of the legacy `{"errors": [...]}` body. Grails 9 retains the legacy
body by default; this follows the same Grails 10 default flip and Grails 11 removal schedule as JSON
rendering. Grails uses the public `ValidationProblemDetailFactory` bean to
adapt the errors to Spring Framework's RFC 9457 `ProblemDetail` type. The resulting response has status
422, the title `Validation failed`, and
an `errors` extension containing stable maps with the object name, optional field name, message, and error
codes:

[source,groovy]
----
import grails.rest.render.errors.ValidationProblemDetailFactory

class BookController {
    ValidationProblemDetailFactory validationProblemDetailFactory

    def save(Book book) {
        if (book.hasErrors()) {
            respond validationProblemDetailFactory.create(book.errors)
            return
        }
        // save the valid book
    }
}
----

Each message is resolved through the application's `MessageSource` for the current locale, so
`messages.properties` entries and Spring Boot's `spring.messages.*` settings apply to validation
responses as they do elsewhere.

With JSON views, a `grails-app/views/errors/_errors.gson` template renders validation errors instead, as in
Grails 8. Applications generated with the JSON views feature or the REST API profile have one; delete it to
answer with the problem, or respond with `validationProblemDetailFactory.create(errors)`, which no view renders.

Applications can also inject the factory when they need to create or customize the problem explicitly.
When `respond` receives a `ProblemDetail`, it sets the HTTP status from the problem, selects
`application/problem+json`, or `application/problem+xml` for an XML response, and fills in an absent
`instance` with the current resource path. A client that accepts neither JSON nor XML, such as a browser
asking for HTML, is answered with `application/problem+json`, as Spring MVC answers it, where Grails 8
rendered the action's view with a 200. A view renders a problem only when `respond` names it with the
`view` argument, and the response keeps the problem's status. A `ProblemDetail` is written through Spring's message
converters, whatever `grails.web.rendering.json.spring` and `grails.web.rendering.xml.spring` are set
to, so the example above answers with `application/problem+json` in Grails 9 as well. A web
application with Spring MVC always has the JSON converter; where none can write the problem, Grails
logs a warning and the legacy converter writes it as a bean, with the problem's status. Spring writes
XML problems with `jackson-dataformat-xml`, and without it Grails writes them in the same format. XML is
rendered by the `grails-xml` module, without which a client asking for XML is answered with
`application/problem+json`.
Rejected field values are excluded by default because they can contain passwords, tokens, or other
sensitive request data. Applications that deliberately need those values can define their own factory
bean after reviewing that exposure risk. It replaces the default one whatever its name, both for `respond` and
for a controller that declares a `validationProblemDetailFactory` property, and takes the `MessageSource` so that
messages stay localized. A bean named `validationProblemDetailFactory` overrides the plugin's bean of that name, so it
needs bean definition overriding, which Grails allows unless `spring.main.allow-bean-definition-overriding` is `false`;
any other name works either way:

[source,groovy]
.grails-app/init/Application.groovy
----
@Bean
ValidationProblemDetailFactory includingRejectedValues(MessageSource messageSource) {
    new ValidationProblemDetailFactory(true, messageSource)
}
----

==== 11. HAL Rendering

Existing Grails HAL JSON renderers remain available through explicit renderer registration.
Adding `spring-boot-starter-hateoas` alone does not register a Grails renderer for Spring HATEOAS
`EntityModel` values. Return those models from a Spring MVC controller or provide an explicit Grails
renderer for the desired media type.

==== 12. Grails Format Resolution and Spring MVC Content Negotiation

Grails format resolution -- `withFormat`, `respond`, and `response.format` -- applies the `grails.mime.*`
rules. Spring MVC keeps its own content negotiation: an `@RestController`, an actuator endpoint or any other
Spring handler continues to match `produces` against the `Accept` header exactly as in a plain Spring
Boot application, and still answers `406 Not Acceptable` for a media type it cannot produce. The
`spring.mvc.contentnegotiation.*` properties therefore continue to work.

Grails reads the `Accept` header with Spring's `MediaType` parser. Ordinary headers resolve as before, but
media type names are now matched case-insensitively: `Accept: Application/JSON` resolves to `json`, where
Grails 8 matched no configured type and resolved to `all`. A configured type with capitals in its name,
such as `application/vnd.Acme+json`, matches whatever the case of the header. The same parser reads
`Content-Type`, so `request.format` is case-insensitive too: `Content-Type: Application/JSON` gives `json`
where Grails 8 gave `null`, and the JSON binding source now binds a body it used to ignore. A value Spring
rejects, such as a quality value above 1, is still read as Grails 8 read it.

The data-format extensions `json`, `xml`, `hal`, `atom`, `rss`, `csv` and `text` declared in
`grails.mime.types` are additionally registered with Spring as format aliases. Spring MVC negotiates
with them only when the application enables parameter negotiation with
`spring.mvc.contentnegotiation.favor-parameter: true`. Spring Boot leaves it disabled, so after the
upgrade `?format=json` still does not change what a Spring MVC endpoint returns. Browser formats such
as `html` and `js` are not registered, preserving Spring's reflected-file-download protection.
Where a format has several media types, an `application/*` one is preferred over a `text/*` one, and Boot's
`spring.mvc.contentnegotiation.media-types.*` overrides these defaults. Invalid names are skipped.

==== 13. Web Unit Tests Set Up More of the Web Layer

Web test traits such as `ControllerUnitTest` and `TagLibUnitTest` now always include the
`restResponder` plugin, even when a spec overrides `getIncludePlugins()`. They also provide JSON
conversion beans with Boot's Jackson configuration, build Spring MVC's message converters from the
test classpath, and add the `grails-xml` beans when that module is on the test classpath, without
loading the XML plugin's dependency graph. A spec that overrides `getIncludePlugins()` or asserts on
the beans in its application context sees these additions.

The traits still do not load the controllers, URL mappings or i18n plugins themselves. A spec that includes one of
them, or defines its own URL mappings holder, link generator or locale resolver, now keeps that bean, where the traits
replaced it with their own. Without `grails-xml` on the test classpath, setting `request.xml` or reading
`request.XML` fails with an `IllegalStateException` that names the module. `GrailsUnitTest` and `ServiceUnitTest` do
not load XML or the web plugins just because those modules are on the classpath. See <<unitTesting,Unit Testing>>.
