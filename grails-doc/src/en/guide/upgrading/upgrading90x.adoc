=== Upgrade Instructions for Grails 8 to Grails 9

This guide outlines the changes introduced in Grails 9 and the steps required to upgrade your application.

[TIP]
====
**Let your coding agent work through this guide.**
Grails publishes the `grails-upgrade` agent skill, which turns this guide into a migration checklist for an AI coding agent, and lists the changes of each Grails 9 release.
Extract it with the SkillsJars Gradle plugin, as xref:gettingStarted#agentSkills[Agent Skills] describes.
While the application is still on Grails 8, declare the skill with its version, since the Grails 8 BOM manages the upgrade skill of Grails 8:

[source,groovy,subs="attributes"]
.build.gradle
----
skill 'org.apache.grails.skills:grails-upgrade:{version}'
----
====

The changes are listed by release. Apply the section of every release after the one the application is on, up to and including the release it is upgrading to.

Once `grailsVersion` names Grails 9, the Grails wrapper is replaced with `./grailsw update-wrapper` (note 37) and the record of the project is written or moved with `grails project migrate` (note 45), run `grails project health` in the project. It reads the files of the project and says, with the id of each finding and what to do, which of the changes below are still to be made, as far as the files show them; it runs in a project that still names Grails 7 or 8 as well. Run it again after each change, until `grails project health --strict` ends with exit code 0. See <<upgradingProjectHealth,note 57>>.

[[grails-9-0-0-M1]]
=== Grails 9.0.0-M1

[[upgradingGroovy6]]
==== 1. Groovy 6

Grails 9 builds on Groovy {groovyVersion} and the matching Spock {spockVersion}; Java 21 is unchanged from Grails 8.
The Grails BOM manages Groovy and Spock, so remove any version an application pins for them and review the https://groovy-lang.org/releasenotes/groovy-6.0.html[Groovy 6 release notes] for language changes that affect application code.

`grails project health` reports a build that compiles for a Java before 21 as `java-target.release`, and a `.sdkmanrc` that selects one as `sdkmanrc.java`, or another major version of Groovy as `sdkmanrc.groovy`; a version of Groovy or Spock the build pins is not checked.

==== 2. Spring Boot 4.2 and Spring Framework 7.1

Grails 9 moves from Spring Boot 4.1 and Spring Framework 7.0, which Grails 8 uses, to Spring Boot {springBootVersion} and Spring Framework {springVersion}.
The managed versions that change include Spring Security 7.2, Spring Data 2026.1, Micrometer 1.18 and Reactor 2026.0.
Review the https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.2-Release-Notes[Spring Boot 4.2 Release Notes] and the https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-7.1-Release-Notes[Spring Framework 7.1 Release Notes] for the changes that affect your application.
The ones most likely to affect a Grails application are:

* *`server.forward-headers-strategy: framework` reads only the `+X-Forwarded-*+` headers by default.*
Spring Framework 7.1's `ForwardedHeaderFilter` reads either the RFC 7239 `Forwarded` header or the `+X-Forwarded-*+` headers, and Spring Boot 4.2 configures it for `+X-Forwarded-*+`.
Before, it read `Forwarded` when the request carried one and `+X-Forwarded-*+` otherwise.
If your reverse proxy sends `Forwarded`, set `spring.mvc.forwarded-headers.header-format: standard`.
The filter also ignores `X-Forwarded-Prefix` now, where it used to add it to the context path, so if your proxy strips a path prefix and sends that header, absolute links and redirects lose the prefix until you set `spring.mvc.forwarded-headers.use-forwarded-prefix: true`.
Spring Boot 4.2 also registers the filter from its Spring MVC auto-configuration, which backs off when the application declares `@EnableWebMvc`; such an application must now register a `ForwardedHeaderFilter` itself.

* *Embedded Tomcat keeps relative redirect locations relative.*
`server.tomcat.servlet.use-relative-redirects`, renamed from `server.tomcat.use-relative-redirects`, now defaults to `true`, Tomcat's own default.
A redirect sent through `HttpServletResponse.sendRedirect` with a path, such as a controller `chain` call, a Spring Security redirect or a `redirect:` view name, now has a relative `Location` header instead of an absolute URL.
A controller `redirect` sets the `Location` header itself and still sends an absolute URL unless you pass `absolute: false`.
Browsers resolve relative locations; set the property to `false` if a client or test expects an absolute URL.

* *`TestRestTemplate` is deprecated for removal.*
Spring Framework 7.1 deprecates `RestTemplate`, and Spring Boot 4.2 deprecates `TestRestTemplate` and `@AutoConfigureTestRestTemplate` with it.
Move `@SpringBootTest` tests to `RestTestClient`, which `@AutoConfigureRestTestClient` injects:
+
[source,groovy]
----
// Before
import org.springframework.boot.resttestclient.TestRestTemplate
import org.springframework.boot.resttestclient.autoconfigure.AutoConfigureTestRestTemplate

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureTestRestTemplate
class BookApiSpec extends Specification {
    @Autowired TestRestTemplate rest
}

// After
import org.springframework.boot.resttestclient.autoconfigure.AutoConfigureRestTestClient
import org.springframework.test.web.servlet.client.RestTestClient

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
class BookApiSpec extends Specification {
    @Autowired RestTestClient client
}
----

* *A problem detail no longer gets the request path as its `instance`.*
RFC 9457 defines `instance` as a URI that identifies the specific occurrence of a problem, so Spring Framework 7.1 no longer sets it to the request path when a handler method returns a `ProblemDetail` or an `ErrorResponse`.
`respond` follows it: a `ProblemDetail` or `ErrorResponse` it writes, and the problem it writes for validation errors, no longer get one either.
A client that reads `instance` gets it only where the application sets it: in a `ResponseEntityExceptionHandler` for Spring MVC controllers, and on the problem an action responds with, including one `validationProblemDetailFactory.create(errors)` makes for validation errors:
+
[source,groovy]
----
ProblemDetail problem = validationProblemDetailFactory.create(book.errors)
problem.instance = URI.create("urn:uuid:${UUID.randomUUID()}")
respond problem
----

* *Spring MVC no longer detects the JAXB XML converter.*
Spring Framework 7.1 stops auto-detecting the JAXB message converter for server applications.
Grails `render` and `respond` write XML through Grails' own converters and are unaffected.
A Spring MVC `@RestController` that returns JAXB-annotated objects needs the converter registered explicitly, as the Spring Framework 7.1 release notes show.

* *Tests load static nested `@Configuration` classes from their superclasses and enclosing classes.*
The Spring TestContext Framework used to ignore such a class unless its class hierarchy declared `@ContextConfiguration`, and now adds it to the test's application context.
Grails 8 already logs a warning for each one it ignores, so a test run on Grails 8 shows the affected tests.
Remove the `@Configuration` annotation, or move the class to a top-level class, if the test should not load it.

* *`bootBuildImage` builds on Ubuntu 26.04.*
The default builder is `paketobuildpacks/ubuntu-resolute-builder`, in place of `paketobuildpacks/builder-noble-java-tiny`, and images are based on Ubuntu 26.04 instead of 24.04.
With no `builder` configured, the run image is `paketobuildpacks/ubuntu-resolute-run-tiny:latest`, which still has no shell; with one configured, it is the run image of the builder, which for `ubuntu-resolute-builder` has a shell.
The builder no longer pins the version of the run image, so set both `builder` and `runImage` to specific versions for repeatable images, or set `builder` to `paketobuildpacks/builder-noble-java-tiny` to keep the previous one.

* *An exception an action throws is now recorded as an error on the HTTP server observation.*
When an error view answered, as the `"500"(view: '/error')` mapping of a generated application does, `http.server.requests` tagged the 500 with `error` and `exception` values of `none`, and tracing did not see a failure.
A `500` mapping to a controller tagged it with `GrailsWrappedRuntimeException` and with the `uri` of that controller, so every failure it answered looked like the same route.
Both now report the exception the action threw and the route of the action, and the span of the request is marked as failed.
That includes an `Error`, such as a failed `assert`, rather than the `ServletException` Spring MVC wraps it in.
These requests were already counted with `outcome=SERVER_ERROR`, but an alert that counts a non-`none` `error` value will see more server errors than before, and a dashboard that reads the `uri` of an error controller will find those failures under the routes of the actions.
After a forward to an error controller, the `jakarta.servlet.error.exception` request attribute holds the exception the action threw rather than a `GrailsWrappedRuntimeException`, for a filter that reads it once the chain has returned. Inside the error controller it still holds the wrapper.
A client error is not recorded, and neither is a failure inside `g:include`, whose error page is rendered inside a page that goes on to answer the request.
The route is now set before the Grails interceptors run, so that a failure in one is reported under the route of the action.
An interceptor whose `before()` returns `false`, to render a 403 or to redirect, stopped the request before its route was set, so the request was reported with a `uri` of `UNKNOWN`, or `REDIRECTION` for a redirect.
It is now reported under the route of the action, so a dashboard or alert keyed on those `uri` values sees those requests move.

* *On Undertow, a request reads as its own dispatch again once a forward returns.*
Undertow left a request reading as a forward once a forward to a path had returned, as Tomcat and Jetty do not.
Spring Framework 7.1's observation filter then took an asynchronous request that had forwarded, for example to an error controller, for a plain one, and reported its failure twice.
`grails-undertow` now restores the dispatcher type when the forward returns, so a filter that reads `getDispatcherType()` once its chain has returned sees `REQUEST` or `ASYNC` rather than `FORWARD`, as it does on Tomcat and Jetty.

* *`http.server.requests.active` is no longer registered by default.*
Spring Boot 4.2 makes this long task timer opt-in.
A dashboard or alert that reads it sets `management.metrics.observations.include-active-long-task-timer` to `true`, which replaces `management.metrics.observations.ignored-meters`.

* *`spring-boot-starter-amqp` no longer means RabbitMQ.*
It is now the starter for generic AMQP 1.0, and RabbitMQ has starters of its own.
An application that uses RabbitMQ through `spring-boot-starter-amqp` or `spring-boot-starter-amqp-test` changes to `spring-boot-starter-rabbitmq` or `spring-boot-starter-rabbitmq-test`, and any import of `org.springframework.boot.amqp.autoconfigure` to `org.springframework.boot.rabbitmq.autoconfigure`.
RabbitMQ over AMQP 1.0 has `spring-boot-starter-amqp-rabbitmq`.

* *The Spring Security plugin no longer saves the requests browsers send on their own.*
A denied request for `/apple-touch-icon.png`, `/manifest.json` or the `/.well-known/appspecific/com.chrome.devtools.json` that Chrome DevTools sends used to be saved, so a login redirected to it instead of to the page the user asked for.
Spring Security 7.2's configuration DSL ignores these paths, which the plugin does not use, so the plugin now ignores them too, with `grails.plugin.springsecurity.requestCache.ignoredPatterns`.
An application that secures a page at one of these paths and wants a login to return to it can leave the path out of that list.

* *Digest authentication in the Spring Security plugin starts and signs users in.*
`useDigestAuth` with its default of hashed passwords used to fail at startup, naming an encoder that no longer exists.
What a user has stored is now the hash a browser computes, which the application computes, as the link:security.html#core-basicAndDigestAuth[guide] shows.
With `digest.useCleartextPasswords`, nobody could sign in with Digest authentication, because the plugin replaced `passwordEncoder` with one that stored `{noop}secret`.
`passwordEncoder` now stays as configured, and the application stores the password as it was typed, so an application with stored values such as `{noop}secret` removes the `{noop}` prefix from them and no longer stores them with `springSecurityService.encodePassword`.
A form or Basic authentication signs a user in with their password in either mode.

* *`fii.alwaysReauthenticate` in the Spring Security plugin takes effect.*
The setting did nothing, because the plugin's security interceptor went straight to the access decision.
An application that sets it now has the `Authentication` of a request to a secured URL authenticated again, while it still holds its credentials, as it does with `providerManager.eraseCredentialsAfterAuthentication` set to `false`.
By default the credentials are erased at sign-in, so a user signed in through a form is not authenticated again.

[TIP]
====
The Spring Boot properties migrator, described in the link:upgrading.html#upgrading80x[Grails 8 upgrade guide], finds the configuration properties Spring Boot 4.2 renames, such as `server.tomcat.use-relative-redirects`.
Spring Boot 4.2 can also make the application fail to start while such a property is left: set `spring.properties.migrator.fail` to `on-warning` to fail on renamed and removed properties, or to `on-error` to fail on removed ones only.
The default, `never`, only logs them.

==== 3. graphql-java 26 for GraphQL Applications

Spring Boot 4.2 manages graphql-java 26, so applications using the GraphQL plugin (`grails-data-graphql`) move from graphql-java 25 to graphql-java 26.1.
graphql-java 26.0 contains breaking changes, listed in its https://github.com/graphql-java/graphql-java/releases/tag/v26.0[release notes].
The ones that can affect a Grails application are:

* *Query complexity limits are enforced by default.*
A query nested more than 100 levels deep, or selecting more than 100,000 fields, now fails validation with a `MaxQueryDepthExceeded` or `MaxQueryFieldsExceeded` error.
To raise the limits, or to turn them off, set new defaults when the application starts, for example in `BootStrap.groovy`:
+
[source,groovy]
----
import graphql.validation.QueryComplexityLimits

class BootStrap {

    def init = {
        QueryComplexityLimits.setDefaultLimits(QueryComplexityLimits.newLimits()
                .maxDepth(150)
                .maxFieldsCount(200_000)
                .build())
        // or, to turn the limits off:
        // QueryComplexityLimits.setDefaultLimits(QueryComplexityLimits.NONE)
    }
}
----
+
graphql-java's parser separately rejects a query nested more than about 165 levels deep, so a `maxDepth` above that has no effect.

* *Schemas built in code are validated like schemas built from SDL.*
A required argument or input field (non-null with no default value) can no longer be deprecated.
The schema the plugin generates never deprecates an argument or an input field, but arguments and input types an application adds through a `GraphQLSchemaInterceptor` must follow the rule.

* *Additional schema types must be named types.*
`GraphQLSchemaInterceptor.interceptSchema` still receives the additional types as a `Set<GraphQLType>`, and the plugin unwraps list and non-null wrappers before it builds the schema, so existing interceptors need no change.
Code that builds a `GraphQLSchema` directly must pass `GraphQLNamedType` instances to `GraphQLSchema.Builder.additionalTypes`.

The other breaking changes (the validation rule filter, the removal of `DirectiveInfo`, and the JSpecify nullability annotations) only affect code that uses graphql-java directly.
The nullability annotations document existing behavior and do not change what graphql-java returns at runtime.

The plugin continues to use graphql-java-extended-scalars 24.0, its latest release, which works with graphql-java 26.1.

[[upgradingGpars]]
==== 4. GPars Integration Deprecated in Favour of Groovy Concurrency

Groovy 6 brings a unified concurrency and parallel-processing toolkit into core under https://groovy-lang.org/releasenotes/groovy-6.0.html#concurrency-toolkit[GEP-18: Integrated Concurrency and Parallel Processing]. The `groovy.concurrent` package provides `Awaitable`, `DataflowVariable`, `Actor`, `Agent`, `Pool`, `ParallelScope` and the parallel collection methods such as `eachParallel` and `collectParallel`. The Groovy release notes describe the toolkit as modernising the patterns from GPars around virtual threads, structured concurrency and Groovy 6's `async`/`await`, and state that previous users of GPars will find much of its functionality there.

With those patterns part of the language, Grails no longer needs the separate GPars library, which was last released in 2014 and depends on Groovy 2.x and the Multiverse STM engine. The `grails-async-gpars` and `grails-events-gpars` modules remain available in Grails 9 but are deprecated for removal: their classes carry `@Deprecated(since = '9.0', forRemoval = true)` and log a warning when selected. They will be removed in a future release.

Their replacements are `grails-async-groovy-concurrent`, providing `org.grails.async.factory.groovy.AwaitablePromiseFactory`, and `grails-events-groovy-concurrent`, providing `org.grails.events.groovy.ActorEventBus`. Both are selected the same way the GPars modules are, by adding the dependency in place of the GPars one:

[source,groovy]
.build.gradle
----
runtimeOnly 'org.apache.grails.async:grails-async-groovy-concurrent'
runtimeOnly 'org.apache.grails.events:grails-events-groovy-concurrent'
----

Do not keep both the GPars and the Groovy module on the classpath: only the first service-loaded `PromiseFactory` is used, and the event bus builder refuses to start when more than one `EventBus` implementation is found.

The Groovy promise factory follows the failure contract of the default `CompletableFuture` factory rather than the GPars one: direct and chained `get()` calls throw `ExecutionException` with the original failure as the cause, a single-promise `onError` recovers with its callback result, and the aggregate `onError` observes the failure and leaves the returned promise failed. `onComplete` and `then` return a new promise instead of the receiver. Promises created by this factory are also Groovy `Awaitable` instances and can be passed to `await` directly.

The Groovy actor event bus delivers each event to its subscribers in publication order on a single Groovy actor. A subscriber that throws without a reply handler is logged and does not stop delivery to the remaining subscribers or later events.

Applications that use GPars directly, for example `GParsPool.withPool { list.eachParallel { } }`, should move to the Groovy equivalents: the parallel collection methods are available on every `Collection` without a pool, and `groovy.concurrent.ParallelScope.withPool(n) { scope -> list.eachParallel { } }` runs them on a pool of a chosen size. Once the deprecated modules are removed, Grails will no longer bring GPars onto the classpath, so an application that still needs it must declare `org.codehaus.gpars:gpars` itself.

NOTE: Groovy 6 marks the concurrency toolkit as incubating. The Grails modules that build on it expose only the Grails `Promise` and `EventBus` contracts, so changes to the Groovy API in later Groovy releases are absorbed by Grails rather than by application code.

`grails project health` reports a GPars module as `deprecated-dependency.gpars`, and a GPars module beside its Groovy counterpart as `deprecated-dependency.gpars-and-groovy`; the use of the GPars API in the sources is not checked.

==== 5. Groovy Code Is Compiled with invokedynamic

Grails 8 compiles every Groovy source set of an application without invokedynamic (`grails { indy = false }` was the default). Grails 9 leaves the setting unset, so the Groovy compiler's own default applies, and on Groovy 6 that is invokedynamic. An application that set `grails { indy = true }` can remove the line. Build logic that read the property, for example `grails.indy.get()`, must allow for it having no value now: use `grails.indy.getOrElse(true)` or check `grails.indy.present`.

An application that has to keep classic call sites, for example while it measures the difference, sets the property explicitly. An application that applies GraalVM's native image plugin cannot: the build fails with the reason, because an image needs invokedynamic.

To keep classic call sites:

[source,groovy]
.build.gradle
----
grails {
    indy = false
}
----

Classic call sites on Groovy 6 need `org.apache.groovy:groovy-callsite` on the classpath. Grails does not carry it, so an application that sets `indy` to `false` declares `implementation 'org.apache.groovy:groovy-callsite'` itself, at the version the Grails BOM manages, and again for every source set that does not see its implementation dependencies, such as the test fixtures of Gradle's `java-test-fixtures` plugin. Without it the Groovy compiler stops with a message naming the module.

A library compiled with classic call sites needs the module too, whatever the application's own setting, because Groovy 6 loads such a class only with it; the failure is a `NoClassDefFoundError` naming `org.codehaus.groovy.runtime.callsite.CallSiteArray`. Spock 2.5, Geb 8 and the Asset Pipeline 5.2 are compiled with invokedynamic, but `org.testcontainers:testcontainers-spock` is not, so an application that uses it declares `testRuntimeOnly 'org.apache.groovy:groovy-callsite'` next to it.

==== 6. XML Web Support Moves to a Separate Module

XML conversion, request-body binding, and REST renderers now live in the optional
`grails-xml` module. In Grails 9 the web starter still brings it, and so does `grails-web-boot`, which the
applications forge and the profiles generate list instead of the starter, preserving existing XML endpoints.
The module depends on `grails-rest-transforms`, and through it on `grails-controllers`, `grails-datasource`,
`grails-converters`, `grails-web-databinding`, `grails-mimetypes`, `grails-domain-class`, `grails-validation` and
`grails-i18n`, so `grails-web-boot` brings those modules and their plugins too. The applications forge generates list
them already; a build that lists `grails-web-boot` without them now loads the REST responder, controllers, data source,
converters, data binding, domain class, MIME types, i18n and XML plugins, so that Grails registers its data formats with
Spring MVC and resolves the locale with its own locale resolver, and excluding `grails-xml` leaves out again those that
nothing else in the build brings. JSON-only applications can exclude `org.apache.grails:grails-xml` now:

[source,groovy]
.build.gradle
----
configurations.configureEach {
    exclude group: 'org.apache.grails', module: 'grails-xml'
}
----

In Grails 10 neither will bring it, and `@Resource` will default to JSON only.
Legacy XML conversion is scheduled for removal in Grails 11: `grails.converters.XML`, the `XmlRenderer`,
`XmlCollectionRenderer`, HAL XML, Atom and Vnd.Error XML renderers, and the XML validation errors
marshaller are deprecated for removal. The converter logs one warning when it first renders XML, and the HAL XML, Atom
and Vnd.Error XML renderers each log one when they are used; the other XML renderers and the errors marshaller warn
through the converter they render with.
MIME type negotiation still recognizes `application/xml`, `text/xml`, Atom, and other XML media
types; recognizing a media type does not install an XML serializer.

New REST controllers, RESTful controllers, resources, and scaffolded controllers generated by the
`rest-api` profile advertise JSON only. Add `xml` to the artefact's `responseFormats` or `formats` declaration when
that endpoint should negotiate XML, which needs `grails-xml`.

Applications that expose XML endpoints or use `grails.converters.XML`, XML object marshallers, XML data
binding, or the XML and Atom renderers need this module. It is supplied transitively by the Grails 9
web starter and `grails-web-boot`; applications without either, and applications upgrading to Grails 10, add it
explicitly:

[source,groovy]
.build.gradle
----
dependencies {
    implementation 'org.apache.grails:grails-xml'
}
----

The module preserves the established Grails XML APIs and compatibility marshalling for domain-shaped
payloads, collections, maps, validation errors, named converter configurations, and include/exclude
projections. With the `DEFAULT` circular reference behaviour, an object that refers to itself is written with the
attribute `ref="."`, where Grails 8 failed with a `ConverterException`. Its XML renderers, and an application's `XmlRenderer` beans, find the view locator and the renderer
registry in the application context when they write a response, the registry `respond` uses where the application has
several, so their `groovyPageLocator` and `rendererRegistry` properties are no longer autowired; they are set only where an
application sets them.

Without the module, nothing renders XML except what the application provides, such as markup views, and `respond`
treats XML as any format nothing renders (see section 15): it answers in the next type the client accepts that the
action responds in, and a client that accepts any type, by sending `*/*` or no `Accept` header, or a browser, in the
first format the action lists that it can render the value in, so an action that lists `['xml', 'json']` answers those
clients in JSON. A markup view renders XML for an action that has one; for an action without one, the client's next
type is tried. Where no type the client accepts can be rendered, `respond` sends a `406 Not Acceptable` error, or a
`404` one for validation errors where the client accepts one of the action's formats, so that the application's error
pages apply, and writes a `ProblemDetail` as
`application/problem+json` (see section 13). An XML request body is not read and raises no error, while the
request parameters bind as they do for a request without a body, except that binding it to a collection with `bindData`
fails, as for any body of a type nothing binds; and `request.XML` throws an
`IllegalStateException` that names the module, while a class compiled with `@CompileStatic` or `@GrailsCompileStatic`
that reads it does not compile. `encodeAsXML` and the `xml` codec still escape text, but an object
other than text is escaped as its string rather than rendered as XML. An application that sees these after
an upgrade needs the dependency above.

A library compiled against Grails 8 that reads `request.XML` or `request.JSON` in statically compiled code keeps working
without being recompiled; `request.XML` still needs this module at run time. Code compiled against Grails 9 reads
`request.XML` from this module, so a plugin that reads it in a class compiled with `@CompileStatic` or
`@GrailsCompileStatic` needs the module to compile, and declares it as an `implementation` dependency so that
applications using the plugin have it.

Set `grails.web.rendering.xml.spring: true` to write ordinary bean responses with Spring Framework's `JacksonXmlHttpMessageConverter`,
backed by the Spring Boot-managed Jackson XML mapper. As in a plain Spring Boot application, that
converter is registered only when Jackson's XML dataformat is on the classpath, so applications that
want it add the dependency themselves:

[source,groovy]
.build.gradle
----
dependencies {
    runtimeOnly 'tools.jackson.dataformat:jackson-dataformat-xml'
}
----

Grails 9 defaults this setting to `false`: adding the Jackson XML dependency alone does not bypass
registered XML marshallers. Enabling it explicitly selects Spring for ordinary beans, even when a
legacy marshaller is registered. `respond` writes such a bean as Spring MVC writes the value a `@ResponseBody` handler
method of the controller returns, with Spring MVC's response body handler, so the application's `ResponseBodyAdvice`
beans apply to it as to a method of the controller, in UTF-8 whatever `grails.converters.encoding` says, as for JSON.
`null`, domain objects, collections, arrays, maps, validation errors, values
`respond` is given `includes` or `excludes` for, and the values of a renderer with a legacy `namedConfiguration`
continue to use the Grails XML converter; migrate these to DTOs or explicit application renderers
before legacy XML conversion is removed in Grails 11.

Without the Jackson XML dependency, `grails-xml` still renders XML through the Grails converter. Applications may also register
their own Spring XML message converter or OXM/JAXB infrastructure through public Spring configuration
APIs.

This change does not affect Grails plugin descriptors. Plugin metadata continues to be generated and
published in its existing descriptor format; `grails-xml` concerns application HTTP payloads only.

==== 7. Opt Into Spring JSON Conversion

Each JSON and XML path keeps its Grails 8 output by default in Grails 9, and has a setting that opts into the
Jackson-based one. A `ProblemDetail` is the exception: `respond` writes it as Spring MVC writes it, whatever the
settings, with the exceptions section 13 lists. The smaller changes that apply whatever the settings, such as `Accept`
headers matched whatever their case, are in sections 4, 7, 9, 11, 13, 14 and 16, and in this section, where `grails-converters`
now brings Boot's `JsonMapper`, which Spring MVC's JSON converter then writes with.

[cols="2,3,1,2", options="header"]
|===
| Setting
| What it governs
| Grails 9 default
| Later default

| `grails.web.rendering.json.spring`
| JSON written by `respond`, including validation errors as problems
| `false`
| `true` in Grails 10

| `grails.converters.json.legacy`
| `grails.converters.JSON`: `render ... as JSON`, `JSON.parse`, `request.JSON`, and `respond` while
`grails.web.rendering.json.spring` is `false`
| `true`
| `false` in Grails 10

| `grails.databinding.json.jackson`
| JSON request bodies bound to command objects and domain classes
| `false`
| `true` in Grails 10

| `grails.converters.json.domain.jackson.enabled`
| Domain classes written by Spring Boot's own `JsonMapper`
| `false`

| `grails.web.rendering.xml.spring`
| XML written by `respond` for ordinary beans
| `false`

| `grails.exceptionresolver.springHandlers`

| `grails.controllers.responseBody`
| Values of actions annotated `@ResponseBody`, written by Spring MVC as the body (see section 18)
| `false`
| `true` in Grails 10
|===

`request.JSON` and data binding parse a request body under different settings, so set
`grails.converters.json.legacy: false` and `grails.databinding.json.jackson: true` together for both to accept the
same JSON. Grails 10 changes the defaults of the three JSON settings together, so that `respond`, `render ... as JSON`,
`request.JSON` and data binding write and read JSON with the same mapper by default.

Grails 9 preserves the legacy `grails.converters.JSON` converter for `respond()` by default and logs one
deprecation warning when that path renders. Opt into Spring MVC's message converters, backed by Boot's
configured Jackson `JsonMapper`, with `grails.web.rendering.json.spring: true`. Grails 10 will enable it
by default; the legacy `respond()` path is scheduled for removal in Grails 11. Jackson can render date
formats, bean properties, circular references, and validation errors differently, and writes an enum as Jackson does,
by its `@JsonValue` or its `toString()`, where the legacy converter writes its name, so review the JSON returned by
`respond()` endpoints when you upgrade. Explicit `render value as JSON` calls still use the
legacy converter.

The setting alone determines the default response path: registering a marshaller does not implicitly
change it. `false` retains the legacy converter (with the warning); `true` uses Spring's converters
even while legacy marshallers are registered. Migrate those representations to Jackson serializers
before enabling it. Two legacy converter settings do not configure Jackson:
`grails.converters.json.pretty.print` gives way to `spring.jackson.serialization.indent-output`,
and `grails.converters.json.date` to Boot's `spring.jackson.*` date settings. Renderer beans an application declares, such as a `JsonRenderer` or an
`XmlRenderer` for one of its types, follow the same settings, apply their own `includes` and
`excludes`, and reach the same named configurations and message converters. A `JsonCollectionRenderer` bean ignores the
`excludes` `respond` is given on the legacy path, as in Grails 8, and applies them on Spring's path where it sets none of
its own. On Spring's path, a `JsonRenderer` for a
domain class writes it as `respond` writes any domain class instance, described below: its associated instances as
references unless `grails.converters.json.default.deep` is set, and its version and class name as the
`grails.converters.json.domain.*` settings select, which naming them in its `includes` does not change. The legacy
converter writes the associated instances of such a renderer in full, and the version or the class name its `includes`
names.

[source,yaml]
.application.yml
----
grails:
    web:
        rendering:
            json:
                spring: true
----

`respond` writes the value as Spring MVC writes the value a `@ResponseBody` handler method of the controller returns,
with Spring MVC's response body handler, so the application's `ResponseBodyAdvice` beans apply to it as to a method of
the controller, also where a named configuration writes it. The handler method is the action's, so its `@JsonView`
selects the properties written, other than those of a problem or of a named configuration. Grails selects the first configured MVC
`HttpMessageConverter` that can write the response type and negotiated JSON media type and advertises a JSON media
type for that class
(`application/json`, `text/json`, or a `+json` subtype). Generic `*/*` string and byte-array converters
are skipped, so strings remain JSON strings and byte arrays use Jackson's base64 JSON representation.
The same media-family rule applies to XML conversion; a generic text converter cannot strip the XML
string element. Where that converter is Spring's `JacksonJsonHttpMessageConverter`, the Grails mapper writes the value
after what the converter writes ahead of it, such as the prefix its `setPrefixJson(true)` or `setJsonPrefix(...)` adds
against JSON hijacking, which is read when the converter first writes a response, so configure it as Spring MVC starts,
as a `WebMvcConfigurer` does. A response `respond` writes with a named configuration, `render json:` and
`grails.converters.JSON` are written without the converter, and so without its prefix. A response written this way is
in UTF-8 and labelled `application/json`, or `text/json` for a client that asks for it, as Spring MVC writes JSON,
whatever `grails.converters.encoding` says, which the legacy converter and `render json:` still write in. Where an
application's own JSON converter writes the response, such as a subclass of Spring's Jackson converter, one with mappers
for the type, or a converter of another library, it is labelled with a JSON type that converter supports.

`grails-converters` depends on Spring Boot's `spring-boot-jackson` module, so Boot's `JsonMapper`, configured by the
`spring.jackson.*` properties, is in every application context that has the converters. An application with
`spring-boot-starter-web`, which the web starter brings with SiteMesh 3, had it already; one without it now has Boot's
`JsonMapper` too, and Spring MVC's JSON converter writes with it rather than with a mapper of its own.

The standard Jackson converter uses an isolated mapper derived from Boot's configured `JsonMapper` for every value but
a `ProblemDetail`, which Spring's converter writes with Boot's mapper itself (see section 13).
It renders domain classes with the same Jackson serializer as the `JsonMapper` itself does when
`grails.converters.json.domain.jackson.enabled` is set, and as `render ... as JSON` does with
`grails.converters.json.legacy` set to `false` (see the section on domain classes below): the
persistent properties and the id, associated instances as references of their id, or in full with
`grails.converters.json.default.deep`, the version and class name with the `grails.converters.json.domain.*`
settings, and what Jackson applies to a bean, such as `@JsonIgnore`, `@JsonInclude` and the naming strategy.
Per-response `includes` and `excludes` apply to domain classes too. On top of that serializer, the converter applies what
sections 7 and 8 describe, which the mapper does not, such as the marshallers registered with `JSON.registerObjectMarshaller(...)`
or an `ObjectMarshallerRegisterer`, subclasses of `DomainClassMarshaller`, enums written by their names, and strings escaped
for an HTML `<script>` element. Ordinary non-domain beans retain Jackson's property rules. Application-provided converter
subclasses and per-type mapper registrations keep their configured behavior and precedence.

A domain object that leads back to itself while it is being written, such as an embedded value that points at its owner,
is written as `{"_ref": "..", "class": "..."}` by default, with a `..` for each JSON object or array from the one the
reference is written in up to the value the object is written as, its type wrapper included, or `.` where it repeats the
object the reference is written in, on which Grails 8 failed; or as
`grails.converters.json.circular.reference.behaviour` selects, by the mapper as well as by a response and the converter. With `IGNORE`, an element of a list is left out and a
property is written as `null`, where the legacy converter fails on the property. A plain bean that leads back to itself is written the same way by a response
and by the converter, and fails on the mapper, as it does in a plain Spring MVC controller.

Boot's shared mapper is not given the Grails domain serializer unless `grails.converters.json.domain.jackson.enabled`
is set, so plain Spring `@RestController` responses retain Jackson's normal domain property model. Both mappers serialize Groovy `GString`
values as strings. Only the Grails mapper serializes Spring `Errors` as an `errors` array containing
object, field, message, and codes, without rejected values; Grails `respond errors` adapts that array into an
RFC 9457 problem response.

Grails retains the legacy converter path when a renderer sets a legacy named converter
configuration, when a per-response `includes`/`excludes` projection is requested and the selected
converter is not Spring's standard Jackson converter, or when no configured MVC converter can write
the selected type and media type. With `grails.web.rendering.json.spring` enabled, Grails logs a warning for each type,
and for each of these reasons, that the legacy converter writes, so that a response the setting does not change is
found, up to 100 of them. Explicit application and plugin `Renderer` beans continue to take precedence over the default
renderer.

Where `respond` writes JSON through Spring MVC's converters, or with a named configuration, a value it fails to write
fails as Spring MVC's Jackson converters fail, as a `ProblemDetail`, which Spring MVC writes itself, does: a type
definition error, such as a property a bean unwraps with the name of one of its own, is an
`HttpMessageConversionException`, and any other failure, one of the response's writer included, an
`HttpMessageNotWritableException`. Spring MVC's own exception resolver answers an `HttpMessageNotWritableException` before
the Grails exception resolver sees it, as it does for any Spring MVC controller: with a 500 and a warning without the stack
trace, and the error page finds the exception in the `jakarta.servlet.error.exception` request attribute rather than in
the model the Grails exception resolver gives it. A type definition error reaches the Grails exception resolver as any
other exception does. The legacy converter fails as it did in Grails 8. `render json:` throws the mapper's own exception,
a Jackson `JacksonException`, and a `ControllerExecutionException` where the response's writer fails, which the Grails
exception resolver sees as any other exception.

Controller unit tests use Boot's Jackson configuration and the same setting. Supply a mapper or
`JsonMapperBuilderCustomizer` from a nested Spring `@Configuration` class, so Boot can see it before
evaluating its conditional beans. A mapper registered by the deprecated `doWithSpring` callback or by
`beanRegistrar()` is too late to make Boot back off. Named JSON
configurations work through `render` and `respond` in `ControllerUnitTest`. Section 16 covers the
other changes to web unit tests.

==== 8. JSON Converter Customization Moves to Jackson

The `grails.converters.JSON.registerObjectMarshaller(...)` API remains supported for
`render ... as JSON` and converter-based rendering. Registering a marshaller does not change the
`respond()` rendering setting. Marshaller registrations apply to its legacy converter path, not to
Spring's message converters. To customize the Spring path, configure Spring Boot's `JsonMapper` so
the same serializer is used by opted-in `respond`, Spring MVC message conversion, and other
Jackson-based integrations:

[source,groovy]
----
import org.springframework.boot.jackson.autoconfigure.JsonMapperBuilderCustomizer
import tools.jackson.databind.module.SimpleModule

@Bean
JsonMapperBuilderCustomizer bookJsonCustomizer() {
    { builder ->
        builder.addModule(new SimpleModule()
                .addSerializer(Book, new BookValueSerializer()))
    } as JsonMapperBuilderCustomizer
}
----

`BookValueSerializer` is an application-provided Jackson `ValueSerializer<Book>`. Use a module when several
serializers belong together, or register an individual serializer directly through the builder customizer.

For different JSON shapes selected by name, replace `JSON.createNamedConfig(...)` with the injectable
`NamedJsonConfigurationRegistry`. Each registration derives an isolated mapper from Spring Boot's configured
`JsonMapper`, so it retains application-wide Jackson settings without changing the shared mapper:

[source,groovy]
----
import grails.converters.json.NamedJsonConfigurationRegistry

class BootStrap {
    NamedJsonConfigurationRegistry namedJsonConfigurationRegistry

    def init = { servletContext ->
        namedJsonConfigurationRegistry.register('catalog') {
            it.serializer(Type, new TypeValueSerializer())
            it.serializer(Category, new CategoryValueSerializer())
        }
    }
}
----

Select the configuration per response with `respond`, or with the `json` render argument. `respond` writes a
`ProblemDetail` as Spring MVC writes it, and validation errors as it writes them without a configuration, whatever
configuration it names, though a name that is not registered throws for them too:

[source,groovy]
----
respond book, jsonConfiguration: 'catalog'
render json: book, jsonConfiguration: 'catalog'
// Without a name, use the default Jackson configuration:
render json: [ok: true]
----

Both accept `includes` and `excludes`. A projection applies to the properties of the type written,
or of each element's type when a collection or array is written, unlike the legacy converter, which
projects only the objects of the class of the value written, so not the elements of a collection unless a
`JsonCollectionRenderer` bean renders it, which applies the `includes` `respond` is given to them but, on the legacy path,
its own `excludes`, an empty list unless the bean sets them, in the place of those `respond` is given, as in Grails 8. It applies to domain objects and other beans alike; objects of
other types inside them are written in full. Properties are named by their bean property names, and a JSON name given by a Jackson
annotation or naming strategy matches as well. A value with no properties to project, such as a map
or a string, throws `IllegalArgumentException` before anything is written. A type that a Jackson
serializer of its own writes is not filtered, and a warning names it the first time, as one does an `Iterable` that is not
a `Collection`, whose elements are not walked before writing in case it can be iterated only once. With
`grails.web.rendering.json.spring: true`, `respond x, includes: [...]` without a configuration name
applies projections the same way; otherwise it uses the legacy converter.
Registered configurations are immutable: configure them inside the registration callback, and
register the name again to replace a configuration rather than mutating a retained reference.

For direct serialization, inject the same registry and use
`namedJsonConfigurationRegistry.writeValueAsString('catalog', book)` or
`namedJsonConfigurationRegistry.writeValue('catalog', writer, book)`. `writeValue` leaves the writer open and
unflushed, as a response's writer is the container's, so flush or close a writer of your own, such as a `FileWriter`,
once it returns. These explicit operations replace the thread-local scope established by `JSON.use(...)`. Every registry has a `deep` configuration, which writes the
associations of domain class instances in full, as `JSON.use('deep')` did, so `render json: book, jsonConfiguration: 'deep'`
writes the associations as `JSON.use('deep') { render book as JSON }` does. The rest is written as the mapper writes it
rather than as the converter does: marshallers registered with `JSON.registerObjectMarshaller(...)` do not apply, an enum
is written as Jackson writes it, such as by its `@JsonValue`, rather than by its name, and `</` is not escaped. A
configuration of the application's own writes associations in full with `it.deep()`. The legacy `JSON.createNamedConfig(...)` and `JSON.use(...)`
APIs, along with `JSON.getNamedConfig(...)` and `JSON.withDefaultConfiguration(...)`, are deprecated
and scheduled for removal in Grails 11 in favor of the request-safe Jackson registry. So are the `namedConfiguration`
property of `JsonRenderer` and `JsonCollectionRenderer` beans, which selects one of those legacy configurations, and
the `renderJson(JSON, RenderContext)` method their subclasses override to render with the legacy converter. This
timetable does not deprecate `JSON.registerObjectMarshaller(...)`.

==== 9. `grails.converters.JSON` Can Write JSON With Spring Boot's JsonMapper

In Grails 9, `render ... as JSON`, `respond` for a JSON request and every other use of `grails.converters.JSON` still
render JSON as Grails 8 did, by default (see <<renderingJsonAsGrails8,Rendering JSON As Grails 8 Did>>). Setting
`grails.converters.json.legacy` to `false` makes the JSON converter write JSON through the application's Jackson
`JsonMapper`, the one Spring Boot auto-configures, so that it renders values as a Spring Boot application does. A later
release makes that the default, so check your application's JSON with the setting before you upgrade to it:

[source,yaml]
----
grails:
    converters:
        json:
            legacy: false
----

While `grails.converters.json.legacy` is not set, Grails logs a warning once at startup that the default will change.
Setting it to either value turns the warning off.

With the setting `false`, the mapper writes the JSON text (numbers and pretty printing), and writes every single value
that it has a dedicated serializer for: dates and times, `Month`, `UUID`, `Locale`, `byte[]`, types with a `@JsonValue`,
and the types of any Jackson module registered with the application. Those values render as Spring Boot renders them,
and `spring.jackson.*` properties apply to them. A number, string or boolean is written by the mapper's serializer for
its type where a Jackson module registered with the application gives the type one, such as `ToStringSerializer` for
`Long`, whether the converter renders it on its own, inside a collection or map, or for a marshaller's `property`,
`convertAnother` or `build` call; otherwise it is written as Jackson writes it. With the setting `false`,
`spring.jackson.serialization.wrap-root-value` also wraps the value the converter renders in an object named after its
class, or its `@JsonRootName`, as Spring Boot wraps the body of a response; with the setting `true` the value is not
wrapped, as in Grails 8. For example, `spring.jackson.time-zone` writes `Date` and `Calendar`
values in that time zone, and converts `OffsetDateTime` and `ZonedDateTime` values to it. The mapper is the
application's only or primary `JsonMapper`, or else Spring Boot's `jacksonJsonMapper`, as for `respond` and data
binding; where the application context has none of those, as in a unit test other than a web test, whose traits
register Spring Boot's, a default `JsonMapper` is used.

With the setting `false`, `JSON.parse` and `request.JSON` parse with the application's Jackson mapper. What they accept
is what the mapper's parser features allow, so strict JSON by default, where Grails' own parser also accepts single quotes,
comments, unquoted names and values, uppercase literals, trailing commas and `new Date(...)`. To accept some of that again,
enable the matching Jackson read features, for example `spring.jackson.json.read.allow-java-comments`,
`spring.jackson.json.read.allow-single-quotes`, `spring.jackson.json.read.allow-unquoted-property-names` or
`spring.jackson.json.read.allow-trailing-comma`; `new Date(...)` and the other forms Jackson has no feature for are no longer
accepted. `grails.converters.json.date: javascript`, which writes `Date` values as JavaScript `new Date(...)` expressions,
therefore needs the setting `true`, whose parser reads them back: those expressions are not JSON, so with the setting
`false` neither `JSON.parse`, `request.JSON` nor a controller unit test's `response.json` could read what the converter
writes, and an application that sets both fails to start with a message that names them. Remove
`grails.converters.json.date` to write dates as the mapper writes them, as the `spring.jackson.*` date settings configure. Text after the value, such as a second JSON document, is rejected as well, unless
`spring.jackson.deserialization.fail-on-trailing-tokens` is set to `false`. What comes back does not change: the same `JSONObject` and `JSONArray` containers, which implement `Map` and `List`,
with the same number types (`Integer`, `Long`, `BigInteger`, `Double` or `BigDecimal`, depending on the number). With the
setting `true`, the default in Grails 9, both parse with Grails' own parser as before, except that a number beyond the
range of a `double`, such as `1e400`, is a `BigDecimal`, where Grails 8 threw a `NumberFormatException`.
`new JSONObject(String)` and `new JSONArray(String)` always parse with Grails' own parser, whatever the setting.

With the setting `false`, the mapper writes every value, as Spring Boot writes it: collections, maps, arrays, records,
`Optional` values, enums and beans, besides the single values above. The converter renders each value in them, so the
values they contain are rendered as any other value is. A marshaller that an application registers, with
`JSON.registerObjectMarshaller(...)` or an `ObjectMarshallerRegisterer`, still takes precedence over the mapper for the types
it supports, and a serializer of a Jackson module registered with the application's mapper takes precedence over those
Grails adds, such as the one for validation errors, as it does in `respond`. A collection, a map or a bean that contains itself is written as before, as an empty collection or map where it
repeats, or as the `grails.converters.json.circular.reference.behaviour` selects. An object is reached again only where it
is the very object being written, as Jackson and `respond` find it: one that is only equal to it, such as a domain class
instance loaded twice, is written in full, where Grails 8 wrote a reference to it.

What Jackson applies to a bean applies to a bean the converter renders, where Grails 8 ignored it: `@JsonProperty`,
`@JsonIgnore`, `@JsonInclude`, `@JsonView`, `@JsonFormat`, `@JsonPropertyOrder`, mix-ins and the mapper's naming strategy and
inclusion. Properties come in the order Jackson gives them, where Grails 8 wrote the bean properties alphabetically and then
the public fields, and a bean with no properties is written as an empty object. The converter's includes and excludes for a
class, `setIncludes` and `setExcludes`, still decide which properties of a bean are written, and match a property by its
bean property name or by the JSON name a Jackson annotation or naming strategy gives it, as those of `respond` and
`render json:` do. A method annotated `@PersistenceMethod` or `@ControllerMethod` is still not a property. Subclasses of `GroovyBeanMarshaller` and
`GenericJavaBeanMarshaller` that you register still render the types they are registered for as they did.

With the setting `false`, two things deliberately differ from Spring Boot, as they do in Grails 8:

* Enums, including one with a `@JsonValue`, render by `name()`, where Jackson 3 writes `toString()` or the `@JsonValue`,
so that the JSON binds back to the enum.
* Strings, including a `GString` or a `StreamCharBuffer`, are escaped for an HTML `<script>` element: `</` is written
as `<\u002f`, and U+2028 and U+2029 as `\u2028` and `\u2029`. The parsed values are the same as Spring Boot's.

With the setting `false`, a bean whose `@JsonUnwrapped` property writes a name the bean writes too, such as an `id` of
both, is written with both, where Spring Boot's mapper, `render json:` and `respond` with
`grails.web.rendering.json.spring` reject it: the converter's includes and excludes, and the class name and the version
of a domain class instance, decide for each value it writes which properties it writes. With the setting `true`, the
converter writes the property as a nested object, as Grails 8 did, since its marshallers do not read Jackson's annotations.

With the setting `false`, the following values render differently than in Grails 8. With the setting left `true`, Grails 9

The other default date and time formats are the same as Grails 8.0.0's, which already renders `Date`, `Calendar`,
`java.sql.Date` and `java.sql.Timestamp` with millisecond precision and supports the additional date and time types.
With the setting `false`, map keys use the mapper's key serializers, instead of Grails' fixed date formats or the key's
`toString()`: a `Date` or `Calendar` key is written in the mapper's configured date format and time zone, a
`ZonedDateTime` or `OffsetDateTime` key keeps its own offset, as before, a `Class` key is its name
(`"java.lang.String"`, where Grails 8 wrote `"class java.lang.String"`), and the key of a type with a `@JsonValue` is
that value.

With the setting `false`, `JSON#toString(false)` does not indent the JSON when `grails.converters.json.pretty.print` is
`true`; Grails 8 ignored the argument. JSON that is not pretty printed is not indented either when the application's
`JsonMapper` indents its output (`spring.jackson.serialization.indent-output`).

With the setting `false`, the JSON marshallers that rendered these values are not registered. They are deprecated:
`DateMarshaller`, `CalendarMarshaller`, `ToStringBeanMarshaller`, `ByteArrayMarshaller`,
`InstantMarshaller`, `LocalDateMarshaller`, `LocalDateTimeMarshaller`, `OffsetDateTimeMarshaller` and
`ZonedDateTimeMarshaller`, in the `org.grails.web.converters.marshaller.json` package. To render one of these types
differently, register a marshaller for it, or configure the `JsonMapper`. The XML marshallers of the same names are not
changed. The default JSON marshallers have implicit priorities that follow their order (-1, -2, and so on), and with
the setting `false` that order differs, so a marshaller registered with an explicit negative priority may come before or
after different defaults.

Whatever the setting, `org.grails.web.json.JSONWriter`, which the converter and its marshallers write to, now writes
through a Jackson `JsonGenerator`, and `new JSONWriter(writer)` writes with a default `JsonMapper`:

* It keeps its public methods, rejects the same misplaced calls, and writes the same JSON text, apart from a `NaN` or
infinite `double`, which it writes as a string (`"NaN"`) where Grails 8 wrote `NaN`, which is not JSON. A `JSONWriter`
given the application's `JsonMapper`, as the converter is with `grails.converters.json.legacy` set to `false`, escapes
every string as that mapper does, a `GString`, a `StreamCharBuffer` or the text of any other value as a `String`, such as
`\u001B` for the escape character where Grails 8 wrote `\u001b`; a `JSONObject` or `JSONArray` it is given is written as
the JSON text it writes itself, as in Grails 8. Wherever a `JSONWriter` writes, `</` is written as `<\u002f`, as the
converter always wrote it, also where `grails-converters` is not on the classpath, where Grails 8 wrote `<\/`. Without
`grails-converters`, where Grails 8 quoted values with `JSONObject` rather than with the converter's encoder, it also
wrote a collection given to `value` as a JSON array, U+2028 and U+2029 unescaped and the vertical tab as
`\u000b`; such a value is now written as its `toString()`, and the characters as the converter writes them. It also accepts a single
value outside any object or array, where it threw a `JSONException`.
* The generator buffers the text. It reaches the `Writer` as the buffer fills, once the JSON text is complete, and when
`flush()` is called, rather than as each value is written. The `Writer` itself is not flushed or closed.
* `array()`, `object()`, `key()` and the `value` methods no longer go through the protected `append` and `comma`
methods. A subclass that overrides those to change the output, or writes to the `writer` field directly, must use the
public methods instead.
* `PrettyPrintJSONWriter` still indents as Grails 8 did, and is deprecated. Use `new JSONWriter(writer, true)`, which
indents with Jackson's default pretty printer and writes with a default `JsonMapper`, as `new JSONWriter(writer)` does. To
indent the JSON the converter writes, set its `prettyPrint` property or `grails.converters.json.pretty.print`: it
indents as Grails 8 did with `grails.converters.json.legacy` left `true`, and with the application's `JsonMapper` with it
set to `false`. With the setting left `true`, `toString(true)` indents as Grails 8's did, by three spaces, which differs
from the layout of the property; with it set to `false` it indents as the property does.

The JavaCC JSON parser in `org.grails.web.json.parser` (`JSONParser`), which Grails does not use, is deprecated. Use
`JSON.parse` or `new JSONObject(String)`.

Whatever the setting, with the `PATH` circular reference behaviour (`grails.converters.json.circular.reference.behaviour`),
an object with a `null` property, or a single value, now renders instead of failing, and a reference that follows a
number now has the right path: `"root.x.other"` where Grails 8 wrote `"root.x.n"`, after a property `n` that is a
number.

Whatever the setting, the includes and excludes a converter is given for the value it renders, with `setIncludes(List)`
and `setExcludes(List)` or by `respond`, apply where the value is a proxy, such as a lazy association Hibernate returns,
to the instance the proxy stands for, and for the rest of the render to the other instances of its class that have none
of their own, as the projection of `respond` does. Grails 8 kept them for the class of the proxy, which it does not
render, and so rendered every property. A marshaller that writes the instance a proxy stands for in its place calls
`standIn(proxy, instance)` on the `JSON` converter it is given before it writes the instance, as the converter's own
marshallers do.

JSON views, the XML converter and the HAL renderer are not changed.

[[renderingJsonAsGrails8]]
===== Rendering JSON As Grails 8 Did

`grails.converters.json.legacy` is `true` by default in Grails 9. The JSON converter then renders values, including
domain classes, with the marshallers of Grails 8, formats map keys and indents pretty printed JSON as Grails 8 did, and
writes with a default `JsonMapper`, so that the application's `spring.jackson.*` settings and Jackson modules do not
change the text: `render ... as JSON` and `JSON#toString` return the same text as in Grails 8. What Grails 8 failed to
render, or rendered as invalid JSON, such as a single value, `NaN`, or a to-many association whose value is a `Map` with
other than one entry, renders as it does with the setting `false`. A reference that the `PATH` circular reference
behaviour writes after a number also has the right path, as described above, where Grails 8 wrote a wrong one, the
`DEFAULT` behaviour writes a reference of `.` for an object that refers to itself, where Grails 8 failed, and the
includes and excludes given for a proxy apply to the instance it stands for, where Grails 8 ignored them. Whatever the
setting, a value nested deeper than the thread's stack lets the converter write, such as an object graph that never ends,
fails with a `ConverterException`, where Grails 8 threw a `StackOverflowError`, or a `ConverterException` where the stack
overflowed in a getter of a bean it wrote. A later
release makes `false` the default; setting `grails.converters.json.legacy` to `true` explicitly keeps the Grails 8
rendering, and turns off the warning that Grails logs while it is not set. With
`grails.converters.json.domain.jackson.enabled` set to `true` as well, the JSON converter still renders as Grails 8 did,
and the application's `JsonMapper` renders domain classes with the module, as described below.

With the setting `false`, to keep the Grails 8 rendering of some types only, register a marshaller for each, for
example in `BootStrap.init`:

[source,groovy]
----
JSON.registerObjectMarshaller(Month) { Month month -> month.name() }
JSON.registerObjectMarshaller(Locale) { Locale locale -> locale.toString() }
JSON.registerObjectMarshaller(byte[]) { byte[] bytes -> bytes as List }
----

==== 10. Domain Classes Render as Jackson Beans of Their Persistent Properties

With `grails.converters.json.legacy` set to `false`, the JSON converter renders a domain class instance with Jackson's own
bean serializer, which Grails shapes to the domain class, as `DomainClassMarshaller` rendered it in Grails 8, with these
differences:

* What Jackson applies to a bean applies to the instance, where the converter ignored it in Grails 8: a property annotated
with `@JsonIgnore`, or with `@JsonProperty(access = WRITE_ONLY)`, is not rendered, nor is one that a class-level
`@JsonIgnoreProperties` names; property names follow `@JsonProperty`, `@JsonNaming` and the mapper's naming strategy
(`spring.jackson.property-naming-strategy`), and the converter's includes and excludes match either name; `@JsonInclude` and `spring.jackson.default-property-inclusion` decide whether a
null or empty property is written; `@JsonView`, `@JsonFormat`, a `@JsonSerialize` serializer on a property, mix-ins, filters
and `@JsonPropertyOrder` apply; a domain class with `@JsonTypeInfo` is written with its type id, and an instance in a
`@JsonUnwrapped` property is written into the enclosing object. As with Jackson's own unwrapping, an instance with a type
id fails there, unless `SerializationFeature.FAIL_ON_UNWRAPPED_TYPE_IDENTIFIERS` is disabled.
* Only the persistent properties are rendered, as in Grails 8: a transient property, a getter with nothing persisted
behind it, or what a `@JsonAnyGetter` method returns, is not. They follow the class name, the id and the version, which are rendered ahead of them when they apply,
in the order the domain class declares them, unless `@JsonPropertyOrder` says otherwise. The entries of a persistent `Map`
property annotated `@JsonAnyGetter` are written in its place, as Jackson writes those of a bean, whatever name the naming
strategy gives the property, where Grails 8 wrote the property as an object.
* GORM names some properties in a `@JsonIgnoreProperties` it adds to every domain class, so Jackson leaves them out:
the tenant identifier of a multi-tenant domain class (`tenantId`) and the `dbo` of a MongoDB domain class, which
Grails 8 rendered. The version is written when it is included, as before.
* A to-many association whose value is a `Map` renders as an object of references, such as `{"a":{"id":1}}`, where it
failed before.
* A domain class with its own `@JsonSerialize` serializer, with a `@JsonValue`, that implements `JacksonSerializable`, or
that a Jackson module provides a serializer for, is written by that serializer, also where it is the value of an
association, which is otherwise written as a reference, with what the property is annotated with, such as `@JsonFormat`
or `@JsonInclude`. Whether a proxy is written with such a serializer is decided by the domain class the association
declares, since the proxy's own class is known only once it is loaded, and an associated class Jackson cannot write,
such as one that unwraps a property with the name of one of its own, is still referenced. A subclass of a domain class that is neither a domain class nor a
proxy of one is written by Jackson, as any class is.
* `DomainClassMarshaller` and `DeepDomainClassMarshaller` render through the serializer. Their constructors and
protected methods (`includesProperty`, `excludesProperty`, `extractValue`, `asShortObject` and
`isRenderDomainClassRelations`) are unchanged, and a subclass that overrides them still renders as it did. They are
consulted before the mapper's value serializers, as `ProxyUnwrappingMarshaller` is.

The application's `JsonMapper` is not changed: writing a domain class instance with it, such as returning one from a
Spring MVC controller, renders it as a Jackson bean, as in Grails 8. To have the mapper render domain classes with the
serializer `render ... as JSON` renders them with, without the marshallers and the rule for enums the converter applies
on top, set `grails.converters.json.domain.jackson.enabled` to `true`:

[source,yaml]
----
grails:
    converters:
        json:
            domain:
                jackson:
                    enabled: true
----

Grails then registers the module as a Jackson `JacksonModule` bean named `domainClassJacksonModule`, which Spring Boot
adds to its `JsonMapper` and to every mapper built from its `JsonMapper.Builder` bean. To add it to a `JsonMapper` you
build otherwise, inject that bean as a `tools.jackson.databind.JacksonModule` and pass it to the builder's `addModule`.
The mapper renders associated instances as references of their id, such as `{"id":3}`,
or in full with `grails.converters.json.default.deep`, and proxies as the instances they proxy, and names the id of a
reference as the referenced class names it.

==== 11. Rendering Single Values as JSON

In Grails 8, rendering a single enum value with `render(Role.HEAD as JSON)` threw a `ConverterException`.
It now produces the JSON string `"HEAD"`. The default enum marshaller uses the enum name, including when the
value is nested in an object or array.

The legacy JSON converter now accepts scalar root values: strings (including GStrings), numbers,
booleans, `null`, and enum names. Use `new JSON(value)` for scalar values, with or without
`grails.converters.json.pretty.print=true`. Groovy's built-in casts for strings and numbers do not
support `value as JSON`; construct the converter explicitly for those values.
Non-null scalar `respond` responses use the same rendering behavior. Rendering a scalar converter
no longer throws a `ConverterException` merely because the root is a scalar.
`JSONWriter` accepts a single value outside any object or array whatever the `grails.converters.json.legacy`
setting, as the section on writing JSON with Spring Boot's `JsonMapper` describes.

==== 12. Opt Into Jackson JSON Request Binding

Grails 9 retains `JsonSlurper` request binding by default and logs a startup deprecation notice. As
in Grails 8, an application `JsonSlurper` bean, for example one using `JsonParserType.LAX`, replaces
the default parser on that path, except for the bodies of a type a `HalJsonRenderer` bean renders, and the JSON bodies
of a type no creator bean handles, as where an application replaces `jsonDataBindingSourceCreator` with a creator for one
class, which a default `JsonSlurper` parses, as in Grails 8; once Jackson parsing is enabled, configure it through
`JsonMapperBuilderCustomizer` instead.
Set `grails.databinding.json.jackson: true` to parse binding bodies with Boot's configured Jackson
`JsonMapper`, JSON, HAL JSON and JSON API bodies alike, among them two kinds Grails 8 always parsed with a default
`JsonSlurper`: the bodies of a type a `HalJsonRenderer` bean renders, which the `halJsonDataBindingSourceCreator` bean then
parses, where it handles that type and parses with Jackson, and the JSON bodies of a type no creator bean handles, as where an application replaces
`jsonDataBindingSourceCreator` with a creator for one class. The mapper is the one Spring MVC reads a `@RequestBody`
map with: that of the first of its message converters that reads JSON, where that is Spring's Jackson converter, so that
a converter a `WebMvcConfigurer` configures parses both, or the mapper that converter has for maps. Where that converter
is not Jackson's, such as Gson's with `spring.http.converters.preferred-json-mapper: gson`, or without Spring MVC, the
mapper is the application's only or primary `JsonMapper`, or else Spring Boot's `jacksonJsonMapper`; where the
application context has none of those, as when it has several and none is primary, a default `JsonMapper` parses them,
as for the JSON converter. Jackson becomes the default in Grails 10 and legacy parsing is removed in Grails 11.
The mapper's parser features and limits then apply to request bodies: the features a `JsonMapperBuilderCustomizer` or
`spring.jackson.json.read.*` sets, such as support for an application-specific input format, and the limits
`spring.jackson.factory.constraints.read.*` or a `JsonFactoryBuilderCustomizer` sets. The mapper reads a
body as plain JSON values, maps, lists, strings, numbers and booleans, which Grails' data binder then binds by their
names, as it binds what `JsonSlurper` reads, so the mapper's naming strategy and date format, the deserializers of a
module for other types, and Jackson annotations on command objects and domain classes do not apply to binding, and
`spring.jackson.deserialization.unwrap-root-value` does not expect a root value around a body, nor do
`use-java-array-for-json-array`, `use-big-integer-for-ints` and `use-long-for-ints` change the lists and whole numbers it
reads. Nor does the mapper's default typing, which `activateDefaultTyping` turns on, apply: a body is read without type
ids, which would otherwise have every body without one fail and let a client name the classes Jackson creates for its
values. It still applies where the application reads with the mapper itself, such as a Spring MVC `@RequestBody`.

Both parsers report a malformed body bound to an object as a binding error, and one bound to a collection with
`bindData` as a `DataBindingSourceCreationException`, as in Grails 8, but Jackson rejects inputs that the legacy
parser accepted, among them trailing content after a document, trailing commas, leading-zero numbers,
unescaped tabs inside strings and trailing comments, and inputs beyond the limits of its
`StreamReadConstraints`, such as the nesting depth and the lengths of numbers, strings and names.
Review clients before enabling the new parser; configure intentional exceptions to the parser features through
`spring.jackson.json.read.*` or a `JsonMapperBuilderCustomizer`, and to the limits through
`spring.jackson.factory.constraints.read.*` or a `JsonFactoryBuilderCustomizer`.

With Jackson enabled, ordinary untyped JSON numbers keep the types the previous parser produced. Values with a fractional part are read
as `BigDecimal` rather than `Double`, so binding a request value such as `1.15` to a `BigDecimal` property
retains exactly the digits the request sent. Whole numbers bind as `Integer`, `Long`, or `BigInteger`
when too large for a `Long`, as with the legacy parser.

==== 13. REST Validation Errors Use RFC 9457 Problems

With `grails.web.rendering.json.spring: true`, `respond()` renders Spring `Errors` as
`application/problem+json` instead of the legacy `{"errors": [...]}` body. Grails 9 retains the legacy
body by default; this follows the same Grails 10 default flip and Grails 11 removal schedule as JSON
rendering. Grails uses the public `ValidationProblemDetailFactory` bean to
adapt the errors to Spring Framework's RFC 9457 `ProblemDetail` type. The resulting response has status
422, the title `Validation failed` and the detail `Request validation failed with 2 errors.`, which the
application's messages translate with the `grails.validation.problem.title` and `grails.validation.problem.detail`
codes, the latter given the number of errors, as `{0,choice,1#1 error|1<{0} errors}` uses it, and
an `errors` extension containing stable maps with the object name, optional field name, message, and error
codes:

[source,groovy]
----
import grails.rest.render.errors.ValidationProblemDetailFactory

class BookController {
    ValidationProblemDetailFactory validationProblemDetailFactory

    def save(Book book) {
        if (book.hasErrors()) {
            respond validationProblemDetailFactory.create(book.errors)
            return
        }
        // save the valid book
    }
}
----

Each message is resolved through the application's `MessageSource` for the current locale, so
`messages.properties` entries and Spring Boot's `spring.messages.*` settings apply to validation
responses as they do elsewhere.

With JSON views, an errors template, `grails-app/views/errors/_errors.gson` or one in the controller's view directory,
renders validation errors instead, as in Grails 8. Applications generated with the JSON views feature or the REST API
profile have one; delete it to answer with the problem, or respond with `validationProblemDetailFactory.create(errors)`,
which no view renders. Without an errors template, Grails 8 rendered validation errors with
`grails-app/views/object/_object.gson`, which those applications also have, writing `null` with a 200; they are now
written as without JSON views, with a 422: as the problem where `grails.web.rendering.json.spring` is `true`, and as
Grails 8 wrote them without JSON views otherwise.

Applications can also inject the factory when they need to create or customize the problem explicitly.
When `respond` receives a `ProblemDetail`, it hands it to the handler Spring MVC's handler adapter writes a
`ResponseEntity` with, so the problem is written as a Spring MVC controller method that returns it is written: the
application's `ResponseBodyAdvice` beans apply to it as to a method of the controller, and its
`ErrorResponse.Interceptor` beans see it. The response has the status the problem carries, and a problem without an
`instance` is written without one, as Spring MVC writes it. A `status` argument decides the status instead, as the
status of a `ResponseEntity` does in Spring MVC: a problem that carries another keeps its own, and Spring MVC logs a
warning. A Spring
`ErrorResponse`, such as an `ErrorResponseException`, is answered with its problem, whose message codes are resolved with
the application's messages as Spring MVC's `ResponseEntityExceptionHandler` resolves them, and with its status and
headers, where Grails 8 wrote it as a bean with a 200. Spring MVC's content
negotiation selects the type, whatever `grails.mime` says. It reads the `Accept` header unless
`spring.mvc.contentnegotiation.*` or a `WebMvcConfigurer` configures it otherwise: with `favor-parameter: true` a
`format` parameter decides ahead of the header, so `?format=json` and `?format=xml` are answered with
`application/problem+json`, as neither `application/json` nor `application/xml` is a problem type, and
`default-content-types` decides for a client that sends no `Accept` header or only `*/*`. The problem is written as
`application/problem+xml` where the request asks for a problem in XML, the action responds in XML and Spring MVC has an
XML converter, which needs `jackson-dataformat-xml`, and as `application/problem+json` otherwise. Unless `respond` names
a view for the problem, a client that asks for `application/xml` or `text/xml` is answered with
`application/problem+json`, as Spring MVC answers it, where Grails 8 wrote the problem as a bean with a 200; so is a
browser, and a client that accepts neither JSON nor XML, such as one asking only for HTML, where Grails 8 rendered the
action's view with a 200. A request Spring MVC's content negotiation rejects, such as one whose `Accept` header has a
quality value above 1 or more than 50 media types, or, with `favor-parameter: true`, one whose `format` parameter names a
format Spring MVC does not know, is answered as Spring MVC answers it: with the status alone, without a body or a
`Content-Type`, for a 4xx or 5xx problem, and otherwise with an `HttpMediaTypeNotAcceptableException`, which Spring MVC's
exception resolver answers with `406 Not Acceptable`.

A view renders a problem only when `respond` names it with the `view` argument: `respond` then picks the format as for
any value, so that a client that asks for `application/xml` is answered in XML where the action responds in XML, and the
view of that format renders the problem with the status it carries. Where the format `respond` picks has no view of the
name, the problem is written in that format where it is JSON or XML, the JSON view of the name renders it in any other
format if there is one, and otherwise it is written as without a view, as `application/problem+json` for a browser where
the application has no GSP of the name. In HTML that view is a GSP: a JSON or markup view of the name, or a JSP, does not
render a problem as HTML. A renderer the application registers for `ProblemDetail`, or for a type other than `Object`
that problems share, such as `Serializable`, renders them in its format; the default renderer of a format, and one the
application registers for `Object`, which stands in for it, do not, so the example above answers with
`application/problem+json` whatever `grails.web.rendering.json.spring` and `grails.web.rendering.xml.spring` are set to. A
`JsonRenderer` or `XmlRenderer` bean registered for problems writes them as Spring MVC writes them, whatever its
`includes` and `excludes`. A web application with Spring MVC always has the JSON converter; where none can write the
problem, Grails logs a warning and the legacy converter writes it as a bean, with the same status. The problem's
properties are written by Spring Boot's mapper as in a Spring MVC controller: a domain class instance, validation errors
or a value that leads back to itself among them is written, or fails, as Jackson writes any bean, whatever the
`grails.converters.json` settings, unless `grails.converters.json.domain.jackson.enabled` gives that mapper the domain
class serializer.
Rejected field values are excluded from the problem by default because they can contain passwords, tokens, or other
sensitive request data. Validation errors an action responds with in XML are not written as a problem, and keep their
rejected values, as in Grails 8. Applications that deliberately need those values can define their own factory
bean after reviewing that exposure risk. It replaces the default one whatever its name, both for `respond` and
for a controller that declares a `validationProblemDetailFactory` property, and takes the `MessageSource` so that
messages stay localized. A bean named `validationProblemDetailFactory` overrides the plugin's bean of that name, so it
needs bean definition overriding, which Grails allows unless `spring.main.allow-bean-definition-overriding` is `false`;
any other name works either way:

[source,groovy]
.grails-app/init/Application.groovy
----
@Bean
ValidationProblemDetailFactory includingRejectedValues(MessageSource messageSource) {
    new ValidationProblemDetailFactory(true, messageSource)
}
----

==== 14. HAL Rendering

Existing Grails HAL JSON renderers remain available through explicit renderer registration.
Adding `spring-boot-starter-hateoas` alone does not register a Grails renderer for Spring HATEOAS
`EntityModel` values. Return those models from a Spring MVC controller or provide an explicit Grails

[[upgradingGrailsFormatResolution]]
==== 15. Grails Format Resolution and Spring MVC Content Negotiation

Grails format resolution -- `withFormat`, `respond`, and `response.format` -- applies the `grails.mime.*`
rules. Spring MVC keeps its own content negotiation: an `@RestController`, an actuator endpoint or any other
Spring handler continues to match `produces` against the `Accept` header exactly as in a plain Spring
Boot application, and still answers `406 Not Acceptable` for a media type it cannot produce. The
`spring.mvc.contentnegotiation.*` properties therefore continue to work.

Grails reads the `Accept` header with Spring's `MediaType` parser. Most headers resolve as before, but
media type names are now matched case-insensitively: `Accept: Application/JSON` resolves to `json`, where
Grails 8 matched no configured type and resolved to `all`. A configured type with capitals in its name,
such as `application/vnd.Acme+json`, matches whatever the case of the header. The same parser reads
`Content-Type`, so `request.format` is case-insensitive too: `Content-Type: Application/JSON` gives `json`
where Grails 8 gave `null`, and the JSON binding source now binds a body it used to ignore. A `Content-Type` that no
configured type matches is read with its type in lower case, so a JSON API body sent as `application/VND.API+json` binds
as one sent as `application/vnd.api+json` does, where Grails 8 ignored it. A `MimeType` equals one whose name differs only
in case, so a renderer or binding source creator registered for a type with capitals is found for it in any case. One
registered for an interface is looked for, after those of the class and its superclasses, among the interfaces of the
class a lookup is made for, where Grails 8 looked among those of `java.lang.Class` when it was given a class, as data
binding and the JSON and markup view resolvers give it. A binding source creator registered for an interface a binding
target implements now handles its bodies in a content type no creator for `Object` handles, and one registered for an
interface of `java.lang.Class`, such as `Serializable`, no longer matches every class, nor does a renderer registered for
one stand in as the fallback renderer of JSON and markup views. A value Spring
rejects, such as a quality value above 1, is still read as Grails 8 read it, except where `respond` writes a
`ProblemDetail` as without a view, which is answered as Spring MVC answers such a client (see section 13). Parameter names are read ignoring case,
as Spring reads them, so `text/html;Q=0.1` has the quality 0.1, where Grails 8 read only a lower-case `q`. The problem types of RFC 9457,
`application/problem+json` and `application/problem+xml`, are the `json` and `xml` formats unless `grails.mime.types`,
or a `MimeTypeProvider` bean, such as a renderer or binding source creator, provides a type of that name. A binding
source creator an application adds to the binding source registry rather than declares as a bean is not among those: a
body sent as `application/problem+json` is bound by the creator of `application/json`, where Grails 8 found a creator the
application added for the problem type; declare it as a bean, or name the type in `grails.mime.types`. The problem
types are read as `application/json` and `application/xml` where those are configured, whatever order `grails.mime.types` lists the types
of the format in, and as the first type of the format otherwise, so `Accept: application/problem+xml, application/atom+xml`
resolves to `atom`, as in Grails 8, which ignored the problem type. Listed ahead of another type, a problem type now counts
as its format: `Accept: application/problem+json, application/hal+json` resolves to `json`,
`application/problem+xml, application/json` to `xml`, and `text/xml, application/atom+xml, application/problem+xml` to
`atom`, where Grails 8 resolved them to `hal`, `json` and `xml`. An `Accept` header of problem types alone Grails 8 resolved
to `all`, so an action answered with its first format;
`Accept: application/problem+json` now selects the `json` format, and `application/problem+xml` the `xml` format where the
action responds in XML. A client that sends only a problem type is therefore answered as one that asks for that format:
`respond` sends `406 Not Acceptable` for an action that does not respond in it, where Grails 8 answered in the action's
first format, and `withFormat` runs no block where it has neither one for that format nor a `*` one, where Grails 8 ran
its first block. `respond` writes a `ProblemDetail` in the type section 13 describes, whatever format this selects,
in XML only where the action responds in XML, and any other value as the format's own type, such as `application/xml`. In `Content-Type`, Grails 8 gave `null`: a body a client
sends as `application/problem+json` is now the `json` format, which `withFormat` selects and the JSON binding source
binds, and one sent as `application/problem+xml` the `xml` format, which the XML binding source of `grails-xml` binds.

Grails 8 merged `text/xml` and `application/xml` into one `xml` type with the larger of their qualities, but kept the
quality and the place of `application/xml`: `Accept: text/xml, application/xml;q=0.1, application/json;q=0.5` resolved to
`json`. The merged type now has the larger quality, and the place of the one of the two the header lists first, which
decides between types of equal quality, so that header resolves to `xml`. A more specific XML type listed after the first of the two now takes that place ahead of the merged
type: `Accept: text/xml, application/json, application/atom+xml, application/xml` resolves to `atom`, where Grails 8
resolved it to `json`.

`respond` answers a client that lists a format the action does not respond in ahead of one it does in the one it does,
and labels the response with it: `Accept: application/xml, application/json` to an action that responds only in JSON
is answered with `application/json`. Grails 8 labelled such a response with the client's first format, here
`application/xml`, and `respond`'s Spring JSON path then wrote it with the legacy converter.

A client that accepts any type is answered in the first format the action lists that a renderer renders the value in,
where Grails 8 answered in the first format listed and sent `406`, or `404` for validation errors, when nothing rendered
it. Validation errors that no renderer writes in the client's first format the action responds in are answered in its
next, where Grails 8 sent `404`. A renderer that renders some values only, such as that of markup views without
`grails-xml`, which renders only with a view, is passed over for a value it cannot render.

`grails.mime.disable.accept.header.userAgents` matched its first user agent with its case in Grails 8, and a user agent
that was not a regular expression failed the first request, after which the setting was ignored. Every user agent listed as
text is now matched ignoring case, as a regular expression of its own, while a `java.util.regex.Pattern` the
configuration gives, on its own or in the list, is used as it is, with its own case and flags, where Grails 8 joined them into one, in which the flags of
one changed the others and a blank one matched every user agent; a blank one is now left out. A string, which Grails 8
ignored, so that the `Accept` header of every client was honoured, is now read as a comma-separated list, and a user agent
that is not a regular expression fails as Spring MVC is configured, naming the setting.

The data-format extensions `json`, `xml`, `hal`, `atom`, `rss`, `csv` and `text` declared in
`grails.mime.types`, or among the defaults where it declares none or `grails.mime.mergeDefaults` adds them, are
additionally registered with Spring as format aliases. The MIME types a `MimeTypeProvider` bean adds are not, since
Spring MVC asks for its formats while it starts. Spring MVC negotiates
with them only when the application enables parameter negotiation with
`spring.mvc.contentnegotiation.favor-parameter: true`. Spring Boot leaves it disabled, so after the
upgrade `?format=json` still does not change what a Spring MVC endpoint returns. Where it is enabled, it also decides the type `respond`
writes a `ProblemDetail` in, as for a Spring MVC controller (see section 13). Browser formats such
as `html` and `js` are not registered, preserving Spring's reflected-file-download protection.
Where a format has several media types, an `application/*` one is preferred over a `text/*` one, and Boot's
`spring.mvc.contentnegotiation.media-types.*` overrides these defaults. Invalid names are skipped.

Grails keeps the MIME types and the `grails.mime.use.accept.header` and `grails.mime.disable.accept.header.*` settings
it resolves formats with in the application context, where Grails 8 kept them in static fields that every application in
the JVM shared. A test that configures `grails.mime.types` or those settings no longer resets them between tests: remove
test code that cleared or set those static fields, such as resetting the MIME types a response cached, since the fields
no longer exist, nor does `HttpServletResponseExtension.loadMimeTypeConfig`, which set them. The `createMimeTypeAndAddToList`
method of `DefaultAcceptHeaderParser` takes the requested `MimeType`, where it took its name and parameters, so a subclass
that overrode the Grails 8 method no longer overrides it. The settings are read once for each application context, which a unit test keeps for all the features of
its spec, so a spec sets them in `doWithConfig` rather than in a feature.

==== 16. Web Unit Tests Set Up More of the Web Layer

Web test traits such as `ControllerUnitTest` and `TagLibUnitTest` now always include the
`restResponder` plugin, even when a spec overrides `getIncludePlugins()`. They also provide JSON
conversion beans with Boot's Jackson configuration, build Spring MVC's message converters from the
test classpath, register Spring MVC's content negotiation manager, the `mvcContentNegotiationManager` bean, with a
`WebMvcConfigurer` bean that applies `spring.mvc.contentnegotiation.*` to it, as Spring Boot's auto-configuration
applies them with one, unless the spec declares a bean of that name, register Spring MVC's handler adapter, the
`requestMappingHandlerAdapter` bean, built as Spring MVC builds it from those converters, that manager and the spec's
`WebMvcConfigurer` beans, unless the spec declares a bean of that name, so that the spec's `ResponseBodyAdvice` and

on the test classpath, without loading the XML plugin's dependency graph. A spec that overrides `getIncludePlugins()` or
asserts on the beans in its application context sees these additions. The manager is built as Spring MVC builds it, from

application (see section 13). The `format` parameter that `favor-parameter` reads is one the spec adds to the request,
with `request.addParameter`, as a query parameter is added, not `params.format`, which stands for the format a URL
mapping gives and which Spring MVC does not read either. A spec for an application that declares `@EnableWebMvc`, which

autowire, responds with the application's renderer registry, its JSON and markup views and the renderers of the
application and of `grails-xml` included, where Grails 8 gave it a registry of the default renderers alone. A test request resolves its format and MIME types from its
content type as a request to an application does, and again when its content type changes, apart from a format the test set, directly or by setting `request.json` or
`request.xml`, which it keeps:
`application/json;charset=UTF-8` is the `json` format, where Grails 8 matched only a configured type's exact name and
gave no format, and `text/xml` is read as `application/xml`.

The traits still do not load the controllers, URL mappings or i18n plugins themselves. A URL mappings holder or link
generator a spec declares itself, in `doWithSpring`, `beanRegistrar()` or a `@Bean` method a nested `@Configuration`
class declares or inherits, from a superclass or an interface, under its name or with its name as an alias, is now kept,
where the traits replaced it with their own; one of a class that configuration class imports is replaced, as in Grails 8.
In every unit test, web or not, the bean of a `@Bean` method such a class inherits also replaces the stand-in the test's

has, is kept: a test resolves locales with the resolver `grails.i18n.localeResolver` configures, as the application does,

==== 17. Opt Into Spring MVC Exception Handlers

Spring MVC resolves an exception with the `@ExceptionHandler` methods of the controller and of the `@ControllerAdvice`
beans only for a handler method, which a Grails action is not, so such methods, and Spring Boot's handler of
`spring.mvc.problemdetails.enabled`, did not see the exceptions Grails actions throw, which the Grails exception
resolver rendered the error page for. Set `grails.exceptionresolver.springHandlers: true` to have them resolve those
exceptions first, as for a Spring MVC controller, with the advice that applies to the controller; an exception none of
them handles is resolved as before. Grails 10 makes it the default, so an application whose `@ControllerAdvice` beans
are meant for its Spring MVC controllers alone should scope them, by `assignableTypes`, `basePackages` or
`annotations`, before then. See <<controllerExceptionHandling,Declarative Controller Exception Handling>>.

[source,yaml]
.grails-app/conf/application.yml
----
grails:
    exceptionresolver:
        springHandlers: true
----

Spring Framework 7.1 adds `ProblemDetailsConfigurer.renderUnhandledExceptions`, which renders any exception no exception
handler method handles as a problem. Turned on in a `WebMvcConfigurer`, it applies to Grails actions whatever
`grails.exceptionresolver.springHandlers` says, and answers every exception, a browser's included, ahead of the Grails
exception resolver, so `"500"` URL mappings no longer apply. Set `grails.exceptionresolver.problemDetails: true` instead,
which writes the same problems and leaves the error page to the clients that prefer HTML. See
<<controllerExceptionHandling,Declarative Controller Exception Handling>>.

==== 18. Actions Can Return Spring MVC Responses

An action that returns a `ResponseEntity` or another `HttpEntity`, a `ProblemDetail`, an `ErrorResponse`,
`HttpHeaders`, a `StreamingResponseBody` or a `ResponseBodyEmitter` has it written as Spring MVC writes what a handler
method returns, whatever the settings, where Grails 8 did not write it. An action that returns `null`, or that renders
the response itself with `render`, `respond` or `redirect`, or forwards the request, is unaffected.

Set `grails.controllers.responseBody: true` to have Spring MVC write the value of an action annotated `@ResponseBody`,
or of an action of a controller annotated so, directly or with an annotation such as `@RestController`, as the body of
the response, as it writes the value of a controller method annotated so, where Grails 8 ignored the annotation and
rendered the action's view for a model. Grails 10 makes it the default, so an application that annotates actions or
controllers so to no effect should remove the annotation before then, or the model of such an action is written in
place of its view, before an interceptor's `after` runs, which then sees no model. See
<<springResponses,Returning Spring MVC Responses>>.

[source,yaml]
.grails-app/conf/application.yml
----
grails:
    controllers:
        responseBody: true
----

==== 19. Generated GORM Identity and Version Properties Stay Within Domain Classes

Grails 9 no longer adds generated `id` and `version` properties to a non-domain superclass of a domain class.
Previously, these properties could be added to a shared abstract base class, causing command objects extending that same base class to inherit persistence properties and fail validation for `id` and `version`.
Generated properties now remain within the domain-class hierarchy. Domain subclasses still inherit them from domain superclasses, and explicitly declared `id` and `version` properties on a superclass are still inherited normally.

This affects any plain base class compiled alongside a domain subclass, even if the base is not shared with a command object.
Review the following compatibility changes before upgrading:

* *Statically compiled base-class methods:* A plain base annotated with `@CompileStatic` can no longer refer to generated `id` or `version` as its own properties. For example, an `isNew()` method whose body is `id == null` could compile in Grails 8 when the fields were generated on the base, but now fails with `[Static type checking] - The variable [id] is undeclared.` Move persistence-dependent methods to the domain class, or give the base an explicit property or accessor contract implemented by its subclasses. A dynamically compiled base method can still resolve these properties at runtime when invoked on a domain instance; this does not make them available on plain instances or command objects.
* *String representation and equality:* `@ToString` and `@EqualsAndHashCode` on a plain base no longer have generated `id` and `version` among that base's declared properties. Review any explicit property lists and any hand-written `equals` or `hashCode` implementation that assumes these fields are declared on the base. Move persistence-dependent behavior to the domain class or adapt it to an explicit contract. Dynamic property access on a domain instance can still resolve inherited or subclass properties, but the base itself no longer declares the generated fields.
* *Stale compiled classes:* A previously compiled base `.class` can retain `id` and `version` until it is rebuilt. An incremental build can therefore hide the new behavior or leave subclasses inheriting stale fields. Clean and rebuild the application and any affected plugins.

When upgrading an affected application:

* Keep a superclass shared by domain classes and command objects in `src/main/groovy`, outside `grails-app/domain`, and do not annotate it as an entity.
* Remove constraints or other workarounds on command objects that existed only to accommodate the accidentally inherited `id` and `version` properties.
* Update code that relied on a non-domain superclass having generated persistence properties to access them through a domain class instead. If non-domain classes genuinely need these properties, declare them explicitly; such declarations remain inherited by all subclasses.
* Perform a clean build of the application and any affected plugins to remove previously compiled classes containing the generated properties:

[,console]
----
./gradlew clean build
----

See xref:theWebLayer#commandObjects[Command Objects] for a trait-based alternative to sharing a non-domain superclass with a domain class.

==== 20. RxGORM Runs on RxJava 3

RxGORM, the reactive variant of GORM in `org.apache.grails.data:grails-datamapping-rx`, is built on RxJava 3 instead of RxJava 1.
Its dependency is now `io.reactivex.rxjava3:rxjava`, and the RxJava 1 artifact `io.reactivex:rxjava` is no longer on the classpath of an application that only uses RxGORM.
Every RxGORM API that returned `rx.Observable` returns `io.reactivex.rxjava3.core.Observable`, and an `@RxSchedule` service method that returned `rx.Single` returns `io.reactivex.rxjava3.core.Single`.

Update the imports of every class that works with RxGORM results:

[cols="1,1",options="header"]
|===
| RxJava 1 | RxJava 3

| `rx.Observable` | `io.reactivex.rxjava3.core.Observable`
| `rx.Single` | `io.reactivex.rxjava3.core.Single`
| `rx.Subscriber` | `io.reactivex.rxjava3.core.Observer`
| `rx.Subscription` | `io.reactivex.rxjava3.disposables.Disposable`
| `rx.Scheduler`, `rx.schedulers.Schedulers` | `io.reactivex.rxjava3.core.Scheduler`, `io.reactivex.rxjava3.schedulers.Schedulers`
| `rx.functions.Func1` | `io.reactivex.rxjava3.functions.Function`
|===

The blocking helpers that tests and scripts use moved onto the `Observable` and `Single` types themselves:

[cols="1,1",options="header"]
|===
| RxJava 1 | RxJava 3

| `observable.toBlocking().first()` | `observable.blockingFirst()`
| `observable.toBlocking().single()` | `observable.blockingSingle()`
| `observable.toList().toBlocking().single()` | `observable.toList().blockingGet()`
| `single.toBlocking().value()` | `single.blockingGet()`
|===

`Observable.toList()` returns a `Single<List<T>>` in RxJava 3.
The RxGORM methods that emit a list, such as the static `list()`, `toList()` and `list()` on a `DetachedCriteria`, and `toListObservable()` on a lazy association, still return an `Observable<List<T>>`, so code that subscribes to them is unchanged.
`findAll()` on a `DetachedCriteria` returns an `Observable<T>`, so `findAll().toList()` is RxJava's own `toList()` and gives a `Single<List<T>>`.

Subscribing with a closure, for example `Book.get(id).subscribe { Book book -> ... }`, is unchanged.
A class that subscribes with a full subscriber implements `io.reactivex.rxjava3.core.Observer` instead of `rx.Subscriber`: it gains `onSubscribe(Disposable)`, which receives the handle that cancels the subscription, and `onCompleted()` is named `onComplete()`.
`DetachedCriteria`, `ObservableProxy` and the lazy association collections implement `io.reactivex.rxjava3.core.ObservableSource`, so their `subscribe(Observer)` method returns `void` rather than a `Subscription`; they can be passed anywhere RxJava 3 accepts an `ObservableSource`, such as `Observable.wrap(..)` or `concatWith(..)`.

RxJava 3 does not allow `null` to be emitted.
An RxGORM operation that has no result completes without emitting, as queries already did; for example `save()` and `insert()` complete empty, instead of emitting `null`, when the datastore reports no identifier for the instance.
An `@RxSchedule` service method that returns a `Single` and produces no result now signals a `java.util.NoSuchElementException`, and one that returns an `Observable` completes empty.
Replace a test that compares `toBlocking().first()` with `null` by one that expects `blockingFirst()` to throw `NoSuchElementException`, or use `firstElement().blockingGet()`, which returns `null` for an empty result.

A datastore implementation of RxGORM built for Grails 8 or earlier, such as the RxGORM for MongoDB plugin, is compiled against RxJava 1 and must be rebuilt against this release before it can be used.
The `RxEntity` domain model has had no datastore implementation for several releases and its removal is under discussion for Grails 9, so an application that implements `RxEntity` should plan to move to `GormEntity` with the RxJava data services, which work on every GORM datastore. The import and blocking-call changes above apply to both.
The `rx-mongodb` profile feature is removed, because the `org.grails.plugins:rx-mongodb` plugin it added has had no release since GORM 6.1 and has never been published to Maven Central, so an application generated with it could not resolve its dependencies.

==== 21. RxJava 1 and RxJava 2 Async and Events Modules Are Deprecated

The RxJava 1 and RxJava 2 implementations of the Grails promise and event bus APIs, `grails-async-rxjava`, `grails-async-rxjava2`, `grails-events-rxjava` and `grails-events-rxjava2`, are deprecated for removal.
They keep working in Grails 9 and log a warning when their promise factory or event bus is created.
Replace either dependency with the RxJava 3 module, `grails-async-rxjava3` or `grails-events-rxjava3`; the `Promise` and `EventBus` APIs an application uses are the same.
See <<asyncPromises,Promises>> and <<events,Events>>.
`grails project health` reports these modules, and `io.reactivex:rxjava` and `io.reactivex.rxjava2:rxjava`, as `deprecated-dependency.rxjava`.

`grails-async-rxjava3` carries a `null` value as the RxJava 1 factory and every other promise factory do: `createPromise()` and `createPromise(Class)` give a promise whose `get()` returns `null`, a task that returns `null` resolves to `null`, and a `null` value keeps its place in the list that `onComplete`, `onError` and `waitAll` deliver.
`grails-async-rxjava2` does not: there `createPromise()` and `onComplete` over a list holding a bound promise of `null` fail with a `NullPointerException`, and a task that returns `null` resolves to the `java.lang.Void` class.

==== 22. Spring Boot Registers the Character Encoding Filter

Grails no longer registers a character encoding filter of its own. It used to, and Spring Boot's backed off, so `spring.servlet.encoding` had no effect in a Grails application. Spring Boot's filter now decodes requests: it runs at `Ordered.HIGHEST_PRECEDENCE`, ahead of every other filter, and `spring.servlet.encoding` configures it.

* The request encoding is now overridden by default, as in any Spring Boot application, so a request that declares a charset of its own is still decoded as UTF-8: its parameters, a body read through `getReader()`, `request.JSON` and `request.XML`, and a JSON or XML body bound to a command object or domain class. The parameters of a PUT, PATCH, DELETE or QUERY form are the exception, as in Grails 8: the `FormContentFilter` that parses them decodes them with the declared charset, forced or not. To keep the charset a request declares, as Grails 8 did, set `spring.servlet.encoding.force-request: false`.
* Grails 8.1 already registers its encoding filter at `Ordered.HIGHEST_PRECEDENCE`, so an application coming from 8.1 sees no change in where the encoding filter runs. In an application coming from 8.0, filters ordered between `Ordered.HIGHEST_PRECEDENCE + 1` and -181, which used to run before Grails' encoding filter, now run after Spring Boot's, with the request encoding set, as section 5 of <<upgrading81x,Upgrading from Grails 8.0 to Grails 8.1>> describes. asset-pipeline's filter at -190 is one: in a packaged application (a WAR or an executable jar) it copies the request's encoding to the precompiled assets it serves, so every asset response now declares a charset, for example `text/css;charset=UTF-8`, and browsers use it for stylesheets and scripts instead of detecting their encoding. A filter among them that reads a request body sent without a charset through `getReader()` now decodes it as UTF-8 instead of ISO-8859-1.
* `grails.filter.encoding` and `grails.filter.forceEncoding` are deprecated. Grails 9 translates them into `spring.servlet.encoding.charset` and `spring.servlet.encoding.force` and logs a warning, and a `spring.servlet.encoding` setting of the application wins over them. Use the Spring Boot properties instead.
* `GrailsFilters.CHARACTER_ENCODING_FILTER` is deprecated, and its order is now `Ordered.HIGHEST_PRECEDENCE`, the order of Spring Boot's encoding filter, where Grails 8.0 had -180. A filter ordered at `GrailsFilters.CHARACTER_ENCODING_FILTER.order + 1` therefore runs right after the encoding filter, and now also ahead of `FormContentFilter` and of Grails' security headers filter at `GrailsFilters.FIRST`: it no longer sees the parameters of a PUT, PATCH, DELETE or QUERY form, and a response it sends without continuing the chain gets no security headers. Order it at `Ordered.HIGHEST_PRECEDENCE + 1` instead, or at `GrailsFilters.ASSET_PIPELINE_FILTER.order + 1` to keep the place it had in Grails 8.0.
* `spring.servlet.encoding.enabled: false` turns the encoding filter off.
* The CAS plugin's single sign-out filter, which reads a parameter of every POST, is registered right after the encoding filter.
* A filter of your own that reads request parameters needs a later order than `Ordered.HIGHEST_PRECEDENCE`, or form input reaches controllers decoded as ISO-8859-1. One registered at exactly `Ordered.HIGHEST_PRECEDENCE` through a `FilterRegistrationBean` runs before the encoding filter.

==== 23. A Configuration Key Below a Value That Is Not a Map Is Absent

In Grails 8, `getProperty` on `grailsApplication.config` answered a dotted key that runs past a value that is not a map with that value: `server.url.port` when `server.url` is a string, `server.ports.0` when `server.ports` is a list, or `grails.gorm.default.constraints.nullable` when `grails.gorm.default.constraints` is a closure from `application.groovy`. `containsProperty` of such a key was `true`. In Grails 9 the key is absent: `getProperty` returns `null` or the default, `containsProperty` returns `false`, and `navigate` answers `null`.

Below a list, a whole-number segment names an element instead, as Spring Boot reads it, and so does an index after the name of the list, whether the list comes from `application.yml` or from `application.groovy`:

[source,groovy]
----
// server.ports: [8080, 8443]
config.getProperty('server.ports.0')      // Grails 8: [8080, 8443], Grails 9: 8080
config.getProperty('server.ports[1]')     // 8443
config.navigate('server', 'ports', '0')   // Grails 8: [8080, 8443], Grails 9: 8080
config.getProperty('server.ports.2')      // Grails 8: [8080, 8443], Grails 9: null
----

A list of maps reads into its elements, as `app.rows.0.name`. An index past the end of the list, a number with a leading zero such as `01`, or any other segment after it, is absent. A map whose keys are numbers, such as `codes: {'0': zero}`, reads as before.

A typed read with a default changes with nothing to point at it, because the default takes over. With the parent set to a boolean as a shorthand for its block:

[source,groovy]
----
// x.y: false
config.getProperty('x.y.enabled', Boolean, true)   // Grails 8: false, Grails 9: true
----

A property source of lower precedence that sets the deeper key now answers it. With `a.b: x` in one property source and `a.b.c: y` in a source of lower precedence, `getProperty('a.b.c')` answers `y` where Grails 8 answered `x`, as a Spring `Environment` over the same sources does, and `containsProperty('a.b.c')` stays `true`. `navigate('a', 'b', 'c')` answers `null`.

===== Required Actions

* Code that reads a child of a string or a closure and relied on being answered with the parent reads the parent instead.
* Code that read a whole list through a key ending in a whole number, such as `server.ports.0`, now gets the element; it reads the list as `server.ports`.
* A typed read with a default below such a value, such as `getProperty('x.y.enabled', Boolean, true)` when `x.y` is `false`, reads the parent, or the configuration sets the deeper key.

==== 24. The Spring Security User Cache Stores Copies

With `cacheUsers` enabled, the Spring Security plugin's user cache now stores users by value, so each lookup gets its own copy, made by serializing the user. Grails 8 stored the instance itself. The authentication manager erases the password of the user it signs in, and it erased the cached instance too: the next sign-in missed the cache and loaded the user again. A copy is erased instead, so the cached user keeps its password and the user kept in the session holds none. In a native image the plugin registers its own user classes for this. A user class or id type of your own needs serialization metadata, which `traceNativeMetadata` records when the login form is listed in `forms`.

===== Required Actions

* A user class of your own is serialized, as `UserDetails` is `Serializable`. A field that cannot be serialized, such as a reference to a domain instance, makes the user uncached: it is loaded on every sign-in, and a warning is logged. Mark such a field `transient`, or hold its id instead.
* Code that changed a user it read from `userCache` and expected the cache to see the change puts the user back with `userCache.putUserInCache`.
* To store users by reference, as Grails 8 did, set `cacheConfig` on the `userCache` bean to a `MutableConfiguration` with `setStoreByValue(false)`.

==== 25. A Class That Is Not Multi-Tenant Keeps Its Datastore Inside a Tenant Block

With a database or a schema per tenant, a domain class that does not implement `MultiTenant` now stays on its own datastore inside a block that binds a tenant, such as `Tenants.withId('acme') { }`, as it does outside one. Only the classes that implement `MultiTenant` follow the tenant. This is what Grails 7 did and what the multi-tenancy guide describes; Grails 8.0 changed it, so an application upgrading from Grails 7 sees no change.

In Grails 8, with GORM for MongoDB and the in-memory datastore of unit tests, every operation on such a class inside the block reached the tenant's database instead: `save`, `get`, `list`, `count`, `where` queries, data service methods, `withSession` and `GormEnhancer.findDatastore`. With GORM for Hibernate, `save`, `get`, `list` and `count` already used the default database, while `where` queries and data service methods did not work, because the tenant's session factory does not map the class; they now use the default database too.

Writes of such a class inside the block go to the default datastore, so they run in a transaction of that datastore:

* A data service of such a class runs its transactions in its own datastore, not the tenant's.
* A transaction of the class's own datastore begun inside the tenant's transaction, such as a `withTransaction` or `withNewTransaction` block of the class or a method of its data service, is independent of the tenant's transaction. What it saves is written when it commits, and stays when the tenant's transaction then rolls back.
* A write of such a class inside the tenant's transaction but outside a transaction of its own datastore, such as a `save()` in a method annotated `@Transactional` that runs in the tenant's transaction, now fails with an `IllegalTransactionStateException`. In Grails 8 the tenant's transaction wrote it to the tenant's database. The tenant's transaction cannot commit or roll back a write to another datastore, so the write would otherwise be lost, or written although the tenant's transaction rolled back. This applies to `save`, `insert`, `delete`, `saveAll` and `deleteAll` without `flush: true`, with GORM for MongoDB and the in-memory datastore of unit tests. With GORM for Hibernate, such a save already failed in Grails 8 and still does.

===== Required Actions

For most applications **no changes are required**.

Move a write of such a class that runs inside a tenant's transaction into a transaction of the class's own datastore: call its data service, or wrap the write in the class's `withTransaction { }` block. A save with `flush: true` also works: it writes at once, and the write stays when the tenant's transaction rolls back.

With GORM for MongoDB, a class that is not multi-tenant and was saved inside a tenant block in Grails 8 has its documents in that tenant's database. Grails 9 reads the class from the default database only, so `list`, `get`, `count` and queries no longer find those documents, although they are still in the tenant's database. Decide what the class is for before upgrading:

* When each tenant should have its own instances, implement `MultiTenant` on the class, which then reads and writes the tenant's database again. Without it, every tenant reads and changes the same instances, in the default database.
* A class that a multi-tenant class references, such as a `Country` of a multi-tenant `Book`, is loaded through the tenant's session, from the tenant's database, so it has to implement `MultiTenant` as well, even when it holds shared data.
* When the instances are shared by every tenant and no multi-tenant class references them, move the documents from the tenants' databases into the default database.

Data services choose their transaction manager in code generated at compile time, so a data service compiled against an earlier release keeps following the tenant until it is compiled again.

==== 26. Unit Tests Run Domain Class Events for Every Data Source and Tenant

In a unit test that implements `DataTest` or `DomainUnitTest`, a save through a data source other than the default one, as `book.secondary.save()` makes, and a save for a tenant with a database or a schema of its own, now run the domain class's events, such as `beforeInsert`, and set its `dateCreated` and `lastUpdated` properties, as they do in the application. In Grails 8 they ran neither. Unit tests still do not set the `@CreatedBy` and `@LastModifiedBy` properties, on any data source, even when the test defines an `AuditorAware` bean, as in Grails 8: the in-memory datastore is not given the application context, so note 28 does not apply to them.

===== Required Actions

* A test that expected such a save to keep the `dateCreated` and `lastUpdated` it was given saves inside a `withoutTimestamps { }` block of that data source's listener, such as `Book.secondary.autoTimestampEventListener`.
* A test that expected a domain class event not to run on such a save expects what the event does.
* The in-memory datastore of unit tests now follows `grails.gorm.events.autoTimestampInsertOverwrite` and `grails.gorm.autoTimestampCacheAnnotations` on every data source, the default one included, as the application does. In an application whose configuration sets `autoTimestampInsertOverwrite: false`, a unit test that expected a save to overwrite the `dateCreated` or `lastUpdated` it was given expects them kept.

==== 27. A Domain Class Has an `autoTimestampEventListener` Property

Every domain class now has a static `autoTimestampEventListener` property, the listener that sets its timestamp and auditor properties (see the Events and Auto Timestamping section of the GORM for link:{hibernate7Guide}index.html#eventsAutoTimestamping[Hibernate 7] guide). A domain class that declares a property of that name of another type no longer compiles: the compiler reports that the return type of its `getAutoTimestampEventListener()` is incompatible with the one in `GormEntity`. A property of that name typed `AutoTimestampEventListener`, such as an injected bean, compiles but hides the static property, so `Book.autoTimestampEventListener` throws `MissingPropertyException`.

===== Required Actions

* Rename a property of a domain class named `autoTimestampEventListener`. Code that used an injected `autoTimestampEventListener` bean in a domain class reads `Book.autoTimestampEventListener` instead, which is the listener of the data source the class's saves go to.

==== 28. Every Data Source Sets the Auditor Properties and Follows the Auto-Timestamp Settings

In an application with several data sources, or with a database or a schema per tenant, a save through a data source other than the default one:

* sets the `@CreatedBy` and `@LastModifiedBy` properties from the application's `AuditorAware`. In Grails 8 only a save through the default data source set them.
* follows `grails.gorm.events.autoTimestampInsertOverwrite` and `grails.gorm.autoTimestampCacheAnnotations`. In Grails 8 it overwrote a `dateCreated` or `lastUpdated` that an instance was saved with, whatever `autoTimestampInsertOverwrite` said.
* with GORM for Neo4j, runs the domain class's events, such as `beforeInsert`, and sets `dateCreated` and `lastUpdated`. In Grails 8 a save through another Neo4j connection ran neither.

===== Required Actions

For most applications **no changes are required**. Check the domain classes saved through a data source other than the default one whose auditor properties, given timestamps or, with Neo4j, events were expected to be left alone.

==== 29. JLine 4

Grails 9 manages JLine 4 (`org.jline:jline`), the line Groovy 6's `groovysh` is built on, in place of JLine 3. The link:{versionsRef}Grails%20BOM.html[Grails BOM dependency table] has the exact version. JLine is the terminal library behind the interactive mode of the `grails` command line and behind `grails shell`, and behind `GrailsConsole`, which application and plugin commands write to. The line reader, terminal and completer APIs keep their `org.jline` packages.

===== Required Actions

* Recompile code of your own that uses JLine, such as an `org.jline.reader.Completer` for a command, against JLine 4. JLine 4 removed APIs that JLine 3 had deprecated, so code that uses them no longer compiles. For example, use `org.jline.builtins.Completers.FileNameCompleter` in place of `org.jline.reader.impl.completer.FileNameCompleter`, and `Terminal.inputEncoding()` and `outputEncoding()` in place of `stdinEncoding()`, `stdoutEncoding()` and `stderrEncoding()`. `TerminalBuilder.codepage(int)` and the `TerminalBuilder.PROP_JNA` and `PROP_JANSI` constants are gone too.
* JLine 4 has no JNA or Jansi terminal provider. Remove a dependency on `org.jline:jline-terminal-jna` or `org.jline:jline-terminal-jansi`: neither has a JLine 4 version, and JLine finds the terminal through its remaining providers. `grails project health` reports such a dependency as `removed-dependency.jline`.

picocli's `info.picocli:picocli-shell-jline3` runs on JLine 4, but picocli has no JLine 4 version of it, and its `PicocliCommands` implements `org.jline.console.CommandRegistry`, which JLine 4 deprecates. JLine's own picocli bridge, `org.jline:jline-picocli`, is built for JLine 4. To move to it, use it at the JLine version the Grails BOM manages.

==== 30. Command Lines of Application Commands

The command line parser of the `grails` command line tool and of `runCommand`, which reads the command line of an application or plugin command, reads two kinds of input differently:

* An empty argument after an option without a value is that option's value, an empty one. `--name "" value` used to give the option `name` the value `value`; now `name` is empty, and `value` is an argument.
* The text inside a pair of double quotes is trimmed, as an argument without quotes always was. `" a "` used to reach the command as ` a `, and now reaches it as `a`.

It also reads three kinds of input it used to fail on or cut short:

* `--name=`, an option with an empty value, threw an `ArrayIndexOutOfBoundsException`, and is now the option `name` with an empty value.
* An argument that is a single `"` threw a `StringIndexOutOfBoundsException`, and is now passed on as it is.
* The value of an option is everything after the first `=`: `--filter=status=active` used to give `status`, and now gives `status=active`.

===== Required Actions

* Check commands that read an option followed by an empty argument, or arguments with spaces inside quotes, and expect the values above.
* Remove workarounds for the three failures, such as passing `--filter=status%3Dactive` and decoding it in the command.

==== 31. A GSP Error Names the Line of the Page It Is On

The line an error in a GSP names was wrong for many pages, and is now the line of the page:

* An expression, a tag or a scriptlet on the last line of a page that does not end with a line break was reported on line 1. It is reported on the last line.
* What follows a `<%-- --%>` or `%{-- --}%` comment could be reported on an earlier line than it is on, also after a comment of one line, and by more the longer the comments before it are. It is reported where it is.
* After an expression, a scriptlet or a tag attribute that spans several lines, an error the compiler finds and the line a stack trace is mapped to were later than the line they are on, by the line breaks inside it. They are on their line. An error inside a scriptlet or an expression of several lines names the line it starts on.
* In a page whose generated class has more than 1,000 lines, an error could be reported on a line that is not its own, and an error near the end of such a page on line 1. They are right for a page of any length.
* What is only found where the page ends, such as a tag or a block that is never closed, was reported on line 1 for a page that ends with a line break. It is reported on the last line of the page.
* An expression that is never closed, `${` without its `}`, was reported on the line the text in front of it starts on. It is reported on the line the expression starts on.

This is the line in the message of a `GroovyPagesException` and of a `GrailsTagException` (`on line [12]`, `[/book/show.gsp:12]`) and what their `getLineNumber()` returns. What a page renders is not changed, with the one exception below. A precompiled page carries these lines, as arguments in its class and in the table of lines beside it, so the compiled pages of an application differ from those of Grails 8 for the same source; they are compiled again when the application is built.

A line of a page ends with a line feed. A carriage return by itself ends no line of a page, so a page that has carriage returns and no line feeds is one line, and every error in it is on line 1. The lines of the class a page is compiled to are counted as the Groovy compiler on the class path counts them, which differs between versions of Groovy for a carriage return by itself; the line of the page that is named does not depend on it.

The exception: an escaped expression, `\${`, that came 63,998 or 63,999 characters after the last expression, scriptlet or tag in front of it, or that many and a multiple of 64,000 more, was written with its backslash, as `\${`. It is written as `${`, as it is anywhere else.

===== Required Actions

None for an application. A test that asserts the line of a GSP error asserts the line of the page instead; there is no setting that brings the earlier numbers back. Not changed: scanning a page with very many comments is still slow, since each comment that is taken out copies the page.

==== 32. Compiled Commands Carry a Descriptor, and Command Tasks Take Arguments One at a Time

NOTE: Notes 32 to 39 and 41 to 55 are about the command line. Grails 9 has one `grails` command, which is not the Grails shell of Grails 8, and it has no profiles. To translate a command line of Grails 8, start at <<cliMappingGrails8,note 55>>: its tables have every command of the Grails shell and of its profiles, every command and option of the Grails Forge command line, and every command and script of the plugins of the framework, each with what it is in Grails 9, and the rules for the environment, the options and the exit codes. The other notes say why, and what else differs.

Compiling a command, in `grails-app/commands` of an application or in `src/cli/groovy` of a plugin, now also writes the file `META-INF/grails-commands/<class name>.json` into the compiled classes, beside `META-INF/grails-cli.factories`. It holds the name and the description of the command, and it goes wherever the compiled classes go, as the registration already does: into the jar of a plugin's `-cli` companion, and for commands under `grails-app/commands` into the archive of the application or plugin. The new `grailsCommandCatalog` task lists the commands of a project from these files, into `.grails/cache/command-catalog.json` in the directory of the project, without loading a class. See xref:commandLine#creatingCustomCommands[Creating Custom Commands].

`runCommand` and the task of each command take the new options `--arg=<argument>`, once for each argument, and `--args-file=<file>`. `--args-file` needs the `grails-console` of this version, which the Grails Gradle plugin adds to `grailsCli` by default; with an older one the task fails saying that the application class `--grails-args-file=...` was not found. `-Pargs="..."` works as it did, including how it is split at spaces and quotes.

===== Required Actions

None for the commands: they run as before with or without the descriptor. To build an archive without the files, exclude them where the archive is put together, for example `tasks.named('bootJar') { exclude 'META-INF/grails-commands/**' }`; the commands are then listed by the names their class names give. A build that has a task of its own named `grailsCommandCatalog` gives it another name, because the Grails Gradle plugin now registers one: a task registered after the plugin is applied fails the build as a duplicate, and one registered before it is kept, with a warning that the catalog is not written.

==== 33. The `grails` Command Runs Script Commands Through the Build

The Grails Gradle plugin registers a task `runScriptCommand` in every application and plugin project. It compiles and runs a script command, `src/main/scripts/<name>.groovy` of the project or `META-INF/commands/<name>.groovy` of a plugin, in a JVM of the build. The `grails` command lists the scripts of a project as commands by the names of their files and runs one through that task; it does not compile or evaluate a script itself. See xref:commandLine#creatingCustomScripts[Creating Custom Scripts].

This is the way a script of your own, and a script of a plugin that is not part of the framework, is run. The plugins of the framework have no scripts any more: what were scripts of Spring Security, Quartz, Geb, scaffolding and database migration are commands, as notes 34, 41 and 54 describe.

Script commands are deprecated, and kept through Grails 9 for the projects and plugins that have them. The scripts a project has in `src/main/scripts` still run, and `grails` warns that they are deprecated when it runs one; the command line creates no new one. `grails create-script NAME`, which wrote `src/main/scripts/<name>.groovy`, is removed (note 42): `grails create-script data-import` ends with exit code 2 and the line `create-script wrote a script command into src/main/scripts. Script commands are deprecated, and the scripts a project has still run: a new command is a class of the application. Type: grails create-command NAME`, and writes nothing. `grails create-command NAME` writes a command of the application, `grails-app/commands/<package>/<Name>Command.groovy`, which runs with the application started around it and is listed by `grails help` with its description. A template of the project at `src/main/templates/artifacts/Script.groovy` is read by no command of `grails` any more.

The `grails` command and the Grails wrapper do not start the Grails shell any more: see note 37, "The `grails` Command Is One Command Line, and the Grails Wrapper Is Replaced".

===== Required Actions

None for a script that only uses what the guide documents for scripts: `description`, `args`, `flag`, `model`, `render`, `template`, `templates`, the methods for working with files (`copy { from ...; into ... }` among them), the console, `ant`, the events (`on`, `before`, `after`, `notify`) and calling another script.

Replace `grails create-script NAME` with `grails create-command NAME` in scripts, continuous integration jobs and documentation of your own, and write the new command in the class it writes: its `handle()` method runs with the application and its classes. To create a new script all the same, write `src/main/scripts/<name>.groovy` by hand, with the name in lower case and with hyphens: it is a command of the project as a script written by `create-script` was, and deprecated.

Where a script is run with `grails` or with `./gradlew runScriptCommand`:

* `gradle.<task>()` is not available. Run the tasks from the command line before or after the script, or make the work a Gradle task.
* A method that names a command that is no script, such as `testApp()` or `runApp()`, fails. Run those commands from the command line.
* A script that imports a class of `org.grails.cli`, such as a completer for its `description`, is not compiled. Remove the import and the `completer` line.
* `profile`, `spring`, `isServerAvailable()` and `waitForStartup()` are not available.
* A listener that `before` or `after` registers, or that `on('<name>Start')` or `on('<name>End')` registers, is given the context of the script it hears, as in the Grails shell. That context is now an `org.apache.grails.core.cli.ExecutionContext`: it has `commandLine` and `baseDir` (and `classesDir` and `targetDir`), and not `console`, `config`, `navigateConfig(...)`, `navigateConfigForType(...)`, `cancel()` or `addCancelledListener(...)`, which the context of the shell had. A listener uses `console`, `config` and `navigateConfig(...)` of the script it is written in.
* The description of a script is not shown by `help`. A command written as a class in `grails-app/commands` is listed with its description, and script commands are deprecated in its favour.
* A script is not run with the classes of the application on its class path, as it never was.
* `-Dgrails.env=NAME` after the name of a script does not set the environment the script runs in: the arguments of a script are data, and the environment is that of the build (`./gradlew -Dgrails.env=NAME runScriptCommand ...`).
* What a script writes through `console` is plain lines, without colours and progress indicators.
* A script that is a link, or that is below a `src`, `src/main` or `src/main/scripts` that is a link, is not run as a script of the project.

A build that has a task of its own named `runScriptCommand` gives it another name: a task registered after the plugin is applied fails the build as a duplicate, and one registered before it is kept, with a warning that the scripts are not run by the plugin's task.

==== 34. Two Database Migration Commands Are Application Commands, and Script Commands of Other Plugins

`dbm-create-changelog` and `dbm-changelog-to-groovy` of the Database Migration plugins (Hibernate 5 and Hibernate 7) were script commands, the only two `dbm-*` commands that were. They are now application commands like the others, with the same names, arguments and options. They run with the application context, as `dbm-update` does: `./gradlew runCommand --arg=dbm-create-changelog --arg=changelog.groovy`, their own Gradle tasks `dbmCreateChangelog` and `dbmChangelogToGroovy`, or by name with `grails` (`grails dbm-create-changelog changelog.groovy`).

`dbm-changelog-to-groovy` now writes to the file it is given (it wrote to the standard output, because of how Groovy 5 reads a file that does not exist yet) and converts YAML and JSON changelogs, which failed.

No plugin of the framework has a script command any more. The scripts of the scaffolding plugin are removed in favour of its commands (note 41), and those of the Spring Security plugins, of Quartz and of Geb are commands or are removed (note 54): none of them is run with `runScriptCommand`.

A script command of another plugin, one of your own or of a third party that has `META-INF/commands/<name>.groovy` in its jar, runs where the build of a project runs scripts: `./gradlew runScriptCommand --arg=<name> --arg=<argument>`, with one `--arg` for each argument. `grails help` does not list the scripts of plugins, and `grails <name>` is no command for one: `grails gradle runScriptCommand --arg=<name> ...` runs the same task from any directory of the project.

===== Required Actions

None for the commands. Code that used the classes `DbmCreateChangelog`, `DbmChangelogToGroovy` or the trait `ScriptDatabaseMigrationCommand` of a database migration `-cli` artifact uses `DbmCreateChangelogCommand` and `DbmChangelogToGroovyCommand`; those artifacts no longer depend on `grails-shell-cli`. A plugin of your own whose script names a completer of the Grails shell in its `description` removes the `import` and the `completer` line: the classes of `org.grails.cli` are not on the class path of a script, a script that imports one is not compiled, and nothing completes the arguments of a script, since the build does not evaluate a description (see note 33).

[[upgradingNoProfileDependency]]
==== 35. A Generated Application Has No Profile Dependency and No `grails-forge-cli.yml`

An application that Grails Forge generates (`create-app` and the other `create-` commands of `grails`, and the Grails Forge website) no longer has two things that the Grails shell and its profiles needed:

* *The `profile` dependency.* `build.gradle` has no `profile "org.apache.grails.profiles:<type>"` line. Nothing of the build or of the running application used that dependency; it told the Grails shell which profile's commands the project has. The commands of `grails` come with the command line and with the plugins of the application.
* *`grails-forge-cli.yml`.* The file at the root of the project is not written. The `.grails` directory is the record of how the application was generated: `.grails/project.yml` has the application type, the default package, the options and the features that were asked for and excluded, and `.grails/forge.lock.yml` has every feature of the application, and for a feature pack that was taken by its coordinates the version, the SHA-256 and, for an `https` address, the repository. The name of the jar file of such a pack, which `grails-forge-cli.yml` had under `featurePacks`, is not recorded any more. `feature add` changes no `grails-forge-cli.yml` either. To see what the record says, run `project show` in the project: it lists the type, the options and the features, and its last line is the `create-` command that creates the same application again; `project regenerate --output <directory>` writes the application as it was generated to another directory, and `project regenerate --diff` names the files that are not as generated.

Not changed: `grails.codegen.defaultPackage` is still written to `grails-app/conf/application.yml`, because the framework reads it when the application runs (`grails.profile` is not written any more: see note 36). Not changed either: the `grails` command still reads the `grails-forge-cli.yml` (or `grails-cli.yml`) of a project that an earlier version generated, once the project is on Grails 9; in a project whose `gradle.properties` still names an earlier version it runs `project migrate` and no other command of the project (note 45).

===== Required Actions

None for the `grails-forge-cli.yml` of an application that exists: it is left as it is. The `profile` line of its `build.gradle` has to be removed, because the build fails with it: see note 39, "The Grails Shell and the Profiles Are Not Published, and a Build Cannot Declare a Profile".

* A tool or script of your own that reads `grails-forge-cli.yml` of a newly generated application reads `.grails/project.yml` (application type, default package, options) and `.grails/forge.lock.yml` (features) instead. There is no option that writes the old file. To have one for such a tool all the same, write it yourself with the keys the tool reads; the `grails` command then warns when it does not say the same default package and features as `.grails`, and goes by `.grails`.
* Do not add the `profile` line back to a newly generated application: nothing reads it, and the build fails with it (see note 39).
* `grails project health` reports a `grails-forge-cli.yml` beside `.grails` as `leftover.earlier-record`, and as `leftover.earlier-record-differs` where it does not name the same default package and features.
* When the files of `.grails` cannot be used, because one was changed by hand or is missing, the `create-*` code generation commands of a newly generated application are not there until the directory is as it was: restore it from version control. An application that has a `grails-forge-cli.yml` goes by that file then, as before.
* A feature pack of your own that writes a file named `grails-forge-cli.yml` or `grails-cli.yml` to the root of the application is refused when the application is generated, because the command line would read that file as the record of a project. Give the file another name.
* An application that a snapshot of Grails 9 generated before this change cannot have a feature added with `feature add` by a later build of the same version: the command says that the application cannot be generated again as it was and names `build.gradle`. Add the dependencies and the configuration of the feature by hand, or generate the application again.

[[upgradingNoProfileAtRunTime]]
==== 36. An Application Has No Profile at Run Time: `grails.profile` Is Not Read

Until Grails 9 the framework read the `grails.profile` key of the configuration while an application started and added its value to the active Spring profiles, and `web` when the key was not there. A running application therefore reported a Spring profile named after the profile it was created from (`web`, `rest-api`, `plugin`, `web-plugin`, `rest-api-plugin`, or a profile of your own), whether or not anything asked for one.

The profile was added late: after the configuration files had been read, after the conditions of the configuration classes had been evaluated, and after the plugins had registered their beans. In Grails 8 it therefore did not select an `application-web.yml` file or a `spring.config.activate.on-profile: web` document, did not register a `@Profile('web')` bean of the application, and was not there for a plugin that asked the environment while it registered its beans. What it changed is the answer that code got when it asked the environment once the application was running.

In Grails 9 nothing reads the key:

* *No Spring profile is active by itself.* The active Spring profiles are the ones that were asked for, with `spring.profiles.active` or `spring.profiles.include` in whatever way Spring Boot takes them, and the name of the Grails environment (`development`, `test`, `production`, or one of your own), as before. `environment.activeProfiles` of a running application no longer has `web`, `rest-api` or another profile name at its end, and `environment.acceptsProfiles(Profiles.of('web'))` is `false` unless `web` was asked for. An application with the key and one without it behave the same.
* *The key is configuration like any other.* It may stay in `application.yml` and may be deleted. Code of your own that reads it still gets the value that is written there. The configuration report (`config-report`) lists it among the other properties, without a description.
* *Generated applications do not have it.* Grails Forge does not write `grails.profile`, the welcome page has no "Profile" row, and the `welcome.app.profile` message is not in the message bundles. `grails.codegen.defaultPackage` is written as before. The type of a generated application is in `.grails/project.yml`.
* *The `profiles` property of a plugin descriptor is not read.* `def profiles = ['web']` in a plugin class was how a plugin said that it takes part only when one of the named profiles is active. Grails has not read the property since 7.1.0: a plugin is enabled whatever it declares, and that does not change. The plugins of the framework and a generated web plugin no longer declare it, and the constant `GrailsPlugin.PROFILES` is deprecated for removal.
* *`grails.config.Settings.PROFILE` is removed.*

===== Required Actions

* `grails project health` reports `grails.profile` in `application.yml` as `leftover.profile-config`. Code that asks the environment for the profile is not checked.

* *Code that asks the environment for the profile while the application runs.* Search the application and the plugins of your own for `acceptsProfiles`, `activeProfiles` and `getActiveProfiles` used with one of the profile names above: in a service, a controller, `BootStrap`, a tag library, or a bean that is created lazily or in a child context after startup. Such a check was `true` in every application of that type and is now `false`; a negated one, such as `!environment.acceptsProfiles(Profiles.of('web'))`, is now `true`. An application that had no `grails.profile` key reported `web`. Either remove the check, when what it guards belongs to the application in every case, or ask for the profile in the main document of `application.yml`:
+
[source,yaml]
----
spring:
    profiles:
        include: web
----
+
`spring.profiles.active` does the same in `application.yml`, but a value given when the application is started (`--spring.profiles.active=...`, the `SPRING_PROFILES_ACTIVE` environment variable or the system property) takes its place, where `spring.profiles.include` is added to it. A profile that is asked for this way is a real one: unlike the profile the framework added, it also registers the `@Profile('web')` beans and reads the `application-web.yml` of the application, so check that the application has none it does not want.
* *`@Profile('web')` beans, `application-web.yml`, `spring.config.activate.on-profile: web`.* Nothing to do for the upgrade: none of them was selected by the profile the framework added, and none is now. When you find one that was written in the belief that it applies to every web application, it never did: remove the condition to make it apply, or delete it.
* *A plugin of your own with `def profiles = [...]`.* Delete the line: it has had no effect since Grails 7.1.0. A plugin that should contribute beans only for some Spring profile asks the environment, which answers with the profiles that were asked for:
+
[source,groovy]
----
import org.springframework.core.env.Profiles

Closure doWithSpring() {
    boolean reporting = applicationContext.environment.acceptsProfiles(Profiles.of('reporting'))
    return { ->
        if (reporting) {
            reportScheduler(ReportScheduler)
        }
    }
}
----
+
A plugin that needs a web application to work says so with what it needs, such as `@ConditionalOnWebApplication` on its auto-configuration, not with a profile.
* *The key.* Delete `grails.profile` from `application.yml` (or `application.groovy`) when nothing of your own reads it. A page or an endpoint of your own that shows it, such as the "Profile" row of a welcome page copied from an earlier version, shows nothing for an application without the key: remove the row.
* *`Settings.PROFILE`.* Code that used the constant to read the key names the key itself, `'grails.profile'`.

[[upgradingOneCommandLine]]
==== 37. The `grails` Command Is One Command Line, and the Grails Wrapper Is Replaced

Until Grails 9 the `grails` command and the Grails wrapper (`grailsw`) started a class that chose between two command lines: the Grails shell, by default, and Grails Forge, with `-t forge`. In Grails 9 there is one command line, and `grails` starts it.

* *`-t` and `--type` are gone.* `grails -t forge create-app myapp` is `grails create-app myapp`. As the first argument the option is refused with exit code 2 and the line `grails has no option -t since Grails 9: it chose between the Grails shell and Grails Forge, and there is one command line now. Give the command without it.`; nothing is run.
* *`GRAILS_PREFERRED_SHELL` is not read.* Whatever its value, the same command line starts, and nothing is said about the variable.
* *The distribution has one command.* The `bin` directory of the binary distribution, and so an installation by SDKMAN, has `grails` and `grails.bat`. `grails-shell-cli` and `grails-forge-cli` are not there.
* *The completion script of the distribution is `bin/grails_completion`* and completes `grails` with every command of the command line; it replaces `bin/grails_forge_cli_completion`, which completed `grails-forge-cli`. In a project, `feature list` shows the features the project has, which `feature add` can add and what each replaces, and why it cannot add the others.
* *Nothing starts the Grails shell.* `grails` without a command starts the interactive console in a Grails project and shows the help elsewhere. The commands there are, in a project and outside one, are listed by `grails help`; see xref:commandLine[The Command Line].
* *Projects are not created from profiles.* `create-app` and the other `create-` commands have no `--profile` option, and `create-profile`, `list-profiles` and `profile-info` are no commands. A project is created from an application type and features, and what a profile of your own gave an application is given by a preset (`--preset`) and plugins with feature packs; see link:applicationTypes.html[Application Types, Features and Feature Packs] and, for each thing a profile had, link:applicationTypes.html#profilesReplaced[What Became of Profiles].
* *The start class moved.* The class that starts the command line is `org.apache.grails.forge.cli.GrailsCli` of the artifact `org.apache.grails.forge:grails-forge-cli`, which the `Main-Class` attribute of the manifest of the `grails-cli` jars names. `org.apache.grails.cli.DelegatingShellApplication` no longer chooses a command line and starts no Grails shell: it is the one class of the artifact `org.apache.grails:grails-cli`, the class every Grails wrapper starts, and it starts the `Main-Class` of its jar (see below). The artifact `org.apache.grails:grails-cli` no longer depends on `grails-shell-cli`; it brings `grails-forge-cli`, and so the whole command line, as a runtime dependency.
* *The Grails wrapper only downloads.* Every Grails wrapper, of Grails 7, 8 and 9, starts `org.apache.grails.cli.DelegatingShellApplication` in the `grails-cli` jar it downloads, and in Grails 9 that class starts the command line of its jar, the class its `Main-Class` names. So the wrapper of Grails 9 starts the command line of Grails 7, 8 and 9, and will not have to be replaced when the command line moves again. Before it starts the class, the wrapper of Grails 9 sets the system property `grails.wrapper.version` to its version: the command line then runs the command it was given and never replaces the files of the wrapper, which only `update-wrapper` does. The wrapper of Grails 7 and 8 sets nothing, and is replaced as described below.
* *`update-wrapper` is a command, and it replaces the wrapper of the project.* Until Grails 9 `./grailsw update-wrapper` only made the wrapper download the command line again, and nothing replaced `grailsw`, `grailsw.bat` and `grails-wrapper.jar`, the three files that are committed in the application. In Grails 9 the wrapper still downloads the command line again, and the command line then replaces the three files by those of its version: link:{commandLineRef}update-wrapper.html[update-wrapper]. `grails update-wrapper`, typed to an installed command line, does the same without the download. The command takes no arguments: `./grailsw update-wrapper COMMAND`, which ran the command after the download, is refused with exit code 2 by the wrapper of Grails 9.

*The wrapper of Grails 7 and 8 replaces itself.* Once `grailsVersion` in `gradle.properties` names a Grails 9 version, the wrapper that is committed in the application downloads the command line of that version and starts `DelegatingShellApplication` in it, as it did before. In Grails 9 that class runs `update-wrapper`, which replaces `grailsw`, `grailsw.bat` and `grails-wrapper.jar` at the root of the application by those of Grails 9 and says so in one line, names link:{commandLineRef}project-health.html[project health] in a second one, and then runs the command that was typed:

[source,console]
----
$ ./grailsw update-wrapper
Updating Grails wrapper, allowed versions to update to are [RELEASE]...
...
...Moved remotely downloaded jar to: /home/me/.grails/wrapper/9.0.0/grails-cli-9.0.0-all.jar
Updated wrapper to version: 9.0.0
The Grails wrapper of the project in /home/me/shop was that of Grails 8.1.2 and is now that of Grails 9.0.0: grailsw, grailsw.bat, grails-wrapper.jar were replaced. Commit them.
grails project health says what else the upgrade notes ask of the project, as far as its files show it.
----

The first lines are those of the download, with its progress in place of `...`. Where `grailsVersion` names a snapshot, such as `9.0.0-SNAPSHOT`, the wrapper allows every kind of release (`[RELEASE,RC,MILESTONE,SNAPSHOT]`), and says before the download that it downloads the latest snapshot (`...A Grails snapshot version has been detected. Downloading latest snapshot.`) and from which address (`... Using Snapshot URL: ...`). With `GRAILS_REPO_URL` set, a line after the first names the repository that is asked first.

* `./grailsw update-wrapper` ends after those lines, with exit code 0, and so does `./grailsw` without a command: the earlier wrapper takes `update-wrapper` from the command line before it starts the class, so the two cannot be told apart, and the run that replaces the wrapper does not start the interactive console. Type `./grailsw` again for the console.
* Any other command is run after the replacement, and the exit code is that of the command. `./grailsw test-app` in a job of continuous integration replaces the files of its checkout, runs the tests, and does the same on the next run until the three files are committed.
* A file is written beside the one it replaces and moved over it, and keeps the mode of the file it replaces, so `grailsw` can be executed by whom it could be before.
* A file that cannot be replaced is named on the standard error, with the reason and what to do by hand, and the other files are replaced: a file that is a symbolic link, which is not followed, a file that is read-only, and every file of a directory that cannot be written to. The command that was typed is run all the same; `./grailsw update-wrapper` ends with exit code 1 then.
* On Windows two of the files are in use while the wrapper runs: `grails-wrapper.jar`, which the JVM has open, and `grailsw.bat`, which the command interpreter is reading. The new ones are written beside them as `grails-wrapper.jar.new` and `grailsw.bat.new`, `grailsw.bat` is replaced by a short batch file that ends this run with the exit code of the command, and the line about the wrapper says that the wrapper completes the replacement when it is next run. The next `grailsw`, with any command, moves the two files into place before it starts Java, and is the wrapper of Grails 9. There is no step to do by hand, and the exit code is 0.
* Nothing is replaced outside a Grails project, and nothing in a project whose `gradle.properties` names Grails 7 or 8, where the command line of Grails 9 says that it works with projects of Grails 9 and later.

===== Required Actions

* *Update the Grails wrapper of the application.* An application has one when the files `grailsw`, `grailsw.bat` and `grails-wrapper.jar` are at its root.
. Set `grailsVersion` in `gradle.properties` to the Grails 9 version.
. Run `./grailsw update-wrapper` in the application, `grailsw update-wrapper` on Windows. It downloads the command line of that version, replaces the three files and names them.
. On Windows the command says that two of the files are replaced when the wrapper is next run. The next step is that run.
. Run `./grailsw --version`. It prints `Grails Version:` with the version that `grailsVersion` names, and no line about the wrapper.
. Commit the three files together with the change of `grailsVersion`. No file named `.new` is left beside them by then; do not commit one.
+
[source,console]
----
$ ./grailsw update-wrapper
$ ./grailsw --version
$ git add gradle.properties grailsw grailsw.bat grails-wrapper.jar
----
* *Where the command cannot write the files, replace them by hand.* That is the case in a checkout that is read-only and for a file that is a link. Download `apache-grails-wrapper-VERSION-bin.zip`, with the Grails 9 version in place of `VERSION`, from the https://github.com/apache/grails-core/releases[release page] and extract it, or create an application somewhere else with the `grails` command of Grails 9 (`grails create-app scratch`) and take the files from its root. Copy `grailsw`, `grailsw.bat` and `grails-wrapper.jar` over the three files at the root of the application, and on Linux and macOS make sure the script can still be executed (`chmod +x grailsw`). The wrapper of Grails 9 starts Grails 7 and 8 as well, so the copy can be made before `grailsVersion` is changed. An installed `grails` of Grails 9 writes the same three files with `grails update-wrapper` in the application, once `grailsVersion` names Grails 9.
* *Remove `-t forge`, `--type forge`, `-t shell` and `--type shell`* from scripts, continuous integration jobs, documentation of your own and run configurations that call `grails` or `grailsw`. A command that was given with `-t forge` is the same command without it. A command of the Grails shell that was given with `-t shell`, or with no option, is looked up in `grails help`; <<cliMappingGrails8,note 55>> says what each of them is now, as does the section "Commands of Earlier Versions" of xref:commandLine[The Command Line] for the ones that are gone, and notes 42 to 54 say what differs for the commands that are kept.
* *Replace `grails-forge-cli` with `grails`*, with the same arguments, wherever the command is called. `grails-shell-cli` has no command that takes its place: its commands are those of `grails` where that section has them.
* *Replace `source .../grails_forge_cli_completion`* with `source "$GRAILS_HOME/bin/grails_completion"`, in zsh after `autoload -U +X bashcompinit && bashcompinit`.
* *Remove `GRAILS_PREFERRED_SHELL`* from shell profiles and continuous integration settings. It has no effect.
* `grails project health` reports a wrapper of Grails 7 or 8 as `grails-wrapper.version`, a `.new` file left beside the wrapper as `grails-wrapper.leftover`, and `GRAILS_PREFERRED_SHELL` as `leftover.preferred-shell`. The command lines of scripts and jobs are not checked.
* *Replace `create-app NAME --profile PROFILE`* with the command of the type of application: `create-app` for `web`, `create-restapi` for `rest-api`, `create-plugin` for `plugin`, `create-web-plugin` for `web-plugin` and `create-rest-api-plugin` for `rest-api-plugin`. A REST API plugin is generated as the profile generated it, with an empty `UrlMappings` and no controller or views. `--features` now adds to the default features of the type and refuses a name that is no feature; `--exclude-features` leaves a default one out.
* *A profile of your own.* Nothing reads a profile artifact. Convert it to a _preset_ and replace `create-app NAME --profile com.acme:acme-profile:1.0.0` with the create command of the preset's type: `create-restapi NAME --preset com.acme:acme-preset:1.0.0`. A preset names one type of application, gives the options of the `create-` commands their defaults, asks for features, and adds dependencies, configuration and files from its skeleton; see xref:applicationTypes#presets[Making Applications from a Preset], which lists what converts and what is converted by hand: a skeleton file that replaces one Grails writes, a skeleton of several projects, a profile that extends another of your own, and the commands of the profile, which become classes of a plugin (xref:commandLine#creatingCustomCommands[Creating Custom Commands]). A feature that some applications need is a plugin with a feature pack, selected with `--features group:artifact:version`.
* *A tool of your own that loads the start class from a `grails-cli` jar* reads the `Main-Class` attribute of the manifest of the jar, which names the class in Grails 7, 8 and 9, or loads `org.apache.grails.forge.cli.GrailsCli` in place of `org.apache.grails.cli.DelegatingShellApplication`. `GrailsCli.main(String[])` ends the JVM with the exit code and `GrailsCli.execute(String...)` returns it. A tool that still starts `DelegatingShellApplication` in a Grails 9 jar gets what the earlier wrapper gets: in a project of Grails 9 that has a Grails wrapper, the three files of the wrapper are replaced before the command line is run. A program that calls `GrailsCli.execute` and is compiled against it declares `org.apache.grails.forge:grails-forge-cli`, which has the class; `org.apache.grails:grails-cli` has it at run time only.
* *A build of your own that depends on `org.apache.grails:grails-cli` to get the Grails shell* does not get it any more.

==== 38. `grails run <file>.groovy` Outside a Project Is Removed, and `GormCompilerAutoConfiguration` With It

Outside a project, the `run` command of the Grails shell compiled a loose Groovy script and started it as a Spring Boot application: `grails run app.groovy`. Dependencies and imports were added to such a script from the annotations it used, and `GormCompilerAutoConfiguration` of `grails-data-hibernate5-spring-boot` and `grails-data-hibernate7-spring-boot` added GORM for Hibernate and the `grails.gorm` imports to a script that had an `@Entity` class.

Grails 9 has neither. The command is removed with the shell and has no replacement: `run` is another name of `run-app` again, as it was in a project, and `grails run app.groovy` is refused with exit code 2, in a project and outside one, with the command that runs the script in an application, `grails run-script app.groovy`. The two artifacts no longer contain `org.grails.datastore.gorm.boot.compiler.GormCompilerAutoConfiguration` or the `META-INF/services/org.grails.cli.compiler.CompilerAutoConfiguration` file that registered it. `HibernateGormAutoConfiguration`, the Spring Boot auto-configuration of the same artifacts, is unchanged.

Scripts inside a project are not affected: `run-script` runs a Groovy script with the application context of the project as before, and the script commands of a project and of its plugins run through `runScriptCommand` as note 33 describes.

===== Required Actions

* *A script that was started with `grails run`.* Make it a project: create an application with the features it needs and move the code of the script into it, or run the code inside an existing application with `run-script`.
* *Code that names `GormCompilerAutoConfiguration`.* Remove it. Nothing takes its place, because nothing compiles a script outside a project.

==== 39. The Grails Shell and the Profiles Are Not Published, and a Build Cannot Declare a Profile

Grails 9 does not build the Grails shell or the profiles, so these artifacts have no Grails 9 version in any repository:

* `org.apache.grails:grails-shell-cli`
* `org.apache.grails.profiles:base`, `plugin`, `profile`, `rest-api`, `rest-api-plugin`, `web` and `web-plugin`

What goes with them:

* *The Grails BOMs manage no version for them.* A dependency on one of these artifacts without a version is not resolved. The BOMs do not manage `org.springframework.boot:spring-boot-cli` either, which they managed for the shell.
* *The Gradle plugins `org.apache.grails.gradle.grails-profile` and `org.apache.grails.gradle.grails-publish-profile` are removed.* They compiled a profile into a jar and published it, and nothing reads such a jar.
* *A `profile` dependency fails the build.* The Grails Gradle plugins used to resolve the `profile` configuration for the shell, with the `web` profile, or `web-plugin` in a plugin, when the build declared none; the `grails.profile` system property that named another default is not read. In Grails 9 the configuration only refuses what is put into it. A build that declares a dependency in it, in the `dependencies` block or with `dependencies.add('profile', ...)`, fails while it is configured, Gradle names the line of the build script, and the message is this one, with the dependency and the project of the build:

[source]
----
Grails 9 has no profiles: remove the 'profile' dependency 'org.apache.grails.profiles:web' from the build of root project 'myapp'. Nothing reads it, and the profiles are not published for Grails 9. See "The Grails Shell and the Profiles Are Not Published, and a Build Cannot Declare a Profile" in the Grails 9 upgrade notes: https://grails.apache.org/docs/latest/guide/upgrading.html
----

Nothing is downloaded for that configuration, and it cannot be resolved or used for dependencies of your own. A build without the line is not changed.

===== Required Actions

* *Remove every `profile ...` line* from the `dependencies` block of `build.gradle`, in every project of the build, and every `dependencies.add('profile', ...)` of build logic of your own. Nothing takes its place. This is also the line that note 35 says a generated application no longer has. `grails project health` reports it as `removed-dependency.profile`, a dependency on the shell or a profile as `removed-dependency.shell`, and the two plugin ids as `removed-dependency.profile-plugin`.
* *Remove dependencies on `org.apache.grails:grails-shell-cli` and on `org.apache.grails.profiles:*`*, in every configuration. Code of your own that used classes of the shell (`org.grails.cli`) has to be written without them; a command of your own is an application command or a script of the project, as notes 32 to 34 describe.
* *Give a dependency on `org.springframework.boot:spring-boot-cli` a version, or remove it.* The Grails shell was what used it.
* *A profile of your own becomes a plugin with a feature pack*: see note 37.
* *A build that applied `org.apache.grails.gradle.grails-profile` or `org.apache.grails.gradle.grails-publish-profile`* removes both plugin ids. There is nothing to apply in their place; the plugin that holds the feature pack is built and published as any other plugin.
* *Build logic of your own that named `BuildSettings.PROFILE` or `BuildSettings.PROFILE_REPOSITORIES`* (`grails.util.BuildSettings` of `grails-gradle-model`) removes the reference: the constants are removed and nothing reads the two system properties. The `GrailsClasspath` tooling model of the Grails Gradle plugin, which the shell asked for the class path of a project, is removed with its `profile` part; a subclass of `GrailsGradlePlugin`, `GrailsWebGradlePlugin` or `GrailsPluginGradlePlugin` no longer passes a `ToolingModelBuilderRegistry` to the constructor.

==== 40. Spring Security REST: Logging Out an Unknown Token Answers 404 With Every Token Storage

The logout endpoint of the Spring Security REST plugin, `/api/logout` by default, answers 404 when the storage does not have the token of the request. With the Redis and the Grails cache token storage it answered 200 for any token, including one that was never issued or was logged out before, because `RedisTokenStorageService.removeToken` and `GrailsCacheTokenStorageService.removeToken` did not throw the `TokenNotFoundException` that `TokenStorageService.removeToken` declares. They throw it in Grails 9, as the GORM and the memcached storage always did.

The memcached token storage also answers for a token that memcached does not accept as a key: one that is longer than 250 bytes or holds a space or a line break. Validating such a token gave a 500 response; it is now a token that was not found, so validation answers 401 and logout answers 404.

===== Required Actions

* *A client that logs out with Redis or Grails cache token storage* treats 404 from the logout endpoint as "this token is not logged in", not as a failure: a second logout of the same token, or a logout after the token expired, answers 404.
* *Code of your own that calls `removeToken`* on one of the two services handles `TokenNotFoundException` where the token may be gone.

==== 41. Scaffolding: `generate-controller` Writes the Service Spec to the Integration Tests

The commands of the scaffolding plugin that the Grails 9 command line runs are its application commands. The Grails shell of earlier versions ran scripts of the same names, and the two did not do the same in every case. The commands now do what the scripts did where the scripts were right:

* *`generate-controller` and `generate-all` write `<Name>ServiceSpec.groovy` to `src/integration-test/groovy`.* The spec is an `@Integration` spec. The application command wrote it to `src/test/groovy`, where it ran with the unit tests.
* *`generate-all` generates the views of every domain class that is found.* When one of several classes was not found, the application command stopped after the controllers and generated no views. The command still fails.
* *`create-scaffold-controller`, `create-scaffold-service` and `generate-scaffold-all` take a class the project has no source of*, by its full name: a domain class of a plugin or of another project of the build. The application commands refused it. A domain class of the project is still found by its simple name and gives its package.
* *`install-templates` of the plugin writes to `src/main/templates/scaffolding` of the project*, whatever the directory the command was started in.
* *`generate-service` without a domain class, or with one that is not found, says so and fails.* It said so and then ended with a `NullPointerException`.

The scripts are removed from the plugin: its jar has no `META-INF/commands`, and `./gradlew runScriptCommand --arg=generate-all ...` finds no script. The commands are run as `grails generate-all org.bookstore.Book`, once the build has listed the commands of the plugins (note 46), as `grails run-command generate-all org.bookstore.Book`, or as `./gradlew runCommand -Pargs="generate-all org.bookstore.Book"`. They ask no questions: the name of the domain class has to be given.

===== Required Actions

* *A build or a CI job that ran a scaffolding script with `runScriptCommand`* runs the command of the same name with `grails` or `runCommand`. A script of your own that called `generateController(...)` or `generateViews(...)` as a method cannot do so: run the commands one after the other.
* *A project that generated a service spec with `./gradlew runCommand -Pargs="generate-controller ..."`* moves `src/test/groovy/<package>/<Name>ServiceSpec.groovy` to `src/integration-test/groovy/<package>/`, or generates it again there and deletes the first one. Nothing changes for a spec that is already in the integration tests.

==== 42. Commands of the Grails Shell and of the Profiles That Are Removed or Renamed

Notes 42 to 55 are about what differs for someone who types `grails` commands, or has them in scripts and continuous integration jobs. They take up where note 37 ends: `grails` is the one command line, and it is not the Grails shell of Grails 8.

Most commands of the Grails shell and of its profiles are commands of `grails` under the name they had. The ones that are not are answered when they are typed: `grails` refuses the name with exit code 2, as it refuses anything that is no command, and adds one line that says what there is in its place. <<cliMappingGrails8,Note 55>> has a table with every command of the shell and of the profiles, the unchanged ones included, and the table "Commands of Earlier Versions" in xref:commandLine[The Command Line] has what the command line says for each name that is gone. In short, these names are no commands any more:

* `test`, the other name of `test-app`, which the shell also read as the environment in front of another command, as in `grails test run-app` (note 43). `run` and `stop` are still other names of `run-app` and `stop-app`, `war` and `package` of `assemble`, and `sh` still runs `shell`, as the short form of its name (note 43).
* `open` of interactive mode (note 47). `exit` and `quit` still leave interactive mode, and `!` is kept: it runs a program of the operating system there, through your shell now.
* `install` in a plugin: it runs nothing, says to run `grails gradle publishToMavenLocal`, and ends with exit code 1.
* `create-profile`, `create-feature`, `create-template`, `create-creator-command`, `create-generator-command`, `create-gradle-command`, `list-profiles` and `profile-info`, which are removed with the profiles (note 37).
* `create-script`, which wrote a script command: script commands are deprecated, and a new command is a class of the application that `create-command` writes. The scripts a project has still run (note 33).
* What `generate-all`, `generate-controller` and `generate-views` of the `rest-api` profile did: the commands of these names are those of the scaffolding plugin, which generate GSP views (notes 41 and 46), and nothing generates JSON views for a domain class.
* `grails run <file>.groovy` outside a project (note 38).

Some commands are there in projects of some kinds only, which note 55 says for each: `create-integration-test` is no command in a plain plugin, `create-functional-test` is one in a REST API project and in a web project with a Geb feature (note 54), `create-job` in a project with the `grails-quartz` feature, `create-domain-resource` and `create-restful-controller` in REST API projects, and `package-plugin` and `publish-plugin` in a project that has a plugin class (`*GrailsPlugin.groovy` under `src/main/groovy`). `install-templates` is another command than it was (note 45).

New for someone who comes from the Grails shell are `create-restapi`, `create-rest-api-plugin`, `create-webapp` (another name of `create-app`), `feature add`, `feature list`, `project show`, `project regenerate` and `project migrate`.

*`list-plugins` and `plugin-info` are kept, and read another source.* `list-plugins` lists the plugins of the Grails release, which the command line knows without the network, and the plugins of the Grails plugin index, which it reads from `https://raw.githubusercontent.com/apache/grails-plugins-metadata/main/grails-plugins-index.json` in the place of the directory listing of `repo.grails.org` the shell read, and it takes a text to list by. `plugin-info` takes the name or the artifact of a plugin, or its coordinates as `group:artifact`, and prints the dependency for `build.gradle` as `implementation`, without a version when the Grails BOM manages the plugin. `plugin-info` still has `--snapshots`. Both have `--offline`, `--json` and `--plugin-index`; the `GRAILS_PLUGIN_INDEX` environment variable names another index, or `none`.

*`GRAILS_PLUGIN_INDEX` is also the feature catalog.* A plugin index named by `GRAILS_PLUGIN_INDEX` is read by the create commands as their feature catalog when neither `--feature-catalog` nor `GRAILS_FORGE_CATALOG` names one; set `GRAILS_FORGE_CATALOG=none` to keep it for `list-plugins` and `plugin-info` only. `plugin-info` names the feature pack the index records for a plugin, and the `--json` documents of both commands have `featurePacks`. A catalog version whose entry cannot be read, or whose pack has a later format, is left out alone; the plugin's other versions are still offered.

*Each command line `plugin-info` shows for a feature pack creates the application, as shown, in the same environment.* It uses the create command of a type the pack is for (`create-restapi` for a pack for REST APIs only), with the version chosen for that type (`applicationType` in `--json`). It adds `--feature-pack-repository` for a pack only in the repository the index names, gives the full name `group:artifact#name` where two plugins have a feature of one name, adds `--feature-catalog` where `GRAILS_FORGE_CATALOG` would read another catalog, and adds `--refresh` for an `https` index. A pack whose feature has the name of a feature of Grails is shown as not offered. `plugin-info` also reads the versions of a plugin installed with `publishToMavenLocal` from the `maven-metadata-local.xml` of a directory in `GRAILS_REPO_URL`, such as `mavenLocal()`.

*Feature packs and presets after the application is created.* `grails feature add` and `grails project regenerate` work for an application created with the feature of a feature pack that is not part of Grails, or made from a preset, when that very pack or preset is there again. The jar is fetched again by the coordinates, the version and the SHA-256 the record has, from the repositories of `GRAILS_REPO_URL`, Maven Central and the repository the record names, or from those of `--feature-pack-repository` (with `--offline`, only from a repository that is a directory). A pack or preset given as a directory is given again with `--feature-pack-dir`; `.grails/forge.lock.yml` now records the SHA-256 of its content (`contentSha256`), and a directory with other content is refused. With `--json`, such a refusal has the reason `pack-missing` or `pack-differs`. The create commands say this once such an application is created, and `project show` says it among its notes. A feature of a pack is still not added by `feature add`.

*`feature list` lists the features of an application with a feature pack.* For an application created with the feature of a feature pack that is not part of Grails, or made from a preset, `grails feature list` listed no feature that could be added and said that a feature cannot yet be added to such an application. It now takes the packs as `feature add` does, with the same options `--feature-pack-dir`, `--feature-pack-repository` and `--offline`: the jar of a plugin is fetched again by the coordinates and the SHA-256 of the record. It lists the features `feature add` can add with them. Without a pack it lists what the application has and says which pack it needs and how it is given, with exit code 0. A pack other than the one of the record ends it with exit code 1. To keep `feature list` from asking a repository, give `--offline`, with `--feature-pack-repository` naming a directory.

*A full name in a pack descriptor names the feature of that plugin's pack.* A full name, `group:artifact#name`, in `requires` and `conflicts` of a feature pack, or in `features` and `conflicts` of a preset, was accepted but never matched. A requirement by full name refused every application, even with the pack of that plugin given, and a conflict by full name refused none. A full name now names the feature of that name of the pack taken from the jar of that plugin, in any version, by its coordinates or from a feature catalog. The pack of a directory or of a file is named by no full name. An application with a feature that a pack conflicts with by full name is now refused: to keep it, remove the entry from `conflicts`. Where a pack of a directory has to satisfy a requirement, name the feature by its name alone. A full name of the pack's own feature is now refused, as its name is.

===== Required Actions

==== 43. The Environment, Short Forms, Options and Exit Codes of the `grails` Command

What stands after `grails` is read by other rules than the Grails shell had.

* *The environment is not given in front of the command.* `grails test run-app`, `grails prod war` and `grails dev run-app` are refused with exit code 2: `test`, `prod` and `dev` are no commands. The refusal ends with a line that says where the environment is given now and the command line to type, such as `Type: grails war -Dgrails.env=production`; `development` and `production` in front of a command are answered the same way, and none of these names is read as the short form of a command of the application. The environment is a system property after the name of the command: `grails run-app -Dgrails.env=test`, `grails war -Dgrails.env=staging`. `-Dgrails.env=NAME` in front of the command, which the shell took wherever it stood, is a mistake as well. Without it `run-app`, `console`, `shell`, `run-command` and `run-script` run for `development`, `test-app` for `test`, and `assemble` (`war`, `package`) for `production`.
* *An option of a command stands after its name.* In front of the name only the options of the command line itself are taken: `--plain-output`, `--non-interactive`, `-x` (`--stacktrace`), `-v` (`--verbose`), `-h` and `-V`.
* *`-v` is `--verbose`, and the version is `-V` or `--version`.* The shell printed the version for `grails -v`; `grails -v` without a command is now refused with exit code 2.
* *An option has two dashes, and one that a command does not have is refused.* The shell took every option with one dash or with two, in front of the command or after it, and ignored the ones it did not know. Only these are still taken with one dash: `-port`, `-host`, `-https` and `-debug-jvm` of `run-app`, `-unit`, `-integration`, `-clean`, `-continuous` and `-debug-jvm` of `test-app`, `-clean` of `assemble`, and `-debug-jvm` of `console` and `shell`. `-stacktrace`, `-verbose`, `-version`, `-plain-output` and `-non-interactive` are refused: write them with two dashes. `--offline` and `--refresh-dependencies` in front of a command are refused as well; for Gradle they stand after `--`, as in `grails compile -- --offline`.
* *`--verbose` asks Gradle for `--info`.* For a command that is a build (`compile`, `test-app`, `assemble` and the others), `-v` or `--verbose` adds `--info` to the arguments of Gradle, and `-x` or `--stacktrace` adds `--stacktrace` and `-Dgrails.full.stacktrace=true`. `run-app --verbose` leaves out the `--quiet` the command otherwise gives Gradle. The debug log of Gradle is `-- --debug`.
* *Short forms in lower case are taken, and a short form that fits two commands is refused.* A command can still be shortened to the first letters of its words with the start of every word after the first in upper case (`cA`, `cDC`, `rA`), as in the Grails shell. Now it can be shortened in lower case as well, which the shell refused: `ra` is `run-app`, `sa` is `stop-app`, `ta` is `test-app` and `cdc` is `create-domain-class`, and more letters of a word tell two commands apart, as `ccon` for `create-controller`. A form with an upper-case letter or a hyphen is read as the shell read it, so `Ra` is still no command. A name the shell had for a command that is gone, such as `test`, is never read as a short form: it is answered with what there is in its place (note 42). `run` and `stop` are other names of `run-app` and `stop-app`, as in the shell, and, as in the shell, nothing is short for them: `r` and `ru`, which start `run-script` and `run-command` as well, are no command, and `st` is still `stats`. Where a short form fits more than one command the Grails shell ran the first, and `grails` runs none, names the commands, each with the shortest form that fits it alone, and ends with exit code 2. In a project `cC` and `cc` fit `create-controller` (`ccon`) and `create-command` (`ccom`), `s` fits `stats` and `shell`, and `co` fits `compile` and `console`; `tA` is still `test-app` and `rA` is still `run-app`. `cS` and `cs` are `create-service`, since `create-script`, which the shell may have run for `cS`, is removed (note 42). `grails help NAME` ends with the shortest form of the command, as `Short form: ra`. A command of the application or of a plugin whose name is a short form of a command of `grails`, as `ra` is, is not a command by that name, which `help` says; it is run with `grails run-command ra` (note 46).
* *What is no command is a failure.* A name that is no command, an option a command does not have and a value it does not take end with exit code 2 and one line of usage, and nothing is run. An option that is meant for Gradle and that the command does not have stands after `--`: `grails compile -- --offline`.
* *Exit codes.* 0 when the command did what it was asked, 2 for a mistake in the command line, 1 for every other failure (a build that failed, no project, a file that is in the way). A command of a project that is given outside a project ends with 1 and `<name> is a command of a Grails project; there is none in <directory> or above it`.
* *Arguments are kept as they are.* `gradle`, `run-command`, `run-script` and the test filters of `test-app` give each argument to Gradle or to the command as the one argument it was: an argument with spaces or quotes is not split and joined again, and an argument that starts with a dash reaches the command. An argument that starts with `@` and names a file is replaced by the arguments in that file; write `@@` for an `@` that is meant.
* *`grails --version`* prints `Grails Version:` and `JVM Version:`, one line each, and `grails help --json` describes the commands of the current directory for a program: each option and parameter with `repeatable`, `split`, `choices` and `default`, and each command with the `relations` of its options; the document stays format 1.

===== Required Actions

* Replace `grails <environment> <command>` with `grails <command> -Dgrails.env=<environment>` for the commands of `grails` itself (`run-app`, `test-app`, `assemble` and `war`, `compile`, `console`, `shell`, `run-script` and the other commands that run the build), with `prod` and `dev` written out as `production` and `development`; the option can be left out where it names the environment the command has anyway. A command of the application or of a plugin that is run by its name is the exception: everything after its name is its own argument, so it runs in `development` whatever `-Dgrails.env=` follows the name, and `grails` warns that it does. Give such a command its environment in front of its name with `run-command`: `grails prod dbm-update` becomes `grails run-command -Dgrails.env=production dbm-update`, the same build as `./gradlew -Dgrails.env=production runCommand --arg=dbm-update`. After the name of the command it runs, `run-command` gives `-Dgrails.env=` to that command as well, without a warning; a script of the application runs in the environment of the build and receives the option after its name as an argument.
* Move options that stood in front of the name of a command behind it, and put the Gradle options a command does not have behind `--`.
* Write options with two dashes, replace `grails -v` and `grails -version` with `grails --version`, and remove options a command does not have: they were ignored, and now fail the command.
* Write out short forms that a script uses, or check them with `grails help <short form>`.
* A script that went on after a `grails` command whatever it answered checks the exit code: 2 means that nothing was run.

[[upgradingGradleWrapper]]
==== 44. The Commands That Build, Test and Run a Project Run Its Gradle Wrapper

The Grails shell ran the build of a project through the Gradle Tooling API, with a Gradle the shell chose. The `grails` command runs the Gradle wrapper of the project, `gradlew` or `gradlew.bat`, as a process, with the arguments the command stands for, and what Gradle writes goes to the terminal as it is. In interactive mode the builds are asked of the Gradle that the wrapper names through the Tooling API (note 47). See link:commandLine.html#gradleBuild[Building with Gradle].

* *A project needs a Gradle wrapper.* In a project that has no `gradlew`, and none in a directory above it that has a `settings.gradle`, the commands that are a build run nothing, say so and end with exit code 1. No other Gradle is used.
* *`gradle`* gives every argument to Gradle as it is and has no options of its own: `grails gradle --help` is the help of Gradle, and `grails help gradle` that of the command.
* *`test-app`* runs the Gradle task `testApp` of the Grails Gradle plugin, which runs every test phase of the project: every `Test` task of its build, and so also a phase the project adds, such as `functionalTest`, which the command did not run before (see note 53). A test that is named, as in `test-app BookControllerSpec`, is looked for in every phase that is run and runs where it is found. `--continuous` is the continuous build of Gradle. `--integration` alone in a project without `src/integration-test` ends with exit code 1.
* *`run-app`* takes `--port`, `--host`, `--https` and `--debug-jvm`, also with one dash as the shell spelt them, and no Gradle task or argument after its name: what is for Gradle follows `--`. New are `--query-tail` (note 54), `--detach`, which returns once the application answers and leaves it running until `stop-app`, `--foreground` and `--ready-timeout`.
* *`run-app --detach` waits where the application is bound.* With `--host` or `server.address` naming one loopback address (`127.0.0.2`, `::1`, `::ffff:127.0.0.2`), the command checks the port, waits for the answer, and has `stop-app` wait for the end at that address only, and the line that says the application answers names it (`http://127.0.0.2:8080`); before, it asked `127.0.0.1` and `::1` only, so an application bound to `127.0.0.2` on Linux was stopped when the time to answer ran out. Without an address, with `localhost` or with `0.0.0.0`/`::` it waits at `127.0.0.1` and `::1` as before. `.grails/run/app.json` gains an `address` field for such an application. To have it waited for at `127.0.0.1` and `::1` as before, bind it to `localhost` or to `0.0.0.0` instead.
* *`run-app` reads the port and the address of `grails-app/conf/application.yml` as the application reads them*, with the loader of the runtime: what a document says for the environment comes before what the same document says for all, and a later document before an earlier one, so a `server.port` for all in a later document wins over one for the environment in an earlier document; a document for a Spring profile counts only when `-Dgrails.spring.profiles.active` (also after `--`), which the application receives as `spring.profiles.active`, selects it; keys in one piece such as `environments.development.server.port` count; and an empty `server.port` names no port, so 8080 is waited on. A project that relied on the earlier reading may be waited for on another port than before; give `--port` to name the port explicitly.
* *`run-app --https` with `-Dgrails.server.ssl.key-store=FILE` after `--`* creates no certificate and passes no key store password, as with the option before `--`: the passwords come from the configuration of the application (`server.ssl.key-store-password`, `server.ssl.key-password`). To use the generated certificate, give no key store.
* *`stop-app`* stops what `run-app` of this command line started for the project, by the record in `.grails/run`. It does not read `build/run-app.pid`, has no `--port` or `--host`, and does not stop an application that was started with `./gradlew bootRun` or by the Grails shell.
* *Leaving the interactive console stops the applications that `run-app` started there without `--detach` as `stop-app` does*: after ending the Gradle that `run-app` started, the console waits, for up to 30 seconds, until nothing takes connections on the port of each application any more, also where a Gradle daemon runs the build, and only then returns (`grails`, or `GrailsCli.execute` in a program of its own). Leaving can therefore take as long as the application takes to shut down; when something still answers after 30 seconds, the console says so. To keep an application running after the console, start it with `run-app --detach` and stop it with `stop-app`.
* *`shell`* runs the Groovy shell of the application. In the Grails shell the command only said to run `gradle shell -q`.
* *`assemble --clean`* runs `clean` first; the shell accepted the option and did nothing for it.
* *`bug-report`* leaves out key files and files with secrets by their names, follows no links and writes `build/<name>-bug-report-<date>.zip`; it still contains `grails-app/conf` as it is.
* *`GRAILS_OPTS` reaches the application and the tests, and its options are separated at any white space.* The Grails Gradle plugin gives the options of `GRAILS_OPTS`, or of `GRAILS_FORK_OPTS` in its place when that is set, to the application that `run-app` (`bootRun`) starts, to the commands of the application and to the tests, with either way of running the build. It used to separate them at each single space: two spaces in a row, or a space in front, gave the JVM an empty argument, which it took for the name of its main class, so the application ended with `Could not find or load main class` before it started; and a tab or a line break left two options joined into one. Any run of spaces, tabs and line breaks now separates two options, and none is empty. Quotes are not read, as before, so an option whose value has a space is set in `build.gradle`. An `-Xmx` or `-Dname=value` there wins over `maxHeapSize` and `systemProperty` of `bootRun` and the other `JavaExec` tasks; for a test task, the task's `maxHeapSize` and `systemProperty` win.
* *The Grails Gradle plugin gives the application and the tests only the bounds of its heap of 768 MB that their options do not name.* The plugin set `minHeapSize` and `maxHeapSize` of every `JavaExec` and `Test` task to `768m` unless `build.gradle` had set them first. A `maxHeapSize` below 768 MB that `build.gradle` set afterwards, or an `-Xmx` below it in `GRAILS_OPTS`, `GRAILS_FORK_OPTS` or the `jvmArgs` of the task, kept the JVM from starting with `Initial heap size set to a larger value than the maximum heap size`, as did a `minHeapSize` or `-Xms` above 768 MB alone, and the plugin's bounds overrode an `-XX:InitialHeapSize=`, `-XX:MinHeapSize=` or `-XX:MaxHeapSize=` there. Now an option that names the maximum (`maxHeapSize`, `-Xmx`, `-XX:MaxHeapSize=`) leaves out both bounds of the plugin, and the JVM chooses the initial heap itself; an option that names only the initial heap (`minHeapSize`, `-Xms`, `-XX:InitialHeapSize=`, `-XX:MinHeapSize=`) leaves out `-Xms768m` and keeps the plugin's maximum, raised to that initial heap when it is larger (`-Xms1g` alone is given `-Xmx1g`). A value a `doFirst` of the task sets as it starts counts too. A build that sets only `maxHeapSize = '2g'` therefore starts the JVM with the initial heap the JVM chooses rather than 768 MB; to keep the initial heap of 768 MB beside a maximum of your own, set `minHeapSize = '768m'` as well. `minHeapSize` and `maxHeapSize` of a task read `null` unless the build sets them, since the plugin gives its bounds as arguments of the JVM.

===== Required Actions

* Commit the Gradle wrapper (`gradlew`, `gradlew.bat`, `gradle/wrapper`) to a project that has none: `gradle wrapper --gradle-version {gradleVersion} --gradle-distribution-sha256-sum <checksum>`, run with an installed Gradle {gradleMinimumVersion} or later, creates it, with the checksum of note 60. `grails project health` reports a project without one as `gradle-wrapper.missing`, a wrapper of a Gradle before {gradleMinimumVersion} as `gradle-wrapper.version`, and one before {gradleVersion}, which new applications are generated with, as `gradle-wrapper.older`.
* Replace `grails run-app <Gradle arguments>` with `grails run-app -- <Gradle arguments>`.
* A job that starts the application with one tool and stops it with `grails stop-app` starts it with `grails run-app --detach`.

[[upgradingProjectRecord]]
==== 45. The `create-*` Commands Read the Record of the Project, and an Application of the Grails Shell Has None

The Grails shell had the commands of the profile that the `profile` dependency of `build.gradle` named, and took the default package of new classes from `grails.codegen.defaultPackage` in `application.yml`. The `grails` command of Grails 9 decides which code generation commands a project has, and where their classes go, from the record of the project: `.grails/project.yml` and `.grails/forge.lock.yml` of an application that Grails 9 generated, or `grails-forge-cli.yml` (earlier `grails-cli.yml`) of one that Grails Forge of an earlier version generated.

*An application that was created with the Grails shell has neither.* In it `create-controller`, `create-service`, `create-domain-class` and the other `create-*` commands, `add-property` and `install-templates` are not listed by `grails help`, and typing one ends with exit code 1:

[source,console]
----
$ grails create-controller Book
| Error create-controller is a command of a Grails project whose record is read; the project in /work/myapp has no .grails/project.yml or grails-forge-cli.yml that is. grails project migrate writes the record of an application that has none
----

The commands that build and run the project (`compile`, `test-app`, `run-app`, `gradle` and the others), `stats`, `bug-report` and the commands of the application and its plugins are there all the same. `grails project migrate`, run in the directory of the application, writes the record:

[source,console]
----
$ grails project migrate
| The record of the application myapp, as it is written to .grails
    type          web              (the profile web, grails.profile of grails-app/conf/application.yml)
    name          myapp            (rootProject.name of settings.gradle)
    package       com.example      (grails.codegen.defaultPackage of grails-app/conf/application.yml)
    jdk           21               (assumed)
    servlet       tomcat           (build.gradle declares org.springframework.boot:spring-boot-starter-tomcat)
    data          hibernate5       (the feature gorm-hibernate5)
    reloading     none             (assumed)
| The 3 features of Grails it is taken to have, each with where it was found
    gorm-hibernate5 (build.gradle declares org.apache.grails:grails-data-hibernate5)
    grails-gradle-plugin (build.gradle declares org.apache.grails:grails-gradle-plugins)
    grails-quartz (build.gradle declares org.apache.grails:grails-quartz)
...
| The record was written: .grails/.gitignore, .grails/.gitattributes, .grails/baseline/index.yml, .grails/forge.lock.yml, .grails/project.yml. No other file of the project was changed. Commit the directory .grails
| grails project health says what else the upgrade notes ask of the project, as far as its files show it
----

The command reads the files of the project as text and changes none of them; it writes the `.grails` directory and nothing else. It takes the type of the application from the profile the application had (`grails.profile` in `application.yml`, or the `profile` dependency of `build.gradle`: `web` is a web application, `rest-api` a REST API, and `plugin`, `web-plugin` and `rest-api-plugin` the types of plugin) and, when neither is there any more, from the Grails Gradle plugins of `build.gradle`; the default package from `grails.codegen.defaultPackage`, then the `group` of the build, then the package of the `Application` class; and the features from the dependencies `build.gradle` declares, or `build.gradle.kts` and `settings.gradle.kts` in a project without a `build.gradle`. It takes the servlet container from the starter `build.gradle` declares, where no servlet feature is found: `spring-boot-starter-tomcat` is `tomcat`, `spring-boot-starter-jetty` is `jetty`, and `spring-boot-starter-undertow` (of a Grails 7 build) or `grails-undertow` is `undertow`. A dependency is read in string notation and in map notation (`implementation group: 'g', name: 'n'`), and nothing is read from a comment. It says where it found each value and what it assumed, and in a line each what it is known not to have read: build files that are applied with `apply from`, dependencies that a version catalog names, what `build.gradle` declares for other projects, and for a project without a `settings.gradle` of its own the build above it. One feature cannot be found in a build at all: Of the two Geb features it finds `geb-with-local-browsers` where the build declares the browser drivers that feature adds, and `geb-with-testcontainers` where it declares the Geb plugin (`testFixtures('org.apache.grails:grails-geb')`) without them. To say it otherwise, give the name with its package (`grails project migrate com.example.myapp`), `--type`, `--features`, `--exclude-features`, `--jdk`, `--servlet`, `--data` or `--reloading`; `--dry-run` shows the record without writing it, and `--force` writes again a record the command wrote. When it cannot work out the type or the package it writes nothing and says which option to give.

With the record the code generation commands are there, and a class that is named without a package goes into the default package. `create-job` is there when `grails-quartz` is among the features, and `create-functional-test` in a web application when a Geb feature is (note 54). The record says that it was written for an application that was there (`generationState: untracked` in `.grails/project.yml`) and holds no copy of generated files, so `feature add` and `project regenerate` refuse the application and change nothing: add the dependencies and the configuration of a feature by hand, as before, and run `grails project migrate --force` again so that the record names the feature. `project show` shows the record.

`project migrate` can be run before or after `grailsVersion` in `gradle.properties` names Grails 9: with `project health` (note 57), it is a command of a project that runs in a project that still names Grails 7 or 8, and it says there that the record is that of an application of Grails 9. Every other command of a project (`compile`, `test-app`, `run-app`, `gradle`, the `create-*` commands, `feature add`, `project show`, the commands of the application) is refused in such a project with exit code 1 and one line that names the version, with or without the record: the command line of Grails 9 works with projects of Grails 9 and later. Until the project is on Grails 9, its own `./grailsw` starts the command line of its version. The command can be run before or after the `profile` line is removed from `build.gradle` (note 39) and `grails.profile` from `application.yml` (note 36): without them the type is taken from the Gradle plugins.

What else differs for these commands:

* *A name has to be the name of a class.* A path (`a/b/Book`), a name with a space or another character no identifier has, a package with a hyphen, a name that ends with `.groovy` and a name that Windows keeps for a device are refused with exit code 2. A name with hyphens is still made a class name (`data-import` becomes `DataImport`).
* *A file that is there already fails the command.* The command writes none of its files, names the one that is in the way and ends with exit code 1. `-f` or `--force` replaces it. Until now such a file was kept with a warning, the other file of the command was written, and the command ended with 0.
* *`create-unit-test BookSpec` writes `BookSpec.groovy`*, and `create-command ImportCommand` writes `ImportCommand.groovy`: a name that already ends with what the command adds is not given it twice.
* *`create-command` writes a command that succeeds.* The class prints its name and the arguments it was given, and its `handle()` returns `true`, so the command runs by its name (`grails data-import orders.csv`) and ends with exit code 0 as it is written. The class the profiles wrote returned `false`, which ends a command with exit code 1, until its body was written. A project that wants the class as it was has the template `src/main/templates/artifacts/Command.groovy`, which `install-templates` copies there, return `false`.
* *`create-functional-test` in a REST API application or REST API plugin* writes a test that uses the HTTP client of the JDK. In a web application or web plugin with a Geb feature it writes a Geb test (note 54).
* *`add-property` only adds lines, and refuses a class it cannot add them to.* The command reads the domain class with the Groovy parser and no longer goes by the look of its lines: a method that returns a `String`, a brace in a comment, a block `static constraints = {}` on one line, an abstract class and a property of a type with parameters (`List<String> tags`) are no longer in the way, and the line endings, the indentation and the end of the file stay as they are. It writes nothing and ends with exit code 1 for a class that is written on one line, a class whose last property is on the line of its closing brace, and, when the property has a constraint, `constraints` that are not a block written in the class (`static constraints = Shared.rules`). See link:{commandLineRef}add-property.html[add-property].
* *The commands work in every directory of the project* and write to the project, also when they are given in `grails-app/views`. They do not write through a link that stands where a directory of the sources is expected.
* *Templates of the project are text.* A template under `src/main/templates` is still used in place of the built-in one, from the locations the profiles had (`artifacts/Controller.groovy`, `testing/Controller.groovy`, `Job.groovy` and so on). The `@artifact.name@` tokens and, in `Job.groovy`, names in braces such as `${className}` are replaced, and nothing is evaluated: a `Job.groovy` with `<% %>` code or an expression such as `${className.toLowerCase()}` fails the command. `artifacts/Script.groovy` is read by no command, since `create-script` is removed (note 33). Templates with logic are not supported.
* *`install-templates` is another command.* `grails install-templates` copies the templates of the `create-*` commands into `src/main/templates/artifacts` and `src/main/templates/testing`. In Grails 8 the name ran the script of the scaffolding plugin, which copied the scaffolding templates; that is now `grails run-command install-templates`, or `./gradlew runCommand -Pargs="install-templates"`, and writes `src/main/templates/scaffolding`.

For an application that Grails 9 generates, commit the `.grails` directory: `project.yml`, `forge.lock.yml` and `baseline` are the record. `.grails/run`, `.grails/cache`, `.grails/transactions` and `.grails/history` are kept out of version control by the generated `.gitignore`. The record is not merged line by line. When two branches that each added a feature are merged, take the record of one side (`git restore --source=HEAD --staged --worktree -- .grails`) and add the features the other side asked for with `feature add`. The lock names the generator by its version and by the identity of its build (`generator.sha256`), so two snapshots of one version are told apart. When `grailsVersion` is changed by hand, the record keeps the version that generated the application until `project migrate` moves it: once `gradle.properties` names the new version, run `./grailsw update-wrapper` and then `./grailsw project migrate` (or the installed `grails` of the new version). It generates the application again from the choices of the record with the new version and writes the baseline and the record under `.grails`, and no other file; afterwards `feature add` and `project regenerate` work, and a file the new version generates otherwise is a change of yours to them. Until then they refuse and name `project migrate`. A record of a later version than the command line is not moved. See "The record over the life of a project" in xref:commandLine#creatingProject[Creating a Grails Project].

===== Required Actions

* *An application that the Grails shell created* (it has no `grails-forge-cli.yml`, `grails-cli.yml` or `.grails` directory): run `grails project migrate` in the directory of the application, before or after `gradle.properties` names Grails 9, check the type, the package and the features it reports, correct them with its options where they are not right, and commit the `.grails` directory. Do not write `.grails/project.yml` or a `grails-forge-cli.yml` by hand. Leave `grails.codegen.defaultPackage` in `application.yml`: the framework reads it when the application runs.
* *An application that Grails Forge of Grails 7 or 8 generated* keeps its `grails-forge-cli.yml`, and nothing has to change (note 35). `grails project migrate` writes a `.grails` record from that file for it too, which `project show` then shows; the commands go by `.grails` afterwards and warn when the file does not name the same package and features, so remove the file then unless a tool of yours reads it.
* *Scripts and jobs that create a class that may be there already* pass `--force`, or check for the file first: the command now fails where it skipped.
* *A `Job.groovy` template of the project with code in it* is rewritten as text with the names in braces, or the class is completed by hand after the command.
* *Replace `grails install-templates`*, where the scaffolding templates are meant, with `grails run-command install-templates`.
* *Where `.grails/run` shows up as untracked* in a project that Grails 9 did not generate, add `.grails/run/` to its `.gitignore`; the directory holds a `.gitignore` of its own that normally keeps it out.
* `grails project health` reports a project without a record as `record.missing`, a record of an earlier version as `record.earlier-generator`, a record of another version of Grails than the project as `record.version-drift`, a `.gitignore` that leaves out `.grails` as `git-files.record-ignored`, and one that does not leave out `.grails/transactions` and `.grails/history` as `git-files.state-ignored`. The templates of the project are not checked.

[[upgradingCommandCatalog]]
==== 46. Commands of the Application and of Plugins Are Listed by the Build

The Grails shell found the commands of the plugins of an application itself, on the class path of the project: `grails dbm-update`, `grails url-mappings-report` or `grails s2-quickstart` worked as soon as the plugin was a dependency. They still do, by the same names. The `grails` command loads no class of the project: it has the commands that the Gradle task `grailsCommandCatalog` of the project has written to `.grails/cache/command-catalog.json` in the directory of the project (note 32), and runs each through the Gradle task `runCommand`.

* *The build keeps the list.* Every build that compiles the project runs `grailsCommandCatalog` after `classes`: `grails compile`, `run-app`, `test-app` and `assemble`, `./gradlew build`, and a build from an IDE. The task is up to date when nothing it reads has changed. The file is in `.grails/cache` of the project and not in the build directory, wherever the build puts that, so `clean` does not remove it; a `.gitignore` the task writes beside it, and the generated `.gitignore` of an application, keep it out of a commit.
* *A name that is not listed yet has the build list the commands.* In a checkout that was never built, or where the list may be out of date, a name that is none of the commands has `grails` run the task once, after a line that says so, and then look for the name again: `grails dbm-update` in a fresh checkout compiles the project, lists the commands and runs `dbm-update`. A name that is still none of them is refused with exit code 2, and a build that fails while it lists ends the command with exit code 1. `grails help`, `grails help <name>` and the commands of `grails` itself never start a build, and with a list that is current a mistyped name is refused at once. With the environment variable `GRAILS_LIST_COMMANDS=false` a name that is none of the commands is refused at once, without a build.
* *`run-command` runs the same command.* `grails run-command dbm-update` and `./gradlew runCommand --arg=dbm-update` run a command whether or not it is listed; `run-command` is the form for an environment in front of the name (below).
* *A command that has the name of a command of `grails` is not run by its name.* `install-templates` of the scaffolding plugin is the example: `grails install-templates` is the command of the command line, with a warning, and `grails run-command install-templates` the one of the plugin.
* *What were scripts of the plugins of the framework are commands like the others.* `s2-quickstart` and the other commands of the Spring Security plugins are run as `grails s2-quickstart ...`, as before, or as `grails run-command s2-quickstart ...` (note 54). `create-job` and `create-functional-test` are commands of `grails` itself.
* *Script commands of other plugins are not listed.* A script that a plugin of your own or of a third party has under `META-INF/commands` is run by the build: `grails gradle runScriptCommand --arg=<name> --arg=<argument>` (note 34). The scripts of the application itself, in `src/main/scripts`, are commands by the names of their files (note 33).
* *A command that needs no application runs without it.* A command that also implements the new `org.apache.grails.core.cli.StandaloneCommand` is listed and run as every other, but the task makes no application context for it, opens no data source and runs no `BootStrap`. `query-tail` of Grails Data is one. See "Commands That Run Without the Application" in xref:commandLine#creatingCustomCommands[Creating Custom Commands].
* *The environment of such a command is `development`.* `grails prod dbm-update` is `grails run-command -Dgrails.env=production dbm-update`, with the option in front of the name of the command that is run, or `./gradlew -Dgrails.env=production runCommand --arg=dbm-update`. After the name everything is an argument of the command: `grails dbm-update -Dgrails.env=production` runs it in `development` with the option as an argument, and a warning on the standard error says so and names the form above.
* *`help` shows no usage of such a command.* For a command of the application or of a plugin `grails help <name>` has its description and where it comes from, not its arguments and options; for a script it has no description. Nothing completes their arguments. `grails help <name>` runs nothing; `grails <name> --help` gives `--help` to the command and runs it through the build.
* *Everything after the name goes to the command*, `--help` and `-x` included.
* *The list is written also when the class path of the commands does not resolve.* A build that compiles a project writes the list of the commands of the application and its plugins also when the runtime class path, or `grailsCliClasspath`, does not resolve completely (a dependency that is not found, or two versions of one module that are both required). The compilation succeeds as it did in Grails 8, which never resolved the runtime class path to compile. The list then has the commands of what resolves and `complete` is `false`. A line of `diagnostics`, which the build also prints as a warning, names the class path and what Gradle could not resolve. `grails help` shows the line, a name that is none of the commands is refused with a line saying the list is not complete, and `grails project health` advises with `command-catalog.incomplete`. Running the application, its tests or a command still fails until the dependencies are corrected. To make a build fail on such a class path, run a task that resolves it, such as `./gradlew dependencies --configuration runtimeClasspath`.

===== Required Actions

* None for `grails <plugin command>` in a script or a continuous integration job: it runs as before, also in a fresh checkout, where the build compiles the project and lists the commands first. A job that wants a mistyped name refused without a build sets `GRAILS_LIST_COMMANDS=false`, and runs the commands of plugins after a build of the project, or as `grails run-command <plugin command>` or `./gradlew runCommand --arg=<plugin command>`, which do not depend on the list.
* `grails <script of a plugin of the framework>`, such as `grails s2-quickstart com.example User Role`, runs the command of that name: read note 54 for what each of them does differently. Do not run them with `runScriptCommand`: the scripts are gone.
* Replace `grails <script of another plugin>` with `./gradlew runScriptCommand --arg=<name> --arg=<argument>`.
* `grails project health` reports a project whose commands are not listed as `command-catalog.missing`, and a list that is not used or may be out of date as `command-catalog.refused` or `command-catalog.stale`, as advice. The command lines of scripts and jobs are not checked.

==== 47. Interactive Mode

`grails` without a command still starts an interactive mode in a project, with completion by the TAB key. It differs from that of the Grails shell:

* *It starts in a project only.* Outside a project, `grails` without a command shows the help. With `--non-interactive` it shows the help everywhere.
* *It is left with `exit` or `quit`*, as the Grails shell was, with Ctrl-D, or with Ctrl-C at the prompt.
* *Its builds are asked of one connection to Gradle*, through the Tooling API, as those of the Grails shell were, but with the Gradle that the wrapper of the project names: a build after the first begins at once. Gradle writes plain text there, without its colors and its display of progress; a failed build is reported as `Gradle did not succeed: the build failed`, where a command line of its own names the exit code of Gradle; and a build does not read what is typed at the terminal. `gradle`, `shell` and `run-app`, which leaves the application running there, start the Gradle wrapper as they do on a command line of their own. The environment variable `GRAILS_GRADLE_RUNNER=process` has every command of interactive mode start the wrapper. See link:commandLine.html#howGradleIsRun[How the `grails` Command Runs Gradle]. `test-app --continuous` runs there until Ctrl-C cancels it. With `GRAILS_CLI_DIAGNOSTICS=true` the command line says on its error output which way it runs Gradle for each command, and why: see link:commandLine.html#gradleRunnerDiagnostics[Seeing How a Command Runs].
* *`open` is gone* (note 42).
* *`!` runs a program of the operating system through your shell.* As in the Grails shell, a line that starts with `!` runs the rest of the line, and `!` alone runs the last command again (the last line that did not start with `!`). The Grails shell split the line into words and ran the first one as the program, without a shell; the line now goes as it was typed to the shell that the `SHELL` environment variable names, or to `/bin/sh` where it names none by its absolute path, and on Windows to `cmd.exe`, so quotes, variables, patterns such as `*.groovy`, pipes and redirections work as in a terminal. The program has the terminal: its output and its error output are shown as it writes them, where the Grails shell showed both together in the output once the program had ended, it reads what is typed, so a program that asks a question works, and Ctrl-C goes to the program and not to interactive mode. An exit code other than 0 is shown in one line, `| Exit code 1`, which the Grails shell did not show. In lines that are piped into `grails` the input of the program is empty. On a command line of its own `grails '!ls'` is refused as a command there is not. The line runs with your rights, as everything you type in interactive mode does. See link:commandLine.html#interactiveModePrograms[Running a Program of the Operating System].
* *The prompt is `grails>`*, and the line `Enter a command name to run. Use TAB for completion:` is not printed before the first one.
* *Commands are completed, with their options.* The commands are those of the current directory, the commands of the application and its plugins that the build has listed among them. The names of Gradle tasks after `gradle` are not completed.
* *`run-app` returns to the prompt* once the application answers on its port, and the application is stopped when interactive mode is left, which waits until its port is closed (note 44), unless it was started with `run-app --detach`. `run-app --foreground` stays with the application. With the `grails-startup-progress` feature, a start that fails while the progress page has the port is reported at once.
* *Ctrl-C while a command runs Gradle* stops Gradle and returns to the prompt. During another command it ends interactive mode, and while the program of a `!` line runs it is the program's.
* *A line that starts with `#` is ignored.*
* *What it tells you to type fits its prompt:* `Run 'help' for the commands`, `To list them now: gradle grailsCommandCatalog`; a command line of its own says the same with `grails` in front.
* *`feature add` completes the names of the features the project does not have.*

===== Required Actions

* In a script that pipes commands into `grails`, the lines that start with `!` are read by the shell now: quote a `*`, `$`, `|`, `;` or `>` there that the program was given as it was. Better, give each command to `grails` on its own command line, with `--non-interactive`, and check its exit code.

[[upgradingSettingsGroovy]]
==== 48. `~/.grails/settings.groovy` Is Not Read

The Grails shell read `~/.grails/settings.groovy`: the repositories it resolved profiles from (`grails.profiles.repositories`), the default group and version of a profile, and proxy settings. The `grails` command reads no such file, and resolves no profile.

* *Repositories.* The feature pack of a plugin that is given to `--features` by its coordinates is taken from the repositories of the `GRAILS_REPO_URL` environment variable and then from Maven Central, or from those that `--feature-pack-repository` names. A feature catalog is named with `--feature-catalog` or `GRAILS_FORGE_CATALOG`. `~/.m2/settings.xml` is not read for either.
* *Proxies.* The JVM of the `grails` command takes the proxy settings of Java from `GRAILS_OPTS` or `JAVA_OPTS`, for example `-Dhttps.proxyHost=... -Dhttps.proxyPort=...`. The build of a project takes them from Gradle, and the application and the tests that the build starts are given those of `GRAILS_OPTS`, or of `GRAILS_FORK_OPTS` in its place, by the Grails Gradle plugin (note 44).
* *`create-app`.* The name may still be given with its package (`create-app com.example.myapp`), and `--inplace` creates the application in the current directory. A name with a character a directory cannot have, and a part of the package that Windows keeps for a device, are refused. `--profile` is no option (note 37).
* *`create-app --inplace` without a name.* The application is named after the current directory, as the shell named it, and the default package is made from that name as from a name given without a package (`my-shop` is the application `my-shop` in the package `my.shop`). The `create-app` of the Grails Forge command line of Grails 8 refused `--inplace` without a name. Two directories the shell took are refused, with exit code 2 and a message that names the directory: one whose name has a dot, which the shell split into a package and a name (`com.example.shop` was the application `shop` in the package `com.example`), and one whose name has a character that cannot be part of the name of a class, such as a space. The same holds for `create-restapi`, `create-plugin`, `create-web-plugin` and `create-rest-api-plugin`.

===== Required Actions

* Delete the profile settings from `~/.grails/settings.groovy`, or the file. Move a repository it named for profiles of your own to `GRAILS_REPO_URL` or `--feature-pack-repository`, for the plugin that now holds the feature pack.
* Move proxy settings to `GRAILS_OPTS` and to the Gradle properties of the build.
* `grails project health` reports the file as `leftover.settings-groovy`.
* A script that runs `create-app --inplace` without a name in a directory whose name has a dot gives the name the shell made of it: `grails create-app --inplace com.example.shop` in a directory `com.example.shop`. In a directory whose name has a space or another character a class name cannot have, give the name the application is to have.

==== 49. A Project Above the Current Directory Has to Be Your Own, and Builds of Several Projects

The commands of a project work in every directory of it: the project is the nearest directory, from the current one upwards, that has a `grails-app` directory or a record, and the search stops at the root of the Git repository. Two things follow that the Grails shell did not have.

* *A project above the current directory is used only when it is your own.* The directory, its `grails-app`, its record and its Gradle wrapper have to be owned by the user who runs the command, and the directory must not be writable by everybody. Otherwise nothing is run or written, one line says which directory or file is not yours, and the command ends with exit code 1. A Gradle wrapper above the current directory that is a symbolic link is run only when the link names its file directly, through no second link, and every directory from the link down to the file is yours and cannot be written to by everybody. The project of the current directory itself is always used. This matters where files belong to another user by design: as root in a container over a directory of the host, in a continuous integration job that runs in a container, and under `sudo`. On Windows only the owner is looked at, and what the Administrators group owns, as everything an elevated administrator creates is, is your own in an elevated process of an administrator and in no other.
* *In a Gradle build of several projects the commands are those of the project the current directory is in.* `run-app` in `apps/shop` runs `:apps:shop:bootRun` with the Gradle wrapper of the root of the build. At the root of such a build, or in a directory of it that is in no Grails project, a command of a project is not run for one of the projects, and there is no option that names the project: the command names the Grails projects of the build, says to run it in the directory of the one that is meant, and ends with exit code 1. This is a limitation of this version. `gradle` works at the root, since Gradle does.
* *Gradle checks the path of the project before it runs a task of it.* The commands that run tasks of a project (`compile`, `test-app`, `run-app`, `run-command`, `war`, `console`, `shell` and the other build commands) name the tasks by the path of the project in its build: the path its directories give, or the root project where the project has settings of its own. Gradle is also given an init script, `.grails/run/project-path.gradle` in the project, that fails the build before any project is configured when the settings do not give the directory of the project that path. Before, a build whose settings gave the directory another path (`project(':service').projectDir = file('app')`), and that path to another directory, ran the tasks of the other project, which could succeed; a project with settings of its own whose `rootProject.projectDir` was moved ran the task of that directory. Such a build is now refused with a message that names the project the directory is. To run a task of such a project, name it yourself: `grails gradle :service:testApp`. The project compared is the one Gradle made once the settings and every callback they register have run, so settings that move a project in a callback, such as `gradle.settingsEvaluated { project(':app').projectDir = file('legacy-app') }`, are refused as settings that move it directly are. A directory that is in no project of the build is refused by Gradle itself (`Project directory '...' is not part of the build defined by settings file '...'`), and the command adds the `include` line. The script is written once per project and kept; `.grails/run` is ignored by Git. `grails gradle` is not checked.
* *A Gradle wrapper above the project that is a link is checked with the files it runs.* The jar and the properties beside the file a linked `gradlew` leads to are now held to the ownership rule as well as those beside the link. A wrapper that ran before can be refused; name its directory in `GRAILS_SAFE_DIRECTORY` to run it all the same.
* *The `gradle` and `gradle/wrapper` directories of a Gradle wrapper above the current directory are checked where they are links.* A `gradle` or `gradle/wrapper` that is a symbolic link, beside the wrapper or beside the file a linked `gradlew` leads to, is held to the ownership rule at the directory it leads to: that directory has to be within the directory of the wrapper, named by the link itself and not through a second link, and it and every directory on the way to it have to be yours and not writable by everybody. A wrapper that ran before can be refused; replace the link with the directory, run the command in the directory of the wrapper, or name that directory in `GRAILS_SAFE_DIRECTORY` to run it all the same.

New with this: `create-app --subproject`, and the same option of the other `create-` commands, writes an application into an existing build. It writes the files of the application only, without a Gradle wrapper, settings and Grails wrapper of its own, and prints the `include` line for the settings of the build.

See "In a Gradle Build of Several Projects" in xref:commandLine[The Command Line] and the section on running Gradle in link:commandLine.html#gradleBuild[Building with Gradle].

===== Required Actions

* Where a job runs `grails` in a directory below a project whose files another user owns, either run the command in the directory of the project, or set `GRAILS_SAFE_DIRECTORY` to the absolute path of the project (several paths are separated as those of `PATH` are; for a Gradle wrapper above the project, name its directory too).
* In a build whose settings give a project a directory of another name (`projectDir = file(...)`, also in a callback such as `gradle.settingsEvaluated { ... }`), run its tasks by their path with `grails gradle <path>:<task>`, or include the project by its directory.
* In a build of several projects, change into the directory of the application before a command of a project: `cd apps/shop && grails test-app`. A job that ran such a command at the root of the build now ends with exit code 1.

==== 50. The Grails Wrapper Reads a Published Directory, and Says When a Repository Override Misses

Besides what note 37 says of the Grails wrapper, two things changed in how `grailsw` finds the command line to download when `GRAILS_REPO_URL` or the `grails.repo.url` system property names a repository:

* A directory that a build published to with the Gradle task `publish`, which has `maven-metadata.xml` files, is read. Until now only a local Maven repository, which has `maven-metadata-local.xml` files, was read from a directory, and a snapshot in a published directory was not found.
* When a repository that was named this way does not have the command line, the wrapper says so, with the repository and the reason, and that it tries the next one. Until now it said nothing and took the command line from another repository, while its first line still said that the repository was overridden.

`GRAILS_WRAPPER_HOME` still names the directory the command line is downloaded to (`~/.grails/wrapper` without it). Outside a project, and without the `PREFERRED_GRAILS_VERSION` environment variable, the wrapper starts the latest version that directory holds; it started the oldest one.

The wrapper also looks into what it downloads, and its failures read differently:

* A download is installed only when it is whole: it matches the strongest checksum file the repository has beside the jar (`.sha512`, `.sha256`, `.sha1`, `.md5`), or, where the repository has none, every entry of the jar matches its CRC, and it has the class the command line starts with. Until now a jar that was cut off was installed, and for a release it was never downloaded again. The checksum is from the same repository as the jar: it finds a damaged download, not a repository that is not to be trusted.
* A jar in the wrapper home that cannot be started, which an earlier wrapper can have left, is said in one line (`The installed Grails command line at [...] cannot be started (...). Downloading it again.`) and downloaded again once.
* A repository whose metadata cannot be read, or that cannot be reached or answers with an error, is passed over with one line on standard error (`The Grails CLI could not be taken from the repository [...]: ...`) and the next one is tried. Until now metadata that could not be parsed ended the wrapper.
* The first repository that gives the jar decides. A download that is not whole is not installed, no other repository is asked, and the wrapper ends with exit code 1 and `The Grails CLI that the repository [...] gave is not installed: ...` with the reason, so that the command line of another repository does not run in the place of the one that was asked for. A download is not whole when it does not match the checksum or the CRC, is no jar with the class the command line starts with, has a checksum file that cannot be read or holds no checksum, or broke off before its end. This holds for Maven Central and the ASF repository as it does for a repository named with `GRAILS_REPO_URL`.
* A release that a repository named with `GRAILS_REPO_URL` does not have gets the line a snapshot got, `...The Grails CLI was not found in the overridden repository [...]`, in place of `There was an error downloading the wrapper jar from [...]` and a stack trace.
* When no repository gave the command line, the wrapper ends with exit code 1 and `Could not find the Grails CLI in any repository:`, followed by a line for each repository with its reason, and no stack trace. The message was `Could not find the Grails Repo in any repository:` with the repositories on the same line for a snapshot, and the stack trace of a missing file for a release.
* A wrapper home that cannot be written to ends the wrapper with exit code 1 and `The Grails wrapper cannot write to [...]`, before a repository is asked.
* A user name and password in the address of a repository are replaced by `+***+` in every message. An address that cannot be read with certainty is printed with everything up to its last `@` replaced, and a remote address in which no host can be found (an unencoded `/`, `#` or `?` in the password) is refused before anything is downloaded: percent-encode such characters in a password (`%2F`, `%23`, `%3F`, `%40`).

===== Required Actions

None for a project. A job that tests a command line of its own through `GRAILS_REPO_URL` looks for the line `...The Grails CLI was not found in the overridden repository` in the output of `grailsw`: it means that the command line of another repository ran. A job that looked for `There was an error downloading the wrapper jar` or `Could not find the Grails Repo in any repository` looks for the lines above. A repository of your own that serves a checksum file beside the jar has to serve the right one: a jar whose checksum file does not match is not installed, and the wrapper ends with exit code 1 rather than take the command line from the next repository. Where `The Grails CLI that the repository [...] gave is not installed` names a repository of your own, correct the jar or its checksum file there; where it names Maven Central or the ASF repository, run the command again.

==== 51. IDEs and Tools That Started the Grails Shell

An IDE integration or a tool that ran Grails commands by starting the class `org.grails.cli.GrailsCli` from the artifact `org.apache.grails:grails-shell-cli` of the version of the project finds no such artifact for Grails 9 (note 39), and a list of commands that is built into such a tool names commands that Grails 9 does not have (note 42).

* The commands that are a build are Gradle tasks, which every IDE with Gradle support runs: `bootRun`, `test`, `integrationTest`, `testApp`, `assemble`, `runCommand`, `runScriptCommand`.
* A tool that starts the command line uses the artifact `org.apache.grails:grails-cli` with its dependencies and the class the `Main-Class` of its jar names, `org.apache.grails.forge.cli.GrailsCli` (note 37), with `--plain-output` and `--non-interactive`, and asks `help --json` for the commands of a directory instead of carrying a list of its own. The commands that are a build start the Gradle wrapper of the project then, as they do on a command line. See "Starting the Command Line from a Tool" in xref:commandLine[The Command Line]. A tool that calls `GrailsCli.execute` in its own JVM compiles against `org.apache.grails.forge:grails-forge-cli` instead. Both need the repository of Gradle, `https://repo.gradle.org/gradle/libs-releases`, for `org.gradle:gradle-tooling-api`.
* What tells a project that Grails 9 generated from an earlier one is its `.grails/project.yml`; the version a project is on is `grailsVersion` in `gradle.properties`.

===== Required Actions

* Where the Grails support of an IDE fails to run a command for a Grails 9 project, run the Gradle task instead, or the `grails` command in a terminal, until the integration supports Grails 9.
* Update tools of your own as described above.

==== 52. `feature add` Replaces a Default Feature, and Generated YAML Configuration Has a Fixed Key Order

This note is for a project that an earlier build of Grails 9 generated, and for anyone who adds features to a project.

*`feature add` replaces a feature the application has by default.* `grails feature add postgres` takes `h2` out of `build.gradle`, `application.yml` and the record of the project and puts PostgreSQL in its place, and says so (`postgres replaces h2, the default of the group database-driver`). A feature that was asked for by name, when the application was created or with an earlier `feature add`, is not replaced by adding another alone: the command refuses with exit code 2 and names both features and the `--replace` option. `grails feature add mysql --replace` replaces it as a default is replaced, and the record becomes that of an application created with the new feature. A feature that another feature of the application requires is not replaced, with the option or without. A feature that would change an option (`--data`, `--servlet`, `--reloading`) is refused as before. Where you changed lines of the default that is replaced, the H2 URL for example, the command reports a conflict and writes nothing.

*`feature add` looks at the features of one command as a whole.* Two or more features of one exclusive group named together, as `feature add h2,postgres`, are refused with exit code 2, with `--replace` or without and whichever of them the application already has. Before, a feature the application had was set aside first: on an application with H2 the command replaced H2 by PostgreSQL, and running it again put H2 back. To get the result of the first run, name only the feature the application is to have, as `feature add postgres`, with `--replace` when the feature it replaces was asked for by name.

*An interrupted `feature add` is undone file by file.* While it is undone, each file is compared again just before it is put back. A file saved in the meantime stops the undoing there instead of being overwritten. The next `feature add` puts back the rest once the file is what it was before the change or what the change made of it.

*An interrupted change keeps a mode that was changed since.* Where the file system has modes, a file that an interrupted `feature add` or `project migrate` wrote, and whose mode was changed afterwards (`chmod 600 grails-app/conf/application.yml`), is no longer put back with the mode it had before the change. The next `feature add` or `project migrate` puts nothing back and names the file with the mode it has and the mode the change gave it. Give the file that mode, or make it what it was before the change, and run the command again; for the earlier result, run `chmod` with the earlier mode once the change was undone. A change that wrote every file is ended as before, and the file keeps its mode. The record of a change in `~/.grails/forge/transactions` has a new format, and one that an earlier build of Grails 9 left is not read: restore the project from version control and remove the file `journal` as the message says.

*`project migrate` ends a move that was interrupted while it wrote the record.* A move interrupted after `forge.lock.yml` and before `project.yml` left a record that does not read, and the next `project migrate` refused it and said to restore or remove the record. It now ends the change first, says so, and moves the record; with `--dry-run` it says that the change is ended by the command without `--dry-run`. The project needs no change.

*`project regenerate --diff` fails on a file of the project it cannot read.* A file that cannot be read, such as one with mode `000`, ends the command with exit code 1 and the line `The files of the project cannot be read: build.gradle cannot be opened`, and `--diff --json` writes a document with the outcome `failed` and the reason `unreadable-file`, as for a directory that cannot be read. Before, a file of the baseline made the command say that the baseline could not be read, `--json` wrote no document at all, and a file of the record without a copy in the baseline was listed as `changed`. Make the file readable to compare it.

*`feature add --dry-run --json` and `project regenerate --diff --json`* write their result as one JSON document (format 1) with an `outcome` and a `reason`, for a program. The exit codes are those of the commands without `--json`. See link:commandLine.html#changeResultsForAProgram[Output for a Program].

*The keys of generated YAML files are in an order that depends on the keys alone.* In `application.yml` and the other YAML files the generator writes, `info`, `dataSource`, `environments`, `hibernate` and `grails` come first and every other top-level key follows alphabetically; under `environments`, `development`, `test` and `production` come first; below that the order is alphabetical. Earlier builds of Grails 9 wrote the keys in the order of the features, so adding a feature could move whole blocks and collide with your own changes.

A project generated by such a build needs no change. `feature add` accepts its baseline, leaves the keys of its files where they are, and puts only the keys of the new feature among them. The baseline under `.grails/baseline` is rewritten in the new order the first time a feature is added; until then `project regenerate` refuses the project.

*What three features and one type generate has changed.* Compared with Grails Forge of Grails 8 and with earlier builds of Grails 9:

* `views-markup` no longer writes `grails-app/views/object/_object.gml`, which the task that compiles markup views failed on, and its other views read `g`, `request`, `response`, `messageSource` and `locale` through `this.`. The Gradle plugin `org.apache.grails.gradle.grails-markup`, which failed when it was applied (`Cannot invoke method get() on null object`), can be applied.
* `cache-ehcache` gives the application Ehcache 3 through JCache, and no plugin. Grails Forge of Grails 8 declared `org.grails.plugins:cache-ehcache:3.0.0`, a plugin for Grails 3 that is in none of the repositories a generated application reads, and earlier builds of Grails 9 declared `5.0.0-RC1`, a release candidate that Grails 9 does not load: its classes need the classic call sites of Groovy (`org.apache.groovy:groovy-callsite`), which Grails 9 does not ship, so the default cache manager of the cache plugin stayed in place, and since the release candidate brings the cache plugin only to the runtime class path, a class using `@Cacheable` did not compile. The feature now requires `cache` and adds `org.apache.grails:grails-cache` and the Jakarta EE variant of `org.ehcache:ehcache` (`requireCapability("org.ehcache:ehcache-jakarta")`), both in the versions the BOM manages. It writes `grails-app/conf/ehcache.xml`, with a default template and an example cache, and the class `JCacheGrailsCacheManager` in `src/main/groovy`, and defines the beans `jCacheManager` and `grailsCacheManager` in `grails-app/conf/spring/resources.groovy`; see link:cache.html#cacheEhcache[Ehcache through JCache]. It no longer sets `grails.cache.ehcache.ehcacheXmlLocation` and `grails.cache.ehcache.lockTimeout`, which only the plugin read, the `cache` feature does not set `grails.cache.cacheManager` beside it, and it is offered for `web` and `rest-api` applications only: a plugin leaves the cache provider to the application that uses it.
* A REST API plugin (`create-rest-api-plugin`) has an empty `UrlMappings` and no controller or views of its own, as the `rest-api-plugin` profile created it; earlier builds of Grails 9 gave it those of a REST API application.

===== Required Actions

* *An application with `views-markup` that an earlier build of Grails 9 or Grails Forge of Grails 8 generated*: delete `grails-app/views/object/_object.gml` if the application does not compile with it, and write `this.` in front of `g`, `request`, `response`, `messageSource` and `locale` in its markup views.
* *An application with `org.grails.plugins:cache-ehcache`*, which Grails Forge of Grails 8 or an earlier build of Grails 9 generated, moves to Ehcache through JCache: in `build.gradle` replace the plugin with `implementation "org.apache.grails:grails-cache"` and `implementation("org.ehcache:ehcache") { capabilities { requireCapability("org.ehcache:ehcache-jakarta") } }`, add `grails-app/conf/ehcache.xml`, `JCacheGrailsCacheManager` and the two beans of `resources.groovy` as an application generated with the feature has them, and remove `grails.cache.ehcache.ehcacheXmlLocation` and `grails.cache.ehcache.lockTimeout` from `application.yml`. Caches that an `ehcache.xml` of the plugin configured in the format of Ehcache 3 go into the new file as they are; a cache the file does not configure is created from its default template. There is no release of the plugin that Grails 9 loads, so the result of the plugin cannot be kept; to keep the cache manager of the cache plugin instead, remove `org.grails.plugins:cache-ehcache` and the `grails.cache.ehcache` settings, which is what an application with the release candidate ran with.
* *Do not reorder an existing `application.yml`* to match the new order. `feature add` keeps the order a file has.
* *To change a default feature for another*, run `grails feature add <feature>`, `postgres` for the default `h2` for example, in the place of editing the build and the configuration by hand. If the feature it would replace was named in `--features` when the application was created, or was added by name, add `--replace`: `grails feature add mysql --replace`.
* *After a conflict on lines of the default*, restore the generated line, add the feature, and make your change again.

==== 53. `test-app` Runs Every Test Phase and a Named Test Where It Is Found, and `project show` Lists Every Option

*`grails test-app` runs every test phase of the project.* The command ran the Gradle tasks `test` and `integrationTest`. It now runs the task `testApp` of the Grails Gradle plugin, which runs every task of the type `Test` the project has: beside those two, a phase of the `testPhases` extension such as `functionalTest`, a test suite of Gradle's `jvm-test-suite` plugin, and a `Test` task a build plugin or the build script registers. A project that has such a task now gets it run by `grails test-app`, and by every job that calls the command, with whatever the phase needs (a browser, containers, a service that has to be running) and for as long as it takes.

A phase is selected with a switch of its name, and several switches select several phases: `--unit` and `--integration` as before, and for any other phase the name of its task without the ending `Test`, in lower case with hyphens, as `--functional` for `functionalTest` and `--end-to-end` for `endToEndTest`; a `Test` task whose name does not end in `Test` has the switch of its own name. An option of the command is never the switch of a phase, so a task `cleanTest` is run with `grails gradle cleanTest`. The build lists the phases of the project for the command line whenever it compiles the project (or with `grails gradle grailsCommandCatalog`), after which `grails help test-app` shows their switches and a switch that is none of them is refused; until then a switch that is no option of the command is taken for a phase, and Gradle fails with the phases the project has when it has none of that name.

The unit tests are run before the integration tests, and both before the other phases. The Grails Gradle plugin orders the `Test` tasks of a project so in every build (`mustRunAfter`), `./gradlew check` included: where Gradle ran `test` and `integrationTest` of one project in parallel, as it can with the configuration cache, it now runs one after the other.

*`grails test-app` with the name of a test*, as in `grails test-app BookControllerSpec` or `--tests '*BookSpec'`, runs the test where it is found. The name is given to every phase that is run; a phase that has no such test passes, and `testApp` fails the build, naming the filter, when no phase ran a test. For test tasks that are named one by one in a command line of Gradle, the project property `grails.test.filter.lenient` of the Grails Gradle plugin does the same: a test task without a match passes, and the task `checkTestFilterMatched` fails the build when no test task ran a test.

A phase that is left out of the build (`grails test-app -- -x functionalTest`) or that the build skips (an `onlyIf` of the build script, `enabled = false`) runs no test, and what it found in an earlier build does not count: when only such a phase has the named test, `testApp` fails, as does `checkTestFilterMatched` with `grails.test.filter.lenient`, and when no phase runs at all it fails with `No test task ran for the given filter (...)`. A phase that is up to date or taken from the build cache still counts the tests of the run whose results it has. To run a named test, do not leave out or skip the phase that has it.

`--clean` runs the tests of every phase that is run again (`--rerun-tests` of `testApp`), also where the build cache has their results; it no longer runs the tasks `cleanTest` and `cleanIntegrationTest`. `--debug-jvm` starts the JVM of every phase that has tests to run suspended, one after the other on port 5005.

The command needs the Grails Gradle plugin of Grails 9 in the build of the project. In a project whose build still has an earlier one, Gradle says that there is no task `testApp` and nothing is run.

*`grails project show` lists every option* of the `create-` command with the value the application was generated with, also the options that were not given, and marks each `default`, `differs from the current default: VALUE` or `not recorded`, compared with the version of the command line that is running. The defaults of a later version of Grails can differ, and the list says what the application has whatever they are. The `create-` command in its last line has every option whose recorded value is not the current default, `--subproject` included. For an application made from a preset it has `--jdk`, `--servlet`, `--data` and `--reloading` whatever their values, because a preset gives these options defaults of its own and the record does not say whether an option came from the preset. For an application whose record `project migrate` wrote, its `--features` names the features that were found in the project as well as those that were given, and a line before it names the ones that were found. `--json` has two more members, `effectiveOptions` and `addedFeatures`; `format` is still 1.

===== Required Actions

* *A project that has a `Test` task beside `test` and `integrationTest`* (functional tests, a test suite of Gradle, a task of a build plugin): decide whether `grails test-app` is to run it where the command is called, in jobs above all. To run what the command ran before, name the two phases: `grails test-app --unit --integration`. To leave one task out: `grails test-app -- -x functionalTest`.
* *A project that has a task named `testApp` of its own* gives it another name: the Grails Gradle plugin does not register its task over it and says so, and `grails test-app` would run the task of the project.
* *A build script or a job that ran `./gradlew test --tests X integrationTest --tests X`* and failed where only one of the two had the test runs `./gradlew testApp --tests X` or `grails test-app X`, or adds `-Pgrails.test.filter.lenient=true`.
* *After an upgrade, run `grails project show`* to see which recorded values are no longer the defaults.

Script commands are deprecated: the scripts of an application and of other plugins still run (notes 33 and 34), and `create-script`, which wrote one, is removed (note 42).

A command of a plugin is run in one of three ways, as every command of an application and its plugins is (note 46):

[source,console]
----
$ grails s2-quickstart com.example User Role
$ grails run-command s2-quickstart com.example User Role
$ ./gradlew runCommand -Pargs="s2-quickstart com.example User Role"
----

All three work as soon as the plugin is a dependency of the project; in a project the build has not compiled yet, the first has the build list the commands of the application and its plugins first. These commands only write files of the project, so they are run without the application being started (they are `StandaloneCommand` classes, as `query-tail` is): the Gradle task `runCommand` compiles the project and calls the command, so the project has to compile, and need not be able to start.

What the commands do differently from the scripts:

* *`s2-quickstart` creates the Requestmap class, takes `--uiOnly`, and refuses `--salt`.* Grails 7 and 8 had the command twice, as the script the shell ran and as a compiled command for `runCommand`, and the two did not do the same. There is one now, and it does what the script did where the script was right. Through `runCommand` the fourth argument, the name of the Requestmap class, created no class and no settings, and `--uiOnly` was refused; both work. `--salt` is refused: the listener it generated could not be compiled. Fewer than three or more than four arguments, a package or a class name that is none, and an option the command does not have fail the command before it writes anything.
* *The settings go to `application.groovy` when the project has one, and to `application.yml` otherwise.* The three commands of Spring Security Core append their settings to `grails-app/conf/application.groovy` when the project has that file, to `grails-app/conf/application.yml`, as one more YAML document at its end, when it has only that, and to a new `application.groovy` when it has neither. The scripts always wrote `application.groovy`. The compiled `s2-quickstart` of Grails 8 wrote YAML that put `authority.className`, the static rules and the filter chain map under `grails.plugin.authority`, where the plugin does not read them.
* *`s2-quickstart` writes nothing when the configuration already has a setting that it writes.* The scripts appended their settings on every run, after the ones that were there, which they replaced without a word: a second run dropped what had been changed since the first, and so would a run in an application created with the `grails-spring-security` feature, which would lose the rule of the feature that restricts `/user/**` to `ROLE_ADMIN`. The command reads `application.groovy` and `application.yml`, both, before it writes anything. When either has a setting that the run would write (the names of the domain classes, `useRoleGroups`, `authority.groupAuthorityNameField`, `requestMap.className`, `securityConfigType`, `controllerAnnotations.staticRules` or `filterChain.chainMap`, as far as the run writes them; with `--uiOnly` the last two), outside the environment blocks or in the block of any environment, whichever environment the command runs in (`environments.<name>` of a YAML document, an `environments` block of `application.groovy`), the command names each file with the keys it has, and the environment of a block that sets them, fails, and writes no class, no listener and no setting. A rule that only production has counts too: the appended YAML document would replace it in production. It fails in the same way when it cannot read one of the files, and when the code of an environment's block in `application.groovy` fails outside that environment, since the command runs the blocks of all environments to read the file. Other settings of the plugin do not count. With `--force` it writes as the scripts did.
* *The user class does not hash its password itself.* `s2-quickstart` writes `<User>PasswordEncoderListener` to `src/main/groovy` and registers it as a bean in `grails-app/conf/spring/resources.groovy` (in a plugin project without that file, in `doWithSpring()` of the plugin class); the listener hashes the password when a user is saved. In an application without a `gormVersion` in its `gradle.properties`, as the applications that Grails 7 and 8 create are, the script of Grails 7 and 8 generated a user class that hashes the password through a `springSecurityService` property instead. Nothing injects that property into a domain class, so such a class stored the password as it was given.
* *`s2-create-persistent-token` and `s2-create-role-hierarchy-entry`* take one class name with its package, and fail without writing anything for no name, more than one, a name without a package, or an option.
* *`init-oauth2` answers to its name.* The compiled command of Grails 8 could only be run as `init-o-auth2`, the name its class gives; that name is no command any more. The command creates `grails-app/conf` when the project has none and does not run the `BootStrap` classes of the application, and neither does `s2-create-acl-domains`.
* *`s2ui-override` and `s2ui-create-challenge-questions` say what is wrong with their arguments* and write nothing, where the scripts ended with an exception: no type or a type that is none, too many arguments, a package or class name that is none, and a number of questions that is not a number of 1 or more. The challenge questions class names the user class as it was given; the script wrote `AppUser` as `Appuser`.
* *`create-job`* is a command of `grails` in a project whose record has the `grails-quartz` feature (note 45). It needs neither the plugin on a class path nor the build. `create-job NightlyJob` and `create-job Nightly` both write `NightlyJob.groovy`.
* *`create-functional-test`* is a command of `grails` in a REST API application or REST API plugin, where it writes a test that calls the application with the HTTP client of the JDK, and in a web application or web plugin whose record has a Geb feature, where it writes a Geb test: one that extends `ContainerGebSpec` with `geb-with-testcontainers`, which a web application has by default, and `GebSpec` with `geb-with-local-browsers`. The script of the Geb plugin only wrote a `GebSpec`. `create-functional-test BookSpec` writes `BookSpec.groovy`, where the script wrote `BookSpecSpec.groovy`, and a file that is there already is kept and fails the command unless `--force` is given. In a web application without a Geb feature it is no command: `grails feature add geb-with-testcontainers` adds the feature, and `grails project migrate` finds it in the build of an application that was not generated by Grails 9 (note 45).
* *The templates of `create-job` and `create-functional-test`* that a project has under `src/main/templates/Job.groovy` and `src/main/templates/FunctionalSpec.groovy` are still used, as text in which `${className}` and the other names in braces are replaced (note 45). The templates of the Spring Security commands are still replaced by a file of the same name under `src/main/templates` of the project.

*`query-tail` is new in Grails 9, and is a command.* Grails 8 has no `query-tail`. Earlier builds of Grails 9 had it as a script that was run with `./gradlew runScriptCommand --arg=query-tail`; it is a command of Grails Data now, run with `grails run-command query-tail`, with `./gradlew runCommand --arg=query-tail`, or as `grails query-tail`. It is a command that runs without the application (`org.apache.grails.core.cli.StandaloneCommand`, note 46): it reads the capture file a running application writes, and starts no second instance of that application. It takes the options the script took, and `--help` prints them. See link:conf.html#queryTail[Finding Query-Heavy Pages with query-tail].

===== Required Actions

* *Replace `grails <script>` and `./gradlew runScriptCommand --arg=<script>`* for the scripts of the table with `grails run-command <name> <arguments>` or `./gradlew runCommand -Pargs="<name> <arguments>"`, and `grails create-job` and `grails create-functional-test` with themselves: they need the feature in the record of the project, not the plugin.
* *Check the user class of an application that ran `s2-quickstart` with Grails 7 or 8.* When the class declares `SpringSecurityService springSecurityService` and calls `encodePassword()` in `beforeInsert`, and the application has no bean that hashes the password (a `<User>PasswordEncoderListener`, or code of your own), look at the stored passwords: if they are not hashed, add a listener as the command of Grails 9 generates it, remove the property and the methods from the class, and hash or reset the passwords that are stored.
* *Check the settings of an application that ran `s2-quickstart` through `runCommand` with Grails 8*: the keys of `grails.plugin.springsecurity` in `application.yml` have to be where the guide of the plugin has them.
* *Replace `init-o-auth2`* with `init-oauth2` where a build ran the command through `runCommand`.
* *Remove `--salt`* from a call of `s2-quickstart`.
* *Give `--force` to a call of `s2-quickstart`* that runs in a project whose configuration already has its settings, as a build or a script that runs it again does, and merge the settings that were there into the ones it appends, which replace them. In an application created with the `grails-spring-security` feature, use the classes of the feature instead. An appended YAML document also replaces the settings of every environment, while an environment of the top-level `environments` block of `application.groovy` keeps its own value: merge the rules of an environment into an `environments` block for it in the appended document, or into its block of `application.groovy`.
* *An application that has `application.groovy` and `application.yml`* finds the settings of the Spring Security Core commands in `application.groovy`.
* *A build of an earlier Grails 9 that ran `runScriptCommand --arg=query-tail`* runs `runCommand --arg=query-tail`.

[[upgradingSpringFormatNegotiation]]
==== 56. Opt Into Spring MVC Content Negotiation for Grails Formats

Set `grails.mime.negotiation.spring: true` to resolve `request.format`, `response.format`, `withFormat` and the format
`respond` writes in with Spring MVC's content negotiation manager, and to have the `format` parameter, URL extensions and
the `grails.mime` settings of the `Accept` header decide what Spring MVC writes for an action too (see
<<springFormatNegotiation,Resolving Formats with Spring MVC Content Negotiation>>). Grails 9 keeps its own rules by
default, and Grails 10 makes the setting the default, so an application should check these answers before then.

[source,yaml]
.grails-app/conf/application.yml
----
grails:
    mime:
        negotiation:
            spring: true
----

The setting changes these answers, which the framework's tests record by running the same requests both ways:

* *The order of the `Accept` header.* Spring MVC takes a more specific type ahead of a less specific one of equal
quality, where the Grails rules keep the order of the header: `Accept: */*, application/json` is the `json` format,
where it is `all` without the setting, and `withFormat` runs the `json` block rather than its first. A type with the
`+xml` suffix still comes ahead of the XML type of equal quality: `Accept: application/xml, application/atom+xml` is
`atom` either way, and Spring MVC now writes what an action returns in that order too. It now also comes ahead of a
`text/xml` the header lists without `application/xml`, which the Grails rules leave first:
`Accept: text/xml, application/atom+xml` is `atom`, where it is `xml` without the setting, and
`Accept: text/xml, application/xhtml+xml` is `html`, so `withFormat` runs its `html` block rather than its `xml` one.
* *Types with the `+json` and `+xml` suffixes.* A type no configured type names, such as `application/merge-patch+json`,
`application/soap+xml` or, without a `hal` format, `application/hal+json`, is the `json` or `xml` format, where the
Grails rules read only the problem types of RFC 9457 so and answer any other as `all`. In `Content-Type` too: a body sent
as such a type is of the `json` format, where its `request.format` is otherwise `null`, and data binding reads it as JSON.
* *A request that accepts no configured type.* Such a request, as one that sends only `Accept: image/png`, and one whose
`Accept` header Spring cannot read, such as `Accept: application/json;q=abc`, is not acceptable: `response.format` and
`response.mimeType` are `null`, `respond` answers `406 Not Acceptable` and `withFormat` runs its `*` block, or no block,
where the Grails rules answer as for a client that accepts any type, with the `all` format, or read the header
leniently. Code that reads `response.format` or `response.mimeType` must allow for `null`.
* *The `format` parameter and URL extensions.* A format no type is configured for is not acceptable, to `respond`, which
answers `406`, and to what Spring MVC writes, where the Grails rules answer in the first configured format;
`withFormat` answers it from the `Accept` header, as for a format it has no block for. A format only Spring MVC's
content negotiation manager maps decides what Spring MVC writes, as without the setting where
`spring.mvc.contentnegotiation.favor-parameter` is on, while `respond` still answers `406` for it. That is a format
`spring.mvc.contentnegotiation.media-types` adds, such as `plain: text/plain`, one Spring MVC registers for the types
its message converters support, or a data format Grails registers with the manager written in another case, such as
`?format=JSON` or `?format=HAL` (see
<<upgradingGrailsFormatResolution,Grails Format Resolution and Spring MVC Content Negotiation>>). The `all` format
leaves the format to the `Accept` header: `?format=all` with `Accept: application/json` is `json`, where it is
otherwise `all`. The first value of the parameter counts.
* *What Spring MVC writes for an action.* The `format` parameter and URL extensions now decide the type of a
`ResponseEntity`, a `ProblemDetail` or another value Spring MVC writes for a request a URL mapping handles, where Spring
MVC read only the `Accept` header: `/book/show/1.json` is answered in JSON whatever the `Accept` header asks for, and
`/book/show/1.html` of an action that returns a map with `406`, since no message converter writes a map as HTML.
`grails.mime.use.accept.header: false` and `grails.mime.disable.accept.header.*` now ignore the `Accept` header for it
too.
* *Without the `all` format.* Where `grails.mime.types` does not list `all`, a request without an `Accept` header is of
the `all` format, as one that sends `Accept: */*` is, where the Grails rules give the first configured format, so
`withFormat` runs its `*` block, or its first block, rather than the block of that format. A type of quality `0` comes
after any other, so `Accept: application/json;q=0, */*;q=0.1` is `all`, where it is otherwise `json`. `?format=all`
leaves the format to the `Accept` header there too, where the Grails rules give the first configured format.
* *Wildcards.* A wildcard such as `text/*` is the `all` format as before, but `withFormat` runs the first block of a
format with a type compatible with it, and `respond` answers in the first such format of the action, where the Grails
rules run the first block and answer in the first format: `withFormat { pdf {...}; html {...} }` runs the `html` block for
`Accept: text/*`.
* *A `Content-Type` Spring cannot read.* A `Content-Type` Spring rejects, such as `application/json;charset=` or a list
of types, is of no format, where the Grails rules read it leniently as `json`.

Other requests resolve as before, among them those of browsers and those that name one configured type. A Spring MVC
endpoint, and Spring Security's filters before a URL mapping has matched a request, negotiate as before.

[[upgradingProjectHealth]]
==== 57. `grails project health` Says What Is Left of an Upgrade

`grails project health` is a new command of a project. It reads the files of the project as text and says what they show of its state: what makes the build fail (an error), what an upgrade note requires and is not done, or what is deprecated for removal (a warning), and what the guide recommends (advice), each with an id, such as `removed-dependency.profile`, and what to do. It changes nothing and runs no Gradle, no generator, no Git and nothing of the network. It ends with exit code 1 when there is an error, and with `--strict` when there is a warning too; `--json` writes every finding as one JSON document for a tool, and `-v` lists the checks that found nothing as well.

It runs in a project whose `gradle.properties` still names Grails 7 or 8, as `project migrate` does, and says there what Grails 9 asks of the project:

[source,console]
----
$ grails project health
| Project legacy on Grails 8.0.1 (gradle.properties), checked by the command line of Grails 9.0.0, offline
| Error   removed-dependency.profile  build.gradle declares the profile dependency org.apache.grails.profiles:web: Grails 9 has no profiles, and the build fails while it is configured. Fix: Remove the profile line from the dependencies of build.gradle; nothing takes its place
| Warning grails-version.earlier      The project is on Grails 8.0.1 (gradle.properties), and the command line is of Grails 9.0.0: what is found is what Grails 9 asks of the project. Fix: Work through the upgrade notes of Grails 9, set grailsVersion in gradle.properties to 9.0.0, and run ./grailsw update-wrapper
| Warning record.missing              The project has no record (.grails/project.yml or grails-forge-cli.yml): the commands that create its classes are not there. Fix: grails project migrate writes it from the files of the project; commit .grails
| Advice  leftover.profile-config     grails-app/conf/application.yml sets grails.profile, which Grails 9 does not read: an application has no profile. Fix: Remove grails.profile from grails-app/conf/application.yml
...
| 6 checks OK (-v lists them). 1 error, 3 warnings, 3 advice, 0 skipped
| Error project health found 1 error: removed-dependency.profile
----

Each note above says in its Required Actions which of its changes the command reports, and as which id. What it reports is what a file shows: a dependency `build.gradle` declares, a version `gradle.properties` or the Gradle wrapper names, the record under `.grails`, the Grails wrapper, `.gitignore` and `.gitattributes`, `.sdkmanrc`, `~/.grails/settings.groovy` and the environment. What the application does when it runs, the sources of the application and the command lines of scripts and jobs are not checked: the notes say what to look for there. A project that `create-app` has just generated has no error and no warning. `project migrate`, and `update-wrapper` when it replaces the wrapper of an earlier major version, end with a line that names the command.

===== Required Actions

* Run `grails project health` (or `./grailsw project health`) in the project after `update-wrapper` and `project migrate`, resolve every error and warning it names, and run it again until `grails project health --strict` ends with exit code 0. Then work through the notes above that the command does not check.
* A job of continuous integration that holds a project to the upgrade notes runs `grails project health --strict`. A tool reads `grails project health --json` and goes by the `id` of each finding, which is never renamed; link:{commandLineRef}project-health.html[project health] lists every id with its level and fix.

[[upgradingCommandLineJava]]
==== 58. The Command Line Needs Java 21, and `project migrate` Reads the Java Version of the Build

The `grails` command line and the Grails wrapper are compiled for Java 21. Their start scripts (`grails`, `grails.bat`, `grailsw`, `grailsw.bat`) now read the version of the Java they are about to start from the `release` file of its installation and refuse an earlier one with a message that names it, such as `ERROR: grailsw needs Java 21 or later, and JAVA_HOME (/opt/java/jdk-17.0.18) is Java 17.0.18.`, and exit code 1, where the JVM ended with `UnsupportedClassVersionError` before (see xref:commandLine[The Command Line]). A `grailsw` of an earlier Grails 9 snapshot has the check once `./grailsw update-wrapper` has replaced it.

`project migrate` reads the version of Java of the build from `compileJava.options.release` (or `options.release = N`, `options.release.set(N)` and `release` in a block of the options), `targetCompatibility`, `sourceCompatibility`, a `JavaVersion` constant and the Java toolchain (`JavaLanguageVersion.of(N)`, or `jvmToolchain(N)` of Kotlin), in `build.gradle` and `build.gradle.kts`, in that order, and names the setting and its line in the `jdk` row, such as `21 (compileJava.options.release of build.gradle, line 68)`. An application that Grails 8 generated for Java 17 has `compileJava.options.release = 17`: the command now says that Grails 9 needs Java 21 or later and that the build has to be changed, and records Java 21 as assumed in place of it, where an earlier Grails 9 snapshot recorded Java 21 as assumed and said nothing.

`grails project health` reads the build the same way. It reports each setting before Java 21, with its line, as `java-target.release`, and a record that `project migrate` wrote with another version of Java than the classes are compiled for as `java-target.record`.

===== Required Actions

* Set `JAVA_HOME` to Java 21 or later, or put a Java 21 or later first on the path, wherever `grails` or `./grailsw` runs, in jobs of continuous integration too. See xref:gettingStarted#requirements[Installation Requirements].
* Change every setting of the build that names a Java before 21 to 21 (or 25), as `compileJava.options.release = 21`, and run `grails project migrate --force` if the record was written before, so that it has the version of the build.

[[upgradingRecordIgnoresMachineState]]
==== 59. The Record Keeps What Is of One Machine Out of Version Control

The `.grails/.gitignore` that `create-app`, the other create commands and `project migrate` write now leaves out `.grails/cache/`, `.grails/history`, `.grails/run/` and `.grails/transactions/` itself, so they stay out of version control also in an application whose root `.gitignore` is older than Grails 9, and committing the directory `.grails` commits the record and nothing else. A `.grails/.gitignore` that is there already is not rewritten: where an earlier Grails 9 snapshot wrote the record, add these lines to it:

[source]
.grails/.gitignore
----
/cache/
/history
/run/
/transactions/
----

`grails project health` reports a project in which no `.gitignore` leaves out `.grails/transactions` or `.grails/history`, neither that of the project nor that of the record, as `git-files.state-ignored`, and names the lines to add to `.grails/.gitignore`. A record whose `.gitignore` has the lines is in order whatever the `.gitignore` of the project says.

===== Required Actions

* Where an earlier Grails 9 snapshot wrote the record, add the four lines above to `.grails/.gitignore`, and take `.grails/transactions`, `.grails/history`, `.grails/run` and `.grails/cache` out of version control if they were committed (`git rm -r --cached` with the paths).

[[upgradingGradleChecksum]]
==== 60. The Generated Gradle Wrapper Names the Checksum of Gradle

`gradle/wrapper/gradle-wrapper.properties` of a generated application has `distributionSha256Sum`, the SHA-256 Gradle publishes for the distribution it names, Gradle {gradleVersion}, and the Gradle wrapper refuses a download that does not have it. To move the application to another Gradle version, give its checksum from https://gradle.org/release-checksums/[Gradle's checksums]: `./gradlew wrapper --gradle-version <version> --gradle-distribution-sha256-sum <checksum>`. Running that with the version the application has adds the checksum to an existing application.

`grails project health` reports a wrapper without `distributionSha256Sum` as `gradle-wrapper.checksum`, and a wrapper of the binary distribution of Gradle {gradleVersion} on `services.gradle.org` whose `distributionSha256Sum` is not the one Gradle publishes for it as `gradle-wrapper.checksum-differs`: the wrapper refuses that distribution wherever it downloads it.

===== Required Actions

* Add `distributionSha256Sum` to the wrapper of an application that has none, with the command above and the version the application has.
* Give the checksum of the new version with `--gradle-distribution-sha256-sum` whenever the Gradle version of the application changes: the checksum of another version makes the wrapper refuse the download.

[[upgradingNeo4jBom]]
==== 61. An Application With GORM for Neo4j Imports `grails-neo4j-bom`

An application with GORM for Neo4j imports `grails-neo4j-bom` as its one Grails BOM, in place of `grails-bom`, also when it uses GORM for Hibernate 5. Grails 8 and earlier snapshots of Grails 9 generated such an application with `grails-bom`, and its runtime class path does not resolve: GORM for Neo4j needs version 4.4.13 of the Neo4j driver, which `grails-neo4j-bom` holds strictly, while `grails-bom` manages the driver of Spring Boot (6.3.0 with Spring Boot 4.2). Compiling such an application succeeds, since a compile does not resolve the runtime class path, but `bootRun`, its tests and its commands fail with `Could not resolve org.neo4j.driver:neo4j-java-driver:4.4.13` and `conflicting requirements`; `grails help` and `grails project health` name the class path as one that does not resolve (note 46). `grails-neo4j-bom` imports `grails-bom` and adds only the driver and the Neo4j test harness, so the application keeps every other version. What the command line of Grails 9 does:

* `grails create-app` writes `grails-neo4j-bom` for `--data neo4j`, the feature `gorm-neo4j` and a preset or feature pack that brings it, in the `dependencies` and the `buildscript` block of `build.gradle` and, with the feature `gradle-build-src`, in `buildSrc/build.gradle`. `grails feature add gorm-neo4j` replaces `grails-bom` with it in an application that Grails 9 generated.
* The create commands, `feature add` and the hosted Forge refuse `gorm-neo4j` with `gorm-hibernate7` (`--data hibernate7`) and with `grails-micronaut`, which no Grails BOM covers together, with a message that starts `gorm-neo4j cannot be combined with` (the command line ends with exit code 2). `feature list` gives that reason for a feature that cannot be added, and `--list-features` marks the feature with `(cannot be combined with ...: no Grails BOM covers both)`.
* `grails project migrate` does not change the build file of an application that an earlier Grails 9 snapshot generated with GORM for Neo4j and `grails-bom`; `grails project regenerate --diff` names `build.gradle` until the BOM is replaced.

===== Required Actions

* In an application with GORM for Neo4j (`org.apache.grails:grails-data-neo4j`), replace `grails-bom` with `grails-neo4j-bom` wherever the build imports it, keeping the version: `implementation platform("org.apache.grails:grails-neo4j-bom:$grailsVersion")`, `classpath platform("org.apache.grails:grails-neo4j-bom:$grailsVersion")`, and `buildSrc/build.gradle`. A build that lets the Grails Gradle plugin import the BOM sets `grails { bom = 'grails-neo4j-bom' }`.
* To keep `grails-bom`, hold the driver with a version of the application's own that no BOM moves, `implementation('org.neo4j.driver:neo4j-java-driver') { version { strictly '4.4.13' } }`, at the version `grails-neo4j-bom` manages; the BOM is the simpler way.
* Scripts that create an application with GORM for Neo4j together with Hibernate 7 or Micronaut fail now, where the application they made did not run; keep GORM for Neo4j with Hibernate 5, or put the Neo4j data in an application of its own.
