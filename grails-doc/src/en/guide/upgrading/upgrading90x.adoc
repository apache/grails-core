=== Upgrade Instructions for Grails and Related Dependencies

To ensure compatibility with Grails {version}, please review the following upgrade instructions carefully.
This guide outlines the necessary steps and warnings to upgrade your Grails project from Grails 8.x to Grails 9.

==== 1. GPars Integration Deprecated in Favour of Groovy Concurrency

Grails 9 builds on Groovy 6, which brings a unified concurrency and parallel-processing toolkit into core under https://groovy-lang.org/releasenotes/groovy-6.0.html#concurrency-toolkit[GEP-18: Integrated Concurrency and Parallel Processing]. The `groovy.concurrent` package provides `Awaitable`, `DataflowVariable`, `Actor`, `Agent`, `Pool`, `ParallelScope` and the parallel collection methods such as `eachParallel` and `collectParallel`. The Groovy release notes describe the toolkit as modernising the patterns from GPars around virtual threads, structured concurrency and Groovy 6's `async`/`await`, and state that previous users of GPars will find much of its functionality there.

With those patterns part of the language, Grails no longer needs the separate GPars library, which was last released in 2014 and depends on Groovy 2.x and the Multiverse STM engine. The `grails-async-gpars` and `grails-events-gpars` modules remain available in Grails 9 but are deprecated for removal: their classes carry `@Deprecated(since = '9.0', forRemoval = true)` and log a warning when selected. They will be removed in a future release.

Their replacements are `grails-async-groovy-concurrent`, providing `org.grails.async.factory.groovy.AwaitablePromiseFactory`, and `grails-events-groovy-concurrent`, providing `org.grails.events.groovy.ActorEventBus`. Both are selected the same way the GPars modules are, by adding the dependency in place of the GPars one:

[source,groovy]
.build.gradle
----
runtimeOnly 'org.apache.grails.async:grails-async-groovy-concurrent'
runtimeOnly 'org.apache.grails.events:grails-events-groovy-concurrent'
----

Do not keep both the GPars and the Groovy module on the classpath: only the first service-loaded `PromiseFactory` is used, and the event bus builder refuses to start when more than one `EventBus` implementation is found.

The Groovy promise factory follows the failure contract of the default `CompletableFuture` factory rather than the GPars one: direct and chained `get()` calls throw `ExecutionException` with the original failure as the cause, a single-promise `onError` recovers with its callback result, and the aggregate `onError` observes the failure and leaves the returned promise failed. `onComplete` and `then` return a new promise instead of the receiver. Promises created by this factory are also Groovy `Awaitable` instances and can be passed to `await` directly.

The Groovy actor event bus delivers each event to its subscribers in publication order on a single Groovy actor. A subscriber that throws without a reply handler is logged and does not stop delivery to the remaining subscribers or later events.

Applications that use GPars directly, for example `GParsPool.withPool { list.eachParallel { } }`, should move to the Groovy equivalents: the parallel collection methods are available on every `Collection` without a pool, and `groovy.concurrent.ParallelScope.withPool(n) { scope -> list.eachParallel { } }` runs them on a pool of a chosen size. Once the deprecated modules are removed, Grails will no longer bring GPars onto the classpath, so an application that still needs it must declare `org.codehaus.gpars:gpars` itself.

NOTE: Groovy 6 marks the concurrency toolkit as incubating. The Grails modules that build on it expose only the Grails `Promise` and `EventBus` contracts, so changes to the Groovy API in later Groovy releases are absorbed by Grails rather than by application code.

==== 2. Groovy Code Is Compiled with invokedynamic

Grails 8 compiles every Groovy source set of an application without invokedynamic (`grails { indy = false }` was the default). Grails 9 leaves the setting unset, so the Groovy compiler's own default applies, and on Groovy 6 that is invokedynamic. An application that set `grails { indy = true }` can remove the line. Build logic that read the property, for example `grails.indy.get()`, must allow for it having no value now: use `grails.indy.getOrElse(true)` or check `grails.indy.present`.

An application that has to keep classic call sites, for example while it measures the difference, sets the property explicitly. An application that applies GraalVM's native image plugin cannot: the build fails with the reason, because an image needs invokedynamic.

To keep classic call sites:

[source,groovy]
.build.gradle
----
grails {
    indy = false
}
----

Classic call sites on Groovy 6 need `org.apache.groovy:groovy-callsite` on the classpath. Grails does not carry it, so an application that sets `indy` to `false` declares `implementation 'org.apache.groovy:groovy-callsite'` itself, at the version the Grails BOM manages, and again for every source set that does not see its implementation dependencies, such as the test fixtures of Gradle's `java-test-fixtures` plugin. Without it the Groovy compiler stops with a message naming the module.

A library compiled with classic call sites needs the module too, whatever the application's own setting, because Groovy 6 loads such a class only with it; the failure is a `NoClassDefFoundError` naming `org.codehaus.groovy.runtime.callsite.CallSiteArray`. Spock 2.5, Geb 8 and the Asset Pipeline 5.2 are compiled with invokedynamic, but `org.testcontainers:testcontainers-spock` is not, so an application that uses it declares `testRuntimeOnly 'org.apache.groovy:groovy-callsite'` next to it.

==== 3. `grails.converters.JSON` Can Write JSON With Spring Boot's JsonMapper

In Grails 9, `render ... as JSON`, `respond` for a JSON request and every other use of `grails.converters.JSON` still
render JSON as Grails 8 did, by default (see <<renderingJsonAsGrails8,Rendering JSON As Grails 8 Did>>). Setting
`grails.converters.json.legacy` to `false` makes the JSON converter write JSON through the application's Jackson
`JsonMapper`, the one Spring Boot auto-configures, so that it renders values as a Spring Boot application does. A later
release makes that the default, so check your application's JSON with the setting before you upgrade to it:

[source,yaml]
----
grails:
    converters:
        json:
            legacy: false
----

While `grails.converters.json.legacy` is not set, Grails logs a warning once at startup that the default will change.
Setting it to either value turns the warning off.

With the setting `false`, the mapper writes the JSON text (numbers and pretty printing), and writes every single value
that it has a dedicated serializer for: dates and times, `Month`, `UUID`, `Locale`, `byte[]`, types with a `@JsonValue`,
and the types of any Jackson module registered with the application. Those values render as Spring Boot renders them,
and `spring.jackson.*` properties apply to them. For example, `spring.jackson.time-zone` writes `Date` and `Calendar`
values in that time zone, and converts `OffsetDateTime` and `ZonedDateTime` values to it. When the application context
has no `JsonMapper`, or has several and none is primary, as in a unit test, a default `JsonMapper` is used.

Parsing JSON does not change. `JSON.parse`, `request.JSON` and `new JSONObject(String)` parse with Grails' own
`JSONTokener`, as before: they accept the same syntax beyond strict JSON (single quotes, comments, unquoted values,
uppercase literals, trailing commas, `new Date(...)`), return the same number types (`Integer`, `Long`, `BigInteger`,
`Double` or `BigDecimal`, depending on the number) and the same `JSONObject` and `JSONArray` containers, which implement
`Map` and `List`.

With the setting `false`, Grails marshallers still render domain classes, beans, enums, collections, maps and arrays,
and now records (as an object of their components) and `Optional` (as its value), so the values they contain are
rendered as any other value is. A marshaller that an application registers, with `JSON.registerObjectMarshaller(...)` or an
`ObjectMarshallerRegisterer`, still takes precedence over the mapper for the types it supports.

A Jackson module registered with the application, such as a `JacksonModule` bean or a `@JacksonComponent` serializer,
applies to `grails.converters.JSON` with the setting `false`, where Grails 8 ignored it. When a module provides a serializer for a type that
Grails 8 rendered as a bean, the serializer renders it instead. The values that the serializer writes, such as a property
it writes with `JsonGenerator#writePOJO`, are rendered by the converter as any other value is, so registered marshallers,
enum names and the circular reference behaviour apply to them. A marshaller registered for the type itself takes
precedence over the module's serializer.

With the setting `false`, two things deliberately differ from Spring Boot, as they do in Grails 8:

* Enums, including one with a `@JsonValue`, render by `name()`, where Jackson 3 writes `toString()` or the `@JsonValue`,
so that the JSON binds back to the enum.
* Strings are escaped for an HTML `<script>` element: `</` is written as `<\u002f` (as `<\/` in a `GString` or a
`StreamCharBuffer`, as in Grails 8), and U+2028 and U+2029 as `\u2028` and `\u2029`. The parsed values are the same as
Spring Boot's.

With the setting `false`, the following values render differently than in Grails 8:

[cols="2,2,3", options="header"]
|===
| Value
| Grails 8, and Grails 9 by default
| `legacy: false`

| `OffsetTime`
| `"03:00:00-03:00"`, `"03:00:00.5+05:30"`
| `"03:00-03:00"`, `"03:00:00.500+05:30"`, from `OffsetTime#toString()`

| `Month`
| `"SEPTEMBER"`
| `9`, a JSON number. A `Month` binds back from its number.

| `java.util.Locale`
| `"zh_TW_#Hant"`, from `Locale#toString()`
| `"zh-Hant-TW"`, its language tag

| `char`, `Character`
| `{}`
| `"c"`

| `byte[]`
| `[1,2,3]`
| `"AQID"`, Base64

| `UUID`, `URI`, a type with a `@JsonValue` other than an enum
| an object of its bean properties
| its value, such as `"123e4567-e89b-12d3-a456-426614174000"`

| `java.util.regex.Pattern`, `java.nio.charset.Charset`, `java.net.InetAddress`
| an object of its bean properties
| its string, such as `"a+b"`, `"UTF-8"` or the host name

| `java.io.File`, `java.nio.file.Path`, `java.nio.ByteBuffer`
| a failure to render it
| `"/tmp/a.txt"`, `"file:///tmp/a.txt"`, and `"AQID"`, Base64

| `char[]`
| `[{},{}]`
| `"ab"`

| An enum constant with a body, whose class is a subclass of its enum
| an object of its bean properties
| its name, as any enum

| `tools.jackson.databind.JsonNode`
| an object of its bean properties
| the JSON it holds

| `Optional`
| `{"empty":false,"present":true}`
| its value, or `null` when it is empty

| A `NaN` or infinite `double`
| `NaN`, which is not valid JSON
| `"NaN"`

| Pretty printed JSON (`grails.converters.json.pretty.print`, `JSON#toString(true)`)
| `"a": 1`, with every array element on its own line, or, from `toString(true)`, indented by three spaces
| `"a" : 1`, the layout of the mapper's default pretty printer

| A single value, such as `render Role.HEAD as JSON`
| a `ConverterException`
| the JSON value, `"HEAD"`
|===

The other default date and time formats are the same as Grails 8.0.0's, which already renders `Date`, `Calendar`,
`java.sql.Date` and `java.sql.Timestamp` with millisecond precision and supports the additional date and time types.
With the setting `false`, map keys use the mapper's key serializers, instead of Grails' fixed date formats or the key's
`toString()`: a `Date` or `Calendar` key is written in the mapper's configured date format and time zone, a
`ZonedDateTime` or `OffsetDateTime` key keeps its own offset, as before, a `Class` key is its name
(`"java.lang.String"`, where Grails 8 wrote `"class java.lang.String"`), and the key of a type with a `@JsonValue` is
that value.

With the setting `false`, `JSON#toString(false)` does not indent the JSON when `grails.converters.json.pretty.print` is
`true`; Grails 8 ignored the argument. JSON that is not pretty printed is not indented either when the application's
`JsonMapper` indents its output (`spring.jackson.serialization.indent-output`).

With the setting `false`, the JSON marshallers that rendered these values are not registered. They are deprecated:
`DateMarshaller`, `CalendarMarshaller`, `ToStringBeanMarshaller`, `ByteArrayMarshaller`,
`InstantMarshaller`, `LocalDateMarshaller`, `LocalDateTimeMarshaller`, `OffsetDateTimeMarshaller` and
`ZonedDateTimeMarshaller`, in the `org.grails.web.converters.marshaller.json` package. To render one of these types
differently, register a marshaller for it, or configure the `JsonMapper`. The XML marshallers of the same names are not
changed. The default JSON marshallers have implicit priorities that follow their order (-1, -2, and so on), and with
the setting `false` that order differs, so a marshaller registered with an explicit negative priority may come before or
after different defaults.

Whatever the setting, `org.grails.web.json.JSONWriter`, which the converter and its marshallers write to, now writes
through a Jackson `JsonGenerator`, and `new JSONWriter(writer)` writes with a default `JsonMapper`:

* It keeps its public methods, rejects the same misplaced calls, and writes the same JSON text. It also accepts a single
value outside any object or array, where it threw a `JSONException`.
* The generator buffers the text. It reaches the `Writer` as the buffer fills, once the JSON text is complete, and when
`flush()` is called, rather than as each value is written. The `Writer` itself is not flushed or closed.
* `array()`, `object()`, `key()` and the `value` methods no longer go through the protected `append` and `comma`
methods. A subclass that overrides those to change the output, or writes to the `writer` field directly, must use the
public methods instead.
* `PrettyPrintJSONWriter` still indents as Grails 8 did, and is deprecated. Use
`new JSONWriter(writer, new JsonMapperSupport(jsonMapper), true)`, which indents with the mapper's default pretty printer.

The JavaCC JSON parser in `org.grails.web.json.parser` (`JSONParser`), which Grails does not use, is deprecated. Use
`JSON.parse` or `new JSONObject(String)`.

Whatever the setting, with the `PATH` circular reference behaviour (`grails.converters.json.circular.reference.behaviour`),
an object with a `null` property, or a single value, now renders instead of failing, and a reference that follows a
number now has the right path: `"root.x.other"` where Grails 8 wrote `"root.x.n"`, after a property `n` that is a
number.

JSON views, the XML converter and the HAL renderer are not changed.

[[renderingJsonAsGrails8]]
===== Rendering JSON As Grails 8 Did

`grails.converters.json.legacy` is `true` by default in Grails 9. The JSON converter then renders values, including
domain classes, with the marshallers of Grails 8, formats map keys and indents pretty printed JSON as Grails 8 did, and
writes with a default `JsonMapper`, so that the application's `spring.jackson.*` settings and Jackson modules do not
change the text: `render ... as JSON` and `JSON#toString` return the same text as in Grails 8. What Grails 8 failed to
render, or rendered as invalid JSON, such as a single value, `NaN`, or a to-many association whose value is a `Map` with
other than one entry, renders as it does with the setting `false`. A reference that the `PATH` circular reference
behaviour writes after a number also has the right path, as described above, where Grails 8 wrote a wrong one. A later
release makes `false` the default; setting `grails.converters.json.legacy` to `true` explicitly keeps the Grails 8
rendering, and turns off the warning that Grails logs while it is not set. With
`grails.converters.json.domain.jackson.enabled` set to `true` as well, the JSON converter still renders as Grails 8 did,
and the application's `JsonMapper` renders domain classes with the module, as described below.

With the setting `false`, to keep the Grails 8 rendering of some types only, register a marshaller for each, for
example in `BootStrap.init`:

[source,groovy]
----
JSON.registerObjectMarshaller(Month) { Month month -> month.name() }
JSON.registerObjectMarshaller(Locale) { Locale locale -> locale.toString() }
JSON.registerObjectMarshaller(byte[]) { byte[] bytes -> bytes as List }
----

==== 4. Domain Classes Can Render Through a Jackson Serializer

With `grails.converters.json.legacy` set to `false`, the JSON converter renders domain classes with a Jackson serializer,
`DomainClassSerializer`, as `DomainClassMarshaller` rendered them, with these changes:

* A property annotated with `@JsonIgnore`, or with `@JsonProperty(access = WRITE_ONLY)`, is no longer rendered.
* A to-many association whose value is a `Map` renders as an object of references, such as `{"a":{"id":1}}`, where it
failed before.
* `DomainClassMarshaller` and `DeepDomainClassMarshaller` render through the serializer. Their constructors and
protected methods (`includesProperty`, `excludesProperty`, `extractValue`, `asShortObject` and
`isRenderDomainClassRelations`) are unchanged, and a subclass that overrides them still renders as it did. They are
consulted before the mapper's value serializers, as `ProxyUnwrappingMarshaller` is.

The application's `JsonMapper` is not changed: writing a domain class instance with it, such as returning one from a
Spring MVC controller, renders it as a Jackson bean, as in Grails 8. To have the mapper render domain classes as
`render ... as JSON` does, set `grails.converters.json.domain.jackson.enabled` to `true`:

[source,yaml]
----
grails:
    converters:
        json:
            domain:
                jackson:
                    enabled: true
----

Grails then registers the serializer with the mapper, as a Jackson module, and the mapper renders associated instances as
references of their id, such as `{"id":3}`, rather than in full, and proxies as the instances they proxy. Of what
Jackson's bean serialization applies to a domain class, the serializer applies the following:

* It leaves out a property annotated with `@JsonIgnore`, or with `@JsonProperty(access = WRITE_ONLY)`, on its field or
getter, and the properties that a class-level `@JsonIgnoreProperties` names, such as those GORM names in the one it adds
to every domain class.
* It names the properties as Jackson does, by `@JsonProperty`, `@JsonNaming` and the mapper's naming strategy
(`spring.jackson.property-naming-strategy`), and names the id of a reference as the referenced class names it.
* It writes the type id of a domain class with `@JsonTypeInfo`. With `include = EXISTING_PROPERTY`, the type id is the
value of that property, so it is written only when the property is persistent; a transient or computed one is not.
* It writes the properties of a domain class instance in a `@JsonUnwrapped` property into the enclosing object. As with
Jackson's own unwrapping, an instance with a type id fails there, unless
`SerializationFeature.FAIL_ON_UNWRAPPED_TYPE_IDENTIFIERS` is disabled.
* A domain class with its own `@JsonSerialize` serializer, with a `@JsonValue`, or that implements `JacksonSerializable`
is written by Jackson, and so is a subclass of a domain class that is neither a domain class nor a proxy of one.

It applies nothing else. Null properties are written whatever `@JsonInclude` or
`spring.jackson.default-property-inclusion` say, properties are written in the converter's order rather than by
`@JsonPropertyOrder` or sorted alphabetically, and `@JsonView`, `@JsonFilter`, `@JsonAnyGetter`, `@JsonIgnoreType`,
`@JsonFormat` and `@JsonSerialize` on a property, and mix-ins, other than the property names they give, do not apply.

==== 5. Generated GORM Identity and Version Properties Stay Within Domain Classes

Grails 9 no longer adds generated `id` and `version` properties to a non-domain superclass of a domain class.
Previously, these properties could be added to a shared abstract base class, causing command objects extending that same base class to inherit persistence properties and fail validation for `id` and `version`.
Generated properties now remain within the domain-class hierarchy. Domain subclasses still inherit them from domain superclasses, and explicitly declared `id` and `version` properties on a superclass are still inherited normally.

This affects any plain base class compiled alongside a domain subclass, even if the base is not shared with a command object.
Review the following compatibility changes before upgrading:

* *Statically compiled base-class methods:* A plain base annotated with `@CompileStatic` can no longer refer to generated `id` or `version` as its own properties. For example, an `isNew()` method whose body is `id == null` could compile in Grails 8 when the fields were generated on the base, but now fails with `[Static type checking] - The variable [id] is undeclared.` Move persistence-dependent methods to the domain class, or give the base an explicit property or accessor contract implemented by its subclasses. A dynamically compiled base method can still resolve these properties at runtime when invoked on a domain instance; this does not make them available on plain instances or command objects.
* *String representation and equality:* `@ToString` and `@EqualsAndHashCode` on a plain base no longer have generated `id` and `version` among that base's declared properties. Review any explicit property lists and any hand-written `equals` or `hashCode` implementation that assumes these fields are declared on the base. Move persistence-dependent behavior to the domain class or adapt it to an explicit contract. Dynamic property access on a domain instance can still resolve inherited or subclass properties, but the base itself no longer declares the generated fields.
* *Stale compiled classes:* A previously compiled base `.class` can retain `id` and `version` until it is rebuilt. An incremental build can therefore hide the new behavior or leave subclasses inheriting stale fields. Clean and rebuild the application and any affected plugins.

When upgrading an affected application:

* Keep a superclass shared by domain classes and command objects in `src/main/groovy`, outside `grails-app/domain`, and do not annotate it as an entity.
* Remove constraints or other workarounds on command objects that existed only to accommodate the accidentally inherited `id` and `version` properties.
* Update code that relied on a non-domain superclass having generated persistence properties to access them through a domain class instead. If non-domain classes genuinely need these properties, declare them explicitly; such declarations remain inherited by all subclasses.
* Perform a clean build of the application and any affected plugins to remove previously compiled classes containing the generated properties:

[,console]
----
./gradlew clean build
----

See xref:theWebLayer#commandObjects[Command Objects] for a trait-based alternative to sharing a non-domain superclass with a domain class.
