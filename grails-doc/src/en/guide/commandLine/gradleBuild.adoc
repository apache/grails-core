The https://gradle.org[Gradle Build System] is used for build related tasks such as compilation, running tests and producing binary distributions of your Grails project.
It is recommended to use Gradle {GradleVersion} or above with Grails.

The build is defined by the `build.gradle` file which specifies the version of your project, the dependencies of the project and the repositories where to find those dependencies (amongst other things).

When you invoke the `grails` command the version of Gradle that ships with Grails (currently {GradleVersion}) is invoked by the `grails` process via the https://docs.gradle.org/current/userguide/tooling_api.html[Gradle Tooling API]:

[source,bash]
----
# Equivalent to 'gradle classes'
$ grails compile
----

You can invoke Gradle directly using the `gradle` command and use your own local version of Gradle, however you will need Gradle 2.2 or above to work with Grails 3.0 (and higher):

[source,bash]
----
$ gradle assemble
----


=== Running Gradle with the Grails Forge CLI

The Grails Forge CLI has a `gradle` command, which runs Gradle in the project the current directory is in, with the Gradle wrapper of that project (`gradlew`, or `gradlew.bat` on Windows):

[source,console]
----
$ grails -t forge gradle build
$ grails -t forge gradle test --tests "example.BookSpec" -x integrationTest
$ grails -t forge gradle bootRun "-Pmessage=two words"
----

Everything after `gradle` is given to Gradle as it is, each argument as the one argument it was on the command line: an argument that has spaces or quotes is not split or put together again, and an option such as `-x`, `-v`, `--stacktrace` or `--help` is an option of Gradle, not of `grails`. The command has no options of its own for that reason, and it needs at least one argument: without any it says how it is used and ends with exit code 2. One thing is read before Gradle gets it, as on every command line of the Grails Forge CLI: an argument that starts with `@` and names a file is replaced by the arguments in that file. Write `@@` for an `@` that is meant for Gradle.

The project is the nearest directory, from the current one upwards, that has a `grails-app` directory, a `.grails/project.yml` or a `grails-forge-cli.yml`, and Gradle runs in that directory, also when the command is given in a directory below it. In a build of several projects the wrapper is the nearest one above the project, and because Gradle runs in the directory of the project, a task that is named without a path is the task of that project and not of the ones beside it. The search does not go above the root of the Git repository the directory is in, or more than 32 directories up. Outside a project, and in a project that has no Gradle wrapper, the command runs nothing, says so and ends with exit code 1: it does not fall back to another Gradle installation.

A project that is found above the current directory is used only when it is your own. Anyone who can write to a directory above the one you work in, a shared temporary directory for example, could otherwise put a `grails-app` directory and a `gradlew` there and have your command run it. So, as Git does with `safe.directory`:

* When the current directory is a project, that project is used, whoever owns it and whatever its files are: you chose to run the command there, and nothing of this rule is applied to it. Only a Gradle wrapper above it is held to the rule.
* A project above the current directory is used only when it is your own. Its directory is owned by the user who runs the command and cannot be written to by everybody. A group that can write to it is taken to be your own: with a group for each user, as is common on Linux, every directory you create is writable by its group. The `grails-app` directory and the records that make it a project (`.grails` with the files in it, `grails-forge-cli.yml`) are owned by that user, and each file among them has no second name elsewhere on the file system (a hard link, which has the owner of the file it is another name of). The Gradle wrapper of such a project is held to the same, and so are `gradle/wrapper/gradle-wrapper.jar` and `gradle-wrapper.properties`, which the wrapper runs.
* A Gradle wrapper above the project is run only from a directory that has a `settings.gradle` or `settings.gradle.kts`, as the root of a build of several projects has, and that is your own in the same way: the directory, the wrapper, the settings file, and the jar and properties of the wrapper.
* The wrapper is a file, or a link to a file in the directory the link is in or in a directory below it, as `gradlew -> gradle/real` is. A link that leads out of that directory is not run.

This is a rule about owners, modes and link counts, as the file system reports them when the command starts. Access control lists are not read, the contents of files are not looked at, and nothing is held between the check and the run, so it does not protect a directory that someone else can still change by other means. On Windows only the owner is looked at.

Otherwise nothing is run, read or written: the command says in one line which directory or file is not yours and why, and ends with exit code 1; the commands that create classes are then not there, as outside a project, and a command that is unknown for that reason says so in a second line. There are three ways to use the project all the same, and the line names them:

* Run the command in the directory of the project.
* Make it your own: `chmod o-w` on a directory everybody can write to.
* Name the directory in the environment variable `GRAILS_SAFE_DIRECTORY`, on your own machine. Its value is a list of absolute paths of directories, separated as the entries of `PATH` are (`:`, on Windows `;`); a directory that is named is used whoever owns it and whatever its modes are. Name the directory of the project, and for a wrapper above the project the directory of the wrapper. An entry is one directory and no pattern; the single value `*` stands for every directory, and gives the rule up.

`GRAILS_SAFE_DIRECTORY` is what to set where the files belong to someone else by design: as root in a container over a directory of the host, in a CI job that runs in a container, and under `sudo`.

The user who runs the command is taken from the process itself: its user id, on Linux otherwise the owner of `/proc/self`, otherwise the name of the user of the process, which is what Windows has. With `sudo` that is root, so a project of your own is not found from a directory below it under `sudo`; in an elevated command prompt on Windows, what the Administrators group owns is not yours either. When the user cannot be established, the command says that, and nothing above the current directory is used.

What Gradle writes goes to the terminal directly, so Gradle shows its colors and its progress as it does when you run `gradlew` yourself, and writes plain text when the output is a file or a pipe. When the build succeeds the command ends with exit code 0. When Gradle ends with any other exit code, the command says which one after the report of Gradle and ends with exit code 1. When the command is cancelled, or `grails` is ended while Gradle runs, the Gradle it started and every process that Gradle started in turn are ended with it, by force if they have not ended after ten seconds; a Gradle daemon that was running before is not ended, and cancels the build. The command then says in one line that Gradle was stopped, whatever exit code Gradle ended with, and says it before it waits for a process that does not end by itself. In the interactive shell Ctrl-C while a command runs Gradle stops Gradle and returns to the prompt. During any other command, `create-app` for one, and at the prompt, Ctrl-C ends the shell at once, and what the command was writing is left as far as it got.

On Windows the wrapper is a batch file, and a batch file does not receive an argument as it is when the argument is empty, contains one of `"`, `%`, `&`, `|`, `<`, `>`, `^` or a control character, or contains a space and ends with a backslash. The command refuses such an argument with exit code 2 before anything is run; run `gradlew.bat` directly for it. For the same reason nothing is run, with exit code 1, when the path of the project or of the wrapper has one of these characters.


=== Building and Testing with the Grails Forge CLI

The Grails Forge CLI has the commands of the `grails` shell that are a Gradle build. Each of them runs the Gradle wrapper of the project the current directory is in, exactly as the `gradle` command above does: the project and the wrapper are found and trusted in the same way, what Gradle writes goes to the terminal in the same way, cancelling stops Gradle in the same way, and the exit codes are the same (0 when the build succeeds, 1 with one line when it fails, when there is no project or no wrapper, and 2 with the usage of the command for a mistake in its use).

[cols="2,3,4"]
|===
|Command |Runs |Options

|`compile`
|`gradlew classes`
|

|`clean`
|`gradlew clean`
|

|`assemble`, `war`, `package`
|`gradlew assemble -Dgrails.env=production`
|`--clean` runs `clean` first. `-Dgrails.env=NAME` selects another environment, and every other `-Dname=value` is given to Gradle too.

|`dependency-report [CONFIGURATION]`
|`gradlew dependencies -Dgrails.env=development`, with `--configuration CONFIGURATION` when one is named
|`-Dname=value`

|`test-app [TEST...]`
|`gradlew test integrationTest -Dgrails.env=test`; `integrationTest` only in a project that has a `src/integration-test` directory
|`--unit` and `--integration` select one of the two tasks. Each `TEST`, and each `--tests TEST`, is a `--tests` filter of both. `--clean` puts `cleanTest` and `cleanIntegrationTest` first. `--debug-jvm` and `--continuous` are the options of Gradle of the same names. `-Dname=value` as above.

|`package-plugin`
|`gradlew jar`
|Only in a plugin project.

|`publish-plugin`
|`gradlew publish`
|Only in a plugin project.
|===

[source,console]
----
$ grails -t forge test-app --unit example.BookSpec "*ControllerSpec.saves a book"
$ grails -t forge war -Dgrails.env=staging
$ grails -t forge compile -- --offline --console=rich
----

Every option of a command becomes arguments of Gradle one for one, so a test filter or a property value with spaces or quotes reaches Gradle as the one argument it was. Whatever follows `--` is not read by the command and is given to Gradle as it is, after the arguments of the command; an option of a Gradle task there, such as `--tests`, belongs to the last task the command names. An option the command does not have is a mistake and is not passed on without the `--`. `--stacktrace` (`-x`) adds `--stacktrace` and `-Dgrails.full.stacktrace=true` to the arguments of Gradle and `--verbose` (`-v`) adds `--debug`; use `-- -x TASK` to leave a task out. The spellings of the shell with one dash (`-unit`, `-integration`, `-clean`, `-continuous`, `-debug-jvm`) are accepted too. A system property is written as `-Dname=value`, or `-Dname` for one without a value; `-D name=value` with a space is accepted as well. A `-D` that stands alone and is not followed by `name=value`, as in `test-app -D BookSpec`, and a `-D` without a name, as in `-D=x`, are mistakes: the command runs nothing, shows its usage and ends with exit code 2. On Windows an argument that a batch file does not receive unchanged is refused, as by the `gradle` command.

These things differ from the `grails` shell:

* The environment is selected with `-Dgrails.env=NAME` after the name of the command. The environment in front of the command (`grails prod war`) is not read by the Grails Forge CLI.
* `test-app --continuous` is the continuous build of Gradle: the tests run once, and again whenever a file they depend on changes, until the command is cancelled. The shell watches four source directories itself and does not run the tests when it starts.
* `test-app --integration` in a project that has no `src/integration-test` directory runs nothing and ends with exit code 1.
* `assemble --clean` runs `clean` first. The shell accepts the option and does nothing for it.
* `package-plugin` and `publish-plugin` are commands only where the project has a plugin class (a file whose name ends with `GrailsPlugin.groovy` under `src/main/groovy`). `install` runs nothing: it says that a plugin is installed into the local Maven repository with `gradle publishToMavenLocal`, and ends with exit code 1.

Two more commands look at the project without running Gradle:

* `stats` prints the table of source files and lines of code by the kind of class, as the shell does. It reads the source directories under `grails-app` and `src` of the project, does not follow links, and does not read the lines of a file larger than 16 MiB. A source directory that is itself reached through a link, as `src/main/groovy` is when `src` is a link, is not counted, and the command names it in a warning.
* `bug-report` writes `build/NAME-bug-report-DATE.zip`, with `NAME` the name of the directory of the project and `DATE` the day as `ddMMyyyy`. The ZIP file holds every file under `grails-app` and `src`, and `build.gradle`, and nothing else of the project: not `settings.gradle` or `gradle.properties`, and nothing of the `build`, `.gradle`, `.git` and `.grails` directories.

WARNING: The configuration of the application under `grails-app/conf` is in the ZIP file of `bug-report` as it is, with any password it holds. Before it says what it created, the command names each `application*.yml`, `application*.groovy` and `application*.properties` file of `grails-app/conf` that went into the ZIP file. Look through them before you attach it to an issue.

`bug-report` leaves out:

* what a version control system or an editor keeps (`.git`, `.gitignore`, `.DS_Store`, files that end with `~`, and the like);
* every directory named `build` or `.gradle`, wherever it is under `grails-app` and `src`, also one that is a package of your application;
* files that are keys or lists of secrets by their name, in upper or lower case: `.env`, `.env.*`, `.netrc`, `.npmrc`, `.pypirc`, `cacerts`; files that end with `.env`, `.jks`, `.p12`, `.pfx`, `.pem`, `.key`, `.keystore`, `.p8`, `.ppk`, `.kdbx`, `.der`, `.asc` or `.gpg`; files that start with `id_rsa`, `id_dsa`, `id_ecdsa` or `id_ed25519`, whatever they end with, as `.env.*` holds for `.env.groovy` too; files that start with `truststore`, `credentials` or `secrets`, unless they are sources (`.groovy`, `.java`, `.gsp`, `.gson`, `.kt`), so that `CredentialsController.groovy` is in the ZIP file; and any of these with `.bak`, `.old` or `~` after its name;
* a file that has another name elsewhere on the file system (a hard link), where the file system tells, `build.gradle` included: it may be a file from outside the project;
* a file whose name, or the name of a directory it is in, has a control character.

It follows no link, so nothing from outside the project is read. It says how many links, key files, directories and hard links it left out, and warns of files it left out for their name. A secret in a file of any other name is not recognized: the list goes by names only. It does not replace a ZIP file of the same name unless `--force` is given, and it writes nothing and ends with exit code 1 when the sources are more than 10000 files or more than 256 MiB.


=== Running the Application with the Grails Forge CLI

The Grails Forge CLI has the commands of the `grails` shell that run the application of the project, or a session with it. They run the Gradle wrapper of the project as the commands above do, with the same rules for the project, the wrapper, the output and the exit codes.

[cols="2,3,4"]
|===
|Command |Runs |Options

|`run-app`, `run`
|`gradlew bootRun --quiet -Dgrails.env=development`
|`--port PORT`, `--host HOST`, `--https`, `--debug-jvm`, `--query-tail`, `-Dname=value`, `-Pname=value`, `--detach`, `--foreground`, `--ready-timeout SECONDS`; `--verbose` leaves `--quiet` out.

|`stop-app`, `stop`
|Nothing: it ends what `run-app` started.
|

|`console`
|`gradlew console --quiet -Dgrails.env=development`
|`--debug-jvm`, `-Dname=value`

|`shell`, `sh`
|`gradlew shell --quiet -Dgrails.env=development`
|`--debug-jvm`, `-Dname=value`

|`run-script FILE...`
|`gradlew runScript -Pargs=FILES -Dgrails.env=development`
|`-Dname=value`

|`run-command NAME [ARG...]`
|`gradlew runCommand --args-file=FILE -Dgrails.env=development`
|`-Dname=value`, before `NAME`
|===

[source,console]
----
$ grails -t forge run-app --port 9090
$ grails -t forge run-app --detach -Dgrails.env=test -Pgrails.gorm.queryTail.enabled
$ grails -t forge stop-app
$ grails -t forge run-command dbm-status --contexts "two words"
$ grails -t forge run-script src/main/scripts/load.groovy
----

`--port` and `--host` are given to the application as `-Dgrails.server.port` and `-Dgrails.server.address`. `--https` gives it a self-signed certificate for `localhost`, which is created in `build/ssl/keystore` when there is none (with the `keytool` of the Java installation the command runs with, and the password `123456`: it is for development on your own computer), and the port 8443 unless a port is given or configured; give `-Dgrails.server.ssl.key-store=FILE` to use a key store of your own. As for the commands above, what follows `--` is given to Gradle as it is, except for `run-command`.

==== The two ways run-app runs

Without `--detach`, `run-app` stays with the application: its output is on the terminal, and the command ends when the application does. Ctrl-C, or ending `grails`, ends Gradle and every process it started, the application among them.

With `--detach`, `run-app` starts the application, waits until it answers on its port, says so and returns with exit code 0. The application then runs until `stop-app`, also when `grails` and the terminal have ended, and what it and the build write is in `.grails/run/app.log` of the project. In the interactive shell this is what `run-app` does without `--detach`, so that it returns to the prompt, and an application started that way is stopped when the shell ends; give `--detach` there to leave it running, or `--foreground` to stay with it.

When the command does not stay with the application:

* The port it waits on is `--port`, or `-Dgrails.server.port`, or the `server.port` of `grails-app/conf/application.yml` (for all environments or for the one the application is run for), or 8080. A port the application works out in another way is not known to the command: give `--port`.
* It asks the loopback address of your computer only (`127.0.0.1` and `::1`), and looks up no name. An application that is bound to another address would not answer there, so `--detach` is refused with such a `--host` or configured `server.address`; use `--foreground`.
* Nothing is started when something answers on the port already, since the command could not tell the application from it.
* An application that shows a page while it starts (the `Grails-Startup-Phase` header) does not count as answering until it is ready.
* The application is given 300 seconds to answer, or `--ready-timeout SECONDS`. When it has not answered by then, when the build ends first, or when the command is cancelled while it waits, everything that was started is ended, the command shows the last lines of `.grails/run/app.log` and ends with exit code 1.
* On Linux and macOS the build runs in a process group of its own and ignores the hang-up of the terminal, so Ctrl-C in the terminal does not reach it.

==== What stop-app stops

`run-app`, in either way, records the process it started in `.grails/run/app.json` of the project: its number, the instant it began, the port and the arguments Gradle was given. `stop-app` ends that process and every process it started in turn, the application among them, first by asking and after 30 seconds by force, waits until nothing answers on the port any more, and removes the record. A Gradle daemon that was running before `run-app` is not ended: it ends the application when the Gradle that `run-app` started is gone. A `run-app` that stays with the application in another terminal then says `Application stopped` and ends with exit code 0.

`stop-app` stops only that. The record is a file in the project, and a project can come from anywhere, so the record alone is not believed. A process is ended only when it has the recorded number and began at the recorded instant (the number of a process that has ended is given to another one sooner or later), is a process of the user who runs the command, is not the command itself or a process that started it, and, where the system shows the command line of a process, was started from the directory of the Gradle wrapper of this project to run `bootRun`. Otherwise nothing is ended, and the command says why and ends with exit code 1; a record of a process that has ended, or one that cannot be read, is removed. `stop-app` never looks for whatever listens on a port, and it has no `--port` or `--host` option. When there is no record it says that no application is running and ends with exit code 1, as the shell does. A second `run-app` while the recorded application runs starts nothing and ends with exit code 1.

The directory `.grails/run`, and the files in it, can be read and written by you only, and the directory has a `.gitignore` that keeps all of it out of version control. It is used only when it and `.grails` are directories and not links.

==== console, shell, run-script and run-command

`console` runs the Swing console of the application and stays with it until its window is closed. `shell` runs the Groovy shell of the application: what you type goes to it until you leave it. Both run Gradle with `--quiet`, so that what is on the terminal is theirs.

`run-script` runs each file with the application started around it, in the order given. A file is named by its path in the project, or by its full path; a name with spaces or quotes reaches the task as the one file it is. A file that is not there is reported before Gradle is started.

`run-command` runs a command of the application (`grails-app/commands`) or of one of its plugins by its name. Everything after the name is given to that command as it is, each argument as the one it was, also an argument that is empty, has spaces, quotes or line breaks, looks like an option of `run-command`, or is `--`: options of `run-command` itself therefore come before the name. The name and the arguments are not on the command line of Gradle. They are written to a file in `.grails/run` that only you can read, which the task reads and which is deleted when the command has ended. An argument with the character U+0000 or with half of a character of two code units, more than 4096 arguments, and arguments of more than 1 MiB are refused with exit code 2.

These things differ from the `grails` shell:

* `run-app` takes no task or other argument for Gradle after its name; what is for Gradle follows `--`.
* `run-app --detach` leaves the application running after `grails` has ended. In the shell an application runs on only inside the interactive mode.
* `run-app --https` without a port waits on port 8443, the one it gives the application.
* `stop-app` ends the Gradle that `run-app` started with everything below it, and goes by the record in `.grails/run`; the shell ends the process whose number the application wrote to `build/run-app.pid`. An application that was started by the shell or by `gradlew bootRun` is not stopped by the `stop-app` of the Grails Forge CLI, and the other way round.
* `shell` runs the shell. In the `grails` shell the command only says to run `gradle shell -q`.
* `run-script` and `run-command` keep each argument as it was. The shell joins the arguments with spaces, the task splits them again, and arguments that start with a dash do not reach the command.
* `s`, `st` and `co` are no short forms of one command any more: `s` and `st` fit `stats`, `stop-app` and `shell`, and `co` fits `compile` and `console`.
