You can create your own commands by running the link:{commandLineRef}create-command.html[create-command] command from the root of your project. For example the following command will create a command called `grails-app/commands/HelloWorldCommand`:

[source,groovy]
----
grails create-command HelloWorld
----

NOTE: Unlike scripts, commands cause the Grails environment to start and you have full access to the application context and the runtime.

Since Grails 3.2.0, commands have similar abilities as scripts in regards to retrieving arguments, template generation, file access, and model building.

If you created a command in a previous version of grails, you can update your command to have those abilities by changing which trait you are implementing.

Commands created in Grails 3.1.x or lower implement the link:{api}org/apache/grails/core/cli/ApplicationCommand.html[ApplicationCommand] trait by default which requires your command to implement the following method:

[source,groovy]
----
boolean handle(ExecutionContext executionContext)
----

Commands created in Grails 3.2.0 or higher implement the link:{api}org/apache/grails/core/cli/GrailsApplicationCommand.html[GrailsApplicationCommand] trait by default which requires your command to implement the following method:

[source,groovy]
----
boolean handle()
----

NOTE: Commands defined this way still have access to the execution context via a variable called "executionContext".

Custom commands can be executed using *grails run-command*:

[source]
----
grails run-command my-example
----

With the Grails Forge CLI a command is run by its own name, once the Gradle task `grailsCommandCatalog` has listed the commands of the project (see xref:commandLine[The Command Line], the section on the commands of the application and its plugins):

[source]
----
grails -t forge gradle grailsCommandCatalog
grails -t forge my-example
----

Commands can also be executed using the *runCommand* gradle task. Note that the gradle task uses camelCase:

[source]
----
gradle runCommand -Pargs="my-example"
----

If the grails server is a subproject (e.g., in a project created with the *angular* profile), the subproject command can still be invoked from the gradle wrapper in the parent project:

[source]
----
./gradlew server:runCommand -Pargs="my-example"
----






With Gradle, a custom command is a piece of functionality that you can add to your Grails application and execute via the command-line interface (CLI). These commands are not part of the core Grails framework but are extensions you can create to perform specific tasks or operations that are unique to your application's requirements. Custom commands are a powerful way to automate various tasks, interact with your application, and perform administrative functions from the command line. When you run custom commands, they cause the Grails environment to start, giving you full access to the application context and the runtime, allowing you to work with the application's resources, services, and configuration as needed within your custom command.

There are several reasons why you might want to write a custom command for your Grails application:

* Automating Tasks: Custom commands allow you to automate routine tasks, such as data migration, database updates, or batch processing, by encapsulating the logic in a command that can be executed on-demand.
* Administrative Operations: You can use custom commands for administrative tasks like user management, system maintenance, and configuration management, making it easier to manage your application in different environments.
* Integration: Custom commands can be used to integrate your Grails application with other systems or services. For example, you can create a command to synchronize data with an external API.
* Customized Workflows: If your application has unique workflows or processes, custom commands provide a way to execute these workflows from the command line.

In Grails, you can create custom commands by implementing the link:{api}org/apache/grails/core/cli/GrailsApplicationCommand.html[GrailsApplicationCommand] trait. By default, this trait requires your command to implement the handle() method as following:

[source,shell]
----
boolean handle()
----

[NOTE]
====
Commands defined this way still have access to the execution context via a variable called "executionContext."
====

Here's a step-by-step guide on how to create custom commands using the GrailsApplicationCommand trait with examples, and how to run these commands.

In Grails, you can create custom commands by implementing the `GrailsApplicationCommand` trait. Custom commands allow you to add functionality to your Grails application that can be executed via the command-line interface (CLI). Here's a step-by-step guide on how to create custom commands using the `GrailsApplicationCommand` trait with examples, and how to run these commands.

**Step 1: Create a Custom Command**

To create a custom command, you need to create a Groovy class that implements the `GrailsApplicationCommand` trait. This trait provides methods for command execution. Let's create a simple example command that greets the user:

[source,groovy]
----
// grails-app/commands/com/example/GreetCommand.groovy
package com.example

import org.apache.grails.core.cli.GrailsApplicationCommand

class GreetCommand implements GrailsApplicationCommand {

    String getName() {
        return "greet"
    }

    String getDescription() {
        return "Greet the user"
    }

    boolean handle() {
        println("Hello, user!")
        return true // Return true to indicate successful execution
    }
}
----

In this example, we've created a `GreetCommand` class that implements the `GrailsApplicationCommand` trait. It provides a `getName()` method to define the command name (overriding the default derived from the class name), a `getDescription()` method for a brief description, and the `handle()` method to specify the code to execute when the command is run.

Step 2: Build Your Grails Application

Before you can use the runCommand task, ensure you have built your Grails application using the following command:

[source,shell]
----
./gradlew assemble
----

This command will compile your application and make it ready for running custom commands.

**Step 3: Run the Custom Command**

To run the custom command, use Gradle's runCommand task. Open your terminal and navigate to your Grails application's root directory. Then, run the custom command with the following Gradle command:

[source,shell]
----
./gradlew runCommand -Pargs="greet"
----

In the command above, replace "greet" with the name of your custom command. This will execute the GreetCommand, and you will see the output.

Here's the expected final output when you run the greet command:

[source,shell]
----
Hello, user!
----

**Additional Features: Command Arguments and Options**

Grails also supports command-line arguments and options for custom commands. You can define these in your command class by implementing the `GrailsApplicationCommand` interface. Here's an example of a command that takes a name as an argument and an optional `--loud` option to make the greeting louder:

[source,groovy]
----
// grails-app/commands/com/example/GreetCommand.groovy
package com.example

import org.apache.grails.core.cli.GrailsApplicationCommand

class GreetCommand implements GrailsApplicationCommand {

    String getName() {
        return "greet"
    }

    String getDescription() {
        return "Greet the user with options"
    }

    boolean handle() {
        // `args` (from the GrailsApplicationCommand trait) holds the remaining arguments
        // after the command name; `--`-prefixed flags are parsed as options instead
        String name = args ? args[0] : "user"
        boolean loud = executionContext.commandLine.hasOption("loud")

        if (loud) {
            println("HELLO, $name! (LOUD)")
        } else {
            println("Hello, $name!")
        }

        return true
    }
}
----

Now you can run the `greet` command with arguments and options:

[source,shell]
----
# Greet the user with the default message
./gradlew runCommand -Pargs="greet"

# Greet a specific user
./gradlew runCommand -Pargs="greet Alice"

# Greet loudly
./gradlew runCommand -Pargs="greet --loud"

# Greet a specific user loudly
./gradlew runCommand -Pargs="greet Alice --loud"
----

This allows you to create more versatile and interactive custom commands for your Grails application.

**Arguments With Spaces, Quotes and Other Special Characters**

`-Pargs` is one text. Gradle hands it to the build, which splits it at spaces and reads single and double quotes the way a shell does, so `-Pargs="greet 'Alice Smith'"` is the command `greet` with the one argument `Alice Smith`. What `-Pargs` holds is therefore quoted twice, once for your shell and once for this split, and a program that puts the text together from arguments has to quote each of them for the split.

The command tasks, `runCommand` and the task of each command, also take the arguments one at a time, each exactly as it is given:

[source,shell]
----
# three arguments: the command, a name with a space in it, and an option
./gradlew runCommand --arg=greet --arg="Alice Smith" --arg=--loud

# the task of a command takes the arguments of the command only
./gradlew dbmGenerateChangelog --arg="my changelog.groovy"
----

Each `--arg` is one argument, in the order given; for `runCommand` the first is the name of the command. Nothing is split, trimmed or unquoted after your shell has read the line, so a value can contain spaces, quotes, `$`, `*`, backslashes, a leading dash or a line break. Gradle does not accept an empty value (`--arg=`).

A program that runs a command, or a command line that cannot carry an argument (an empty one, or one your shell cannot quote), gives the arguments in a file instead:

[source,shell]
----
./gradlew runCommand --args-file=build/tmp/greet-args.json
----

The file is UTF-8 and holds a JSON array of strings, one for each argument, for example `["greet", "Alice \"Al\" Smith", ""]`. A relative path is in the project directory. The file can be at most 1 MiB and hold at most 4096 arguments, and an argument cannot contain the character U+0000. The file is read when the task runs and is not deleted. What it holds is not put on a command line: the JVM that runs the command is given the path of the file and reads it, so the arguments appear in no process listing and in no log of the build. Because the arguments are not on the Gradle command line either, a build with the configuration cache reuses its configuration when only the arguments change, which is not so for `--arg` and `-Pargs`.

Use one of the three forms in a build: `--arg`, `--args-file` or `-Pargs`. The task fails when it is given arguments in more than one of them.

In the command, `executionContext.commandLine.rawArguments` is the arguments as they were given, the name of the command first. `args` and the options of `executionContext.commandLine` are what Grails reads from them, as before: an argument that starts with a dash is an option, which takes the argument after it as its value unless it has one of its own (`--name=value`), surrounding white space and surrounding double quotes are removed, and an empty argument is left out.

In summary, creating custom commands in Grails using the `GrailsApplicationCommand` trait is a powerful way to extend your application's functionality beyond the web interface. You can define the command's name, description, and logic, and then execute it from the command line, optionally passing arguments and options as needed.

**Using the `executionContext` in the Grails Custom Commands**

In Grails, the executionContext is a runtime context object that provides valuable information about the current execution environment of a Grails application. It includes details such as the application's environment (e.g., development, production, test) and allows developers to access this context within custom commands.

Custom commands in Grails can use the executionContext to make informed decisions and perform specific tasks based on the current runtime environment. For example, developers can write conditional logic in custom commands that execute differently in production, development, or testing environments. This flexibility enables custom commands to adapt and behave differently depending on the context in which they are run, making them versatile tools for managing and extending Grails applications.

Suppose you have a Grails application that manages customer data, and you want to create a custom command to perform data backup. In this scenario, you may want the backup process to behave differently depending on whether you're running it in a development, staging, or production environment.

Here's an example of how you can create a custom command that uses the executionContext to determine the backup behavior:

[source,groovy]
----
// grails-app/commands/com/example/BackupCommand.groovy
package com.example

import org.apache.grails.core.cli.GrailsApplicationCommand

class BackupCommand implements GrailsApplicationCommand {

    String getName() {
        return "backup"
    }

    String getDescription() {
        return "Backup customer data"
    }

    boolean handle() {
        // Access the executionContext to determine the environment
        def environment = executionContext.environment

        if (environment == "production") {
            // Perform a full backup in the production environment
            println("Performing a full backup of customer data (Production)")
            // Add production-specific backup logic here
        } else {
            // Perform a partial backup in other environments
            println("Performing a partial backup of customer data (Non-production)")
            // Add non-production backup logic here
        }

        return true // Return true to indicate successful execution
    }
}
----

In this example:

- The custom command, named `BackupCommand`, is created to back up customer data.
- It checks the `executionContext` to determine the current environment.
- If the environment is "production," it performs a full backup with production-specific logic.
- In all other environments, it performs a partial backup with non-production logic.

When you run this custom command using `./gradlew runCommand -Pargs="backup"`, it will adapt its behavior based on whether you're in a production or non-production environment, demonstrating how the `executionContext` can be used to make environment-specific decisions in a realistic scenario.

**How to Create a Custom Command from a Grails Plugin**

Plugins publish their commands in a *companion cli artifact* (`<plugin-artifactId>-cli`) instead of
the plugin's runtime jar, so command code and its CLI-only dependencies never reach an
application's runtime classpath (`bootRun`, `bootJar`, `bootWar`). Here is the complete workflow:

1. **Create a Grails Plugin:** If you don't already have a Grails plugin, create one:
+
[source,shell]
----
grails create-plugin my-plugin
----

2. **Define the Command in a `cli` source set:** compiled plugin commands live in `src/cli/groovy`
(not `grails-app/commands`, which is compiled into the runtime jar). Give them a package that is
unique to the cli artifact. Code-generation scripts and multi-step YAML/JSON commands may stay in
`src/main/scripts`; when `grails-plugin-cli` is applied they are copied into the companion jar as
`META-INF/commands` and excluded from the runtime plugin jar. You may also place them directly under
`src/cli/resources/META-INF/commands`:
+
[source,groovy]
----
// src/cli/groovy/com/example/myplugin/cli/AuditReportCommand.groovy
package com.example.myplugin.cli

import org.apache.grails.core.cli.GrailsApplicationCommand

class AuditReportCommand implements GrailsApplicationCommand {

    String description = 'Prints an audit report'

    @Override
    boolean handle() {
        println 'Audit report...'
        return true
    }
}
----
+
When this source set compiles with `grails-core-cli` on its classpath, the command is registered
automatically in `META-INF/grails-cli.factories` inside the cli jar — no manual registration file
is needed.

3. **Apply the Grails cli-artifact plugin in `build.gradle`:** it wires everything — the `cli`
source set as a feature variant, the `grails-core-cli` contract and the plugin's own runtime
classes on the cli compile classpath, the `Grails-Cli-Artifact` manifest advertisement on the
runtime jar, and (when the Grails publish plugin is applied) the companion publication:
+
[source,groovy]
----
plugins {
    id 'org.apache.grails.gradle.grails-plugin'
    id 'org.apache.grails.gradle.grails-plugin-cli'
    id 'org.apache.grails.gradle.grails-publish'
}

cliArtifact {
    // recommended: a unique, stable JPMS module name matching the cli package
    automaticModuleName = 'com.example.myplugin.cli'

    // optional: customize the companion coordinate (defaults to '<plugin-artifactId>-cli');
    // the advertised coordinate is also carried as a capability of the cli variants, so
    // in-build consumers can require it either way
    // artifactId = 'my-plugin-tools'
}

dependencies {
    // additional CLI-only dependencies of the commands, if any:
    // cliImplementation 'org.example:some-cli-tool'
}
----

4. **Publish both artifacts:** publishing the plugin publishes the companion alongside it, as its
own coordinate with its own pom, sources, and javadoc:
+
[source,shell]
----
./gradlew publishToMavenLocal
# com.example:my-plugin        (runtime — no command code)
# com.example:my-plugin-cli    (the commands)
----
+
NOTE: Without the Grails publish plugin, the cli feature is still built and advertised, but the
companion publication must be configured manually from the `cli` software component.

5. **Consume the plugin from an application:** the application declares only the runtime plugin.
The Grails Gradle plugin reads the `Grails-Cli-Artifact` manifest attribute from the plugin jar,
adds `com.example:my-plugin-cli` to the application's `grailsCli` configuration, and registers the
per-command Gradle task automatically:
+
[source,groovy]
----
dependencies {
    implementation 'com.example:my-plugin:1.0.0'   // my-plugin-cli follows automatically
}
----

6. **Run the Command:**
+
[source,shell]
----
./gradlew runCommand -Pargs="audit-report"
# or, via the automatically registered per-command task:
./gradlew auditReport
----

If an application disables the automatic discovery (`grails { cliAutoProvision = false }`), it
declares the companion explicitly instead:

[source,groovy]
----
dependencies {
    implementation 'com.example:my-plugin:1.0.0'
    grailsCli 'com.example:my-plugin-cli:1.0.0'
}
----

By packaging commands this way, the plugin's runtime jar stays free of command code and CLI-only
libraries, while applications get the commands with no additional build configuration.

**Depending on Another Module's CLI Tier**

Within a multi-project build, one project's cli tier may build on another project's cli companion.
Declare the dependency on the owning project with a *capability* naming the companion:

[source,groovy]
----
dependencies {
    cliApi(project(':my-other-plugin')) {
        capabilities {
            requireCapability('com.example:my-other-plugin-cli')
        }
    }
}
----

The cli-artifact plugin publishes such a dependency as a plain dependency on the companion
coordinate (`com.example:my-other-plugin-cli`) in both the pom and the module metadata, so
external consumers resolve the published artifacts directly. This works with a customized
`cliArtifact { artifactId = ... }` as well: the customized coordinate is carried as a capability
of the cli variants, and the published metadata records the customized plain coordinate.

A library that consumes a cli tier in its *main* configurations (`api`/`implementation`) rather
than a `cli` source set — and therefore does not apply the cli-artifact plugin — applies the
`org.apache.grails.gradle.grails-cli-library` plugin to publish its cli dependencies the same way:

[source,groovy]
----
plugins {
    id 'java-library'
    id 'org.apache.grails.gradle.grails-cli-library'
}

dependencies {
    api(project(':my-other-plugin')) {
        capabilities {
            requireCapability('com.example:my-other-plugin-cli')
        }
    }
}
----

WARNING: Capability requests are a build-internal addressing scheme. Never declare
`requireCapability` on an *external* (binary) Grails dependency — published metadata cannot
satisfy it and resolution fails with a capability conflict. External consumers always depend on
the plain `-cli` coordinate, e.g. `grailsCli 'com.example:my-plugin-cli:1.0.0'`.

**Listing Commands Without Running Them**

When a command is compiled, from `grails-app/commands` of an application or from `src/cli/groovy` of a plugin, the compiler writes a descriptor of it beside its registration: `META-INF/grails-commands/<class name>.json`, with the name and the description of the command. Tools read it to list the command without loading its class or starting the application. The descriptor holds what the source says as a constant:

* The name is the one the class name gives (`AuditReportCommand` is `audit-report`), or the string that `getName()` returns or that the property `name` is set to.
* The description is the string that `getDescription()` returns or that the property `description` is set to. Without one, the description is the name.
* A `getName()` that works the name out when it is called cannot be described: such a command has no descriptor and is listed by the name its class name gives. A description that is worked out is left out of the descriptor.

Write the name in lower case letters and digits, in words joined by single hyphens, with at most 64 characters, and the description on one line of at most 512 characters; a command whose descriptor has anything else is left out of the list, with the reason. A command whose name or description is not written that way gets a descriptor without the description, or none when it is the name. A command written in Java, or registered by hand in `META-INF/grails-cli.factories`, has no generated descriptor. Add the file to the resources next to the registration:

[source,json]
.src/cli/resources/META-INF/grails-commands/com.example.AuditReportCommand.json
----
{"format": 1, "class": "com.example.AuditReportCommand", "name": "audit-report", "description": "Writes the audit report", "target": "application"}
----

The `grailsCommandCatalog` task of an application or plugin project writes the list of the commands the project can run with `runCommand` to `build/grails/command-catalog.json`:

[source,shell]
----
./gradlew grailsCommandCatalog
----

It lists the commands of the project itself, of the `-cli` companions of its plugins, of plugin jars that register commands, and, when `grails { legacyCommandSupport = true }` is set, the commands of Grails 7 plugins. The file is one JSON document:

[source,json]
----
{"format": 1, "complete": true, "diagnostics": [],
 "commands": [
   {"name": "audit-report", "aliases": [], "description": "Writes the audit report",
    "origin": "com.example:my-plugin-cli:1.0.0", "target": "application", "registration": "descriptor"}
 ]}
----

* `origin` is the coordinates of the artifact the command comes from, or `application` for a command of the project itself.
* `registration` says how much is known: `descriptor` for a command with a descriptor; `factories` for a command that is registered without one, whose name is the one its class name gives and whose description is empty; `legacy` for a command of a Grails 7 plugin, listed the same way.
* `complete` is `false` when something could not be listed, and `diagnostics` then says what and why, one line each: a descriptor that is not as described above, a name that two commands have (neither is listed, because the task does not choose between them), or Grails 7 commands in a project without `legacyCommandSupport`. The task prints the same lines as warnings.

The names, descriptions and origins in the file come from the project's dependencies. They are checked to be one line without control characters, and nothing more: a program that shows them must show them as plain text and give no meaning to anything in them.

Every command in the file is run with `./gradlew runCommand --arg=<name>` followed by its arguments. The task loads no class of the project or of its dependencies, and the file has neither a time nor a path of the machine in it, so the same commands give the same file.

The Grails Forge CLI reads this file: in the project, every command in it is a command of the Grails Forge CLI under its name, listed by `help` with its origin and run through `runCommand` with its arguments as they were typed. Nothing runs the task for you, so run it again when the commands of the project have changed. A command whose name is a command of the Grails Forge CLI itself, another name of one or the short form of one, such as `install-templates`, is not added there; `help` says so, and the command is run with `runCommand` as above.
