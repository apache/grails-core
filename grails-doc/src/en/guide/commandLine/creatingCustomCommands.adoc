You can create your own commands by running the link:{commandLineRef}create-command.html[create-command] command from the root of your project. For example the following command will create a command called `grails-app/commands/HelloWorldCommand`:

[source,groovy]
----
grails create-command HelloWorld
----

As it is written, the class prints its name and the arguments it was given and returns `true`, so `grails hello-world` runs and succeeds at once:

[source,groovy]
----
boolean handle() {
    // args holds what was given after the name of the command. Return true when the command has
    // done its work, and false to end it with exit code 1.
    println "Ran ${name} with the arguments ${args}"
    return true
}
----

Replace that body with the work of the command. `handle()` returns `true` when the command succeeded; `false`, or an exception, ends the command with exit code 1.

NOTE: Unlike scripts, commands cause the Grails environment to start and you have full access to the application context and the runtime.

Since Grails 3.2.0, commands have similar abilities as scripts in regards to retrieving arguments, template generation, file access, and model building.

If you created a command in a previous version of grails, you can update your command to have those abilities by changing which trait you are implementing.

Commands created in Grails 3.1.x or lower implement the link:{api}org/apache/grails/core/cli/ApplicationCommand.html[ApplicationCommand] trait by default which requires your command to implement the following method:

[source,groovy]
----
boolean handle(ExecutionContext executionContext)
----

Commands created in Grails 3.2.0 or higher implement the link:{api}org/apache/grails/core/cli/GrailsApplicationCommand.html[GrailsApplicationCommand] trait by default which requires your command to implement the following method:

[source,groovy]
----
boolean handle()
----

NOTE: Commands defined this way still have access to the execution context via a variable called "executionContext".

A command is run by its name with the `grails` command:

[source]
----
grails my-example
----

The build lists the commands of the application and its plugins whenever it compiles the project, and `grails` has the build list them when a name it does not know yet is typed, so a new command is run by its name at once (see xref:commandLine[The Command Line], the section on the commands of the application and its plugins). `grails run-command` runs the same command, and takes an environment in front of its name:

[source]
----
grails run-command my-example
grails run-command -Dgrails.env=production my-example
----

Commands can also be executed using the *runCommand* gradle task. Note that the gradle task uses camelCase:

[source]
----
gradle runCommand -Pargs="my-example"
----

If the Grails application is a subproject of a larger Gradle build (here one named `server`), the subproject command can still be invoked from the gradle wrapper in the parent project:

[source]
----
./gradlew server:runCommand -Pargs="my-example"
----






With Gradle, a custom command is a piece of functionality that you can add to your Grails application and execute via the command-line interface (CLI). These commands are not part of the core Grails framework but are extensions you can create to perform specific tasks or operations that are unique to your application's requirements. Custom commands are a powerful way to automate various tasks, interact with your application, and perform administrative functions from the command line. When you run custom commands, they cause the Grails environment to start, giving you full access to the application context and the runtime, allowing you to work with the application's resources, services, and configuration as needed within your custom command.

There are several reasons why you might want to write a custom command for your Grails application:

* Automating Tasks: Custom commands allow you to automate routine tasks, such as data migration, database updates, or batch processing, by encapsulating the logic in a command that can be executed on-demand.
* Administrative Operations: You can use custom commands for administrative tasks like user management, system maintenance, and configuration management, making it easier to manage your application in different environments.
* Integration: Custom commands can be used to integrate your Grails application with other systems or services. For example, you can create a command to synchronize data with an external API.
* Customized Workflows: If your application has unique workflows or processes, custom commands provide a way to execute these workflows from the command line.

In Grails, you can create custom commands by implementing the link:{api}org/apache/grails/core/cli/GrailsApplicationCommand.html[GrailsApplicationCommand] trait. By default, this trait requires your command to implement the handle() method as following:

[source,shell]
----
boolean handle()
----

[NOTE]
====
Commands defined this way still have access to the execution context via a variable called "executionContext."
====

Here's a step-by-step guide on how to create custom commands using the GrailsApplicationCommand trait with examples, and how to run these commands.

In Grails, you can create custom commands by implementing the `GrailsApplicationCommand` trait. Custom commands allow you to add functionality to your Grails application that can be executed via the command-line interface (CLI). Here's a step-by-step guide on how to create custom commands using the `GrailsApplicationCommand` trait with examples, and how to run these commands.

**Step 1: Create a Custom Command**

To create a custom command, you need to create a Groovy class that implements the `GrailsApplicationCommand` trait. This trait provides methods for command execution. Let's create a simple example command that greets the user:

[source,groovy]
----
// grails-app/commands/com/example/GreetCommand.groovy
package com.example

import org.apache.grails.core.cli.GrailsApplicationCommand

class GreetCommand implements GrailsApplicationCommand {

    String getName() {
        return "greet"
    }

    String getDescription() {
        return "Greet the user"
    }

    boolean handle() {
        println("Hello, user!")
        return true // Return true to indicate successful execution
    }
}
----

In this example, we've created a `GreetCommand` class that implements the `GrailsApplicationCommand` trait. It provides a `getName()` method to define the command name (overriding the default derived from the class name), a `getDescription()` method for a brief description, and the `handle()` method to specify the code to execute when the command is run.

Step 2: Build Your Grails Application

Before you can use the runCommand task, ensure you have built your Grails application using the following command:

[source,shell]
----
./gradlew assemble
----

This command will compile your application and make it ready for running custom commands.

**Step 3: Run the Custom Command**

To run the custom command, use Gradle's runCommand task. Open your terminal and navigate to your Grails application's root directory. Then, run the custom command with the following Gradle command:

[source,shell]
----
./gradlew runCommand -Pargs="greet"
----

In the command above, replace "greet" with the name of your custom command. This will execute the GreetCommand, and you will see the output.

Here's the expected final output when you run the greet command:

[source,shell]
----
Hello, user!
----

**Additional Features: Command Arguments and Options**

Grails also supports command-line arguments and options for custom commands. You can define these in your command class by implementing the `GrailsApplicationCommand` interface. Here's an example of a command that takes a name as an argument and an optional `--loud` option to make the greeting louder:

[source,groovy]
----
// grails-app/commands/com/example/GreetCommand.groovy
package com.example

import org.apache.grails.core.cli.GrailsApplicationCommand

class GreetCommand implements GrailsApplicationCommand {

    String getName() {
        return "greet"
    }

    String getDescription() {
        return "Greet the user with options"
    }

    boolean handle() {
        // `args` (from the GrailsApplicationCommand trait) holds the remaining arguments
        // after the command name; `--`-prefixed flags are parsed as options instead
        String name = args ? args[0] : "user"
        boolean loud = executionContext.commandLine.hasOption("loud")

        if (loud) {
            println("HELLO, $name! (LOUD)")
        } else {
            println("Hello, $name!")
        }

        return true
    }
}
----

Now you can run the `greet` command with arguments and options:

[source,shell]
----
# Greet the user with the default message
./gradlew runCommand -Pargs="greet"

# Greet a specific user
./gradlew runCommand -Pargs="greet Alice"

# Greet loudly
./gradlew runCommand -Pargs="greet --loud"

# Greet a specific user loudly
./gradlew runCommand -Pargs="greet Alice --loud"
----

This allows you to create more versatile and interactive custom commands for your Grails application.

**Arguments With Spaces, Quotes and Other Special Characters**

`-Pargs` is one text. Gradle hands it to the build, which splits it at spaces and reads single and double quotes the way a shell does, so `-Pargs="greet 'Alice Smith'"` is the command `greet` with the one argument `Alice Smith`. What `-Pargs` holds is therefore quoted twice, once for your shell and once for this split, and a program that puts the text together from arguments has to quote each of them for the split.

The command tasks, `runCommand` and the task of each command, also take the arguments one at a time, each exactly as it is given:

[source,shell]
----
# three arguments: the command, a name with a space in it, and an option
./gradlew runCommand --arg=greet --arg="Alice Smith" --arg=--loud

# the task of a command takes the arguments of the command only
./gradlew dbmGenerateChangelog --arg="my changelog.groovy"
----

Each `--arg` is one argument, in the order given; for `runCommand` the first is the name of the command. Nothing is split, trimmed or unquoted after your shell has read the line, so a value can contain spaces, quotes, `$`, `*`, backslashes, a leading dash or a line break. Gradle does not accept an empty value (`--arg=`).

A program that runs a command, or a command line that cannot carry an argument (an empty one, or one your shell cannot quote), gives the arguments in a file instead:

[source,shell]
----
./gradlew runCommand --args-file=build/tmp/greet-args.json
----

The file is UTF-8 and holds a JSON array of strings, one for each argument, for example `["greet", "Alice \"Al\" Smith", ""]`. A relative path is in the project directory. The file can be at most 1 MiB and hold at most 4096 arguments, and an argument cannot contain the character U+0000. The file is read when the task runs and is not deleted. What it holds is not put on a command line: the JVM that runs the command is given the path of the file and reads it, so the arguments appear in no process listing and in no log of the build. Because the arguments are not on the Gradle command line either, a build with the configuration cache reuses its configuration when only the arguments change, which is not so for `--arg` and `-Pargs`.

Use one of the three forms in a build: `--arg`, `--args-file` or `-Pargs`. The task fails when it is given arguments in more than one of them.

In the command, `executionContext.commandLine.rawArguments` is the arguments as they were given, the name of the command first. `args` and the options of `executionContext.commandLine` are what Grails reads from them, as before: an argument that starts with a dash is an option, which takes the argument after it as its value unless it has one of its own (`--name=value`), surrounding white space and surrounding double quotes are removed, and an empty argument is left out.

In summary, creating custom commands in Grails using the `GrailsApplicationCommand` trait is a powerful way to extend your application's functionality beyond the web interface. You can define the command's name, description, and logic, and then execute it from the command line, optionally passing arguments and options as needed.

**Using the `executionContext` in the Grails Custom Commands**

In Grails, the executionContext is a runtime context object that provides valuable information about the current execution environment of a Grails application. It includes details such as the application's environment (e.g., development, production, test) and allows developers to access this context within custom commands.

Custom commands in Grails can use the executionContext to make informed decisions and perform specific tasks based on the current runtime environment. For example, developers can write conditional logic in custom commands that execute differently in production, development, or testing environments. This flexibility enables custom commands to adapt and behave differently depending on the context in which they are run, making them versatile tools for managing and extending Grails applications.

Suppose you have a Grails application that manages customer data, and you want to create a custom command to perform data backup. In this scenario, you may want the backup process to behave differently depending on whether you're running it in a development, staging, or production environment.

Here's an example of how you can create a custom command that uses the executionContext to determine the backup behavior:

[source,groovy]
----
// grails-app/commands/com/example/BackupCommand.groovy
package com.example

import org.apache.grails.core.cli.GrailsApplicationCommand

class BackupCommand implements GrailsApplicationCommand {

    String getName() {
        return "backup"
    }

    String getDescription() {
        return "Backup customer data"
    }

    boolean handle() {
        // Access the executionContext to determine the environment
        def environment = executionContext.environment

        if (environment == "production") {
            // Perform a full backup in the production environment
            println("Performing a full backup of customer data (Production)")
            // Add production-specific backup logic here
        } else {
            // Perform a partial backup in other environments
            println("Performing a partial backup of customer data (Non-production)")
            // Add non-production backup logic here
        }

        return true // Return true to indicate successful execution
    }
}
----

In this example:

- The custom command, named `BackupCommand`, is created to back up customer data.
- It checks the `executionContext` to determine the current environment.
- If the environment is "production," it performs a full backup with production-specific logic.
- In all other environments, it performs a partial backup with non-production logic.

When you run this custom command using `./gradlew runCommand -Pargs="backup"`, it will adapt its behavior based on whether you're in a production or non-production environment, demonstrating how the `executionContext` can be used to make environment-specific decisions in a realistic scenario.

**The Three Kinds of Command**

A command of an application or of a plugin is one of three kinds. Its class says which, and the name of each kind says how it is run:

[cols="2,3,3,4"]
|===
| Kind | The class | What runs it | What the command has

| *Application command*
| implements `ApplicationCommand` or `GrailsApplicationCommand` and neither of the two below
| the build of the project (the Gradle task `runCommand`), which compiles the project and starts the application around the command
| the application context, beans, GORM, the configuration as the application sees it, an environment

| *Gradle command*
| also implements link:{api}org/apache/grails/core/cli/GradleCommand.html[GradleCommand]
| the build of the project (the Gradle task `runCommand`), which compiles the project and does *not* start the application
| the compiled classes of the application, the class path the build resolves, the directories the build gives (a build directory that was moved); no application context

| *Standalone command*
| also implements link:{api}org/apache/grails/core/cli/StandaloneCommand.html[StandaloneCommand]
| the `grails` command line, as a plain Java process: no Gradle, no application
| the files of the project and its own class path; a command of a plugin does not have the classes of the application
|===

All three are created, registered, listed and typed in the same way: `grails create-command`, a class in `grails-app/commands` (or in `src/cli/groovy` of a plugin), and `grails <name>`. Both interfaces are markers without methods. Choose the kind that needs the least:

* A command that needs a bean, a domain class with GORM, or the configuration as the application sees it is an *application command*. The `dbm-` commands of the Database Migration plugin are: they read the configuration of the application and its data source.
* A command that would also work if the application could not start, but needs the compiled classes of the application, a class path only Gradle resolves, or a directory only the build knows, is a *Gradle command*. `query-tail` of Grails Data is one: the build tells it where the build directory is. `s2-quickstart` is one: it reads `application.groovy` of the project as code, which may name classes of the application.
* A command that only renders templates into the project or reads its files is a *standalone command*. The commands of the Scaffolding plugin (`generate-all`, `generate-controller`, `generate-views`, ...) and the other commands of the Spring Security plugins (`s2-create-persistent-token`, `s2ui-override`, `init-oauth2`, ...) are.

*An application command* is every example above this section: `handle()` runs with `applicationContext` set and the beans of the application injected.

*A Gradle command* is run by the build without the application:

[source,groovy]
.grails-app/commands/com/example/ListFieldsCommand.groovy
----
package com.example

import org.apache.grails.core.cli.GradleCommand
import org.apache.grails.core.cli.GrailsApplicationCommand

class ListFieldsCommand implements GrailsApplicationCommand, GradleCommand {

    String description = 'Lists the fields of classes of the application'

    boolean handle() {
        // the classes of the application are on the class path: the build compiled them before the command runs
        args.each { String name ->
            Class<?> type = Class.forName(name)
            println "${type.name}: ${type.declaredFields.findAll { !it.synthetic }*.name.sort().join(', ')}"
        }
        true
    }
}
----

`grails list-fields com.example.Book`, `grails run-command list-fields com.example.Book` and `./gradlew runCommand --arg=list-fields --arg=com.example.Book` all start the Gradle task `runCommand`, which does this for such a command:

* The application is not started: no application context, no plugins, no data source, no `BootStrap`. The `Application` class is not initialized.
* `applicationContext` is `null`, and nothing is injected into the command. A `skipBootstrap` property is not read.
* The command gets what every command gets that is not of the application: the command line (`args`, `executionContext.commandLine`), the directories of the project (`executionContext.baseDir`, `classesDir`, `targetDir`), and with `GrailsApplicationCommand` the helpers for templates, files and models (`render`, `template`, `file`, `model`, ...).
* The class path is that of every command the build runs: the compiled classes of the application, its run time dependencies, and the command line tier (`grailsCli`). The project is compiled before the command runs, so it has to compile.
* The configuration of the application is not loaded. A command that needs a setting reads the file, `grails-app/conf/application.yml` for example, and gets what is written there, without what an environment block, a profile, a system property or a plugin would change.
* `true` ends the task successfully; `false` or an exception fails it.

*A standalone command* is run by the `grails` command line itself, as a process of its own:

[source,groovy]
.grails-app/commands/com/example/CreateReportCommand.groovy
----
package com.example

import org.apache.grails.core.cli.GrailsApplicationCommand
import org.apache.grails.core.cli.StandaloneCommand

class CreateReportCommand implements GrailsApplicationCommand, StandaloneCommand {

    String description = 'Creates a report class from a template'

    boolean handle() {
        if (!args) {
            System.err.println('Usage: create-report <name>')
            return false
        }
        def model = model(args[0])
        render template: template('artifacts/Report.groovy'),
               destination: file("src/main/groovy/${model.packagePath}/${model.simpleName}Report.groovy"),
               model: model
        true
    }
}
----

The template is `src/main/templates/artifacts/Report.groovy` of the project, or `META-INF/templates/artifacts/Report.groovy` of a plugin, with `${packageName}` and `${className}` where the package and the class name go. `grails create-report Sales` starts no Gradle:

----
$ grails create-report Sales
| Running the command create-report of the application, as a process of its own, without Gradle
----

* The `grails` command line starts `java` with a main class of Grails that finds the command by its name, calls `handle()`, and ends with 0 for `true` and with 1 for `false` or an exception. The output of the process is the output of the command; it reads what is typed unless `--non-interactive` is given.
* `applicationContext` is `null`, nothing is injected, and the configuration of the application is not loaded, as for a Gradle command. The command gets the command line, the directories of the project, and the helpers of `GrailsApplicationCommand`.
* *The class path is the one the last build of the project wrote down* (see "The class path of standalone commands" below). A standalone command of the application has the compiled classes of the application, its run time dependencies and the command line tier. A standalone command of a plugin has the run time dependencies and the command line tier, and *not the classes of the application*: it runs also while the application does not compile, which a command that generates code has to. A command of a plugin that needs the classes of the application is a Gradle command.
* *Nothing is run that is older than what it is made from.* When `build.gradle`, `settings.gradle` or `gradle.properties`, a command in `grails-app/commands`, or, for a command of the application, any source of the application was changed since the class path was written down, `grails` runs the build once, after a line that says why, and then starts the command: `| Building the project before create-report is run without Gradle, with the Gradle task grailsStandaloneCommands: src/main/groovy was changed after .grails/cache/standalone-commands.json was written`. The second run starts no build.
* The Java that is started is the one the Gradle wrapper of the project would be started with: the one `JAVA_HOME` names, and without `JAVA_HOME` the one that runs `grails`. A Java that is older than the classes of the project were compiled for is not started, and the command says which version is needed.
* `grails run-command create-report Sales` and `./gradlew runCommand --arg=create-report --arg=Sales` run the same command with Gradle, as a Gradle command is run, for a build script or a continuous integration job that calls the task. `run-command` is also the way to run it when `grails` will not start it itself.
* A standalone command has no environment of its own. `grails.env` is `development` in its process, as it is for every command run by its name; `grails run-command -Dgrails.env=production <name>` runs it with Gradle and that system property. Neither loads the configuration of an environment.

The descriptor of a command, and the catalog of the build, name the kind as the `target`: `application`, `gradle` or `standalone`. The interface on the class is what decides how the command is run. A class that implements both interfaces is a standalone command.

**How to Create a Custom Command from a Grails Plugin**

Plugins publish their commands in a *companion cli artifact* (`<plugin-artifactId>-cli`) instead of
the plugin's runtime jar, so command code and its CLI-only dependencies never reach an
application's runtime classpath (`bootRun`, `bootJar`, `bootWar`). Here is the complete workflow:

1. **Create a Grails Plugin:** If you don't already have a Grails plugin, create one:
+
[source,shell]
----
grails create-plugin my-plugin
----

2. **Define the Command in a `cli` source set:** compiled plugin commands live in `src/cli/groovy`
(not `grails-app/commands`, which is compiled into the runtime jar). Give them a package that is
unique to the cli artifact. Code-generation scripts and multi-step YAML/JSON commands may stay in
`src/main/scripts`; when `grails-plugin-cli` is applied they are copied into the companion jar as
`META-INF/commands` and excluded from the runtime plugin jar. You may also place them directly under
`src/cli/resources/META-INF/commands`:
+
[source,groovy]
----
// src/cli/groovy/com/example/myplugin/cli/AuditReportCommand.groovy
package com.example.myplugin.cli

import org.apache.grails.core.cli.GrailsApplicationCommand

class AuditReportCommand implements GrailsApplicationCommand {

    String description = 'Prints an audit report'

    @Override
    boolean handle() {
        println 'Audit report...'
        return true
    }
}
----
+
When this source set compiles with `grails-core-cli` on its classpath, the command is registered
automatically in `META-INF/grails-cli.factories` inside the cli jar — no manual registration file
is needed.

3. **Apply the Grails cli-artifact plugin in `build.gradle`:** it wires everything — the `cli`
source set as a feature variant, the `grails-core-cli` contract and the plugin's own runtime
classes on the cli compile classpath, the `Grails-Cli-Artifact` manifest advertisement on the
runtime jar, and (when the Grails publish plugin is applied) the companion publication:
+
[source,groovy]
----
plugins {
    id 'org.apache.grails.gradle.grails-plugin'
    id 'org.apache.grails.gradle.grails-plugin-cli'
    id 'org.apache.grails.gradle.grails-publish'
}

cliArtifact {
    // recommended: a unique, stable JPMS module name matching the cli package
    automaticModuleName = 'com.example.myplugin.cli'

    // optional: customize the companion coordinate (defaults to '<plugin-artifactId>-cli');
    // the advertised coordinate is also carried as a capability of the cli variants, so
    // in-build consumers can require it either way
    // artifactId = 'my-plugin-tools'
}

dependencies {
    // additional CLI-only dependencies of the commands, if any:
    // cliImplementation 'org.example:some-cli-tool'
}
----

4. **Publish both artifacts:** publishing the plugin publishes the companion alongside it, as its
own coordinate with its own pom, sources, and javadoc:
+
[source,shell]
----
./gradlew publishToMavenLocal
# com.example:my-plugin        (runtime — no command code)
# com.example:my-plugin-cli    (the commands)
----
+
NOTE: Without the Grails publish plugin, the cli feature is still built and advertised, but the
companion publication must be configured manually from the `cli` software component.

5. **Consume the plugin from an application:** the application declares only the runtime plugin.
The Grails Gradle plugin reads the `Grails-Cli-Artifact` manifest attribute from the plugin jar,
adds `com.example:my-plugin-cli` to the application's `grailsCli` configuration, and registers the
per-command Gradle task automatically:
+
[source,groovy]
----
dependencies {
    implementation 'com.example:my-plugin:1.0.0'   // my-plugin-cli follows automatically
}
----

6. **Run the Command:**
+
[source,shell]
----
./gradlew runCommand -Pargs="audit-report"
# or, via the automatically registered per-command task:
./gradlew auditReport
----

If an application disables the automatic discovery (`grails { cliAutoProvision = false }`), it
declares the companion explicitly instead:

[source,groovy]
----
dependencies {
    implementation 'com.example:my-plugin:1.0.0'
    grailsCli 'com.example:my-plugin-cli:1.0.0'
}
----

By packaging commands this way, the plugin's runtime jar stays free of command code and CLI-only
libraries, while applications get the commands with no additional build configuration.

**Depending on Another Module's CLI Tier**

Within a multi-project build, one project's cli tier may build on another project's cli companion.
Declare the dependency on the owning project with a *capability* naming the companion:

[source,groovy]
----
dependencies {
    cliApi(project(':my-other-plugin')) {
        capabilities {
            requireCapability('com.example:my-other-plugin-cli')
        }
    }
}
----

The cli-artifact plugin publishes such a dependency as a plain dependency on the companion
coordinate (`com.example:my-other-plugin-cli`) in both the pom and the module metadata, so
external consumers resolve the published artifacts directly. This works with a customized
`cliArtifact { artifactId = ... }` as well: the customized coordinate is carried as a capability
of the cli variants, and the published metadata records the customized plain coordinate.

A library that consumes a cli tier in its *main* configurations (`api`/`implementation`) rather
than a `cli` source set — and therefore does not apply the cli-artifact plugin — applies the
`org.apache.grails.gradle.grails-cli-library` plugin to publish its cli dependencies the same way:

[source,groovy]
----
plugins {
    id 'java-library'
    id 'org.apache.grails.gradle.grails-cli-library'
}

dependencies {
    api(project(':my-other-plugin')) {
        capabilities {
            requireCapability('com.example:my-other-plugin-cli')
        }
    }
}
----

WARNING: Capability requests are a build-internal addressing scheme. Never declare
`requireCapability` on an *external* (binary) Grails dependency — published metadata cannot
satisfy it and resolution fails with a capability conflict. External consumers always depend on
the plain `-cli` coordinate, e.g. `grailsCli 'com.example:my-plugin-cli:1.0.0'`.

**Listing Commands Without Running Them**

When a command is compiled, from `grails-app/commands` of an application or from `src/cli/groovy` of a plugin, the compiler writes a descriptor of it beside its registration: `META-INF/grails-commands/<class name>.json`, with the name and the description of the command. Tools read it to list the command without loading its class or starting the application. The descriptor holds what the source says as a constant:

* The name is the one the class name gives (`AuditReportCommand` is `audit-report`), or the string that `getName()` returns or that the property `name` is set to: where the property is declared, or when the command is made, by statements such as `name = 'audit'` or `setName('audit')` in an initializer block, in every constructor, or in a method of the command or of a class it extends that one of them calls. The last of those statements to run decides.
* The description is the string that `getDescription()` returns or that the property `description` is set to, in the same ways. Without one, the description is the name.
* Of a command that extends another class, what the command declares or sets itself comes before what it inherits, as it does when the command runs: a command that sets `name` in its constructor, or in a method its constructor calls, is described by that name, whatever name the class it extends gives.
* A name that is worked out, that is set only under a condition, to a string that is given to the method that sets it, or to a different string by each constructor, cannot be described. Neither can a name that is set, or may be set after the statements above, by code the compiler does not read: a closure, a method of another class or of the Groovy runtime, reflection, code the command is handed to, a trait other than `ApplicationCommand` and `GrailsApplicationCommand` that gives its fields values, or a class compiled in another project or jar. Such a command has no descriptor and is listed by the name its class name gives, which runs it too. A description given in such a way is left out of the descriptor.
* A property that is declared `final` is the string it is declared with. Groovy lets a constructor of the class set such a property again; when one does, the property is read as any other is, from what the constructors leave it as.
* A method that is given the command may stop holding it on one way through its code (`command = null` in one branch of an `if`). Each way is read with what holds the command on that way, and where the ways meet again and it is no longer certain what holds the command, a name that is set from there on is not described.
* The name a command is listed by is the name that runs it: the name of its descriptor, or the name its class name gives when it has none. Another command that gives itself that name when it is made, in a way the compiler does not read, does not take it over: of an `AlphaCommand` and a `BetaCommand` that have no descriptors, `beta` runs `BetaCommand`, whatever `AlphaCommand.getName()` returns. A name that no command is listed by, or that more than one is, which is then not listed, runs the command that has that name when it is made.

Write the name in lower case letters and digits, in words joined by single hyphens, with at most 64 characters, and the description on one line of at most 512 characters; a command whose descriptor has anything else is left out of the list, with the reason. A command whose name or description is not written that way gets a descriptor without the description, or none when it is the name. A command written in Java, or registered by hand in `META-INF/grails-cli.factories`, has no generated descriptor. Add the file to the resources next to the registration:

[source,json]
.src/cli/resources/META-INF/grails-commands/com.example.AuditReportCommand.json
----
{"format": 1, "class": "com.example.AuditReportCommand", "name": "audit-report", "description": "Writes the audit report", "target": "application"}
----

`target` is the kind of the command: `application`, `gradle` for a command the build runs without the application, or `standalone` for one that runs as a process of its own; a descriptor without it is of a command of the application.

The `grailsCommandCatalog` task of an application or plugin project writes the list of the commands the project can run with `runCommand` to `.grails/cache/command-catalog.json` in the directory of the project. That is where the `grails` command reads it, and it is the same place whatever the build directory of the project is, so the task writes there also in a build that moves its build directory. Next to the file the task writes a `.gitignore` that keeps the directory out of a commit. Every build that compiles the project runs the task, after `classes`, and it is up to date when nothing it reads has changed; it can also be run by itself:

[source,shell]
----
./gradlew grailsCommandCatalog
----

It lists the commands of the project itself, of the `-cli` companions of its plugins, of plugin jars that register commands, and, when `grails { legacyCommandSupport = true }` is set, the commands of Grails 7 plugins. The file is one JSON document:

[source,json]
----
{"format": 1, "complete": true, "diagnostics": [],
 "commands": [
   {"name": "audit-report", "aliases": [], "description": "Writes the audit report",
    "origin": "com.example:my-plugin-cli:1.0.0", "target": "application", "registration": "descriptor"}
 ]}
----

* `origin` is the coordinates of the artifact the command comes from, or `application` for a command of the project itself.
* `target` is the kind of the command (see "The Three Kinds of Command" above): `application` for a command that is run with the application started around it, `gradle` for one the build runs without the application, and `standalone` for one the `grails` command line runs as a process of its own, without Gradle. A command without a descriptor is listed as `application`, whatever its class says; the build runs it as its class says, and `grails` runs it through the build.
* `registration` says how much is known: `descriptor` for a command with a descriptor; `factories` for a command that is registered without one, whose name is the one its class name gives and whose description is empty; `legacy` for a command of a Grails 7 plugin, listed the same way. A command listed by the name its class name gives is run by that name also when it has another name of its own; `runCommand` looks for a command by the name it is listed by first, and by the name a command has of its own when no command, or more than one, is listed by that name.
* The file lists at most 512 commands in at most 512 KiB, which is what the `grails` command reads: when a project has more, the first by name are listed and a line of `diagnostics` says how many are not.
* `complete` is `false` when something could not be listed, and `diagnostics` then says what and why, one line each: a descriptor that is not as described above, a name that two commands have (neither is listed, because the task does not choose between them), a descriptor in a jar for a class of the application (the command keeps what the application says of it, and the other descriptor is not used), Grails 7 commands in a project without `legacyCommandSupport`, or a class path the commands run with (`runtimeClasspath` or `grailsCliClasspath`) that does not resolve completely, with what Gradle could not resolve in it. The task prints the same lines as warnings.
* The task resolves those class paths leniently, so that a build that compiles the project, which does not need them, does not fail because one of them does not resolve: the file then lists the commands of what resolves. Running a command with such a class path fails as running the application does, until the dependencies are corrected.

**The class path of standalone commands**

Beside the catalog the build writes `.grails/cache/standalone-commands.json`, with the Gradle task `grailsStandaloneCommands`, which runs after `grailsCommandCatalog` in every build that compiles the project. It is what lets the `grails` command line start a standalone command without asking Gradle for a class path:

[source,json]
----
{"format": 1,
 "commands": {"create-report": "application", "generate-all": "dependencies"},
 "application": ["/work/app/build/classes/groovy/main", "/work/app/build/resources/main"],
 "dependencies": ["/home/me/.gradle/caches/modules-2/files-2.1/.../grails-scaffolding-cli-9.0.0.jar", "..."],
 "sources": ["/work/app/grails-app/controllers", "/work/app/src/main/groovy", "..."],
 "java": 21}
----

* `commands` has the commands of the catalog whose `target` is `standalone`, and for each the class path it runs with: `application` for a command of the project (the entries of `application`, then those of `dependencies`), `dependencies` for a command of a plugin (those of `dependencies` alone). `dependencies` is `runtimeClasspath` and then `grailsCliClasspath`, in that order. Only what exists is written down: a directory of classes that no compiler wrote to, as `build/classes/java/main` of a project without Java sources, is left out. A project without a standalone command has a file without a path.
* The paths are those of this machine, which is why they are in a file of their own: the catalog has none and is the same for the same commands everywhere, so a build cache can keep it; this file is never taken from a build cache. `.grails/cache` holds a `.gitignore` that keeps both out of a commit.
* `sources` are the directories of the sources of the project, and `java` is the Java version its classes are compiled for. `grails` takes the file for out of date when it is older than the catalog, when the catalog is (a build file, a file in `grails-app/commands` or a descriptor the compiler wrote is newer than it), when an entry of a class path is no longer there, and, for a command of the project, when a directory or a file in one of `sources` was changed after the file was written. It then runs `grailsStandaloneCommands`, which compiles the project, and reads the file again. The task holds itself to the same rule and writes a file that is older than one of those again.
* The file has at most 4096 class path entries of at most 1024 characters each, in at most 2 MiB. A class path that is longer, or has a path with a line break or with the character that separates the entries of a class path, is not written down; neither is one that has the output of another project of the build, which only the build keeps current, or one that does not resolve completely. The file then has `throughGradle` with the reason and no path, and `grails <name>` runs the command with the Gradle task `runCommand`, after a line that says why. A long class path is given to `java` in a file (`@file`), so its length is not held to what a command line carries.
* Starting Java on what the file names runs it, so `grails` holds the file to what it holds a Gradle wrapper above the project to. The catalog, this file, `.grails` and `.grails/cache` are files and directories, no links, owned by you, and not writable by everybody. Every entry of a class path is a whole path to a file or a directory in the build of the project, in the Gradle user home (`GRADLE_USER_HOME`, or `~/.gradle`) or in the local Maven repository (`~/.m2/repository`), and it and every directory from it up to that place are owned by you or by root and are not writable by everybody. Otherwise nothing is started, Gradle is not run either, the command ends with exit code 1, and one line says what is wrong and that `grails run-command <name>` runs the command with the build. A directory named in the environment variable `GRAILS_SAFE_DIRECTORY` is used whoever owns it, with what is in it, as it is for a project: name the directory of a repository that is somewhere else, such as a `maven { url = file(...) }` repository outside the project, there.
* A class path is taken from the file only for a command the catalog lists with the `target` `standalone`.

The names, descriptions and origins in the file come from the project's dependencies. They are checked to be one line without control characters, and nothing more: a program that shows them must show them as plain text and give no meaning to anything in them.

Every command in the file is run with `./gradlew runCommand --arg=<name>` followed by its arguments. The task loads no class of the project or of its dependencies, and the file has neither a time nor a path of the machine in it, so the same commands give the same file.

The `grails` command reads this file: in the project, every command in it is a command of `grails` under its name, listed by `help` with its origin and run through `runCommand` with its arguments as they were typed. Every build that compiles the project keeps the file current, and where it is missing or out of date, a name that is no command has the `grails` command run the task once before it refuses the name. A command whose name is a command of the command line itself, another name of one or the short form of one, such as `install-templates`, is not added there; `help` says so, and the command is run with `grails run-command install-templates`.

[[runAppOptions]]
**Adding Options to `run-app` from a Plugin**

A plugin, or an application, can give `grails run-app` an option of its own that sets a property of the application `run-app` starts. The option is declared, not programmed: no code of the plugin runs in the `grails` command. The command line artifact of Grails Data does this for `grails run-app --query-tail`, which starts the application with `grails.gorm.queryTail.enabled=true`.

The declaration is one JSON resource, `META-INF/grails-command-options.json`. A plugin that ships its commands as a companion `-cli` artifact puts it beside them, in `src/cli/resources/META-INF/`; a plugin without a companion puts it in `src/main/resources/META-INF/`; an application puts it in `src/main/resources/META-INF/` or `grails-app/conf/META-INF/`.

[source,json]
.src/cli/resources/META-INF/grails-command-options.json
----
{
  "format": 1,
  "options": [
    {
      "command": "run-app",
      "name": "audit-trail",
      "description": "Log every change the application makes to a domain object.",
      "type": "boolean",
      "property": "myplugin.audit.enabled",
      "value": "true"
    },
    {
      "command": "run-app",
      "name": "tenant",
      "description": "The tenant the application runs as.",
      "type": "string",
      "property": "myplugin.tenant"
    }
  ]
}
----

[cols="1,4"]
|===
|Member |Meaning

|`format`
|The number `1`.

|`command`
|The command the option is one of. `run-app` is the only command that takes declared options in this version; the member is there so that another command can take them later, and an option for any other command is not used.

|`name`
|The long name of the option without its two hyphens: `audit-trail` is typed `--audit-trail`. Lower-case letters and digits in words joined by single hyphens, starting with a letter, 2 to 32 characters.

|`description`
|One line for the help of `run-app`, at most 200 characters, without `$`, `%` and `@`. The help shows it with where the option comes from and the property it sets.

|`type`
|`boolean` for a switch, which is also what an option without the member is, or `string` for an option that takes a value: `--tenant acme` or `--tenant=acme`.

|`property`
|The property of the application the option sets, as it is written in `application.yml`: two or more parts of letters, digits, hyphens and underscores joined by dots, at most 128 characters. See below for the properties no option can set.

|`value`
|What a switch sets the property to: letters, digits, dots, hyphens and underscores, at most 64 characters. `true` without the member. An option of the type `string` has no such member: its value is the one typed.
|===

The build of the application lists the declarations it finds on the class path of the application and of its commands, with the commands themselves: the Gradle task `grailsCommandCatalog` writes them into `.grails/cache/command-catalog.json` as the member `commandOptions`, each with the `origin` it comes from. Every build that compiles the project runs the task. The `grails` command reads the options there and nowhere else, so an option is one of `run-app` once the project has been built with the plugin; before that, the option is refused as one `run-app` does not have, with a line that says how the options are listed.

[source,json]
----
"commandOptions": [
  {"command": "run-app", "name": "audit-trail", "description": "Log every change the application makes to a domain object.",
   "type": "boolean", "property": "myplugin.audit.enabled", "value": "true", "origin": "com.example:my-plugin-cli:1.0.0"}
]
----

An option that is given becomes one system property of the build, `-Dgrails.myplugin.audit.enabled=true`, which the Grails Gradle plugin hands to the application without the `grails.` in front, as it does with `--port` and with any `-Dgrails.NAME=VALUE` of `run-app`. The application reads `myplugin.audit.enabled` as it reads any property, and a value in `application.yml` gives way to it. With Gradle alone the same is `./gradlew bootRun -Dgrails.myplugin.audit.enabled=true`. The value of a `string` option is given to Gradle as the one argument it is, whatever it contains, and never to a shell. A `-Dgrails.myplugin.audit.enabled=...` on the same command line is left as it was typed, and the option adds nothing to it.

A declaration comes from a jar and ends on the command line of a JVM, so it is held to the form above, and what is not as it has to be is not used:

* An option whose name, description, type, property or value is not as the table says is left out alone. The task says so in the `diagnostics` of the file and as a warning of the build, by the place of the option in its resource and without repeating anything of it, and `grails help` shows the line.
* No option sets a property of the JVM or of the build, or one that decides which environment, configuration, profiles or classes the application starts with. Refused are the properties `grails.env`, `base.dir`, `server.port`, `server.address` and `logging.config`, and every property that starts with `java.`, `javax.`, `jdk.`, `sun.`, `com.sun.`, `user.`, `os.`, `file.`, `line.`, `path.`, `http.`, `https.`, `ftp.`, `socks.`, `org.gradle.`, `groovy.`, `loader.`, `spring.config.`, `spring.profiles.`, `spring.main.`, `spring.application.`, `spring.devtools.`, `spring.cloud.`, `server.ssl.`, `grails.config.` or `grails.project.`, whatever its case and with or without the hyphens and underscores of its words (`spring.config.additional-location` is `spring.config.additionalLocation`).
* An option `run-app` has itself stays its own: a declared `port`, `detach` or `help` is not added, and `grails help`, `grails help run-app` and `help --json` say so.
* A name two plugins declare differently is the option of neither, and the diagnostics name both. A plugin and its companion that declare the same thing declare it once. What the application declares holds over what a plugin declares for the same name, so an application can settle such a clash by declaring the option itself.
* A resource has at most 32 KiB and 16 options, and a project at most 32 declared options, the first by name.

The plugin's code is on the class path of the application and runs in it with every right the application has, with or without an option; the rules keep a declaration from reaching further than that, into the command line of Gradle or the JVM of the build, and from changing what the application is behind the name of a harmless switch. The help of `run-app` shows each declared option with the artifact that declares it and the property it sets.

`test-app`, `console` and the other commands take no declared options.
