You can create your own Command scripts by running the link:{commandLineRef}create-script.html[create-script] command from the root of your project. For example the following command will create a script called `src/main/scripts/hello-world.groovy`:

[source,groovy]
----
grails create-script hello-world
----

NOTE: In general Grails scripts should be used for scripting the Gradle based build system and code generation. Scripts cannot load application classes and in fact should not since Gradle is required to construct the application classpath.

See below for an example script that prints "Hello World":

[source,groovy]
----
description "Example description", "grails hello-world"

println "Hello World"
----

The `description` method is used to define the output seen by `grails help` and to aid users of the script. The following is a more complete example of providing a description taken from the `generate-all` command:

[source,groovy]
----
description( "Generates a controller that performs CRUD operations and the associated views" ) {
  usage "grails generate-all <<DOMAIN CLASS>>"
  flag name:'force', description:"Whether to overwrite existing files"
  argument name:'Domain Class', description:'The name of the domain class'
}
----

As you can see this description profiles usage instructions, a flag and an argument. This allows the command to be used as follows:

[source,groovy]
----
grails generate-all MyClass --force
----


==== Template Generation


Plugins and applications that need to define template generation tasks can do so using scripts. A example of this is the Scaffolding plugin which defines the `generate-all` and `generate-controllers` commands.

Every Grails script implements the link:{api}org/grails/cli/profile/commands/templates/TemplateRenderer.html[TemplateRenderer] interface which makes it trivial to render templates to the users project workspace.

The following is an example of the link:{commandLineRef}create-script.html[create-script] command written in Groovy:

[source,groovy]
----
description( "Creates a Grails script" ) {
  usage "grails create-script <<SCRIPT NAME>>"
  argument name:'Script Name', description:"The name of the script to create"
  flag name:'force', description:"Whether to overwrite existing files"
}

def scriptName = args[0]
def model = model(scriptName)
def overwrite = flag('force') ? true : false

render  template: template('artifacts/Script.groovy'),
        destination: file("src/main/scripts/${model.lowerCaseName}.groovy"),
        model: model,
        overwrite: overwrite
----

If a script is defined in a plugin or profile, the `template(String)` method will search for the template in the application before using the template provided by your plugin or profile. This allows users of your plugin or profile to customize what gets generated.

It is common to provide an easy way to allow users to copy the templates from your plugin or profile. Here is one example on how the angular scaffolding copies templates.

[source,groovy]
----
templates("angular/**/*").each { Resource r ->
    String path = r.URL.toString().replaceAll(/^.*?META-INF/, "src/main")
    if (path.endsWith('/')) {
        mkdir(path)
    } else {
        File to = new File(path)
        SpringIOUtils.copy(r, to)
        println("Copied ${r.filename} to location ${to.canonicalPath}")
    }
}
----


==== The "model"


Executing the `model` method with a `Class`/`String`/`File`/`Resource` will return an instance of link:{api}grails/codegen/model/Model.html[Model]. The model contains several properties that can help you generate code.

Example:

[source,groovy]
----
def domain = model(com.foo.Bar)

domain.className == "FooBar"
domain.fullName == "com.foo.FooBar"
domain.packageName == "com.foo"
domain.packagePath == "com/foo"
domain.propertyName == "fooBar"
domain.lowerCaseName == "foo-bar"
----

In addition, an `asMap` method is available to turn all of the properties into a map to pass to the `render` method.


==== Working with files


All scripts have access to methods on the link:{api}org/grails/cli/profile/commands/io/FileSystemInteraction.html[FileSystemInteraction] class. It contains helpful methods to copy, delete, and create files.



==== Scripts and the Grails Forge CLI


The Grails Forge CLI has every script `src/main/scripts/<name>.groovy` of a project as a command, by the name of its file:

[source,console]
----
$ grails -t forge create-script data-import
$ grails -t forge help
...
Commands of the application and its plugins:
  data-import  (script of the application)
$ grails -t forge data-import orders.csv --dry-run
| Warning Script commands are deprecated. Write a new command as a class of the application: create-command
----

A script is run by the build of the project, and not by the Grails Forge CLI. The command starts the Gradle task `runScriptCommand` with the Gradle wrapper of the project, and that task compiles and runs the script in a JVM of the build. A script is code of the project, as its build file is: whoever runs the build of a project runs its scripts, and nothing else does. The Grails Forge CLI itself never compiles, evaluates or opens a script:

* To list the scripts it reads the names of the files in `src/main/scripts` and nothing of what they hold. The description of a script is therefore not shown by `help`. `DataImport.groovy` and `data-import.groovy` are both the command `data-import`. A file is a command when it is a plain file, not a link, whose name is made of the letters a to z and digits, in words that capitals or hyphens set apart, and gives a name of at most 64 characters. `help` and `help --json` say how many `.groovy` files are no commands, without naming them. A directory with more than 4096 files has no commands at all, and of more than 256 scripts the first 256 in the order of their names are commands; `help` says so in both cases. A directory that `src`, `src/main` or `src/main/scripts` is a link to is not listed. The build finds the script to run by the same rule: a link is not run as a script of the project, by the Grails Forge CLI or by `./gradlew runScriptCommand`, and where two files give one name the one that is listed is the one that is run.
* A script that has the name of a command of the Grails Forge CLI, or of a command the build lists (see xref:commandLine[The Command Line], the section on the commands of the application and its plugins), is not a command. `help` says so, and how the script is still run: `grails -t forge gradle runScriptCommand --arg=<name>`.
* Everything after the name is given to the script as it is, each argument as the one argument it is, in a file that only you can read and that is deleted afterwards. The exit code is 0 when the script ran and did not return `false`, and 1 otherwise, with one line that says why: what the script threw, that it returned `false`, or the first mistake and its line when it could not be compiled. The arguments are data: `-Dgrails.env=production` after the name of a script is an argument the script can read (`commandLine.systemProperties`) and does not change the environment the script runs in, which is that of the build, and `--` among them does not end the flags.
* Below a project that is not your own, where the Grails Forge CLI does not use the project (see xref:commandLine[The Command Line]), its scripts are no commands.

The task can be run without the Grails Forge CLI. The first `--arg` is the name of the script, each further one an argument of it; `--args-file` names a UTF-8 file with a JSON array of strings, the name first, for a caller that is a program:

[source,console]
----
$ ./gradlew runScriptCommand --arg=data-import --arg=orders.csv --arg=--dry-run
$ ./gradlew runScriptCommand --args-file=build/tmp/arguments.json
----

The JVM of the script has what the project depends on at run time and the `grailsCli` dependencies on its class path. The classes of the project are not on it and the project is not compiled first, so that a script can generate code for an application that does not compile yet; a project that it depends on (`implementation project(':lib')`) is built, as for anything that uses that class path. A script that is not found in `src/main/scripts` is looked for among the files of `META-INF/commands` on that class path, where the scripts of plugins are, by the same rule for names (`CreateJob.groovy` is `create-job`); the scripts of plugins are run by the task and are not listed by `help`. What a script says through `console` arrives as whole lines of plain text, since Gradle is no terminal, and progress indicators are not drawn. The stack trace of what a script threw is shown when the build is started with `-Dgrails.full.stacktrace=true`.

A script that the build runs has `description`, `args`, `argsMap`, `flag`, `model`, `render`, `template`, `templates`, the methods for working with files, `console`, `config` and `navigateConfig` (read from `grails-app/conf/application.yml` and `application.groovy`), `ant`, the events (`on`, `before`, `after`, `notify`), and calling another script as a method. A closure reaches what its delegate has, as in any Groovy script: `copy { from ...; into ... }`, the nested elements of an Ant task and builders work, and a method that is not there is a `MissingMethodException` a script can catch. It does not have what belonged to the Grails shell:

[cols="1,2", options="header"]
|===
| In a script | With the build

| `gradle.compileGroovy()`
| A script cannot run a build from inside the build. Run the tasks from the command line (`grails -t forge gradle compileGroovy`), or make the work a task of the build that depends on them.

| `testApp()`, `runApp()` and other commands that are no scripts
| Run them from the command line, one after the other. A method that names another script (`generateController('Book')` for `generate-controller`) runs that script.

| Classes of `org.grails.cli`, such as the completers named in a `description`
| They are not on the class path: remove the `import`. A script that imports one is not compiled, and the message says so. A class that is named in the `description` closure without an import does no harm, because the closure is not run.

| `profile`, `spring`, `isServerAvailable()`, `waitForStartup()`
| Not there. A script that uses one of them fails with one line that names it.
|===

Script commands are kept for the applications that have them and are deprecated. A new command is written as a class in `grails-app/commands` (see xref:commandLine#creatingCustomCommands[Creating Custom Commands]), which the Grails Forge CLI lists with its description.
