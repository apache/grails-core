[NOTE]
====
The `create-app` and related commands are available in both the Grails Shell CLI and the Grails Forge CLI.

- To create a project using the default Grails Shell CLI:
`$ grails create-app myapp`
- To use Forge-specific options (such as `--java-version`, `--features`, etc.):
`$ grails -t forge create-app myapp`

====

The primary command for creating a new project is `create-app`, which creates a standard Grails web application that communicates over HTTP. For other types of applications, see the documentation below.

Creating a project is the primary usage of the Grails Forge CLI.  You can also generate an application with grails-shell, which uses profiles for generation.

The `create-app` and other commands support extended options in Forge, which must be run using the following format:

[source,console]
----
$ ./grails -t forge create-app myapp
----

After generating a project with Forge, switch to the created directory and use the default Grails shell CLI (`./grails`) to manage, run, test, and deploy your application.

[cols="1,3,4a,8a"]
|===
| Command | Description | Options | Example

| create-app / create-webapp
| Creates a Grails web application
|
[none]
* -jdk, --java-version
* -s, --servlet
* -d, --data (-g, --gorm are legacy aliases)
* -t, --test
* -f, --features
* -i, --inplace
|
[source,console]
----
./grails -t forge create-app \
    --servlet=tomcat \
    --jdk=11 \
    --data=hibernate5 \
    --test=spock \
    --features=github-workflow-java-ci \

=== The `create-` command flags

The "create-*" commands are used to produce a fundamental Grails project, allowing for the inclusion of optional flags to select additional features, to customize Grails Data settings, an embedded servlet, the test framework, and the Java version.

[cols="4,8,6a"]
|===
| Flag | Description | Example

| -jdk, --java-version
| The JDK version the project should target
|
[source,shell]
----
--java-version 21
----

| -s, --servlet
| Which Servlet Implementation to configure. Possible values: none, tomcat, jetty, undertow.
|
[source,shell]
----
--servlet=tomcat
----

| -d, --data (-g, --gorm are legacy aliases)
| Which Grails Data implementation to configure. Possible values: hibernate5, hibernate7, mongodb. The value hibernate is accepted as a legacy alias for hibernate5.
|
[source,shell]
----
--data hibernate5
----

| -t, --test
| Which test framework to use. Possible values: junit, spock.
|
[source,shell]
----
--test spock
----

| -f, --features
| The features to use. Possible values: h2, gorm-hibernate5, gorm-hibernate7, spring-boot-starter-jetty, micronaut-http-client, cache-ehcache, hibernate-validator, postgres, mysql, cache, database-migration, grails-gsp, hamcrest, gorm-mongodb, gorm-graphql, assertj, mockito, grails-undertow, github-workflow-java-ci, jrebel, testcontainers, sqlserver, grails-console, views-markup, views-json, gorm-neo4j, asciidoctor, grails-web-console, logbackGroovy, mongo-sync, shade, properties, grails-spring-ai, spring-ai-openai, spring-ai-anthropic, spring-ai-ollama
|
[source,shell]
----
--features github-workflow-java-ci,micronaut-http-client
----

| -i, --inplace
| Create a project using the current directory
|
[source,shell]
----
--inplace
----

| --feature-pack-dir
| A directory that holds the feature pack of a plugin, whose feature can then be selected with `--features`. Can be given more than once. A pack is code: use one only when you trust where it comes from. See xref:plugins#forgeFeaturePacks[Adding a Feature to Application Creation].
|
[source,shell]
----
--feature-pack-dir ../acme-audit/src/main/forge
----

|===

=== The `.grails` directory of a project

A project that is generated by a `create-` command or by https://start.grails.org/[the Grails Forge website] has a `.grails` directory, which records how the project was generated:

[cols="1,3"]
|===
| File | What it records

| `.grails/project.yml`
| What was asked for: the type of application, its name and default package, the options (`jdk`, `servlet`, `data`, `reloading`) and the features that were selected by name.

| `.grails/forge.lock.yml`
| What that came to: the version of the generator and of Grails, and every feature the application has, including the default ones and those another feature requires, in the order they were applied. For a feature of a feature pack it says that it came from one.

| `.grails/baseline/`
| A copy of every generated file as it was generated (`files/`), with an index of their SHA-256 digests, whether each is text or binary, and whether it is executable (`index.yml`).
|===

Beside them, `.grails/.gitattributes` tells Git to keep the bytes of these files as they are, whatever its setting for line endings is, because the digests are of those bytes.

The files contain no time of day and nothing of the machine they were written on: generating the same application again with the same version gives the same files.

Commit all of them to version control with the rest of the project. They are what lets the tooling tell the files you changed from the files as they were generated, on any clone of the project. The baseline doubles the generated files in the repository, which is intended. The generated `.gitignore` excludes only what is of one machine: `.grails/cache/`, `.grails/transactions/`, `.grails/run/` and `.grails/history`.

Do not edit these files by hand, and do not change the copies under `.grails/baseline/files`. Each file is checked against the others when it is read, so a change to one of them makes the whole record unusable; the `create-*` code generation commands then say what is wrong, in one line, and fall back to `grails-forge-cli.yml`.

A `create-` command with `--inplace` does not generate over a directory that already has such a record. A file that already exists in the directory is kept, as before, and the baseline holds the file as it would have been generated.
