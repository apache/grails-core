The `grails-testing-support-mongodb` library provides Testcontainers-based MongoDB support for both unit and integration tests.

When creating an application with https://start.grails.org[Grails Forge], select the `mongodb-testing-support` feature together with `gorm-mongodb` or `mongo-sync` to include this dependency automatically.

== Installation

Add the following dependency to your `build.gradle`:

[source,groovy,subs="attributes"]
----
testImplementation "org.apache.grails.testing:grails-testing-support-mongodb"
----

NOTE: Docker must be available for Testcontainers to start a MongoDB container.

== Unit Testing

Extend `org.apache.grails.testing.mongo.AutoStartedMongoSpec` in unit tests. A MongoDB Testcontainers instance is started automatically and injected into the specification.

[source,groovy]
----
import org.apache.grails.testing.mongo.AutoStartedMongoSpec
import org.grails.datastore.mapping.mongo.MongoDatastore
import spock.lang.Shared

class BookSpec extends AutoStartedMongoSpec {

    @Shared
    MongoDatastore mongoDatastore

    void "test mongo connection"() {
        expect:
        mongoHost
        mongoPort
        dbContainer.running
    }
}
----

If a shared `MongoDatastore` field is declared and `shouldInitializeDatastore()` returns `true` (the default), the datastore is bootstrapped against domain classes in the packages returned by `getMongoPackages()` (defaults to the package of the specification).

=== Sharing a Container with Test Helpers

Since Grails 7.0.18, a unit-test helper that is not a specification can call the public
`org.apache.grails.testing.mongo.StartMongoGrailsUnitExtension.getSharedContainer()` accessor. This lets the helper
reuse the container that `AutoStartedMongoSpec` instances on the same thread share instead of starting another one.
The first request on a thread starts its container; later requests on that thread return the same container.

Call the accessor after Spock has started its global extensions, for example from `setupSpec()` or a helper called
by it:

[source,groovy]
----
import org.apache.grails.testing.mongo.StartMongoGrailsUnitExtension

def container = StartMongoGrailsUnitExtension.getSharedContainer()
----

The accessor throws `IllegalStateException` before the unit-test extension has started or after it has stopped.
Spock manages the extension's lifecycle, and the extension stops the shared containers when the test run ends.
Callers must not stop the returned container or invoke the extension's lifecycle methods themselves: another
specification or helper can still need the container.

== Integration Testing

For integration tests, Spock global extensions start a single MongoDB container for the test run when MongoDB is not already listening on port `27017`. Connection details are exposed via system properties such as `grails.mongodb.url`, `grails.mongodb.host`, and `grails.mongodb.port`.

The extension stops a container it started when the test run ends. It does not stop an existing MongoDB server.

== MongoDB Container Version

The MongoDB image version defaults to `7.0.19`. Override it with the `mongodbContainerVersion` system property:

[source,groovy]
----
tasks.withType(Test).configureEach {
    systemProperty "mongodbContainerVersion", "7.0.25"
}
----

== Transactions With an Embedded Replica Set

A standalone MongoDB refuses multi-document transactions, so a specification that exercises them extends `org.apache.grails.testing.mongo.EmbeddedReplicaSetSpec` instead. It starts an embedded replica set of one member through the `grails-data-mongodb-embedded` module and the flapdoodle library behind it, which the test class path has to provide, and exposes the URL of the running server as `mongoUrl`. No Docker is needed.

[source,groovy,subs="attributes"]
----
testImplementation "org.apache.grails.testing:grails-testing-support-mongodb"
testImplementation "org.apache.grails:grails-data-mongodb-embedded"
testImplementation "de.flapdoodle.embed:de.flapdoodle.embed.mongo:4.33.0"
----

The embedded server runs the release line that `mongodbContainerVersion` names, `V8_0` for `8.0` for example, so a container-backed specification and a replica-set one run against the same MongoDB release. When flapdoodle does not run that line yet, the newest line it does run is used instead, and a line on standard error, starting `Embedded MongoDB:`, names both. It is written there rather than logged, so it appears in the test output whatever SLF4J binding the tests use. `org.apache.grails.testing.mongo.EmbeddedMongoVersions.lineFor(String)` answers which line a version maps to.
