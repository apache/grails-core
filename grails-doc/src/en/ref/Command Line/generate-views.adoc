== generate-views

=== Purpose

Generates the views for a domain class: GSP views, or JSON views in a REST API application

=== Examples

[source,console]
----
grails generate-views org.bookstore.Book
grails generate-views Book Author
grails generate-views "*"
----

=== Description

Grails supports a feature known as static scaffolding, which generates a CRUD (Create/Read/Update/Delete) interface for a domain class as source files. Once generated, the files are yours to change, and they are not updated when the domain class changes.

The `generate-views` command generates the GSP views that implement CRUD for the domain class. For the domain class `org.bookstore.Book` it writes `index.gsp`, `show.gsp`, `create.gsp` and `edit.gsp` to `grails-app/views/book`.

One view is written for each `.gsp` template: those of the project under `src/main/templates/scaffolding` when it has any, and otherwise those of the scaffolding plugin. A project can therefore add a view to what is generated by adding a template (see link:{commandLineRefFromRef}install-templates.html[install-templates]).

In a REST API application it generates JSON views instead, as the section "JSON Views and a REST Controller" below describes. For the domain class `org.bookstore.Book` it writes `index.gson`, `show.gson` and the template `_book.gson`, which the other two render a book with, to `grails-app/views/book`. They are written from the templates `index.gson`, `show.gson` and `_domain.gson`, each of the project under `src/main/templates/scaffolding` when it is there and of the scaffolding plugin otherwise.

Usage:

[source,console]
----
grails generate-views <domain class>... [--force] [--views=gsp|json]
----

Arguments:

* `domain class` - The name of a domain class of the project, which is case-sensitive, with or without its package: `Book` or `org.bookstore.Book`. Several names can be given. `*` stands for every domain class under `grails-app/domain`; quote it so that the shell of the operating system does not expand it.

Flags:

* `force` - Replace files that are there already (`--force`)
* `views` - The kind of views to generate, `gsp` or `json` (`--views=json`), where the kind the application is given by itself is not the one that is wanted. The value follows `=` or is the next word: `--views=json` and `--views json` are the same.

=== JSON Views and a REST Controller

// TOOLS-VERIFY: the four rules by which the scaffolding tools choose GSP or JSON views (TOOLS-DESIGN section 8; P3).
In a REST API application and in a REST API plugin the command generates what the `rest-api` profile generated before Grails 9: JSON views in place of GSP views, and a controller for a REST resource in place of a controller for pages. Which of the two an application is given is decided as follows:

* With `--views=json` it is JSON views and the REST controller, and with `--views=gsp` GSP views and the controller for pages, whatever the application has.
* Without the option the features of the project decide, as the record of the `grails` command line has them (see link:{guidePath}commandLine.html#creatingProject[Creating a Grails Project]): a project with the feature `gsp` is given GSP views and the controller for pages, and one with the feature `views-json` and without `gsp` JSON views and the REST controller. That is a REST API application and a REST API plugin. A project with neither feature is given GSP views.
* A project without a record, which the `grails` command line neither generated nor migrated, is given what its views are: GSP views when a file under `grails-app/views` ends with `.gsp`, and JSON views and the REST controller when none does and one ends with `.gson`.
* Everywhere else it is GSP views and the controller for pages. An application that has both GSP and JSON views is therefore given GSP views, as before, unless the option asks for JSON views. `build.gradle` is not read: the tool runs without the class path of the application, and does not ask it.

link:{commandLineRefFromRef}generate-controller.html[generate-controller], link:{commandLineRefFromRef}generate-views.html[generate-views] and link:{commandLineRefFromRef}generate-all.html[generate-all] decide it the same way and take the same option, so a controller and views that are generated one after the other fit together.

A REST API application has the commands when it has the `scaffolding` feature, which it does not have by default: create it with `grails create-restapi myapi --features scaffolding`, or add the feature later with `grails feature add scaffolding`. The feature gives a REST API application the standalone tools of the scaffolding plugin and not the plugin, which the running application has no use for.

=== Running the Command

The command is a tool of the scaffolding plugin (`org.apache.grails:grails-scaffolding`). It only reads and writes files of the project, so it is a standalone tool, in the companion `grails-scaffolding-cli-standalone` of the plugin: `grails` starts it by its name as a Java process of its own, without Gradle and without the application, with the class path the last build of the project wrote down, and the project need not compile (see "A Standalone Tool" in link:{guidePath}commandLine.html#creatingTools[Creating Tools]). `run-tool` and the Gradle task `runTool` run it with the build, without the application. An application that depends on the plugin has the tool, and so has one that declares the standalone tools of the plugin alone (`grailsCliStandalone "org.apache.grails:grails-scaffolding-cli-standalone"`), as a REST API application with the `scaffolding` feature does: that keeps the plugin, GSP and the fields plugin off every class path of the application, of its tests and of its other tools. There are three ways to run it:

[source,console]
----
$ grails generate-views org.bookstore.Book                              <1>
$ grails run-tool generate-views org.bookstore.Book                  <2>
$ ./gradlew runTool -Pargs="generate-views org.bookstore.Book"       <3>
----
<1> By its name. The build lists the tools of the application and its plugins whenever it compiles the project, and in a project it has not compiled yet `grails` has it list them first. See "Tools of the Application and its Plugins" in link:{guidePath}commandLine.html[The Command Line].
<2> With `run-tool`, which runs it with the build of the project.
<3> With Gradle alone. `--arg=generate-views --arg=org.bookstore.Book` in place of `-Pargs` gives each argument as it is.

=== Failures

A file that is there already is kept: the command warns that it skips the file and goes on. With `--force` the file is replaced.

Without a domain class the command says `No domain-class specified` and fails. With a `--views` that is neither `gsp` nor `json` it says what the option takes, writes nothing and fails. A domain class that is not found is named (`Domain class not found for name: ...`); the files of the other classes are generated, and the command fails.

When the command fails, the Gradle task fails, and `grails` ends with exit code 1.

Before Grails 9 the Grails shell ran a script of the same name. The plugin has no scripts any more, and the command asks no questions: the name of the domain class has to be given.
