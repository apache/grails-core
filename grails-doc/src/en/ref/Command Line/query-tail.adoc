== query-tail

=== Purpose

Shows the statements a running application executes, SQL through Hibernate, Cypher through Neo4j,
commands through MongoDB and the reads and writes of the simple in-memory datastore, grouped by the
controller and action that ran them, or the GraphQL operation, so that the pages
running the most queries, and the queries repeating within one request, stand out. The application must be started with capture turned on; see
link:{guidePath}conf.html#queryTail[Finding Query-Heavy Pages with query-tail].

=== Examples

[source,groovy]
----
grails run-app --query-tail         // in one terminal: run the application with capture on

grails query-tail                   // in another: the pages, refreshing as requests are served
grails query-tail --statements      // the statements themselves, the most run first
grails query-tail --page=book/show  // the statements of one page
grails query-tail --stream          // every statement as it runs, grouped by request
grails query-tail --all --once      // a report of everything captured so far, then exit
----

=== Description

Usage:

[source,groovy]
----
grails query-tail [--statements | --stream] [--page=<controller/action>] [--top=<n>] [--all] [--once] [--file=<path>]
----

Without options the command follows the capture and shows the pages, the ones running the most
statements per request first: for each page how many requests were seen, the average and the
highest number of statements per request, the total, and the statement that repeated most within a
single request. The summary refreshes as statements run; press Ctrl-C to stop.

Arguments:

* `statements` - Rank the statements themselves instead of the pages that run them, with how often each ran and on how many pages.
* `stream` - Print every statement as it runs, with a header for each request, instead of a summary. A request that comes back after another interrupted it is headed as continued.
* `page` - Only the statements of one page, given as `controller/action` or as a controller name; implies `--statements`, or filters the stream when `--stream` is given. A namespaced controller's pages match without the namespace as well as with it, and the page of a GraphQL operation, such as `graphql/index (query BookList)`, matches the page it ran on as well as its own name.
* `top` - How many rows to show, or `0` for all of them. Defaults to 30.
* `all` - Read what the application has run so far, not only what it runs from now on.
* `once` - Print the summary of what has been captured and exit, which with `--all` is a report of the whole run so far.
* `file` - The capture file, a relative one read against the application directory, as the application reads `grails.gorm.queryTail.file`. Defaults to the one the application writes, `build/query-tail/capture.log` or the file `grails.gorm.queryTail.file` names. A build directory moved in `build.gradle` is followed by the application, which the Grails Gradle plugin hands it as `grails.project.target.dir`, but not by this command, which runs outside Gradle, unless the command is started with the same property, as with `JAVA_OPTS=-Dgrails.project.target.dir=out grails query-tail`: otherwise name the file in `grails.gorm.queryTail.file` or give it here.

The command does not start the application, and it is not a reason to boot it: it runs without
the application context and only reads the capture file. When there is no capture yet it waits for
one and says how to start the application so that it writes one. When the application restarts,
the command starts over with the new run. Statements run outside a web request, by a scheduled job
for example, are shown under the thread that ran them, after the pages of requests, and the thread
is not counted as a request. The numbers in the name of a thread are replaced by `?`, so the threads
an executor numbers as it starts them, such as `pool-?-thread-?`, are one page, which `--page` names by
the name of any of them.

The command keeps counts rather than the statements it reads, and only the ids of the requests
that ran a statement last, so it can follow a capture however long it grows. It remembers the 10000
requests that ran a statement last to count each request once, and to find the most statements a
request ran and repeated, it follows the 1000 requests of each page that ran a statement last. A
request that runs another statement only after that many other requests have is counted again, and
its counts start again from that statement, which takes that many requests in flight at once.
`--statements` follows no request of a page. It keeps the pages of 1000 threads apart, and counts
the statements of any other thread together, under `thread:(other threads)`.

Statements are shown as they were captured, without their values: literals appear as `?` and
comments are left out. A statement whose values could not be taken out is captured as
`(statement withheld: its values could not be redacted)`. The summaries count the withheld
statements together, as `(statements withheld: their values could not be redacted)`, and never as a
repeat of one another, since what each one was is not known. A statement is read whole however long it is, up to 16 MiB of its line in
the capture; a longer one, longer than any command MongoDB runs, is counted with what was read of
it and shown ending in `... (cut)`. See link:{guidePath}conf.html#queryTail[Finding Query-Heavy Pages with query-tail].
