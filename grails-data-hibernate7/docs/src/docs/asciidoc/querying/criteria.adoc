Criteria is an advanced way to query that uses a Groovy builder to construct potentially complex queries. It is a much better approach than building up query strings using a `StringBuilder`.

Criteria can be used either with the `createCriteria()` or `withCriteria(closure)` methods.

The builder uses Hibernate 7's Criteria API (based on JPA Criteria). The nodes on this builder map to GORM query constraints which are then translated into JPA Criteria predicates.

[source,groovy]
----
def c = Account.createCriteria()
def results = c.list {
    between("balance", 500, 1000)
    eq("branch", "London")
    or {
        like("holderFirstName", "Fred%")
        like("holderFirstName", "Barney%")
    }
    maxResults(10)
    order("holderLastName", "desc")
}
----

This criteria will select up to 10 `Account` objects in a List matching the following criteria:

* `balance` is between 500 and 1000
* `branch` is 'London'
* `holderFirstName` starts with 'Fred' or 'Barney'

The results will be sorted in descending order by `holderLastName`.

If no records are found with the above criteria, an empty List is returned.

[[HibernateCriteriaDSL]]
==== Hibernate Criteria DSL

In Hibernate 7, the criteria builder has been completely rewritten to leverage the JPA Criteria API. The `HibernateCriteriaBuilder` implements the GORM criteria DSL and provides seamless integration with Hibernate 7 features.

The DSL supports all standard GORM criteria methods such as `eq`, `ne`, `gt`, `lt`, `ge`, `le`, `between`, `like`, `ilike`, `in`, `isNull`, `isNotNull`, `isEmpty`, `isNotEmpty`, and more.

[source,groovy]
----
def results = Person.withCriteria {
    ilike('firstName', 'b%')
    or {
        ge('age', 18)
        isNull('parent')
    }
}
----

==== Conjunctions and Disjunctions


As demonstrated in the previous example you can group criteria in a logical OR using an `or { }` block:

[source,java]
----
or {
    between("balance", 500, 1000)
    eq("branch", "London")
}
----

This also works with logical AND:

[source,java]
----
and {
    between("balance", 500, 1000)
    eq("branch", "London")
}
----

And you can also negate using logical NOT:

[source,java]
----
not {
    between("balance", 500, 1000)
    eq("branch", "London")
}
----

All top level conditions are implied to be AND'd together.


==== Querying Associations


Associations can be queried by having a node that matches the property name. For example say the `Account` class had many `Transaction` objects:

[source,groovy]
----
class Account {
    ...
    static hasMany = [transactions: Transaction]
    ...
}
----

We can query this association by using the property name `transactions` as a builder node:

[source,java]
----
def c = Account.createCriteria()
def now = new Date()
def results = c.list {
    transactions {
        between('date', now - 10, now)
    }
}
----

The above code will find all the `Account` instances that have performed `transactions` within the last 10 days.
You can also nest such association queries within logical blocks:

[source,java]
----
def c = Account.createCriteria()
def now = new Date()
def results = c.list {
    or {
        between('created', now - 10, now)
        transactions {
            between('date', now - 10, now)
        }
    }
}
----

Here we find all accounts that have either performed transactions in the last 10 days OR have been recently created in the last 10 days.


[[criteriaAssociationAliases]]
==== Association Aliases

`createAlias('association', 'alias')` creates an inner join. Restrictions, projections, and ordering on `alias.property` reuse that association join rather than adding another join. The three-argument overload accepts `0` for an inner join, `1` for a left outer join, or `2` for a right outer join. Hibernate 7 does not support full joins through this overload; other values produce an inner join.

Every explicitly requested alias of an entity association creates a join, even when no restriction, projection, or order references it. For example, `createAlias('favorite', 'a', 1)` followed by `createAlias('favorite', 'b', 0)` creates both a left join and an inner join. The inner join excludes entities with no favorite even when `b` is otherwise unused. This also applies to counts and paginated queries.

An explicitly declared alias takes precedence over an association path with the same name. For example, after `createAlias('favorite', 'f')` and `createAlias('likes', 'favorite')`, `f.label` refers to the favorite entity, while `favorite.label` refers to an element of `likes`. This applies independently to restrictions, projections, and ordering; using `f.label` only in a projection or an order does not change which association `favorite.label` restricts.

Aliases declared inside an association block are relative to that association. For example, `likes { createAlias('tag', 't'); eq('t.name', 'a') }` joins the tag of each like, not a tag on the outer entity. A local alias can reuse an outer alias name without changing the outer alias. Aliases declared in a `list { ... }` closure are discarded when another `list { ... }` query starts on the same builder.

An unused entity alias inside an association block still creates its requested join in that association's scope. For example, `likes { createAlias('tag', 't') }` excludes likes with no tag, even without a restriction on `t`. Using join type `1` retains those likes. These join semantics also apply to counts and paginated totals.

===== Collection Aliases

Declaring two different aliases for the same entity-valued collection in `createCriteria()` or `withCriteria` creates independent joins, so restrictions on those aliases can match different associated entities:

[source,groovy]
----
def teams = Team.withCriteria {
    createAlias('likes', 'a')
    createAlias('likes', 'b')
    eq('a.label', 'first')
    eq('b.label', 'second')
}
----

Each alias retains its own join type: `createAlias('likes', 'a')` followed by `createAlias('likes', 'b', 1)` leaves `a` as an inner join rather than changing it to a left join. In particular, `isNull('a.label')` does not match an entity with no likes. This also applies when an explicitly declared alias has the same name as the association path, for example `createAlias('likes', 'likes')` followed by `createAlias('likes', 'other')`. Repeated restrictions, projections, and ordering on one alias still reuse that alias's join.

For a collection of basic values, such as `static hasMany = [schools: String]`, each explicit alias represents an independent element join with its own join type. For example, restrictions on two aliases can match different elements of the same collection. The collection property itself remains available for collection restrictions such as `sizeEq('schools', 2)`, even when an alias is used to restrict an individual element.

These aliases are also preserved when calculating a paged criteria result's `totalCount` and when calling `count { ... }` with projections. This includes multiple aliases of an entity collection and aliases of basic-value collections. The total count uses the alias restrictions without applying the page's `max` or `offset`.

===== Aliases in Subqueries

An association alias declared in a detached subquery joins from the subquery's own root, even if its name matches an association path or alias in the outer query. A locally declared alias takes precedence. Referencing an outer query's alias explicitly, without redeclaring it in the subquery, can still correlate the subquery with the outer query.

A plain dotted association path in a detached subquery, such as `eq('favorite.label', 'second')`, resolves from the subquery's own root when its entity has that association, rather than reusing an outer query's implicit association join. This applies to either operand of a property comparison, including `eqProperty('name', 'favorite.label')`, and to comparisons inside nested junctions. When the subquery entity does not have that association, the path can instead reference an existing enclosing query join. For example, a subquery over `Like` can use `eqProperty('favorite.label', 'label')` to correlate with an outer `Team` query that joins `favorite`. This works whether the outer join comes from a dotted path restriction or `createAlias('favorite', 'f')`. A dotted-path restriction in the outer query must come before the exists; otherwise, use `createAlias` on the outer query.


==== Querying with Projections


Projections may be used to customise the results. Define a "projections" node within the criteria builder tree to use projections.

[source,java]
----
def c = Account.createCriteria()

def numberOfBranches = c.get {
    projections {
        countDistinct('branch')
    }
}
----

When multiple fields are specified in the projection, a List of values will be returned. A single value will be returned otherwise.

Common projections include `count`, `countDistinct`, `groupProperty`, `avg`, `min`, `max`, `sum`, `id`, and `property`.


==== SQL Restrictions


You can restrict the results with a native SQL condition, which is added to the `where` clause of the query as written, in parentheses.

[source,java]
----
def c = Person.createCriteria()

def peopleWithShortFirstNames = c.list {
    sqlRestriction "char_length(first_name) <= 4"
}
----

SQL Restrictions may be parameterized to deal with SQL injection vulnerabilities related to dynamic restrictions.

[source,java]
----
def c = Person.createCriteria()

def peopleWithShortFirstNames = c.list {
    sqlRestriction "char_length(first_name) < ? AND char_length(first_name) > ?", [maxValue, minValue]
}
----

NOTE: Note that the parameter there is SQL. The `first_name` attribute referenced in the example refers to the persistence model, not the object model like in HQL queries.

Each `?` in the SQL is bound to the value at the same position in the list, so the number of `?` placeholders must match the number of values, and a value must not be `null`. A `?` in a string literal, such as `'%?'`, in a quoted identifier or in a comment is not a placeholder.

The SQL is read the way the database reads it, from the dialect of the connection the query runs on, so that a `?` the database does not read as a placeholder is not counted as one:

* On SQL Server and Sybase, square brackets quote an identifier, so a `?` inside `[...]` is part of a name, and block comments nest. On every other database, square brackets hold an array literal or an array subscript, and the placeholders inside them are bound as any other: `pages = ANY(ARRAY[?, ?])` takes two values on PostgreSQL or H2.
* On MySQL and MariaDB, a backslash escapes in a string, so `'it\'s ?'` is one string; `#` starts a comment, and `--` starts one only when a space follows it.
* On PostgreSQL, a block comment nests, `$tag$...$tag$` is a string, an `E'...'` string escapes with a backslash, and `??` is a literal question mark, not two placeholders. H2 has `$$...$$` strings.
* On Oracle, `q'[...]'` is a string.
* On H2, `//` starts a comment as `--` does, and `$$...$$` is a string.

On every database a string in single quotes, an identifier in double quotes and a comment hold no placeholder. A backquote is read as quoting on every database, as it does on MySQL, MariaDB and H2 in their MySQL mode. The defaults of each server are assumed: the server modes that change what a quote or a backslash means, such as `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES` of MySQL, are not read from the server. In HQL, only `/* ... */` is a comment: Hibernate rejects `--` and `//`.

The SQL of a `sqlProjection` column alias may be written as a string in single quotes on MySQL and SQL Server, which accept that form.

When the query joins other tables, qualify the columns with `{alias}`, which stands for the table alias of the queried class, so that a column a joined table also has is not ambiguous:

[source,java]
----
def c = Person.createCriteria()

def peopleWithShortFirstNames = c.list {
    pets {
        eq 'name', 'Lucky'
    }
    sqlRestriction "char_length({alias}.first_name) <= ?", [4]
}
----

Inside an association block, such as `pets { ... }`, the condition restricts the association, as the other criteria in the block do, and `{alias}` stands for the table alias of the association instead. This includes an association block inside an `and`, `or` or `not` block.

A <<querying-detachedCriteria,detached criteria>> accepts `sqlRestriction` too.

==== SQL Projections


The `projections` node also accepts native SQL, for a value that only SQL computes, such as a date truncated to the day.

[source,java]
----
// Box is a domain class...
class Box {
    int width
    int height
    Date packedAt
}
----

[source,java]
----
def c = Box.createCriteria()

def results = c.list {
    projections {
        sqlProjection '(2 * (width + height)) as perimeter, (width * height) as area', ['perimeter', 'area'], [INTEGER, INTEGER]
    }
}
----

The first argument to the `sqlProjection` method is the SQL which defines the projected values, separated by commas, each one optionally followed by `as` and its column alias, which may be quoted the way the database quotes an identifier: in double quotes, in backquotes, or in square brackets on SQL Server. The second argument is the list of column aliases of the projected values, and the third is the list of their types. A type is a constant of `org.hibernate.type.StandardBasicTypes`, such as `INTEGER`, `LONG`, `STRING` or `TIMESTAMP`, which the DSL provides under the same name, an `org.hibernate.type.Type` or a Java class.

The query above returns the perimeter and the area of each box, in a list each: `[[18, 14], [20, 16], [22, 18], [26, 36]]`. If only one value is projected, the alias and the type do not need to be in a list:

[source,java]
----
def totalArea = Box.createCriteria().get {
    projections {
        sqlProjection 'sum(width * height) as totalArea', 'totalArea', INTEGER
    }
}
----

The `sqlGroupProjection` method groups the results by a SQL group by clause, a single expression or a comma separated list of them, given as its second argument:

[source,java]
----
def results = Box.createCriteria().list {
    projections {
        sqlGroupProjection 'width, sum(height) as combinedHeightsForThisWidth', 'width', ['width', 'combinedHeightsForThisWidth'], [INTEGER, INTEGER]
    }
}
----

The query above returns the combined heights of the boxes of each width: `[[2, 24], [4, 9]]`. A SQL projection combines with the other projections, such as `rowCount()`, and the results can be ordered by its column alias with `order`. The group by clause may also name a column alias, which stands for the SQL that it names. A restriction such as `gt('height', 5)` always restricts the property, even if a column alias has the same name.

As in a SQL restriction, `{alias}` in the SQL stands for the table alias of the queried class, so a column that a joined table also has is not ambiguous:

[source,java]
----
def boxesPerDay = Box.createCriteria().list {
    projections {
        sqlGroupProjection "date_trunc('day', {alias}.packed_at) as day", "date_trunc('day', {alias}.packed_at)", ['day'], [TIMESTAMP]
        rowCount()
    }
}
----

==== Setting Properties in the Criteria Instance


The builder allows setting properties that control how the query is executed.

[source,groovy]
----
import org.hibernate.FetchMode
...
def results = c.list {
    maxResults(10)
    firstResult(50)
    cache(true)
    readOnly(true)
    lock(true)
    fetchMode("aRelationship", FetchMode.JOIN)
}
----

If a node within the builder tree doesn't match a particular criterion it will attempt to set a property on the Criteria object itself. This allows full access to all the properties in the criteria.

==== Advanced Hibernate 7 Features

The Hibernate 7 criteria builder supports several advanced features:

* **Pessimistic Locking:** Use `lock(true)` to obtain a pessimistic write lock.
* **Query Caching:** Use `cache(true)` to enable query caching for the results.
* **Read-Only Mode:** Use `readOnly(true)` to disable dirty checking for loaded entities.
* **Fetch Mode:** Use `fetchMode("association", FetchMode.JOIN)` to specify Eager/Lazy fetching strategies.


==== Using Scrollable Results


You can use Hibernate's https://docs.hibernate.org/orm/7.0/javadocs/org/hibernate/ScrollableResults.html[ScrollableResults] feature by calling the scroll method:

[source,groovy]
----
def results = crit.scroll {
    maxResults(10)
}
def f = results.first()
def l = results.last()
def n = results.next()
def p = results.previous()

def future = results.scroll(10)
def accountNumber = results.getLong('number')
----

To quote the Hibernate documentation on ScrollableResults:

____
A result iterator that allows moving around within the results by arbitrary increments. The Query / ScrollableResults pattern is very similar to the JDBC PreparedStatement / ResultSet pattern and the semantics of methods of this interface are similar to the similarly named methods on ResultSet.
____

Contrary to JDBC, columns of results are numbered from zero.


==== Querying with Eager Fetching


In the section on eager and lazy fetching we discussed how to declaratively specify fetching to avoid the N+1 SELECT problem. However, this can also be achieved using a criteria query:

[source,groovy]
----
def criteria = Task.createCriteria()
def tasks = criteria.list{
    eq "assignee.id", task.assignee.id
    join 'assignee'
    join 'project'
    order 'priority', 'asc'
}
----

Notice the usage of the `join` method: it tells the criteria API to use a `JOIN` to fetch the named associations with the `Task` instances. It's probably best not to use this for one-to-many associations though, because you will most likely end up with duplicate results. Instead, use the `select` fetch mode:

[source,groovy]
----
import org.hibernate.FetchMode as FM
...
def results = Airport.withCriteria {
    eq "region", "EMEA"
    fetchMode "flights", FM.SELECT
}
----

Although this approach triggers a second query to get the `flights` association, you will get reliable results — even with the `maxResults` option.

NOTE: `fetchMode` and `join` are general settings of the query and can only be specified at the top-level, i.e. you cannot use them inside projections or association constraints.

An important point to bear in mind is that if you include associations in the query constraints, those associations will automatically be eagerly loaded. For example, in this query:

[source,groovy]
----
def results = Airport.withCriteria {
    eq "region", "EMEA"
    flights {
        like "number", "BA%"
    }
}
----

the `flights` collection would be loaded eagerly via a join even though the fetch mode has not been explicitly set.


==== Method Reference


If you invoke the builder with no method name such as:

[source,groovy]
----
c { ... }
----

The builder defaults to listing all the results and hence the above is equivalent to:

[source,groovy]
----
c.list { ... }
----

[format="csv", options="header"]
|===
Method,Description
*list*,This is the default method. It returns all matching rows.
*get*,Returns a unique result set i.e. just one row. The criteria has to be formed in a way that it only queries one row. This method is not to be confused with a limit to just the first row.
*scroll*,Returns a scrollable result set.
*listDistinct*,If subqueries or associations are used one may end up with the same row multiple times in the result set. This allows listing only distinct entities and is equivalent to `DISTINCT_ROOT_ENTITY` of the CriteriaSpecification class.
*count*,Returns the number of matching rows.
|===


==== Combining Criteria


You can combine multiple criteria closures in the following way:

[source,groovy]
----
def emeaCriteria = {
    eq "region", "EMEA"
}

def results = Airport.withCriteria {
    emeaCriteria.delegate = delegate
    emeaCriteria()
    flights {
        like "number", "BA%"
    }
}
----

This technique requires that each criteria must refer to the same domain class (i.e. `Airport`).
A more flexible approach is to use Detached Criteria, as described in the following section.
