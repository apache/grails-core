= Grails Benchmarks

JMH microbenchmarks for Grails framework hot paths -- the code that runs on every request or
every bound object, where a regression directly costs users latency.

This module is a build-time-only harness. It is *not published*, is not part of the BOM, and
nothing at runtime depends on it.

JMH is licensed under GPLv2 with the Classpath Exception, an ASF Category X license. Its use is
acceptable here because this build-time-only module is never published or included in Grails runtime
artifacts.

== Running locally

The repository baseline is JDK 21, so point `JAVA_HOME` at a JDK 21 if it is not your default.
Run everything from the repository root:

[source,bash]
----
JAVA_HOME=/path/to/jdk-21 ./gradlew :grails-benchmarks:jmh
----

A full run at default settings takes several minutes. While iterating, narrow it to one class
and cut the iteration counts:

[source,bash]
----
JAVA_HOME=/path/to/jdk-21 ./gradlew :grails-benchmarks:jmh \
  -Pjmh.include=UrlMappingsBenchmark \
  -Pjmh.forks=1 -Pjmh.warmupIterations=1 -Pjmh.iterations=1
----

Add allocation profiling with `-Pjmh.profilers=gc`, which populates the `gc.alloc.rate.norm`
(bytes per operation) metric the CI report shows as an advisory column.

== Comparing results locally

Render a report from a JMH JSON result file with the Gradle comparison task:

[source,bash]
----
./gradlew -q :grails-benchmarks:jmhCompare --args="--head build/results/jmh/results.json"
----

Add `--base <path>` to compare paired base and HEAD results. Add `--output <file>` to write the
rendered Markdown report to a file as well as standard output.

== Indy vs classic callsite (local)

Grails apps default to Groovy invokedynamic *off* (`grails { indy = false }`). Framework modules
and this harness honour the same toggle via `-PgrailsIndy` (wired through `CompilePlugin` and
`gradle/grails-extension-gradle-config.gradle`). Clean between modes so every Groovy class is
recompiled:

[source,bash]
----
# Classic callsite (Grails default / non-indy)
./gradlew clean :grails-benchmarks:jmh \
  -PgrailsIndy=false \
  -Pjmh.resultFile=$PWD/build/jmh-noindy.json \
  -Pjmh.forks=2 -Pjmh.warmupIterations=3 -Pjmh.iterations=5

# Invokedynamic
./gradlew clean :grails-benchmarks:jmh \
  -PgrailsIndy=true \
  -Pjmh.resultFile=$PWD/build/jmh-indy.json \
  -Pjmh.forks=2 -Pjmh.warmupIterations=3 -Pjmh.iterations=5

# Compare (treat non-indy as base, indy as head)
./gradlew -q :grails-benchmarks:jmhCompare \
  --args="--base build/jmh-noindy.json --head build/jmh-indy.json --output build/jmh-indy-vs-noindy.md"
----

On Groovy 6, non-indy compilation also needs `groovy-callsite` on the classpath (already managed
in the canary BOM).

== App-level validation (grails-test-examples)

Microbenchmarks prove hot-path deltas. Real apps prove the stack still behaves the same way once
Spring Boot, URL mappings, interceptors, GSP/views, and filters are in play.

### Methodology (same discipline as JMH)

1. *Same machine, sequential A/B.* Never compare across machines or concurrent load.
2. *Clean rebuild each mode.* `./gradlew clean ... -PgrailsIndy=false|true` so framework modules
   and the app recompile with classic callsites or invokedynamic (`CompilePlugin` +
   `grails-extension-gradle-config.gradle`).
3. *Full app stack.* Gated `@Integration` specs boot Spring Boot (`RANDOM_PORT`) and issue real
   HTTP through `HttpClientSupport` - not mocked controllers.
4. *Warmup then measure.* Default 200 discarded requests, then 1000 timed samples. Split samples
   into fork-shaped rawData so `:grails-benchmarks:jmhCompare` can consume the JSON.
5. *Rulers / stability.* Prefer apps with no external DB cold-start noise for the first pass
   (in-memory H2). Skip Geb/browser paths for timing. Do not use wall-clock of the whole
   integration suite as a primary metric (Spock setup dominates).
6. *Secondary metrics only.* Compile time and full-suite wall clock are informative, not verdicts.

### Gated specs

| App | Project | Spec | Path under test |
| --- | --- | --- | --- |
| latency | `:grails-test-examples-latency` | `AppBenchFastPingSpec` | `GET /fast/ping` (plain `render`) |
| app1 | `:grails-test-examples-app1` | `AppBenchInterceptorDemoSpec` | `GET /interceptorDemo/one` |
| gsp-layout | `:grails-test-examples-gsp-layout` | `AppBenchDemoRenderTextSpec` | `GET /demo/renderText` |

Enable with `-PappBench=true`. Specs are `@IgnoreIf` when the flag is off, so normal CI is unchanged.

### One app, both modes

[source,powershell]
----
$out = "$PWD/build/app-bench"
New-Item -ItemType Directory -Force -Path $out | Out-Null

./gradlew clean :grails-test-examples-latency:integrationTest `
  "-PgrailsIndy=false" "-PappBench=true" `
  "-PappBenchOut=$out/latency-noindy.json" `
  --tests "latencyapp.AppBenchFastPingSpec"

./gradlew clean :grails-test-examples-latency:integrationTest `
  "-PgrailsIndy=true" "-PappBench=true" `
  "-PappBenchOut=$out/latency-indy.json" `
  --tests "latencyapp.AppBenchFastPingSpec"

./gradlew -q :grails-benchmarks:jmhCompare `
  --args="--base $out/latency-noindy.json --head $out/latency-indy.json --output $out/latency-indy-vs-noindy.md"
----

### Orchestrate all three apps

[source,powershell]
----
pwsh grails-benchmarks/scripts/run-app-indy-bench.ps1
# optional: -Warmup 100 -Samples 500
----

Reports land in `build/app-bench/*-indy-vs-noindy.md` and `build/app-bench/all-apps-indy-vs-noindy.md`.

=== Known blocker on Groovy 6 (non-indy)

Compiling the framework with `-PgrailsIndy=false` currently produces *broken* interface
default methods that reference a missing CallSite holder class, for example:

----
// GrailsApplicationLifeCycle.beanRegistrar() with indy=false
invokestatic grails/core/GrailsApplicationLifeCycle$1.$getCallSiteArray
----

`GrailsApplicationLifeCycle$1` is not emitted into `grails-core.jar`, so real apps fail at
boot with:

----
java.lang.NoClassDefFoundError: grails/core/GrailsApplicationLifeCycle$1
----

With `-PgrailsIndy=true` the same default method compiles to a direct `return null` and apps
boot. Framework JMH microbenchmarks still run under both modes because they never execute
these default methods. Until this GROOVY-11158 / interface-default-method packaging issue is
fixed, *app-level* A/B is blocked on the non-indy side: measure indy apps, and treat non-indy
boot failure as a hard regression rather than a timing result.

== Gradle properties

|===
| Property | Default | Purpose

| `jmh.include` | `.*` | Comma-separated benchmark include patterns (regex)
| `jmh.forks` | `1` | JVM forks per benchmark. CI uses `2`
| `jmh.warmupIterations` | `1` | Warmup iterations. CI uses `3`
| `jmh.iterations` | `1` | Measurement iterations. CI uses `5`
| `jmh.warmupTime` | `1s` | Duration of each warmup iteration
| `jmh.iterationTime` | `1s` | Duration of each measurement iteration
| `jmh.resultFormat` | `JSON` | JMH result format
| `jmh.resultFile` | `build/results/jmh/results.json` | Absolute path for the result file
| `jmh.profilers` | none | Comma-separated JMH profilers, for example `gc`
| `jmh.failOnError` | `true` | Fail the build when a benchmark throws
|===

`jmh.failOnError` defaults to `true` deliberately. JMH otherwise drops a benchmark that throws
during `@Setup` from the results file while still reporting build success, which would silently
shrink the comparison set in CI.

== Layout

Benchmarks are Java, under `src/jmh/java`. Setup fixtures are Groovy, under `src/main/groovy`.
The comparison tool is Groovy in the `report` source set, under `src/report/groovy`.

That split is intentional. A benchmark written in Groovy measures Groovy's dynamic call-site
machinery as much as the Grails API under test, so the measured method stays in Java. Fixtures
are Groovy only where the Grails API genuinely requires it -- the URL mappings DSL, the
`Validateable` trait, and view templates are all closure-based. Fixtures live in `main` rather
than `src/jmh/groovy` because the `me.champeau.jmh` plugin puts the main source set's output on
the jmh compile classpath, which keeps the benchmark source set pure Java and preserves normal
JMH annotation processing.

The `report` source set depends on Groovy alone and on no Grails project. The CI reporting job
runs it after a bare checkout, so it must render Markdown without compiling the framework.

Benchmarks are grouped by package, and the CI report aggregates per group:

|===
| Package | Covers

| `urlmappings` | Request URI matching (warm and cold cache) and reverse URL creation
| `databinding` | Binding a map onto an object, with and without type conversion
| `gsp` | GSP parsing (template text to generated Groovy source)
| `interceptors` | Interceptor URI match decisions
| `views` | JSON and markup view rendering
| `ruler` | Pure-JDK probes used to detect an unstable CI runner
|===

The `ruler` benchmarks touch no Grails or Groovy code. Because CI measures the base and head
revisions on the *same* runner, a ruler that moves between the two halves of a run means the
runner itself was unstable and the whole comparison is untrustworthy. They are excluded from
verdicts and group summaries.

== Known gap: validation

`Validateable.validate()` is a genuine hot path and belongs in this suite, but it is not here yet.
A benchmark was written and then withdrawn because it was too unstable to be useful: measured at
2 forks x 5 iterations it showed 80-160% relative error, against 15-20% for the pure-JDK rulers on
the same otherwise-idle machine. At that spread the confidence intervals can never separate, so the
comparison would report `no clear change` no matter what happened to validation performance, while
still consuming CI time and contributing a meaningless number to a group geometric mean.

Two things were ruled out. Object construction was moved into `@Setup`, so the map constructor is
not being measured. Errors were reset between invocations, because `doValidate()` copies an
object's existing errors into the new error set and repeated validation of a failing object
otherwise grows that set without bound. Neither brought the variance down to a usable level, which
points at bimodal behaviour across forks rather than at the fixture.

Anyone picking this up should start by raising the fork count to see whether the distribution is
bimodal, and by checking whether `findConstraintsEvaluator()` and `evaluator.evaluate()` are
re-doing work on every call.

== Adding a benchmark

Prefer paths that are hot per request, cheap to construct without a Spring context or servlet
container, and meaningful to users. Anything with an internal cache is a good candidate, since
cache-effectiveness regressions are exactly what this suite is meant to catch.

Keep the total benchmark count modest. CI runs the whole suite twice per shard, so every added
benchmark costs roughly double its runtime on every performance-labelled pull request.

Every `@Benchmark` method must return its result or consume it through a `Blackhole`, otherwise
the JIT can eliminate the work being measured.

== CI

Upstream PR https://github.com/apache/grails-core/pull/16071 adds `.github/workflows/benchmark.yml`
to run this suite on pull requests labelled `performance` (merge commit vs base, single runner,
`:grails-benchmarks:jmhCompare` report). That workflow is intentionally *not* on this experimental
indy-comparison branch; run the suite locally (see Indy vs classic callsite above). The Groovy
compare tool lives in `grails-benchmarks/src/report/groovy` and is covered by
`./gradlew :grails-benchmarks:test`.
