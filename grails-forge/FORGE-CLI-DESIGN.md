# One generator: Forge, feature packs, and a profile-free console

**Issue:** apache/grails-core #16348 · **Pull request:** #17114 · **Target:** 9.0.x · **Revision:** 104, 2026-11-24 · **Contract checked against:** `7739cc503d6`

This is the maintainers' design of the Grails 9 command line: one `grails` command built on Grails Forge, feature packs in place of profiles, and the commands that work in a project. Users read the Grails guide. Where the guide documents a behaviour, this document states the decision in a sentence and links the guide page by its path in the repository instead of repeating it. When this document, the guide and the code disagree, the code wins, then the guide, and the disagreement is fixed where it was found.

Keeping it current: section 1 has one row per capability. A change that alters what a capability does, its limits or its evidence updates that row and adds a row to the [change log](#changelog). A gate that is still open is a row of section 2 and is named in the Follow-up column of section 1; it never lives only in the [History](#history).

<a id="architecture"></a>
## 3. Decisions that stand

Each decision in a few sentences, with the guide page that documents the behaviour. Where a decision came from, and what it replaced, is in the [History](#history).

<a id="one-cli"></a>
### 3.1 One command tree

- **One tree, one entry point.** The picocli root `ForgeCommand` is started as `grails` by `org.apache.grails.forge.cli.GrailsCli` of `grails-forge-cli`, the `Main-Class` of the `grails-cli` jars; the only commands of the distribution are `grails` and `grails.bat`. The Grails shell, its dispatcher, `-t`/`--type`, `GRAILS_PREFERRED_SHELL` and the alias start scripts are removed. The name `DelegatingShellApplication` survives only as the class the wrapper of Grails 7 and 8 starts, which replaces that wrapper and then runs `GrailsCli`. See [commandLine.adoc][g-cl] and note 37. The name `DelegatingShellApplication` survives as the one class of `grails-cli` (plain Java, alone in the package `org.apache.grails.cli`), which every Grails wrapper starts: it starts the `Main-Class` of its jar, and for the wrapper of Grails 7 and 8, which does not set `grails.wrapper.version`, the command line first replaces that wrapper.
- **One catalog of commands.** `CommandCatalog` is built from the picocli model of each invocation, and in the console after each command, so dispatch, `help`, `help --json`, short forms, "did you mean" and the lines for the commands of earlier versions see the same commands. A command of the command line keeps its name and short forms over a command of the application. See [commandLine.adoc][g-cl], "Help" and "Short forms of commands".
- **Only generation starts the generator.** The help, the version, refusals, the build commands and the code generation commands never start the Forge application context; the commands that generate from the features of Grails start it when they run. See "What a Command Starts" in [commandLine.adoc][g-cl].
- **Forge's own environment.** Forge is a production application that generates projects for development: the command line, `checkForgePack` and `forgePackTest` run in production whatever `grails.env` or `GRAILS_ENV` their JVM is given (`ForgeEnvironment`), and every template is compiled for production (revisions 52 and 53). The environment of a project is given to its build, as `-Dgrails.env`, and never to Forge.
- **For programs.** Exit code 0 when done, 2 for a mistake in the command line, 1 for any other failure; `--plain-output` and `--non-interactive`; one JSON document on the standard output for the `--json` forms. See "Output for a Program, and Running Without a User" in [commandLine.adoc][g-cl].
- **Projects of Grails 9 and later.** In an earlier project the commands of a project are refused (exit 1); `project migrate`, the create commands and `--version` run. See "In a Project of an Earlier Version of Grails" in [commandLine.adoc][g-cl].
- **Start-up.** A command is a short-lived JVM: the start scripts give it `-XX:TieredStopAtLevel=1` and the command line loads its classes ahead on a second thread (`StartupPreload`). The console, the one long-lived JVM, gets neither flag. `GRAILS_OPTS=-XX:TieredStopAtLevel=4` restores the default; `-Dgrails.cli.preload=false` turns preloading off.

<a id="engine"></a>
### 3.2 Feature packs

- **What a pack is.** A descriptor that is data and templates that are code, in the main jar of a plugin under `META-INF/grails-forge/`. A pack is code the user trusts: the command line names where it came from and what it adds before anything is written, and the hosted Forge never loads one. See [forgeFeaturePacks.adoc][g-fp] and [customizingGeneration.adoc][g-cg].
- **Templates are GSP over a versioned model.** Template API 1 is `PackModel`; a new API is added beside it in `PackModel.of` and `PackModel.APIS`. A template is read for `${}`, `<% %>`, `%{ }%` and ten instruction tags, and everything else is written as it is. Mustache was dropped in revision 6, once external packs were for the command line only: GSP is the engine of the framework's own templates, and a second engine would have had to be kept beside it.
- **Compatibility is declared.** `compatibility.grails` and `compatibility.forge` are version ranges; a snapshot, milestone or release candidate counts as the release it leads to; a pack that is not for the running Grails or Forge is refused, selected or not.
- **A pack only adds.** It cannot change a setting, a build property, a dependency version or a file another feature gives the application; a conflict fails with both sides named, before anything is written. The build file is generated from a model, and packs contribute through typed channels (`dependencies`, `platforms`, `buildPlugins`, `build.properties`, `build.extensions`), never through a `build.gradle` template or a patch. Not open to packs: `build.imports`, `build.settings`, `build.repositories` and `build.buildscript` (not built), and `build.blocks` (Forge's packs only).
- **One selection.** Compiled features and packs share string feature names and string IDs of exclusive groups. Selection runs to a fixed point: the named features, what they require (a cycle is a mutual requirement), then the defaults; an explicit choice wins over a default; `--exclude-features` cannot remove a requirement or a hidden feature; an option that was given is a choice. `FeatureSelectionSpec` holds it; see [creatingProject.adoc][g-cp].
- **The framework's features are packs where the format can say what they do.** 61 packs under `META-INF/grails-forge-bundled/` of `grails-forge-core` use keys only a pack of Forge has (how it is selected, conditions, the data source of a driver, versions Forge knows), and their templates are compiled when Forge is built. 13 stay classes because they are the engine: the build file and its two companions, the two configuration formats, the readme, the application class, the BOM, the project settings, the message bundles of a plugin, the two Micronaut features and the Grails wrapper. `BundledPackGoldenSpec` holds what each pack adds, for each application type.
- **Not built:** commands from packs (`artefacts`), `flags`, parameters, `when` and the other selection keys for a plugin's pack, a cache of compiled external templates, and a class loader, sandbox or timeout for a pack.

<a id="metadata"></a>
### 3.3 Catalog and distribution

- **The main jar only.** A pack travels inside the main jar of its plugin; no classifier artifact. The Grails Gradle plugin packages it (`copyForgePack`), checks it in a JVM of its own as part of `check` (`checkForgePack`), and tests it with generated applications on request (`forgePackTest`). No command scaffolds a pack. See [forgeFeaturePacks.adoc][g-fp].
- **Fetching.** The exact main jar by its coordinates, without resolving its dependencies, hashed in memory and not kept. Repositories: those of `GRAILS_REPO_URL`, then Maven Central, or those `--feature-pack-repository` names; `--feature-pack-sha256` pins the jar; a snapshot resolves to a timestamped artifact. Nothing else is read: no credentials, `settings.xml` or `~/.grails/forge.yml` (note 48).
- **One catalog format.** A catalog is `grails-plugins-index.json` of `apache/grails-plugins-metadata`, with a `pack` member in a version. No catalog is read unless the user names one, so a name that is not a feature of Grails is refused without a request to the network. A catalog is trusted as much as the plugins it names. The change to the indexer that writes `pack` members is drafted in that repository and not merged.
- **Versions follow the application's BOM.** When the Grails BOM of the application manages a plugin, the version it manages is the one taken (the tables `META-INF/grails-forge-boms/*.tsv` are built into Forge from the BOMs).
- **Finding plugins.** `list-plugins` and `plugin-info` keep the names the shell had: the plugins of the release come from a list in the command line, which `BundledPluginsSpec` holds to the sources, and those of the community from the plugin index. See "Finding Plugins" in [commandLine.adoc][g-cl].

<a id="project-state"></a>
### 3.4 Project state

- **The record is committed.** `project.yml`, `forge.lock.yml` and `baseline/` are committed, so that every clone has the same inputs and the same merge ancestor; the baseline duplicates the generated files on purpose. The run state and the directory of transactions are ignored. See "The `.grails` directory of a project" in [creatingProject.adoc][g-cp].
- **Deterministic and checked.** Sorted, without a time of day, with `/`, LF and UTF-8 on every system. The lock binds the manifest and the index of the baseline by their digests and ends with its own; a record that does not read is not used. The options recorded are those the application has (`none` where it has no feature of the kind).
- **Tooling metadata only.** The application reads nothing of `.grails` at run time; `grails.codegen.defaultPackage` stays in `application.yml` because code reads it there. `grails-forge-cli.yml` is not written; it is read as the record of an earlier version.
- **Two kinds of record.** `generationState: tracked`, written by the generator with a baseline, and `untracked`, written by `project migrate` without one. Only a tracked record is replayed.
- **The generator is named, not downloaded.** The lock names the generator, its version, the digest of its build, the version of Grails and the template API; `feature add` and `project regenerate` need the running command line to be that one, name `project migrate` for the record of an earlier version or of another build that generates other files, which moves it to the running generator, and the later version otherwise, and never fetch an old generator. The digest is computed when Forge is built, from the sources, packs, wrapper and version tables of the generator rather than from the jar or the commit, so that the build cache keeps working; another build of the same version is the same generator when it generates the same files, since snapshot builds leave the snapshot repository.
- **The record over the life of a project.** Merges, manual upgrades and manual removals are handled with the existing commands, never by editing digests: see "The record over the life of a project" in [creatingProject.adoc][g-cp].

<a id="console"></a>
### 3.5 Commands in a project

- **Where Gradle runs.** `GradleBuild.of` alone decides:

  | Where a command runs | What runs Gradle | Why |
  | --- | --- | --- |
  | A command line that runs one command | The project's Gradle wrapper, as a process | Gradle has the terminal: its colours, progress, input and every option. The Tooling API would save less than a tenth of a second. |
  | The console | The Tooling API, on one connection the console keeps | One JVM runs many builds: a further build takes about 50 ms instead of about 350, and a build is cancelled by a token. |
  | `gradle`, `shell`, a `run-app` that leaves the application running | The wrapper, always | What is typed after `gradle` has to mean what it means to Gradle; `shell` needs the terminal; the application has to outlive the command line. |
  | Any, with `GRAILS_GRADLE_RUNNER=process` or `tooling-api` | What the variable names | The way out where one path misbehaves. |

  Both paths take the Gradle version from the wrapper and reuse the daemon; neither tells when an application is ready, which is asked of the application. This changes if the Tooling API can draw on a terminal without losing what Gradle writes to the error stream, or if the console hands its input to a build. See "How the `grails` Command Runs Gradle" in [gradleBuild.adoc][g-gb].
- **Trust.** A project, a wrapper or a build root above the current directory is used only when it is the user's own (owner, modes, link counts; a directory a group can write to counts as the user's); `GRAILS_SAFE_DIRECTORY` names the exceptions. See "Running Gradle with the `grails` Command" in [gradleBuild.adoc][g-gb] and note 49.
- **Builds of several projects.** A project is named by the directory a command is given in, as for Gradle and Git. The wrapper of the build root is run, and tasks are addressed by the path the directories give. The settings script is neither read, which would mean evaluating a build script, nor written: `--subproject` prints the `include` line. See "In a Gradle Build of Several Projects" in [commandLine.adoc][g-cl].
- **Running the application.** `run-app` returns when the application answers `HEAD /`, which can be before `BootStrap` has finished; where it has startup progress, a failed start ends the wait at once (revision 47). Its record in `.grails/run` is the owner's alone, and `stop-app` ends only a process whose number, start, user and command line match it. See "Running the Application with the `grails` Command" in [gradleBuild.adoc][g-gb].
- **Commands of the application and its plugins.** The build lists them (`grailsCommandCatalog`, which finalizes `classes`), and the command line reads the list without starting Gradle, so the help never starts a build; a top-level name that is no command in a project whose list is missing or stale has the build list them once, and a mistyped name with a current list is refused at once. A command runs in the build (`runCommand`), with its arguments in a file so that each stays one argument, in one of two targets: `application` (the application context over a mock servlet, no server) and `standalone` (`org.apache.grails.core.cli.StandaloneCommand`, no context). A target that runs inside the command line is not built. See "Commands of the Application and its Plugins" in [commandLine.adoc][g-cl] and [creatingCustomCommands.adoc][g-cc].
- **No code of a project runs in the command line.** A script of a project runs in its build (`runScriptCommand`), and a template under `src/main/templates` is text with tokens. The framework ships commands, not scripts; the script DSL is deprecated, kept through 9.x and can be removed in the next major version; the command line creates no script (`create-script` is removed, revision 93). See [creatingCustomScripts.adoc][g-cs].
- **What an IDE needs is on the Grails side.** The `grails-cli` artifact and `GrailsCli`, `--plain-output`, `--non-interactive`, `help --json` for the commands of a directory, `.grails/project.yml` to recognize a project, and the Gradle tasks to run it. The IntelliJ plugin has not moved to it (gates [G8](#g8), [G9](#g9)). See note 51.

<a id="feature-add"></a>
### 3.6 Changing a generated project

- **Replay before change.** `feature add` and `project regenerate` generate the application again from its record with the same generator. The replayed record has to equal the committed one byte for byte, so a generation that differs (another repository override, another build of the generator) is refused rather than merged. See [creatingProject.adoc][g-cp].
- **The merge.** For each file whose bytes or mode differ between the baseline **A** and the proposal **B**, the working file **C** is merged by lines, on Myers edit scripts and lines that both sides keep in place. The merge is never bolder than `git merge-file`, except that a stretch both sides changed in the same way is taken; every result is checked by counting its lines, and the work is bounded (200,000 lines, 2,000 changed lines, 50 million line pairs). Binary files and the executable flag are compared whole. JGit is not used: the Grails BOM does not manage it.
- **All files or none.** The new files and the copies of the replaced ones are staged in the project, so that each replacement is a rename within one file system; the journal is kept outside the project, in `~/.grails/forge/transactions/<digest of the path of the project>/journal`, because a project tree is untrusted input. A change is completed or undone by the digests of its files, and by the mode the change gave a file where it would be put back. The new baseline is the pristine proposal, never the user's files. A lock file keeps two commands apart; it cannot keep an editor out.
- **What `feature add` may change.** It adds. A default that the new feature displaces is replaced; a feature that was asked for is replaced only with `--replace`; an option is never changed; nothing is removed on request. See "Adding a feature to a project" in [creatingProject.adoc][g-cp].
- **Migration and adoption.** `project migrate` writes an untracked record from evidence read as text and runs nothing of the build, so it works where the build cannot be configured. Adoption, `project init` (choose the type, options and features, review the whole difference, write a baseline), is not built: gate [G24](#g24). Open questions: [Q1](#q1), [Q2](#q2).

<a id="hosted"></a>
### 3.7 Hosted Forge

The hosted service runs the same generator with the framework's features only: no external pack, catalog, private repository, exclusion or `feature add`, and `NoFeatureCatalogSpec` holds that no class of the command line is on its class path. Its ZIP carries the record; the preview leaves out the copies of the baseline, and the feature diff leaves out `.grails`, so that a diff applied by hand leaves the record as it was (see [creatingProject.adoc][g-cp]). This work does not change the 8.1 versions of the service, which keep profiles; the 9.0 rollout is gate [G20](#g20).

<a id="verdict"></a>
### H.1 The proposal and its verdict (revisions 1 to 11)

The design was imported on 2026-10-26 from [issue #16348, comment 6150508865](https://github.com/apache/grails-core/issues/16348#issuecomment-6150508865) (revision 10, 2026-10-13); the verbatim import is the first commit of the branch, "Document the Forge and CLI unification proposal". Its proposals and the verdict on them:

1. The command line searches plugin metadata and selects plugins: yes, from `apache/grails-plugins-metadata`, with a feature pack (descriptor and templates) in the jar of a plugin.
2. The command line adds a plugin's feature to an existing application: yes, scoped: a committed baseline, a lock and a transactional three-way merge.
3. `create-app` leaves the shell: yes; the name became Forge's, and the dispatcher, `-t` and `GRAILS_PREFERRED_SHELL` went.
4. Profiles are removed: yes, all together in 9.0, nothing in a minor release.
5. The interactive capabilities of the shell stay: yes, in a command layer without profiles.
6. `.grails/` is ignored by Git: partly; the manifest, lock and baseline are committed, caches and run state ignored.

The release boundary was decided on 2026-10-26: PR #16551, which made Forge a Grails application and merged on 2026-10-14, is 8.1.x; everything else is 9.0.x, and 8.1 keeps profiles and both command lines. Revision 9 had planned the additions for 8.1.x; revision 11 moved them to 9.0.x. Precedents weighed: Quarkus codestarts (declarative extension metadata with templates in a classifier jar), Spring Initializr (a declarative dependency catalog, code only in the service), and the `feature.yml` plus `skeleton/` of Grails 3 profiles, which had the right shape in the wrong engine.
